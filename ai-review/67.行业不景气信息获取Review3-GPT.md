\# 第三轮 WealthSail 代码 Review



结论：六项整改基本落实，整体比上一版更可靠，但还不能判定完全没有问题。



我已读取当前 `master` 的代码，HEAD 为 `c5ef8b5`，并对照了第 66 份 Gemini Review、新增测试，以及前端实现。工作区显示比 `origin/master` 超前 6 个提交，原有 Review 文档仍是未跟踪文件，未被混入提交。



这次能够确认的改进包括：利润增长的跨指标误判防护、风险引文的近期性与语义检查、商业化早期与已确认行业风险解耦、逐类别保留14天风险、Lower Highs 参与折价升级，以及前端对搜索凭证缺失的提示。



不过，审查还发现三个与经济事实认定准确性直接相关的遗留边界：



1\. 两条均未核验原文的媒体引用，仍可能把行业风险升级为 `CONFIRMED`。

2\. 两家不同企业的“利润增长”和“现金回款”，仍可能拼接成同一个业绩兑现结论。

3\. 商业化早期阶段证据的辅助验证目前只检查近期日期，没有真正检查引文是否支持该阶段。



这三项值得再做一轮小范围修正，而不是继续大面积重构。



\## 一、仍需处理的问题



\### P1-1：两个未核验原文的来源，仍可确认行业风险



代码： `backend/macro/industry\_cycle.py:438-472`



现在确实增加了 `claimSupported`，这是正确改进。但最终判定仍允许：



```

check\["claimSupported"] and (    check\["verification"] == "SOURCE\_CHECKED"    or check\["independentSourceCount"] >= 2)

```



其中 `claimSupported` 的语义判断使用的是来源记录中的 `quote`。如果网页尚未核验，该引文仍可能来自模型的自报内容。



因此，两个不同域名、标题不同、但原文都没有核验成功的来源，仍可触发 `CONFIRMED`，造成20分扣减和1倍折价。



这不是推测：`tests/unit/test\_industry\_semantics\_review2.py` 中的 `test\_two\_independent\_current\_supporting\_quotes\_can\_confirm\_without\_checked\_original` 正好把这种行为当作预期结果。



建议： 未核验来源即使有两个，也先归为高可信线索，不能直接宣称行业风险已确认。可以继续触发保守保护，但应与经核验的事实确认分开。



\### P1-2：不同公司的利润和回款仍可拼接成“业绩兑现”



代码： `backend/macro/industry\_cycle.py:493-510`



当前 `earnings\_verified` 主要要求利润与现金回款来自不同事实子句，而没有强制检查它们是否属于同一家企业、同一报告期。



考虑：



\- A公司：2026年三季度净利润同比增长25%。

\- B公司：2026年三季度客户回款2亿元。



即使两个来源均经过原文核验，当前代码仍可能将它们组合为 `earningsVerified=True`。



这会将方向标记为 `EARNINGS\_DELIVERY`，并影响盈利类风险的解除。



建议： 新增 `entityId/companyName`、`reportPeriod` 等结构化事实身份。同一家公司、同一口径的利润与回款才能组成公司级盈利兑现证据。



注意，这依然不能直接证明整个行业都进入业绩兑现阶段。



\### P2-1：商业化阶段的原文语义验证还不完整



代码： `backend/macro/industry\_cycle.py:250-257`



`\_early\_quote\_supported()` 目前只要求证据类别符合预期、来源日期处于近90天。



它没有检查引文是否真的出现试制、验证、尚未量产、尚未商业化等事实。



例如，近期新闻只写着：



> 某企业发布新产品并计划建设新工厂。



如果模型将它标为 `COMMERCIALIZATION\_EARLY`，该阶段依然有机会通过核验，并触发0.5倍折价。



建议复用风险引文验证的思路，对阶段证据增加独立语义校验。无法确认时保留 `UNKNOWN`。



\### P2-2：旧年份风险事件仍可能被当成近90天的变化



代码： `industry\_cycle.py:202-211`



`\_old\_quote\_year()` 允许当前年份和上一年份：



```

years.isdisjoint({reference, reference - 1})

```



假设研究日期是2026年10月31日，一篇2026年10月发表的文章引用：



> 2025年1月，机器人行业融资笔数同比下降30%。



因为2025年属于“上一年份”，这段明显超过90天的历史事实不会被年份过滤。



这意味着文章发布时间近期，不代表文章描述的风险事件近期。



建议把 `publishedDate` 和 `eventPeriod` 分开验证。无法识别风险事实发生区间时，不升级为已确认的近期行业变化。



还有一个相反方向的边界：`\_risk\_quote\_supported()` 中宽泛的 `未` 否定匹配，可能把“未上市企业融资笔数下降”误当成否定句，造成真实风险证据被降级。这也值得补一个测试。

\## 三、回归验证评价



从代码和新增测试看，本次整改是有针对性的，尤其值得肯定的是：



\- 不再将商业化早期自动等同于已确认行业衰退。

\- 单企盈利不会清除五类行业级历史风险。

\- 历史风险合并保留各自原始时钟，不因其他风险的新观察而自动续期。

\- Lower Highs 和相对弱势都已进入折价升级。

\- 双轨计划仍从原始价格锚点计算，没有看到本轮新增的重复折价路径。

\- 缓存逻辑未被这轮语义修正破坏。



你提供的 4243项后端通过、512项前端通过 是较充分的回归记录。旧 ledger 的7处既存 lint 可以暂时独立处理；偶发超时测试既然最终全量重跑通过，建议保留记录并观察，不必因此扩散本轮修改范围。



但这次连接的工作区没有可读取的独立测试执行记录，因此我没有复跑并独立确认这些测试数字，也没有完成生产联网或PostgreSQL联调。



\## 四、最终处理建议



| 问题             | 优先级  | 是否建议本轮处理 |

| -------------- | ---- | -------- |

| 两条未核验引文升级已确认风险 | P1   | 是        |

| 不同企业利润与回款拼接    | P1   | 是        |

| 商业化早期证据缺少语义验证  | P2   | 是，修改很小   |

| 历史风险事件时间识别     | P2   | 是        |

| 检索遗漏赛道透明展示     | P2   | 可以顺手补齐   |

| 独立搜索执行记录       | 独立功能 | 后续单独实现   |

| 真实持仓暴露模型       | 独立功能 | 后续单独实现   |



最终判断：本次六项整改可以认可，但我建议再修复上述两项 P1 和两项 P2 后，就结束这一轮静态代码整改。



无需继续增加大量规则和复杂度。后续更有价值的工作，是通过真实联网资料、历史行业事件和基金净值做端到端验证，检验系统是否真的能识别经济降温，而不只是通过更多单元测试。



对于当前版本，我认为可以进入受控观察和人工复核阶段，但尚不适合让 `CONFIRMED` 行业风险或绿色业绩兑现标签成为无人审核的自动投资决策依据。
