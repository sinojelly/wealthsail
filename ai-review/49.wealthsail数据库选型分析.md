\### 二、 为什么对于这个项目，SQLite 是一个强有力的备选？



1\. \*\*NAS 部署的终极追求是“省心与易备份”\*\*：

在 NAS 上跑应用，最怕的就是升级或迁移时数据库卷（Volume）损坏或丢失。SQLite 只有一个文件，配合极空间（Zspace）或群晖的定时快照、WebDAV 同步、或者简单的脚本，就能实现最粗暴、最绝对安全的异地/多版本备份。恢复时直接把文件覆盖即可，不需要恢复 SQL 脚本。

2\. \*\*硬件资源更契合 Homelab\*\*：

你的 NAS 核心是 Intel N97 处理器，运行 Docker 时内存和 CPU 资源能省则省。SQLite 省去了 PostgreSQL 进程常驻的开销。





3\. \*\*1\~10 人的规模触发不了 SQLite 的短板\*\*：

SQLite 经常被误解为“只能做玩具”，但实际上像 Git, 很多大型浏览器、桌面软件以及高并发边缘服务都在用它。对于财富/投研助手这类以“读多写少、单机低并发”为主的系统，SQLite 的响应速度甚至比通过网络协议连接的 PostgreSQL 更快（因为是进程内调用）。



\---



\### 三、 决定是否替换的“关键卡点”



在做决定前，需要检查 WealthSail 项目代码中是否深度绑定了 \*\*PostgreSQL 专有特性\*\*：



\* \*\*检查点 1：行级安全策略 (RLS)\*\*

从项目目录中可以看到 `migrations/005\_rls\_security\_policies.sql`。这是 PostgreSQL 独有的多租户安全特性。如果你的部署场景只有 1\~10 个可信用户（或者本质上是单人/家庭/小团队自用），根本不需要复杂的 RLS 权限隔离。

\* \*\*检查点 2：JSONB 与复杂函数\*\*

如果代码里大量使用了 PostgreSQL 特有的 `JSONB` 字段高性能查询、特定的窗口函数或数据库扩展，改成 SQLite 需要重写部分 SQL 或 ORM 查询（不过现代 SQLite 对 JSON 和窗口函数支持已经很完善了）。

\* \*\*检查点 3：SQLAlchemy / ORM 适配\*\*

如果项目底层使用了 SQLAlchemy 等主流 ORM，且没有写死原生的 Postgres SQL 片段，那么切换数据库驱动（从 `psycopg2/asyncpg` 改为 `aiosqlite`）通常只需要改动连接字符串 `DATABASE\_URL` 和少许配置。

\* \*\*Docker 部署优势\*\*：只需挂载一个本地文件夹到容器的 `/app/data` 目录下，数据库文件稳稳躺在 NAS 硬盘里，配合 NAS 的备份工具高枕无忧。





\* \*\*方案 B：如果你想保持原样，少改代码\*\*

# Codex建议继续用 PostgreSQL

**我的建议：当前这个 WealthSail 项目继续使用 PostgreSQL，更划算。暂时不建议迁移到 SQLite。**

我读了你给的分析，也核对了代码。文档对 SQLite 轻量化优势的判断基本合理，但**明显低估了这个项目的迁移成本**。仓库现在有 **87 份数据库迁移 SQL**，已经把不少权限、业务规则和任务协调逻辑放进 PostgreSQL。

即使按文档中的“1～3 人使用、最多 10 人、NAS 部署”来评估，我仍然倾向保留 PostgreSQL。

| 判断点 | 项目实际情况 | 对选型的影响 |
|---|---|---|
| 数据访问 | 直接使用 `asyncpg` 和大量原生 SQL，未采用可直接切换数据库的 ORM。[连接层](D:/develop/gitee/WealthSail/backend/common/database.py:112) | 迁移需要修改连接、事务和查询，不能只换驱动、改连接字符串 |
| 后台写入 | 数据采集和消息投递通过 `FOR UPDATE SKIP LOCKED` 领取任务。[任务领取](D:/develop/gitee/WealthSail/backend/jobs/data_tasks.py:313) | 需要重做 SQLite 下的原子领取、互斥和重试机制 |
| 用户隔离 | 每次业务事务设置数据库角色、用户和租户上下文，由 RLS 执行隔离。[权限上下文](D:/develop/gitee/WealthSail/backend/common/database.py:218) | 迁移意味着调整权限架构，并重新验证账户与租户隔离 |
| 金额与份额 | 账本使用 `NUMERIC(28,8)`、`NUMERIC(28,10)` 保存金额、份额和净值。[账本字段](D:/develop/gitee/WealthSail/migrations/003_reference_and_ledger.sql:107) | 必须重新设计精确数值存储和计算，不能直接换成浮点数 |
| 搜索功能 | 基金名称匹配已经使用 `pg_trgm` 和 GIN 索引。[搜索索引](D:/develop/gitee/WealthSail/migrations/068_fund_master_trgm.sql:8) | 还要适配搜索行为及索引方案 |

这里最容易误判的是：**用户人数少，不代表后台写入少。** Worker 会独立运行调度、采集、报告、消息投递等任务，即使没人打开网页，也会访问数据库。SQLite 的 WAL 支持读写并行，但同一数据库仍然只有一个写者；它可以通过排队处理这些写入，不过现有队列和锁的实现需要相应调整。[SQLite 官方说明](https://www.sqlite.org/wal.html)

金额这一点也不能忽略。SQLite 中声明 `NUMERIC(28,8)`，不会获得 PostgreSQL 等价的精确小数语义。可以采用整数缩放或十进制文本等方案，但份额、净值和 SQL 聚合都需要一起检查。[SQLite 类型说明](https://www.sqlite.org/datatype3.html)

你给的文档中，还有两处需要修正。

**第一，“直接复制文件、网盘同步就能完美备份”说得太绝对。** SQLite 开启 WAL 后，已提交数据可能仍在 WAL 文件中。在线备份应该使用 Backup API、`VACUUM INTO` 或经过验证的一致性快照，不能随意复制运行中的文件。PostgreSQL 的 `pg_dump` 本身也能生成一致性备份，并允许普通业务读写继续运行。[SQLite 备份](https://www.sqlite.org/backup.html)、[PostgreSQL 备份](https://www.postgresql.org/docs/current/backup-dump.html)

**第二，“切换后能省掉 NAS 上 PostgreSQL 的常驻开销”，需要先确认部署方式。** 当前根目录的 [docker-compose.yml](D:/develop/gitee/WealthSail/docker-compose.yml:7) 只有 API、Worker 和前端，没有数据库容器；部署文档画的是连接外部 Supabase PostgreSQL。是否能节省 NAS 资源，要看你最终是否把数据库也部署到 NAS。此次没有实测 NAS 内存和负载，不能仅凭 N97 型号认定 PostgreSQL 太重。

如果你的目标是“全部放 NAS、少维护、备份方便”，我建议走这条路线：

1. **保留 PostgreSQL，部署一个独立数据库实例。** 项目已经为普通 PostgreSQL 提供 `auth.uid()` 等兼容对象，不需要自托管整套 Supabase。[兼容初始化](D:/develop/gitee/WealthSail/migrations/001_initial_schemas.sql:11)
2. **先测资源，再调整连接池和后台任务并发。** 当前连接池默认是每池最少 2、最多 10，可以按实际负载优化。[连接池配置](D:/develop/gitee/WealthSail/backend/config.py:52)
3. **优先补自动备份和恢复演练。** 定时逻辑备份、保留多个版本，并在空库验证恢复；这比为了备份方便而整体换库，投入更小、收益更直接。

如果以后准备单独做一个“单用户、离线、功能收敛”的轻量版，SQLite 很值得考虑。**对现有完整版本，我会把精力放在 PostgreSQL 的部署和备份简化上。**
