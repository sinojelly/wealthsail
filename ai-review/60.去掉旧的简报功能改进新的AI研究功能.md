\# WealthSail 每日自动投研流程重构方案



我的建议是：把“公共机会数据采集 → Codex AI 研究”合并为一条有先后依赖的每日研究流水线；旧的 08:30 宏观简报、08:35 个性化简报及对应微信推送全部默认关闭。



但有一处需要纠正：目前代码中的“晨间机会推送”并不是把上述两份旧简报转发到微信。 它是另一项功能，读取当天成功完成的 Codex AI 机会研究报告，再提取机会内容向企业微信群机器人发送。



因此，应将两类通知明确区分：



\- 旧盘前简报微信通知：随旧盘前简报关闭。

\- 每日 AI 机会研究微信推送：保留实现，但默认关闭；将来需要时再单独启用。



这样既能去掉你不需要的旧功能，又不会误删未来可能有价值的 AI 投研结果推送。



\## 一、目标架构：每天只调度一次研究流水线



每日 AI 投研流水线



保留



每天 08:30（北京时间）



统一调度入口 · 每个自然日一次



阶段 1：公共机会数据采集



行情、宏观数据、热点、基金及机会线索



阶段 2：数据质量检查



等待采集结束 · 检查有效性与时间戳 · 冻结输入



阶段 3：Codex AI 研究



一次模型调用 · 验证来源 · 生成投资机会分析



阶段 4：报告验证与持久化



结果为 READY 后，网页展示今日报告



可选：AI 机会研究微信推送



默认关闭 · 不影响研究结果生成



旧的盘前宏观简报、个性化简报、原有报告消息分发，不再作为这条流水线的组成部分。



核心原则是：一个主开关、一个调度入口、串行依赖、分别记录阶段状态、模型调用严格去重。



\## 二、你对当前执行顺序的担心是有依据的



核对 `backend/jobs/alpha\_runtime.py` 和 `backend/jobs/daily\_research.py` 后，可以确定：当前实现虽然有部分等待逻辑，但还不是严格的串行流水线。



目前有两条独立循环：



\- `run\_alpha\_public\_service()`：08:30 开始公共数据采集。

\- `run\_daily\_research\_service()`：08:30 开始每日研究，并可能再次尝试调用公共数据采集函数。



两者都有机会执行 `sync\_alpha\_public()`。



代码通过数据库唯一约束防止同一天重复创建正式采集批次，但这只是防止重复登记，不等于保证采集完成后才执行研究。



目前至少有三个需要修正的问题：



1\. 等待超时后可能提前继续。 研究任务看到采集记录为 `CLAIMED` 且未超过 10 分钟时，会返回 `WAITING\_PUBLIC\_DATA`，一分钟后再试。但超过 10 分钟后，即使采集还没有完成，也可能继续生成研究输入。

2\. 采集失败未必阻止 AI 研究。 当批次已经标记为 `FAILED` 时，现有流程并没有统一执行“停止模型调用”的质量门禁；可能读取以前的数据继续生成报告。

3\. 自动研究没有保存明确的采集批次关联。 现有 `source\_batch\_id` 主要用于调试链路，正常每日执行没有明确传入本次采集批次 ID，不利于事后审计和验证。



因此，我建议把“采集完成”设为后续研究的硬性前置条件，而不是只依赖 08:30 的时间碰巧一致。



\### 改造后的规则



\- 每天 08:30 只启动一个 `DailyResearchPipeline`。

\- 第一阶段完成后，检查当日采集批次的最终状态。

\- `READY`：进入 AI 研究。

\- `PARTIAL`：按明确的数据质量标准判断能否降级研究；若允许，报告必须标注数据缺失。

\- `FAILED`、`CLAIMED`、采集超时：不调用 Codex，进入有限重试或待处理状态。

\- AI 研究必须记录所使用的采集批次 ID、数据时间和输入摘要。

\- 数据采集、模型生成、报告验证分别记录状态，网页能够独立展示。



这样不会为了追求形式上的串行而阻塞其他完全无关的后台任务，只约束同一条 AI 研究依赖链。



\## 三、开关方案：只保留一个研究主开关



不建议继续为公共采集和 Codex 研究分别设置两个业务开关。因为采集是研究的前置步骤，用户应该启用的是完整的“每日 AI 投研”功能。



建议最终配置如下：



| 配置项                                | 用途                      | 默认值     |

| ---------------------------------- | ----------------------- | ------- |

| `DAILY\_RESEARCH\_ENABLED`           | 统一开启公共采集、输入构建、Codex 研究  | `false` |

| `PRE\_MARKET\_REPORTS\_ENABLED`       | 旧 08:30 宏观和 08:35 个性化简报 | `false` |

| `MORNING\_OPPORTUNITY\_PUSH\_ENABLED` | 每日 AI 研究结果的企微群推送        | `false` |

| `FUND\_1430\_ENABLED`                | 原有 14:30 基金相关功能         | 保持原配置   |

| `POST\_MARKET\_REVIEW\_ENABLED`       | 原有盘后复盘                  | 保持原配置   |

| `INTRADAY\_TRACKING\_ENABLED`        | 原有盘中异动检查                | 保持原配置   |



\### 推荐的 NAS 配置



这是代码改造完成以后，应写入 `deployment/env/worker.env` 和必要的 `api.env` 的目标配置，而不是现在就能全部生效的配置。



```

\# 每日 AI 投研：统一开关

DAILY\_RESEARCH\_ENABLED=true



\# 旧盘前简报：关闭

PRE\_MARKET\_REPORTS\_ENABLED=false



\# 每日 AI 机会研究微信推送：关闭

MORNING\_OPPORTUNITY\_PUSH\_ENABLED=false

```



原来的 `ALPHA\_PUBLIC\_ENABLED` 暂时保留以兼容其他公共数据使用场景，但不再用于决定每日 AI 流水线是否采集。当每日研究启用时，公共机会数据采集是强制内部步骤，不受第二个开关控制，也不再启动独立的 08:30 采集循环。



`ALPHA\_OPPORTUNITY\_ENABLED` 也不应拿来控制每日 AI 研究本身，因为它还管理 14:30 机会检查等功能。



\## 四、旧功能怎样安全关闭？



建议只关闭自动执行，先不要删除历史数据、数据库结构和旧报告实现。



| 旧功能         | 实施方式                              | 是否保留历史 |

| ----------- | --------------------------------- | ------ |

| 08:30 宏观简报  | 从调度入口禁用 `PRE\_MARKET\_MACRO`        | 保留     |

| 08:35 个性化简报 | 从调度入口禁用 `PRE\_MARKET\_PERSONALIZED` | 保留     |

| 两份简报的企业微信通知 | 停止新增相关 Outbox 消息，并安全处理未发送的旧消息     | 保留发送历史 |

| 旧简报页面       | 从主要入口隐藏自动生成操作，历史详情仍可查看            | 保留     |

| AI 研究机会推送   | 独立开关默认关闭                          | 保留实现   |



具体修改：



`backend/jobs/session\_switches.py`



当前：



```

REPORT\_SESSION\_SWITCHES = {    "PRE\_MARKET": "daily\_research\_enabled",    ...}

```



改成：



```

REPORT\_SESSION\_SWITCHES = {    "PRE\_MARKET": "pre\_market\_reports\_enabled",    "INTRADAY": "intraday\_tracking\_enabled",    "FUND\_1430": "fund\_1430\_enabled",    "POST\_MARKET": "post\_market\_review\_enabled",}

```



这样既阻止新旧盘前简报调度，也能让原有报告租约恢复流程遵守关闭设置，不影响 Codex 日报。



在 `backend/config.py` 增加：



```

pre\_market\_reports\_enabled: bool = Field(default=False)morning\_opportunity\_push\_enabled: bool = Field(default=False)

```



`backend/jobs/alpha\_opportunities.py`



目前 `sync\_alpha\_opportunities()` 使用 `daily\_research\_enabled` 来判断是否发送晨间机会推送。



应改为由 `morning\_opportunity\_push\_enabled` 控制晨间分支，同时保留 `ALPHA\_OPPORTUNITY\_ENABLED` 的机会服务总约束。



这样即使每日 AI 研究开启，也不会自动发送微信群消息；14:30 功能可以继续独立工作。



需要注意：关闭旧报告自动生成，不会自动清除已经排队的旧 Outbox 消息。因此还要确保未发送的历史盘前通知不会在恢复 Worker 后突然发出去，但不能直接删除整张消息表。



\### 现在还没有改代码，能否临时停掉旧简报？



可以通过数据库将 `workflow.jobs` 中 `report\_session='PRE\_MARKET'` 的自动作业设为 `is\_enabled=false`，它不会关闭每日 Codex 研究。



但这属于临时运维措施，不是正式独立开关。操作前应先只读确认所有受影响的作业，并保留恢复所需的作业 ID 和原状态。



至于晨间 AI 推送，目前没有真正独立的开关。临时关闭 `ALPHA\_OPPORTUNITY\_ENABLED` 会连带影响 14:30 机会检查，因此我不建议这样做。



\## 五、核心代码改造设计



\### 1. 统一调度入口



建议沿用现有 `run\_daily\_research\_service()` 作为唯一的每日研究调度器，而不是再增加一套定时框架。



修改 `backend/jobs/alpha\_runtime.py`：



\- 每日研究开启时，只注册每日研究流水线。

\- 不再同时注册独立的 `run\_alpha\_public\_service()`。

\- 其他市场数据刷新、后台队列、报告消费者保持原有机制。



保留 `sync\_alpha\_public()` 作为采集实现，让流水线统一调用。



预期核心逻辑：



```

async def run\_daily\_research\_pipeline(pool, settings, now):    # 1. 检查当日流水线是否已执行    # 2. 读取或领取当日公共采集批次    batch = await ensure\_today\_public\_batch(pool, now)    # 3. 必须等待采集完成    if batch.status not in {"READY", "PARTIAL"}:        return await handle\_source\_not\_ready(batch)    # 4. 验证质量和来源    quality = validate\_public\_batch(batch, now)    if not quality.can\_research:        return await record\_source\_blocked(quality)    # 5. 从指定批次构建研究输入    packet = await build\_research\_packet(        pool, batch\_id=batch.id, now=now    )    # 6. 执行 Codex 研究    return await execute\_daily\_research\_once(        pool, settings, packet, source\_batch\_id=batch.id    )

```



这是推荐的结构示意，不是可以直接替换的完整实现。



\### 2. 完整采集后才允许调用 Codex



这里建议建立明确的质量门禁。



| 采集状态         | 是否调用 Codex | 处理             |

| ------------ | ---------- | -------------- |

| `READY`      | 是          | 正常研究           |

| `PARTIAL`    | 有条件        | 关键数据满足要求才允许    |

| `CLAIMED`    | 否          | 等待完成           |

| `FAILED`     | 否          | 记录失败，按安全重试规则处理 |

| 当日批次不存在      | 否          | 首先执行采集         |

| 当日批次失效或来源不可信 | 否          | 标记数据不可用        |



有一点非常重要：不是所有宏观数据都必须在当天公布。例如 CPI、PPI、M2 是月度数据，不能要求它们的观察期等于当天。质量门禁应分别验证真实公布期、抓取时间、来源可靠性和允许的滞后窗口。



同时，模型只能引用本次输入冻结时已经取得的事实，不能把历史缓存伪装成当天的新数据。



\### 3. 数据库记录怎样设计？



当前已经存在：



\- `market.alpha\_public\_batches`：公共采集批次。

\- `research.daily\_research\_runs`：每日 AI 研究执行记录。

\- `research.daily\_research\_results`：研究最终结果。



可以继续使用这些表。



首先修正自动研究对 `source\_batch\_id` 的使用，让每次成功登记的研究都明确关联实际读取的采集批次。



对于更完整的阶段监控，我建议再增加一张轻量级的流水线运行表，例如：



`research.daily\_research\_pipeline\_runs`



用于记录当日开始时间、当前阶段、最近心跳、采集批次、模型执行记录、结束时间和失败原因。



原因是目前研究任务在数据库登记之前出现异常，网页可能只能看到“未派发”，不知道究竟停在采集还是输入构建阶段。



新增数据库结构应使用新的前向迁移版本，例如 095；不要修改已经在 NAS 执行过的 093，也不要通过清空每日记录来实现重试。



\### 4. 失败重试怎么设计？



公共采集失败可以安全重试，但模型调用不能简单重复。



建议采用下面的策略：



| 阶段              | 推荐重试策略             |

| --------------- | ------------------ |

| 数据采集前的网络预检查     | 有界重试               |

| 公共数据请求暂时失败      | 有界重试，同一逻辑批次记录尝试次数  |

| 数据不满足质量标准       | 不调用模型，记录缺失原因       |

| Codex 登录或能力预检失败 | 不消耗模型执行槽位；允许有限预检重试 |

| 已登记并启动 Codex 研究 | 不自动重复调用模型          |

| 模型返回但验证失败       | 记录 FAILED，不重复付费生成  |

| 模型调用超时且结果不确定    | 记录 UNCERTAIN，人工核实  |



当前公共数据采集以日期唯一约束防重复，因此若要支持采集失败后的重试，需要进一步设计同一每日批次的尝试记录和租约，而不是删除旧批次、重新插入一条。



调度时间仍是北京时间 08:30，但它表示研究开始时间，不是报告完成时间。



建议将自动执行和重试限定在明确的当天执行窗口内。例如上午 08:30～10:30；超过窗口后标记 `MISSED`，默认不再夜间突然补跑。具体窗口设成配置项，避免重演这次晚上修复 Worker 后突然运行大量任务的情况。



\## 六、网页应该怎么展示新的流水线？



建议首页只保留一张“每日 AI 研究”主卡片，展开后显示各阶段，而不是让用户看到几项都叫“08:30”的独立任务。

&#x20;  READY · 已获取最新可用数据

2\. 数据质量检查

\## 七、实施文件和验收范围



建议交给 Codex 分四个阶段完成，不要一次大规模删除旧业务代码。



| 阶段         | 主要文件                                                                                            | 验收目标                           |

| ---------- | ----------------------------------------------------------------------------------------------- | ------------------------------ |

| A. 隔离旧简报   | `backend/config.py`、`backend/jobs/session\_switches.py`、`backend/jobs/alpha\_opportunities.py`    | 旧简报和推送关闭，AI 研究继续               |

| B. 合并研究流水线 | `backend/jobs/alpha\_runtime.py`、`backend/jobs/daily\_research.py`、`backend/jobs/alpha\_public.py` | 只有一个 08:30 研究入口，采集完成后才调用 Codex |

| C. 持久化和状态  | `backend/macro/daily\_repository.py`、`backend/macro/alpha\_repository.py`、新迁移、相关 API              | 采集与研究可追踪，有正确的失败/超时状态           |

| D. 前端和部署保障 | `DailyResearchReport.tsx`、相关页面、NAS 部署脚本                                                         | 状态清晰，Worker 未启动或挂载失败时部署明确失败    |



验收测试需要覆盖这些关键场景：



1\. 08:30 同时收到多个调度 Tick、重启或并发请求时，只有一条采集批次、最多一次正式 Codex 模型执行。

2\. 采集耗时超过 10 分钟时，模型仍然等待，不使用尚未完成的数据。

3\. 采集失败、数据缺失或来源不合格时，不调用 Codex。

4\. 正式研究报告关联本次采集批次，并且只有 `READY` 才显示“研究成功”。

5\. 两份旧盘前简报均不会自动生成，也不会向微信投递；历史报告仍可访问。

6\. 关闭 AI 晨间推送不影响 14:30 的基金机会检查，其他盘中和盘后开关也不受影响。

7\. Worker 启动失败、NAS 目录缺失、超出补跑窗口时有明确的运维错误，而不是静默漏执行。

8\. Windows 本地测试与 NAS PostgreSQL 迁移测试通过；测试隔离 Codex 调用，不消耗真实模型额度。



\## 八、建议的上线顺序



先修复旧功能开关、禁用旧盘前调度和推送，确保打开每日 AI 研究不会同时产生旧简报。然后再改造公共采集与 Codex 研究的统一流水线。第三步完善数据库阶段状态和前端。最后在隔离测试数据库验证，才部署 NAS。



正式部署时，应避免在今天已登记研究名额的数据库上通过删除历史记录进行重跑。已有 `READY`、`FAILED`、`UNCERTAIN` 都应保留；新逻辑从下一个自然日开始正常运行。



最终系统保留的日常主流程应当是：



08:30 自动公共数据采集 → 数据质量验证 → Codex 分析经济和市场重要变化 → 识别可能受益或受损的投资方向与基金 → 验证并保存报告 → 网页展示。



旧宏观简报、旧个性化简报和对应的企业微信消息默认全部关闭。每日 AI 研究的微信推送也默认关闭，但保留以后单独启用的能力。



这比把所有任务都简单设成 08:30 同时启动，更符合你希望建立的可靠、低成本、以投资机会研究为核心的 WealthSail。
