> Review 日期：2026-08-27
> Review 范围：`0daf671a38e0fa25be906e42a8eba6deccc15f2b` ～ `5bfc3c245126840f90206bf48d2bd48d52eca8f6`（含首尾提交）
> 对比基线：`0daf671` 的父提交 `c889cbf180aad6b7dc840dc322821d1edf3e2bfc`
> 设计基线：`docs/01`、`docs/04`、`docs/06`、`docs/07`、`docs/08`、`docs/09`、`docs/10`
> 检查维度：设计遵循、功能正确性、安全性、可读性、可扩展性、性能、可维护性、测试有效性和部署可行性

## 1. 结论摘要

这三个提交不能按原样进入生产。原始变更共涉及 23 个文件，增加约 7,186 行、删除 43 行；其中真正符合现有生产架构、值得保留的内容主要是运行时数据库角色供给脚本的增强，以及“单用户单渠道至多一个 ACTIVE binding”的目标。其余主要问题不是文字风格问题，而是会造成部署失败、运行时失败、需求倒退或形成第二套不可维护实现的结构性问题。

原始版本的最高风险如下：

1. **P0——正式迁移链不可执行**：新增 `017_self_push_only_hardening.sql` 与已有 `017_portfolio_import_authorization.sql` 使用相同版本号。`scripts/migrate.py:load_migrations()` 明确拒绝重复版本，因此升级会在连接数据库前报 `duplicate migration version: 017`。
2. **P0——报告生成真实路径会抛 `TypeError`**：`backend/reports/repository.py` 给 Outbox 方法新增必填 `user_id`，但 `backend/reports/service.py` 的生产调用点没有传入。新增测试只直接调用 Repository，没有覆盖报告生成到 Outbox 的真实协作边界。
3. **P1——多用户 MVP 需求被回退**：原设计、migration 019、`docs/10` 和上一轮整改都要求 tenant 报告按全部 ACTIVE binding 逐用户展开。`0daf671` 改成只给 acting user；定时任务 acting user 固定为 OWNER，其他 1～2 个试运行用户将收不到四时段报告。
4. **P1——产生第二套领域实现**：`d1c2127` 在仓库根部新增 `modules/database.py`、`modules/identity`、`modules/market_data`、`modules/portfolio`、`modules/research` 等约 4,631 行生产代码，与 `docs/10` 规定的单一 `backend/` 模块化单体相冲突。FastAPI 和 Worker 均未导入这套代码，新增功能实际不可达。
5. **P1——特权函数默认暴露**：migration 020 新增两个 `SECURITY DEFINER` 函数，却没有像 migrations 011/013 那样 `REVOKE ... FROM PUBLIC`。其中 `identity.create_tenant` 接收调用者提供的 owner UUID，且与 MVP“只允许邀请注册、不开放自助创建 tenant”相冲突。
6. **P1——企微绑定存在跨所有者冲突错误**：按全局唯一 external hash 做 `ON CONFLICT DO UPDATE` 时没有核对旧 binding 的 tenant/user。相同企微身份尝试绑定第二个 WealthSail 账号时，新 challenge 会被消费，却引用旧账号 binding，形成错误的授权状态。
7. **P1——环境名拼写错误会 fail-open**：`APP_ENV` 是任意字符串，而安全校验只在精确等于 `production` 时开启。`APP_ENV=prod` 会同时跳过运行时角色 readback、生产 secret 校验和 Secure Cookie 分支。

因此，本轮结论为：**原始变更不通过；完成本文第 8 节整改和第 9 节验证后，可以作为新的修复提交进入后续部署验证。**

## 2. 各提交设计遵循情况

### 2.1 `0daf671`

提交标题是“恢复 POST_MARKET 调度时间为 15:30”，但实际只修改：

- `backend/reports/repository.py`；
- `tests/unit/test_outbox_delivery.py`；
- 新增 `migrations/017_self_push_only_hardening.sql`。

它没有修改 `backend/jobs/scheduler.py`。当前 15:30 配置早已存在于基线，提交标题不能描述实际变更，降低了审计和回滚时的可信度。

实际代码把“租户内逐用户推送”改成“只推 acting user”，与以下设计冲突：

- MVP 明确支持 2～3 个用户；
- `docs/10` 要求 Outbox 按全部 ACTIVE binding 展开并独立重试；
- migration 019 专门给 Domain API 增加 tenant 内脱敏 binding 枚举权限；
- 定时任务只选 tenant OWNER 作为生成报告的系统 acting user，不能代表唯一收件人。

该提交对“每用户每渠道最多一条 ACTIVE binding”的约束方向是正确的，但把“绑定去重”和“报告收件人范围”错误地耦合在一起，并使用了冲突的 migration 017 版本号。

### 2.2 `d1c2127`

新增代码有大量注释和类型标注，表面完整，但没有进入生产装配图：

```text
FastAPI / Worker
  └─ backend/*        ← 当前生产入口实际使用

modules/*             ← 仅被新增单元测试导入，没有生产调用方
```

这违反 `docs/10` 的两个核心决定：

1. 生产代码只有一个顶层 `backend/` 包；
2. API/Jobs → Service → Repository/Integrations，领域间通过公开服务协作，不再复制数据库、错误模型、身份模型和领域服务。

这套平行实现还存在以下具体缺陷：

| 位置 | 问题 | 影响 |
| --- | --- | --- |
| `modules/identity/jwt.py` | `iat/exp` 写成 ISO 字符串，而现有 `python-jose` 解码器使用 NumericDate | 新 token 无法被生产 `backend.common.auth` 接受 |
| `modules/identity/service.py` | 提供自助 `create_tenant` | 与“邀请制进入既有 tenant”的 MVP 需求冲突 |

| `modules/market_data/service.py` | 把证券代码字符串写入 UUID 类型 `market_observations.subject_id` | 真实 PostgreSQL 写入失败，Fake 测试未发现 |
| `modules/market_data/service.py` | 一批快照/观测没有显式事务 | 中途失败会留下部分批次和部分观测 |
| `modules/market_data/service.py` | 价格路径大量经过 `float` | 违反金融金额/价格使用 Decimal/NUMERIC 的设计约束 |

| `modules/portfolio/service.py` | 手工期初持仓伪造成 BUY + 现金/费用分录 | 违反“未知历史只记 ADJUSTMENT，不推断交易/现金流”的账本语义 |

| migration 021 | decision UPDATE policy 没有限制 `user_id = auth.uid()` | 若未来直接接入，EDITOR 可撤回同 tenant 其他用户决策 |

文件体量也反映出边界不清：identity service 1,011 行、market service 1,088 行、portfolio service 1,593 行。身份、Provider、命令、投影、查询和数据库 SQL 混在单文件中，不利于局部测试、替换和代码所有权划分。

### 2.3 `5bfc3c2`

这一提交的主要方向合理：

- API/Worker 使用不同 LOGIN；
- LOGIN 本身不带 BYPASSRLS，Worker 通过 NOLOGIN domain role 激活权限；
- Worker 可以单向降权到 `wealthsail_api` 做 tenant transaction；
- provision 脚本补充属性重申、角色关系和 readback；
- 本地非生产环境允许跳过角色 readback，解决本地超级用户/简化角色环境无法启动的问题。

但还存在三处需要修正或澄清：

1. `skip=True` 发生在 `process` 参数校验之前，未知进程类型会被静默接受；
2. `skip=not settings.is_production` 与任意字符串 `APP_ENV` 组合后会 fail-open；
3. migration 021 为尚未接入生产的平行服务提前放宽表权限和 RLS，没有真实 PostgreSQL 集成测试，既扩大权限面又形成“迁移已完成、功能已交付”的错误印象。

角色供给脚本本身保留。它是 Supabase 专用脚本，`DATABASE postgres` 与 PostgreSQL 16 的 membership option 语法应在目标 Supabase 实例上执行一次真实预检；不能只凭静态测试判定部署成功。

## 3. 可读性 Review

### 做得较好的部分

- 新服务有 docstring、类型标注和领域术语说明；
- 角色供给脚本补充了角色图、为什么 LOGIN 不能持有 BYPASSRLS 等背景；
- 新测试命名普遍能表达意图。

### 需要改进的部分

1. 注释与实现不一致比缺注释更危险，例如“AkShare 60 秒 cache”实际没有 cache，“self-push”与多用户设计相反。
2. 单文件超过 1,000～1,500 行，读者无法快速判断命令、查询、Provider、投影和安全边界。
3. 提交标题与实际变更不一致，`0daf671` 是最明显案例。
4. 新旧 `backend.*` 与 `modules.*` 使用相似名称但不同 JWT、错误类、数据库事务和 TenantContext，读者很容易导错包。
5. `*.broken` 这种过宽 ignore 会隐藏任何目录下的重要诊断文件；只保留标准 `.coverage` ignore。

## 4. 可扩展性与软件架构 Review

扩展性的关键不是提前复制一套“未来完整服务”，而是保持一个可演进的生产骨架：

- 新领域能力应放进 `backend/<domain>/api.py|service.py|repository.py`；
- API DTO、租户鉴权、事务、审计和错误 envelope 复用现有公共组件；
- Worker 使用 `backend/jobs` 和现有 integrations；
- 对外只通过领域 Service/Port 协作；
- schema 权限必须随真实命令一起增加，不能提前给未接入模块授权。

原平行实现不能自然扩展，原因是每修一次 JWT、RLS、错误码、时间/Decimal 或连接池规则，都必须同步两套代码；其中任何一套遗漏都会出现本次已验证的协议漂移。

后续若实现 trade fill、decision、password reset，应拆成独立增量：先在 `backend/` 写 API/Service 行为测试，再写 Repository 和 forward migration，最后增加真实 PostgreSQL RLS/触发器集成测试。不要从已删除平行模块整体复制回来。

## 5. 性能 Review

原始新增代码主要性能风险为：

1. 每次组合写命令后重放 tenant 全部历史账本；
2. 投影刷新按账户、持仓逐条查询和写入，形成 N+1；
3. 股票和 ETF 路径重复抓取同一份 AkShare 全市场 DataFrame；
4. 场外基金逐代码串行抓取；
5. 观测批次逐行 `execute`，没有批量参数和统一事务；
6. 进程内 cache 只写在注释里，无法减少 Provider 压力。

正确方向应是：账本追加后只更新受影响账户/标的，投影批量 upsert；Provider 原始响应按 provider+endpoint+参数做短 TTL request coalescing；基金请求使用有上限的并发；整批观测在同一事务中写入，并以 source snapshot/hash 保证幂等。因为原模块完全不可达，本轮没有把这些高风险算法接进生产，而是删除重复实现，避免形成隐性性能债务。

## 6. 测试质量 Review

原始全量测试曾显示 `238 passed`，但不能证明新增功能可用：

- 新增五组测试只导入 `modules.*`，没有经过 FastAPI router、Worker 或真实生产 Service；
- Fake connection 依靠 SQL 子串返回 Python dict，无法验证 UUID 列类型、PostgreSQL 触发器、RLS、GRANT、事务回滚和 `SECURITY DEFINER` 默认权限；
- migration 测试只调用 `discover_migrations()`，没有调用生产真正使用的 `load_migrations()`，所以重复 017 没被发现；
- Outbox 测试只直接调用 Repository，未覆盖生产 Service 调用签名；
- JWT 测试只用新编码器解新 token，没有做 `modules` 编码、`backend` 解码的兼容测试。

本轮增加/恢复的有效回归保护包括：

- 完整调用 `load_migrations()`，保证每个版本只有一个文件；
- `APP_ENV` 非法值拒绝；
- role-boundary 即使 skip 也必须验证 process；
- binding migration 必须包含跨 owner 拒绝码和 race-safe ownership predicate；
- tenant 报告对两个 ACTIVE binding 生成两个独立 idempotency key；
- 无 ACTIVE binding 时不写 Outbox。

## 8. 已完成整改

### 8.1 恢复单一生产架构

删除本次新增且只被自身测试引用的平行文件：

- `modules/database.py`、`modules/errors.py`；
- `modules/identity/jwt.py`、`modules/identity/service.py`；
- `modules/ledger/repository.py`；
- `modules/market_data/service.py`；
- `modules/portfolio/service.py`；
- `modules/research/service.py`；
- 对应的五个孤立单元测试文件。

原来已存在且仍被生产/测试使用的 `modules/agent/tool_loop.py`、`modules/ledger/service.py`、`modules/market_data/providers.py` 没有删除；本轮只回退此次新增的重复层。

这不是删减既有需求：trade fill、decision、password reset 等能力仍应按需求优先级在 `backend/` 正式实现和验收；删除的是“没有生产入口却看起来像已交付”的影子代码，避免误判完成度。

### 8.2 修复多用户 Outbox

`insert_report_outbox_deliveries()` 恢复为：

- 按 tenant 查询全部 WeCom ACTIVE binding；
- 每个 binding 一个 Outbox row；
- 每个 row 使用 binding id 形成独立幂等键；
- 任一收件人的失败不阻塞其他收件人；
- 无 binding 时报告仍可发布，但不创建投递。

该语义与 migration 019、2～3 用户 MVP 和 `docs/10` 一致。

### 8.3 修复 migration 与 binding 安全

删除重复 017 和两个为平行模块服务的 020/021，新增唯一的：

`020_channel_binding_uniqueness_hardening.sql`

新 migration：

- 原子锁定 pending challenge；
- 锁定可能冲突的 external identity；
- 若旧 binding 不属于 challenge tenant/user，返回 `BINDING_EXTERNAL_ID_ALREADY_BOUND`；
- `ON CONFLICT DO UPDATE` 再加 tenant/user equality predicate，覆盖并发竞态；
- 同 tenant/user/channel 的旧 ACTIVE binding 原子撤销；
- 清理历史重复 ACTIVE 行后创建 partial unique index；
- 固定 `search_path`，撤销 PUBLIC EXECUTE，仅授权 `wealthsail_api`。

### 8.4 修复环境与角色校验

- `APP_ENV` 只允许 `development/test/staging/production`；
- `is_production` 不再对任意字符串做隐式判断；
- `verify_runtime_login_boundary()` 在 skip 之前验证 process；
- `docs/10` 说明非生产 skip 会记录 WARNING，不能作为生产验收；
- `docs/10` 的升级终点更新为 migration 020，并说明多用户投递与 binding 去重不是同一语义。

## 10. 仍需部署环境验证的事项

以下事项不能用 Fake connection 或纯静态测试替代，发布前仍必须执行：

1. 在“全新数据库”和“已应用到 019 的升级数据库”各执行一次真实 PostgreSQL migration；
2. 验证 migration 020 的函数 owner、PUBLIC/anon/authenticated/wealthsail_api EXECUTE 权限；
3. 并发提交相同 external hash、不同 challenge owner，确认只允许一个 owner 成功且失败事务不消费 challenge；
4. 两个不同用户分别绑定企微后，触发同一 tenant 的四个 session，确认各生成一条独立 delivery；
5. 单个 binding 失败/撤销时，确认其他用户的 delivery 不被阻塞；
6. 在目标 PostgreSQL 16/Supabase 上执行 `scripts/provision_supabase_roles.sql`，验证 API 不能 SET Worker、Worker 可以显式降权到 API；
7. 使用真实 `APP_ENV=production`、独立 DSN 和 secrets 启动 API/Worker，确认 role-boundary readback 失败关闭有效。

这些项在本地无专用 PostgreSQL/Supabase 测试实例时标记为 **NOT_RUN**，不能用本报告的单元测试结果替代生产上线 Gate。

## 11. 后续实现建议

按价值和风险排序：

1. **P0：PostgreSQL migration/RLS 集成测试**——在 CI 临时库执行 001～020，并从 019 做 upgrade 测试；这是避免再次出现“238 tests passed 但部署必失败”的最有效措施。
2. **P0：两用户 WeCom E2E**——覆盖绑定、换绑、冲突、撤销、四时段逐用户投递、单用户失败隔离。
3. **P1：正式实现成交草稿/确认**——放入 `backend/ledger` 或 `backend/portfolio`，遵循 DRAFT → CONFIRMED → immutable ledger → REVERSAL，不修改历史事实。
4. **P1：正式实现 decision 记录/撤回**——本人写入/撤回；若要支持 ADMIN 代操作，必须是独立命令、二次认证、原因和审计，不能靠宽泛 UPDATE policy。
5. **P2：密码重置**——只有确认 MVP 需要后再实现；token 永不在常规 API 响应/日志暴露，统一 anti-enumeration 响应，并显式收紧 `SECURITY DEFINER` 权限。
6. **P2：Provider 性能治理**——共享短 TTL request cache、限流并发、批量事务、增量投影和真实延迟指标；不要再把 Provider 与组合写命令放进同一个千行 Service。

## 12. 最终评价

`5bfc3c2` 的 API/Worker 登录分离和角色自检方向正确，值得保留；binding 唯一性目标也正确。主要失败来自把“代码量和测试数量”当作交付完成度：新增的大量代码没有进入生产依赖图，测试又只验证了自建 Fake 世界，因而同时漏掉迁移编号冲突、生产签名错误、真实 PostgreSQL 类型/触发器冲突和多用户需求回退。

整改后的结构重新遵循“单一 `backend/` 模块化单体 + forward-only migration + tenant RLS + 逐用户 Outbox”的既定设计。后续应坚持以生产入口和端到端追溯矩阵判断功能是否完成，而不是以孤立模块是否存在判断。
