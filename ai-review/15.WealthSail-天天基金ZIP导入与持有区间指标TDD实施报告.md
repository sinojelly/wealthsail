## 1. 结论

本期批准的“**本地采集器 + 单个 v2 ZIP + Web 预览确认 + 当前快照权威替换 + 历史流水仅作来源事实 + 官方单位净值异步回填**”已经完成前端、后端、数据库、Worker、采集器、自动化测试和部署文档实现。

实现遵循以下核心不变量：

1. 服务端不登录天天基金，不接收 Cookie、密码或浏览器资料；
2. DRAFT 预览不改变账本；确认前必须人工复核；
3. 当前持仓快照按基金逐项替换，预览后账户变化会拒绝陈旧确认；
4. 历史交易不伪造为 WealthSail 的 BUY/SELL/CASH_IN/CASH_OUT；
5. 账本确认与外部净值获取分属两个故障域，指标失败不回滚已确认持仓；
6. 金额、份额、成本和净值全链路使用 Decimal/NUMERIC/十进制字符串；
7. 所有批次、来源绑定、来源事实、账本效果和异步任务均有租户隔离、幂等与审计来源；
8. 功能默认关闭，数据库先迁移到 021、部署 Worker 后才允许灰度开启。

仓库级门禁通过；隔离 PostgreSQL 的空库 001→021、重复执行以及 020→021 升级回读均通过。真实天天基金会话在本次验证时已失效，采集器正确失败关闭；内置浏览器控制环境初始化失败，因此本报告不把真实第三方采集和渲染验收虚报为 PASS，仍列为部署前联调项。

## 3. 需求与设计遵循情况

### 3.1 端到端流程

| 设计决策 | 实现结果 | 状态 |
|---|---|---|
| 单个 ZIP，不选择目录 | Web 仅上传一个 `.zip`；服务端按 v2 manifest 解析 | 已遵循 |
| 上传后先预览 | `POST /portfolio/imports/tiantian/preview` 只保存 DRAFT | 已遵循 |
| 一个来源绑定一个专用账户 | `portfolio_source_bindings` 有租户/账户/Provider 部分唯一索引和复合外键 | 已遵循 |
| 当前快照权威 | NEW/UNCHANGED/CHANGED/CLOSED/CONFLICT；确认按基金冲正和替换 | 已遵循 |
| 历史流水只作来源事实 | 保存 source records/transactions，不写伪成交和现金流 | 已遵循 |
| 人工持有日起始日 | 证据不足时要求逐项输入，保存 `USER_CONFIRMED` | 已遵循 |
| 官方单位净值 | Worker 写 `market_observations(field_code='NAV')`，不使用盘中估值代替 | 已遵循 |
| 指标异步 | 确认返回 `PENDING`；持久任务回填 NAV 并物化指标 | 已遵循 |
| 可恢复向导 | 服务端批次历史/详情恢复 DRAFT 和确认结果 | 已遵循 |
| 多角色 | OWNER/ADMIN/EDITOR 可写，VIEWER Web/API/RLS 只读 | 已遵循 |
| 灰度开关 | `TIANTIAN_IMPORT_ENABLED=false` 默认关闭 | 已遵循 |

### 3.2 明确没有做的危险简化

- 没有让用户选择服务器无法访问的“本机目录”；
- 没有在服务端运行保存密码/Cookie 的爬虫；
- 没有把来源交易直接塞入不可变账本；
- 没有把最早一条交易机械当成当前持有起始日；
- 没有在请求进程中同步拉完整历史 NAV；
- 没有在指标失败后重新确认或重放账本；
- 没有把缺失净值、收益或百分比转换为 `0`；
- 没有允许 VIEWER 仅靠隐藏按钮来“实现权限”，后端和数据库仍独立检查。

## 4. 主要实现内容

### 4.1 本地采集器

`tools/tiantian-fund-importer` 现在可以：

- 从结构化响应发现并校验当前持仓、份额、成本、市值和来源净值；
- 按普通基金业务类型、年度不重叠日期窗口和全部分页采集成功流水；
- 二次分类活期宝现金管理、普通基金、非过账和待人工复核记录；
- 对订单去重、银行卡尾号脱敏、CSV 公式注入防护；
- 在私有目录保存本地核对文件，上传 ZIP 只包含允许成员；
- 生成稳定匿名来源账号 UUID、manifest、文件 SHA-256 和
  `wealthsail-tiantian-import/v2` 包；
- 页面结构漂移、登录失效、持仓汇总不平或部分响应时失败关闭。

### 4.2 ZIP 安全边界

后端解析器执行：

- 压缩体积、解压体积、条目数、压缩比、持仓数、交易数、JSON 深度和文本长度限制；
- 拒绝绝对路径、路径穿越、重复成员、符号链接和非法成员；
- manifest Schema、成员白名单、逐文件 SHA-256、字段形状和业务语义校验；
- 流式写入受限临时文件，请求结束清理；
- 解析阶段不持有数据库事务，防止慢上传/解压长期占用连接和锁。

### 4.3 数据库设计

Migration 021 增加或扩展：

- `ledger.portfolio_source_bindings`：匿名来源与专用账户绑定；
- `ledger.portfolio_import_batches/items`：包版本/哈希、来源时点、状态哈希、终态幂等、逐项快照和持有日决定；
- `ledger.portfolio_import_source_records`：导入包中全部可审计来源记录；
- `ledger.portfolio_source_transactions`：确认后的标准化第三方交易事实；
- `ledger.position_period_metrics`：按账户/基金/日期物化持有区间指标；
- `workflow.job_runs`：增加数据任务类型、payload、可用时间和 claim 索引；
- 唯一索引、租户复合外键、终态不可变触发器、账本冲正唯一效果、RLS 和列级最小授权。

没有再增加一套“天天基金持仓真值表”。当前持仓仍由既有不可变账本和投影表达，新表只管理来源、导入命令和衍生指标，避免双真相。

### 4.4 预览和确认服务

预览服务完成：

- 新建或核验来源绑定和目标账户；
- 同包/同命令幂等；
- 基于当前账户投影计算状态哈希；
- 生成每只基金稳定 item ID 和差异状态；
- 推断候选持有起始日和质量状态；
- 保存待复核、排除摘要、交易覆盖期和 DRAFT。

确认服务在单事务内完成：

- 校验 If-Match/version、人工复核和空账户额外确认；
- 对批次/账户加锁并重新校验目标账户状态哈希；
- 按基金生成旧来源基线的唯一 REVERSAL 和新 ADJUSTMENT；
- 保存来源交易，重建 position/NAV 投影；
- 固化批次终态、命令幂等键和审计；
- 提交 `FUND_NAV_BACKFILL` 持久任务。

相同确认重试返回同一结果，不重复产生经济效果。确认后不可编辑/删除；后续快照通过新的逐基金冲正链更正。

### 4.5 持有期和区间指标

持有起始日算法支持申购、赎回、转换、红利再投、清仓后再买，并输出：

- `TRANSACTION_RECONCILED`
- `PARTIAL_HISTORY`
- `MISMATCH`
- `INSUFFICIENT_DATA`
- `USER_CONFIRMED`

区间指标使用官方单位净值计算当前 NAV、最高/最低 NAV 及日期、距高点、距低点和区间位置。除零区间、缺页、无净值、日期冲突和历史证据不足都会显式降级，不用 0 或“正常”掩盖。

### 4.6 Worker 与故障恢复

- `FUND_NAV_BACKFILL`：分页抓取并幂等保存官方 NAV，然后触发指标物化；
- `POSITION_PERIOD_METRICS_REBUILD`：只重算已有 NAV 的指标；
- 数据任务使用数据库 lease、并发上限、最大尝试次数和指数退避；
- Worker 崩溃后租约到期可恢复；
- 首次 Provider 失败后的用户“重试指标”重新排完整 NAV 回填，而不是只重算空数据；
- API 详情从最新持久任务和指标行推导 `PENDING/READY/PARTIAL/CONFLICT/FAILED`。

### 4.7 前端

导入页实现：

- 拖放/选择单 ZIP、本地基础校验；
- 首次创建专用账户或选择已绑定账户；
- 上传失败时复用稳定幂等键；
- 新增/变更/不变/关闭/冲突标签和计数；
- 交易覆盖期、活期宝排除、待复核和警告展示；
- 全量复核勾选、空账户二次确认、持有起始日逐项决定；
- 409 陈旧预览刷新、DRAFT 取消、服务器历史恢复；
- 账本成功与指标失败分开展示，指标可单独重试；
- 只对确认后 `PENDING` 的查询结果轮询，终态停止轮询；
- VIEWER 只读说明；Dialog 焦点圈、Escape、焦点恢复和 body scroll 锁；
- 持仓页展开显示官方净值高低点、百分比、持有方法、成本收益和口径说明。

- 将持有区间指标接入 14:30 报告和盘后复盘，但必须携带方法、来源、质量和弃权原因；
- 支持其他基金平台时复用 Provider/Package Parser/Source Binding 端口，不复制一套账本。

## 9. 最终判断

从代码、数据模型和故障语义看，本实现符合批准设计，避免了第三方流水伪造成交、同步长事务、双真相持仓表和指标失败重放账本等高风险简化。MVP 的扩展性主要通过来源绑定、版本化包解析、不可变账本来源链和持久数据任务获得，未来增加其他基金平台时不需要推翻核心架构。

当前可以进入隔离服务器部署和 2～3 用户试点前联调；在真实采集、目标 Supabase readback 和浏览器渲染证据补齐前，不应把 TT-FR 需求状态批量改成系统级 `PASS`。
