# WealthSail `b58af11` Web 工作台 Review 与修复方案

> Review 对象：`b58af11aeefda041e69b74990b3debbc3f7ade6f`
> Review 日期：2026-08-23
> Review 范围：Web 产品范围、租户与会话、企业微信绑定、账本初始化、风险政策、API 契约、前端工程、需求追溯和测试验收
> 实施原则：保留详细需求与架构描述；先修安全、事实和阶段边界，再完善体验；L1 实现必须可平滑扩展，但不预付 L2–L4 的交互复杂度

## 1. 结论

`b58af11` 将 Web 工作台从零散描述提升为独立设计文档，四时段报告、资产大盘、风险政策、企业微信绑定和证据链等方向正确，也改善了文档导航。但原提交还不能直接作为开发基线，主要原因不是页面数量不足，而是以下对象边界没有闭合：

1. 多租户切换与 JWT 租户解析互相矛盾；
2. 绑定 token 生成时尚无企业微信身份，却提前创建 `channel_bindings`；
3. 初始入金和买入被错误合并为单一 `trade_fills` 草稿；
4. L1 风险页面暴露了仅属于 L4 的债券、黄金和大宗配置；
5. API 章节只有路由目录，缺少可实施的幂等、并发、角色、错误和精度契约；
6. 新 Web 能力没有需求 ID、追溯关系和异常测试；
7. 收益率、估值和基准对比没有统一金融口径；
8. 前端技术选项、会话安全、缓存隔离、响应式和异常状态仍未收敛。

本次修复采用“模块化单体不变、对象职责收紧、增量 Migration 扩展”的方案，不推翻既有架构。

## 2. 问题与修复决策

### 2.1 活动租户上下文

#### 原问题

Web 文档同时要求支持多租户切换、禁止请求携带租户上下文，并声称 `identity.is_tenant_member` 能自动提取租户。实际该函数只接收一个已经给出的 `target_tenant` 并判断 membership，不能决定用户当前操作哪个租户。若前端还复用没有 tenant scope 的请求缓存，切换时可能短暂显示上一租户数据。

#### 修复决策

- PostgreSQL 表、组合外键、RLS、缓存/队列 namespace 继续保持多租户扩展能力；
- L1 每个 access token 只绑定一个活动租户，不在页面内即时切换；
- 用户将来属于多个租户时，必须显式选择后由后端重新校验 active membership，并签发新的 tenant-scoped access token；
- `identity.is_tenant_member` 只作为 membership predicate，不再描述成租户提取器；
- 所有前端 Query Key 包含 active tenant subject，登出、失权或重新签发租户会话时清空敏感缓存。

这样既满足 MVP 2–3 用户隔离，又为后续家庭/团队租户保留扩展点。

### 2.2 企业微信绑定挑战与正式绑定

#### 原问题

原流程在生成 token 时写入 `channel_bindings`，但该表要求 `external_user_hash NOT NULL`。在用户尚未从企业微信发送 `/bind` 前，服务端并不知道外部用户 ID。直接让企业微信消息进入 Domain API 还绕过了签名、nonce、message ID、allowlist 和限速验证。

#### 修复决策

- 新增 `identity.binding_challenges` 保存一次性 token 的 keyed hash、tenant/user、过期、尝试次数、状态和幂等键；
- token 明文只在创建响应中返回一次，禁止进入数据库、日志、分析 SDK、URL query 和模型上下文；
- 企业微信消息必须先经过 WeCom Adapter/Gateway 的签名、防重放、allowlist 和消息长度校验；
- Adapter 验证 challenge 后，在同一事务中创建/激活 `channel_bindings` 并消费 challenge；
- 解绑是 `REVOKED` 软撤销，保留历史和审计，不物理删除；
- L1 普通用户只能管理自己的绑定，跨用户恢复只允许 OWNER/ADMIN 经重新认证的受控 API 执行。

### 2.3 初始资产导入与真实成交

#### 原问题

`trade_fills` 表达真实买卖成交，没有“入金金额”字段。把入金和买入一起塞进 `/ledger/fills/draft`，再在确认时同时执行 `record_cash_in` 与 `record_buy`，会让一条 fill 承担两个事实，并在重复确认时产生重复入金风险。

#### 修复决策

- 普通出入金继续使用独立 cash command；
- 普通成交继续使用 `trade_fills(DRAFT)`，确认后只产生该 fill 对应的买卖经济效果；
- 新用户初始化改为 `portfolio_import_batches + portfolio_import_items`：自然语言、表单或 CSV 只生成导入批次，逐项校验和预览后由一个幂等命令为每个 item 原子生成带来源链的期初 `ADJUSTMENT` 事件；它不是历史 CASH_IN/BUY 或真实 fill，收益从导入基线开始；
- 批次任一项目失败则全部回滚；撤销已确认批次只能追加冲正事件；
- 数据库在确认前拒绝空批次和非 `VALID` 项；item 的 INSERT/UPDATE/DELETE 都锁定并检查父批次，批次进入终态后明细不可新增、修改或删除；
- 所有写接口要求 `Idempotency-Key`，版本化资源要求 `If-Match` 或等价 version 条件更新。

### 2.4 L1 风险政策边界

#### 原问题

原页面把权益、固收、黄金/大宗、现金四项滑块全部纳入 L1，但 PRD 明确黄金、债券和大宗真实数据在 L4；数据设计也规定这些目标字段在 L1 只为空扩展点。

#### 修复决策

- L1 页面只编辑基准、单标的上限、最大回撤容忍、提醒预算和静默窗口等已支持约束；
- 债券、黄金和大宗目标不出现在可提交表单中，可在路线图说明中展示为禁用的 L4 扩展；
- 任意百分比示例不成为默认值；
- 只有完整、适用于当前资产范围、经用户确认的新政策版本才可进入 `CONFIRMED`；
- 确认新版本和退役旧版本在同一事务完成，已确认内容不能原地覆盖；
- 008 之前已有政策缺少可信确认人/时间时标记 `LEGACY_MIGRATED`，不伪造历史确认人；旧政策可受控退役，新政策必须记录 `USER_CONFIRMED + confirmed_by + confirmed_at`；
- Migration 008 在任何 schema 变更前检查同一作用域多个当前 CONFIRMED 政策，发现冲突立即失败并要求人工调查，不替用户静默选一个版本。

### 2.5 API 与角色权限

#### 原问题

原 API 章节未定义 DTO、状态码、分页、错误、Decimal、时间、数据质量、幂等、乐观锁和权限。角色清单遗漏 `EDITOR`，绑定列表和解绑接口也没有区分本人操作与管理员操作。

#### 修复决策

- 明确 access token、refresh cookie、CSRF 和 token 存储边界；
- 统一 Decimal 字符串、ISO 8601 时间、Asia/Shanghai 交易日语义、quality/as_of/method_version；
- 定义统一错误 envelope 和 `correlation_id`；
- GET 使用 cursor 分页；mutation 禁止无条件自动重试；
- 采用 OWNER/ADMIN/EDITOR/VIEWER 页面与命令权限矩阵，最终授权始终由 Domain API 执行；
- 风险政策使用 draft/update/confirm 三类命令，绑定使用 challenge/consume/revoke 状态机；
- 撤销普通 JWT 对 binding 和投资政策的直接写权限，避免绕过重新认证、幂等、审计和角色检查；
- 正式 binding 采用本人 RLS 加列级白名单，只返回状态字段，不暴露 `external_user_hash`、新旧 token/hash 兼容列；
- `secret_refs`、原始 jobs/job_runs/outbox/audit 表对所有浏览器 JWT 撤销 SELECT，OWNER/ADMIN 运维页也必须经 Domain API 获取脱敏 DTO。

### 2.6 收益、估值和图表精度

#### 原问题

“当日盈亏、累计盈亏、年化收益率、净值曲线”没有现金流、费税、分红、估算净值、非交易日和基准对齐口径。前端又要求 JSON 使用字符串，但图表库最终需要渲染数值，缺少明确转换边界。

#### 修复决策

- 绝对累计盈亏按当前权益减累计净入金计算，费税和分红来自账本；
- 组合收益率使用现金流中性的 TWR；历史不足一年不展示“年化”标签；
- 场外基金估算进入组合时，页面整体标记 `ESTIMATED`，不得显示为正式净值；
- 基准来自已确认政策；未设置时不偷偷选择沪深 300；
- 后端 Decimal 计算并返回字符串；前端使用 Decimal 库格式化，只有 `ChartNumberAdapter` 可转换为展示用 Number，转换结果禁止参与业务判断或回写。

## 3. 前端选型收敛

L1 采用一套明确组合：

- React 19 + Vite + TypeScript；
- Tailwind CSS + CSS variables；
- TanStack Query，不再同时保留 SWR；
- 原生 Fetch 的统一 wrapper，不再同时保留 Axios/Fetch；
- React Hook Form + Zod；
- 从 FastAPI OpenAPI 生成 TypeScript DTO；
- decimal.js 负责展示格式化，业务计算仍在后端；
- Recharts 只消费隔离后的展示数值；
- 360px–4K 响应式、键盘、读屏、焦点和非纯色状态是 L1 验收项。
