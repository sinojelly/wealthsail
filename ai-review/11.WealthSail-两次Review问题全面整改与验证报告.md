## 1. 结论摘要

本轮已经把两次 Review 中能够在代码、数据库迁移、测试、部署模板和文档内闭环的问题集中整改。核心结果如下：

1. **数据库信任边界恢复**：浏览器认证角色不再拥有核心事实表写权限；API 与 Worker 使用不同登录凭据和运行角色；Worker 通过 `NOINHERIT + BYPASSRLS` 承担系统任务，并只获得所需表权限。
2. **认证和多租户闭环补齐**：MVP 改为邀请制注册；访问令牌与可轮换 HttpOnly refresh cookie 配合；租户切换由服务端重新签发会话；企微只能通过验签回调完成绑定；跨租户 header 伪造被拒绝。
3. **组合资产不再伪造完整估值**：资产投影只由已确认账本事实重建；缺少行情或基金净值时记录估值覆盖率和未定价数量，组合、风险检查和报告按不完整数据降级或弃权。
4. **场外基金 14:30 最小可信闭环完成**：只计算用户实际持有的基金；基于已披露持仓、残余基准假设和覆盖率形成确定性估算；低于 60% 覆盖率时返回 `UNAVAILABLE/ABSTAIN`，同时保存观测、来源与证据引用。
5. **四时段任务与企业微信投递可靠性修复**：任务使用数据库 lease 和幂等键；Outbox 原子认领、短事务、带租约重试；生产者不再传入任意 `touser`，Worker 从已验证绑定解析收件人；不再在结果未知时跨通道自动补发。
6. **前端从演示壳收敛为真实状态工作台**：删除伪成交、伪导入成功、伪证据和伪导出；错误不再渲染为空数据；金额类型支持部分估值；tenant 切换清理私有缓存；关键交互补充键盘可访问性。
7. **迁移、部署和 CI 可验证**：生产迁移与开发 seed 分离；新迁移执行器具有 checksum、事务和 readback；API/Worker 环境文件、数据库角色和容器边界拆分；统一验证脚本与 CI 已覆盖前后端、文档和构建。

当前代码已达到“可进入受控 MVP 联调”的工程状态，但**还不能仅凭本地自动化结论宣称可直接生产发布**。历史凭据轮换、真实企业微信链路、生产模型网关、TLS/备份恢复、容量压测和观察期仍是发布前外部 Gate。

## 5. 关键设计修改说明

### 5.1 数据库与权限

本轮没有推翻现有 schema，而是通过兼容 migration 扩展，保持后续 L2–L5 可演进：

- `wealthsail_api` 是 NOLOGIN 组角色，继承受限的 `authenticated` 读能力并获得 Domain API 所需命令权限。
- `wealthsail_worker` 是 `NOINHERIT BYPASSRLS` 组角色；它只对市场来源、任务、Outbox 等系统表获得精确权限，并可在需要复用 tenant 业务逻辑时显式切换到 API 角色。
- 生产登录角色不在 migration 内写死密码，由 Secret Store/平台创建，再分别授予 API 或 Worker 组角色。
- 新增邀请、refresh session、job lease、Outbox lease、基金披露、估值完整性和报告证据关系，不重建已有核心稳定 ID。
- 迁移 readback 除版本/checksum 外，还验证角色属性、成员关系、敏感授权、列名、旧演示 seed 和旧认证函数，防止 SQL “执行成功但安全语义错误”。

### 5.2 组合投影与部分估值

过去最危险的设计不是计算误差，而是把缺失净值或行情当作 0，再给出看似精确的总资产和风控结论。本轮改为：

1. 已确认 ledger 是唯一经济事实；投影可删除重建。
2. 已知金额与完整总金额分开；只有所有必要位置均可定价时才给出完整总资产。
3. 同时返回覆盖率、未定价仓位数和 quality status。
4. 风险规则遇到部分估值时不输出虚假的“通过”；报告也明确降级或弃权。

这种设计可自然扩展到更多账户、基金、黄金、债券和多市场，而不需要改变“事实—观测—投影—报告”的主链。

### 5.3 基金 14:30

MVP 不追求复制基金公司盘中估值，而是提供可解释、可弃权的持仓相关估算：

- 输入：用户实际持有基金、最近披露成分、成分实时/最近行情、残余部分基准假设、上一已知净值。
- 输出：估算收益率、估算净值、上下界、披露覆盖率、数据时间与状态。
- Gate：有效覆盖率低于 60% 时不发布数值结论；来源过期或数据不完整时标记 `UNAVAILABLE`。
- 审计：保存每个 observation 与 report item 的 evidence 关系，前端只展示真实证据。

后续可替换行情/基金数据 Provider，或加入行业/风格残差模型，但不改变估值器契约和弃权机制。

### 5.4 Scheduler、Outbox 与企业微信

可靠链路现在是：

`时段调度 -> 获取 job lease -> 生成幂等报告 -> 写 tenant 级 Outbox -> Worker 原子 claim -> 从已验证绑定解析收件人 -> 外部发送 -> 回写 delivery 状态`

重要约束：

- 报告服务不知道外部 `touser`，避免业务层接受任意路由。
- 外部 HTTP 调用不在数据库事务/连接占用期间执行。
- token 失效只允许一次受控刷新；消息长度按 UTF-8 字节校验。
- 应用消息结果未知时不自动切 Bot 补发，避免双消息。
- Bot WebSocket 是默认关闭的实验通道，不是 MVP 发布依赖。

### 5.5 前端可信状态

- 资产和收益支持 `null`，页面明确显示“估值不完整”，而不是 `¥0.00`。
- API 错误、空列表和加载中分别渲染。
- tenant/user 进入 Query Key；会话变化时主动清理私有缓存。
- 企业微信绑定只展示一次性 challenge；浏览器不能提交 external id；解除绑定需要二次密码确认。
- 修复报告列表查询契约：前端使用 `tradeDate`，后端 OpenAPI 现在显式声明同名 alias。此前后端的 `trade_date` 会静默忽略前端筛选，此问题由真实 API 冒烟发现并新增契约回归测试。

## 7. 文档同步与多 Agent 局限

本轮没有为了缩短文档删除需求、场景、架构说明或长期演进内容，而是做 AS-IS/TO-BE 分层：

- `docs/01` 保留 L0–L5 全景，但明确股票、场内/场外基金、四时段、企业微信和 2–3 用户是当前 MVP；新增 Chat 追溯需求。
- `docs/03/06/10` 更新当前迁移、seed、角色、部署和目录实情。
- `docs/04/08` 补充 Chat、基金估值、迁移、认证和异常分支测试/追溯。
- `docs/02/05/07/09` 继续保留多 Agent 与 Skill 远期说明。

多 Agent 需求**没有删除**，但仍为 L5 最后优先级、默认关闭，原因和约束已经写入需求、架构、安全与验收文档：

1. 共享模型、检索与提示上下文会产生高度相关错误，多数票不能把同源幻觉变成事实。
2. 角色扮演容易制造“看似充分争论”的虚假确定感。
3. 更多 Agent 显著增加 token、搜索、延迟、重试组合和观测成本。
4. 非确定并发顺序降低可复现、审计和回归能力。
5. 每增加一个工具主体都会扩大 Prompt 注入、越权、跨租户传播和敏感数据复制面。
6. 多 Agent 永远不能成为行情事实源、金额/仓位计算器、风险裁决者、账本写入者或交易授权者。
7. 启用前必须用固定 Golden set 和人工盲评证明相对“单 Agent + 确定性规则 + 反方清单”的净增益，同时满足成本、p95 延迟、安全和可回放 Gate；任一指标退化立即通过 feature flag 回退单 Agent。

这保证需求仍可扩展，但不会让远期实验污染 MVP 架构和投资可信度。

## 11. 最终评价

两次 Review 的主要代码和设计缺陷已经从“局部打补丁”收敛为一条一致的 MVP 主链：

`邀请制用户 -> 租户隔离 -> 已确认账本 -> 可解释投影/基金估值 -> 四时段报告 -> 证据与质量状态 -> Outbox -> 已验证企微绑定 -> 用户交互复盘`

这条链保持了后续扩展空间，同时把事实、计算、模型解释和外部投递的权限分开。当前最重要的后续工作不是继续增加功能，而是完成历史凭据处置、真实第三方联调、生产基础设施和正式验收运行证据。只有这些 Gate 关闭后，才能把“本地工程验证通过”升级为“可生产发布”。
