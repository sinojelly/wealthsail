## 1. 结论摘要

- 设计遵循结论：**部分符合**。模块化单体、API/Worker 分权、RLS、四时段枚举、天天基金导入、企业微信逐用户投递和 Docker Compose 主拓扑均已实现；但调度时序、Webhook 重放、Outbox 状态/可观测性、市场热点数据流和 Nginx 运行边界存在实现偏离。
- 风险统计：P0 0，P1 9，P2 6，P3 0；另记录 1 项不宜在本轮伪装成已完成的产品能力缺口。
- 修复目标：本报告中的已验证问题全部整改；不能只改文档来掩盖实际运行缺陷。
- 交付结论：整改前不建议交付；整改后的后端单测、Ruff、集成/E2E 本地套件和前端门禁均已通过，真实 Supabase/企业微信/TLS 仍按目标环境验收处理。
- 文档已升级到 v2.7，并明确区分“已经实现”“仓库已具备但外部平台未启用”“仍需真实 Supabase/企微/TLS 验收”三种状态。

最重要的结论如下：

1. `tests/unit/test_identity_service.py` 已无 Git 冲突文本，但被改为导入不存在的 `modules.errors/modules.identity`，导致 CI 后端门禁无法启动。
2. 盘中任务覆盖午休，且 14:30 的 `INTRADAY` 与 `FUND_1430` 被串行执行，可能延迟对时点敏感的基金报告。
3. 企业微信 POST 回调只有 300 秒新鲜度校验，没有跨进程、可恢复的消息去重，不能称为完整防重放。
4. Outbox 文档使用不存在的 `RETRY` 状态并遗漏 `UNKNOWN/CANCELLED`；没有 binding 时的零投递也未留下文档承诺的明确可观测事实。
5. `/market/hot` 在 GET 请求中直接访问外部 Provider，与 Worker 生产、API 只读投影的总体边界不一致。
6. Nginx 文档、Compose 服务名、SSE 缓冲、头像路径限制和 TLS 终止拓扑存在多处漂移。

### F-03 [P1] 企业微信 POST 回调缺少真正的重放去重

- 置信度：高。
- 位置：`backend/integrations/wecom.py:280-388`。
- 触发条件：攻击者或企业微信在 300 秒窗口内重复发送相同合法加密回调。
- 实际行为与影响：签名和时间戳仍然有效，业务命令会再次进入处理；当前绑定挑战的一次性语义只能保护 `/bind`，不能保护未来交互命令。

- 修复建议：增加数据库持久化的 provider+消息摘要 claim，原子首次领取；重复报文返回成功但不重复执行业务。
- 验证方法：同摘要首次 claim 成功、第二次失败；迁移/readback 检查函数权限和表边界。

### F-13 [P1] 绑定创建与成功审计不在同一事务，文档还夸大了失败限速

- `INTRADAY` 改为 09:30–11:30、13:00–15:00 的交易窗口，每五分钟一个逻辑业务桶；同桶
  重复 tick 使用相同 key，相邻桶使用不同 key。

- 新增独立 `run_recoverable_jobs` 循环：执行最近 30 分钟内的 `PENDING/FAILED` 报告 run，默认
  最多 5 次并复用原业务 key；FAILED 设置下一次重试时间，避免热循环。完整“重大偏离才触发”的
  风险评估/静默合并仍按 F-15 保留为 TARGET，不在文档中夸大。

### 6.3 企业微信与身份事务

- migration 026 新增 `workflow.wecom_callback_claims` 和固定 `search_path` 的
  `SECURITY DEFINER workflow.claim_wecom_callback(text)`；应用角色没有表权限，API 只有函数
  EXECUTE。
- 回调完成验签和解密后，以 CorpID + MsgId 构造不透明 SHA-256；无 MsgId 时对已认证明文做

  `WECOM_BOUND` 审计，任何一步失败都整体回滚。
- 纠正加密描述：当前为 API/Worker 共享 AES-GCM 对称密钥 + API 数据库角色不可读密文列；
  公钥/KMS/keyring 和来源级持久限速仍是 TARGET。

### 6.4 市场热点与质量传播

- migration 027 新增只允许 Worker INSERT、API SELECT 的 `market.market_hot_snapshots`；快照
  保存条目、来源时间、抓取时间、质量和方法版本。
- Worker 在正式 session 中刷新热点；`GET /market/hot` 只读数据库，不再调用 AkShare、东财或

## 8. 数据库、部署与回退

  --confirm-target db.example:5432/postgres --dry-run

  --confirm-target db.example:5432/postgres

已经应用的 migration 文件；先停止新 Worker 流量、保留表和数据，以新的 forward-fix 修复。旧 API
