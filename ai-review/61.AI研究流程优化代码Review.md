\### 问题 1：Migration 095 又引入了事务边界问题



P1 · 上线前必须修复



文件：`migrations/095\_daily\_research\_pipeline.sql`



这次新增的 095 仍然是：



```

BEGIN;



CREATE TABLE research.daily\_research\_pipelines (

&#x20;   ...

);



\-- 其他授权和策略



COMMIT;

```



而之前的 `589da2e` 已经修复了 094 的同类问题。



现在 `scripts/migrate.py` 在 Python 层用 `async with conn.transaction()` 同时包裹迁移 SQL 和迁移账本写入。SQL 文件内部再执行 `COMMIT`，可能提前结束外层数据库事务，使 DDL 和迁移账本失去原子性。



修复：



1\. 删除 095 第一行 `BEGIN;` 和最后一行 `COMMIT;`。

2\. 保留所有表、约束、RLS 和授权逻辑。

3\. 增加静态测试：每个迁移 SQL 都不能在顶层自行执行 `BEGIN`、`COMMIT` 或 `ROLLBACK`。

4\. 重建或清理专用的隔离测试数据库，再重新执行迁移测试。



由于 095 尚未部署 NAS，可以直接修正该文件。这与修改已经应用过的生产迁移是两回事。



\### 问题 2：采集阶段重启后，可能无法恢复当天任务



P1 · 影响每日自动投研可靠性



涉及：



\- `backend/jobs/daily\_research.py`

\- `backend/macro/daily\_pipeline\_repository.py`



目前 `claim\_pipeline()` 只允许重新接管一种状态：



```

state = 'RUNNING'

AND stage = 'WAITING\_SOURCES'

AND lease\_until <= 当前时间

AND research\_run\_id IS NULL

```



但在 Worker 正常收到取消信号时，`sync\_daily\_research()` 会将任务写成 `UNCERTAIN`，即使此时只在 `COLLECTING`（采集公共数据）阶段，还完全没有调用过 Codex。



由此可能出现：



1\. 07:00 开始采集。

2\. 07:05 因 NAS 升级、Worker 重建或正常关闭，采集被取消。

3\. 流水线被标记为 `UNCERTAIN`。

4\. 07:10 Worker 重新启动，仍在允许补启动的窗口内。

5\. 由于已有终态记录，`claim\_pipeline()` 无法重新领取，今天的研究不再执行。



这违背了你希望在 07:00–09:00 期间能够安全恢复研究的运维目标。



建议明确区分两个边界：



\- 模型执行槽位尚未登记：允许在安全条件下恢复采集和输入准备，但必须校验旧采集批次、租约和尝试记录，避免重复采集、覆盖结果。

\- 模型执行槽位已经登记：不自动重新调用 Codex，保持现有的严格防重策略。



不能把“采集前失败”和“模型调用结果不确定”都当成同一种不可恢复的 `UNCERTAIN`。



\### 问题 3：30 分钟租约缺少持续续约，慢任务可能被误判为异常



P2 · 建议上线前完善



文件：`backend/macro/daily\_pipeline\_repository.py`



目前流水线每次切换阶段时更新租约，租约长度固定为：



```

LEASE = timedelta(minutes=30)

```



但是某一阶段持续运行时，没有独立的心跳续约机制。



例如：



\- 07:00 数据采集完成。

\- 07:10 开始构建研究输入。

\- 因外部接口、数据量或网络问题，单个阶段耗时超过 30 分钟。

\- 流水线租约过期，网页可能显示 `PipelineLeaseExpired`。

\- 后续阶段更新会因为租约已失效而失败。



当前 Codex 研究默认超时 900 秒，通常低于 30 分钟租约，但采集、输入构建和报告核验的总耗时不能仅靠这个超时保证。



建议为运行中的流水线增加轻量心跳：定期在仍持有正确租约令牌时续约，发现令牌失效时立即停止后续派发。不要使用无条件续约，也不要因此延长模型调用的安全上限。



\### 问题 4：07:00–09:00 启动窗口的边界还需要明确



P2 · 设计与实现需要统一



`sync\_daily\_research()` 在 09:00 之后不允许领取新的流水线，这是合理的。



但是 `\_execute\_daily\_research()` 还有第二次窗口检查：即使流水线在 07:00 正常启动，如果公共采集和输入准备一直进行到 09:00 以后，仍然会返回 `MISSED`，不再调用模型。



这意味着：



\- 07:00 正常启动；

\- 08:55 采集完成；

\- 09:02 研究输入准备完成；

\- 最终当天没有 AI 研究报告。



建议明确两种不同限制：



启动截止时间：09:00，超过后不得创建新的每日流水线。



已启动流水线的运行期限：单独设置合理上限。只要仍持有有效租约、数据时效满足要求，而且模型执行槽未被消费，就允许完成后续研究准备。是否允许 09:00 后才首次调用模型，应作为明确的业务规则，而不是被“启动窗口”顺带限制。



如果你的本意是“09:00 前必须开始模型调用”，那么当前行为可以保留，但文档和网页需要明确写成模型派发截止时间，不能只称为补启动窗口。
