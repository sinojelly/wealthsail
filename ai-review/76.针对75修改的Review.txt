## 初步结论

这轮优化方向正确，但我不建议马上部署生产。 我发现一个可能显著降低每日研究成功率的 P1 风险，以及一个明确的前端显示错误。

值得保留的改进包括：

- 模型审核输入去重，冻结的完整审计材料没有被删除。
- 正式方向可以引用顶层行业审核，不必重复输出全部五类风险。
- 五类反方核查、历史风险继承、价格保护和评分规则仍然保留。
- `NOT_FOUND` 不能再仅凭模型自报就当作已执行搜索。
- 新增了 Prompt 字节数、搜索动作、页面读取、模型及来源核验耗时的观测。
- 历史研究可以按已知的冻结合同版本重验。

但最值得注意的是：审查变严格后，真实搜索虽然已经执行，也可能由于凭证匹配方式过于严格，被系统认定为没有执行。

## 二、仍然存在的具体问题

| 优先级 | 问题                           | 影响                      | 是否建议部署前修复 |
| --- | ---------------------------- | ----------------------- | --------- |
| P1  | 搜索执行凭证采用查询字符串完全匹配            | 真实搜索可能被误判为未执行，导致正式报告失败  | 是         |
| P2  | 远程 Runner 回执超限时降级为 `PARTIAL` | 模型成功但执行证明丢失，可能影响投资方向审核  | 建议验证      |
| P2  | 前端搜索核验状态显示错误                 | 即使已完成核验，页面仍可能说“尚未验证”    | 是，改动很小    |
| P2  | 严格验证器未始终校验回执所属研究 ID          | 单独调用严格验证接口时，本次研究身份绑定不完整 | 建议补强      |

### 1. P1：真实搜索很可能无法满足完全匹配

位置：

`backend/integrations/research_execution.py`，`executed_task_ids()`，约第 333 行。

当前逻辑：

```
hashes = {    row["queryHash"]    for row in receipt["queryReceipts"]}
```

后面只有实际搜索字符串与任务预设字符串的 SHA-256 完全相同，才认定任务执行。

假设服务器生成：

```
机器人 具身智能 融资降温 最近90天
```

但模型实际搜索：

```
2026年人形机器人融资减少 企业倒闭
```

两次搜索高度相关，但哈希完全不同。

系统会判定：

```
真实搜索：已执行
任务执行凭证：未匹配
行业审核：仍未完成
正式方向：可能被拒绝
```

而且五类审核中只要某些 `NOT_FOUND` 没有相应执行证明，该行业就可能无法获得完整审核资格。

这是我目前最担心的问题：新版为了保证研究可信度，有可能再次出现“AI 推理成功，正式业务失败”。

源码里的离线测试使用的是预先构造的完全一致查询，不能证明真实 Codex 会自动使用服务器提供的原始查询字符串。

建议修复方式：

不要改为模糊字符串匹配，那会降低真实性。应当让受控搜索任务拥有服务器生成的 `taskId`，并在真实工具执行边界绑定任务身份，记录实际查询、完成状态和关联证据。

在无法实现受控任务执行之前，至少要将“搜索执行了，但未匹配预设任务”单独统计为 `EXECUTION_UNMATCHED`，保留任务待审，不伪装已经通过。

最重要的上线验收指标是：

实际执行任务数 / 本批计划任务数，以及因凭证不匹配而失去正式资格的方向数量。

如果这一比例异常，即使所有单元测试通过，也不应直接开启每天 7 点的自动研究。

### 2. P2：远程 Runner 回执降级会影响审核资格

位置：`backend/codex_runner.py`，约第 405–423 行。

当前处理方式是：如果完整模型报告加上执行回执超过传输体积限制，优先保留报告，把执行回执缩小或省略。

这是正确的故障保护，避免附加观测让模型成果直接丢失。

但缩小时会将：

```
"coverage": "PARTIAL","queryReceipts": [],
```

这意味着搜索证据关联全部不可使用。

对于依赖搜索执行证明的 `NOT_FOUND` 审核，正式资格可能随之下降。

因此建议额外测试：大型报告 + 大量搜索回执 + 远程 Runner 响应接近大小限制，确认系统会记录明确原因、保留部分成果，而不是让用户只看到新的行业核验失败。

更好的长期方案是让执行回执与研究报告使用独立的有界传输或持久化通道，避免二者争抢同一个 2 MiB 响应预算。

### 3. P2：前端有一个明确的状态显示错误

位置：

`frontend/src/features/fund-screener/components/ResearchTopicRegistry.tsx`

当前页面写死：

```
<p>
  独立搜索执行凭证尚未验证；
  五类核查结构不代表实际搜索完成。
</p>
```

但后端 `audit_assurance()` 已经能够返回：

```
searchExecutionVerified = true
```

也就是说，即使核验成功，页面仍然显示“尚未验证”。

同时，`frontend/src/api/research-topic-registry.ts` 将字段类型声明成：

```
searchExecutionVerified: false;
```

这里应该声明为 `boolean`，并根据真实状态动态显示。

这是一个可以确定的前端问题，不是推测。

### 4. P2：严格验证器的研究身份绑定还可以更完整

`research_assurance.verified_tasks()` 支持检查 `research_id`，但在 `daily_research.py` 的严格校验流程里，部分调用没有传入明确的研究 ID。

在现有正常 Worker 路径中，材料由服务器生成并归档，风险受到限制。但从接口契约看，严格验证器单独运行时，没有完整利用已经存在的研究 ID 绑定能力。

建议给 V2 严格校验增加明确的运行身份上下文，让正式验收和离线恢复都验证相同的研究身份，而不是只依赖冻结任务哈希和时间。

这属于加强一致性与审计，不是我已经证实存在跨租户漏洞。

## 三、成本优化是否安全？

从静态代码看，这轮压缩没有明显删除核心风险规则。

合成 50 项审核任务输入视图

优化前

31,930 字节

优化后

10,866 字节

该审核视图的 UTF-8 字节数减少约 66%，不是整次模型输入或 Token 消耗减少 66%。

从价值看，这次优化值得保留。它减少了重复合同内容，也允许模型不再为每个正式方向重写五类风险。

但你的主要成本可能仍来自实际网页搜索、反复打开页面、逐家公司核对及长上下文推理。因此，即使输入视图缩小 66%，也不能保证 9 分钟会恢复到 6 分钟。

我建议下一轮不要再扩大 Prompt，而是利用新增工作量观测进行实际对比。
