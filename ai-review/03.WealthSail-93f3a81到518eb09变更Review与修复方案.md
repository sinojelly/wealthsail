## 1. 结论摘要

## 3. 阻断级问题

### 3.1 Hermes 与数据库信任边界冲突

`docs/03` 把 `SUPABASE_SERVICE_ROLE_KEY` 放入项目或 Hermes `.env`，但 `docs/06`、`docs/07` 又规定 Hermes 只能调用 scoped API。Hermes WeCom 工具集可包含终端能力，service role 又能绕过 RLS，两者不能处于同一通用 Agent 运行环境。

修复决定：

- Hermes/WeCom 只持有短期、限定 audience/scope 的 API 凭据；
- tenant/user 只能由后端根据认证会话或已消费的渠道绑定解析；
- service role 仅限受控后台管理任务，不进入 Agent、前端、示例、日志；
- Worker 使用专用最小权限数据库角色；
- 文档中的 Hermes 与数据库直连图改为 `Hermes -> Domain API -> PostgreSQL`。

### 3.2 企业微信错发与伪成功

当前 `send_markdown_message()` 默认 `to_user="@all"`，凭据缺失返回 `MOCK_SENT`，幂等键只存在内存。对于多用户资产系统，这会形成错发、误报成功和重启后重复推送风险。

修复决定：

- 收件人改为必填，拒绝空值和 `@all`；
- 缺少凭据默认返回明确 `CONFIG_ERROR`，只有显式 `dry_run=True` 才允许模拟；
- Adapter 不再声称拥有持久幂等；生产幂等由 `workflow.outbox` 和渠道 message ID 保证；
- 绑定 token 使用注入的服务端 secret，不提供源码内默认 key；
- 绑定 token 增加一次消费、尝试次数、限速、撤销和 tenant/user 绑定语义。

### 3.3 RLS、角色和不可变事实不一致

当前 migration 为所有 tenant 表批量创建 SELECT/INSERT/UPDATE/DELETE policy，仅检查 active membership。VIEWER、EDITOR、OWNER 没有差异，账本、审计、Outbox 也没有 append-only 保护。

修复决定：

- `is_tenant_member()` 只负责读取资格；新增 `has_tenant_role()` 处理写入角色；
- 普通成员对 ledger/audit 只读；受控 API/Worker 通过专用角色或 SECURITY DEFINER command function 写入；
- 已确认 ledger event 禁止 UPDATE/DELETE，错误以 REVERSAL 表达；
- RLS 是逻辑行隔离，文档统一移除“物理隔离”表述；
- `SECURITY DEFINER` 固定 owner/search_path 并撤销 PUBLIC EXECUTE，再按角色授权；
- 所有 tenant 子资源使用复合外键或可信父对象推导 tenant，禁止跨租户关联。

### 3.4 建议、决策、订单意图和真实成交混淆

用户回复“确认买入”只能证明接受建议，不能证明券商已经成交。MVP 不接券商时，真实账本必须来自用户二次确认的成交事实或导入数据。

修复决定：

```text
recommendation
    -> decision_action(ACCEPTED/IGNORED/DEFERRED)
       + lifecycle(RECORDED/RETRACTED/SUPERSEDED)
    -> optional order_intent(L4)
broker fill / user-confirmed fill / statement import
    -> trade_fill(DRAFT -> CONFIRMED/REJECTED/CANCELLED)
    -> ledger command（仅 CONFIRMED）
    -> immutable ledger event
```

- 盘中“确认建议”仅写 decision；
- 用户填写成交价、数量、费用、时间并再次确认后才记账；
- 盘后自然语言先解析成成交草稿，展示校验结果，不直接落账；
- L4 券商接入仍要求耐久审批、幂等回报和人工控制。

## 4. 重要设计问题

### 4.1 阶段边界

保留所有需求，但统一分级：

| Level | 范围 | 处理方式 |
|---|---|---|
| L0 | 租户、Auth、稳定 ID、账本、来源/时点、幂等、审计、RLS、Outbox | MVP 前置 Gate |
| L1 | A股、场内/场外基金、四时段、企业微信、2～3 用户 | 当前唯一交付范围 |
| L2 | 多账户、基金穿透、归因、行为诊断、提醒预算 | L1 稳定后增量表/投影 |
| L3 | 权利清晰的音视频/文档/微博等内容和证据链 | 单独媒体治理模块 |
| L4 | 港美股、债券、黄金、大宗、宏观周期、回测、DSL、券商意图 | 高级能力 |
| L5 | 多 Agent 对抗、Skill 自进化和复杂耐久自治 | 最后优先级、实验性 |

L4/L5 场景可继续在 PRD 全景图中展示，但每个节点必须显式标注 Level；另设只包含 L0/L1 的 MVP 闭环图。

### 4.2 多 Agent 局限性与降级决定

多 Agent 保留为长期探索需求，优先级调整到最后，原因如下：

1. 多个 Agent 并不等于多个独立认知来源；如果使用相同模型、Prompt 和数据，错误高度相关；
2. 辩论可能增加篇幅和信心，却不必然提升事实准确率或收益；
3. Token、延迟、工具调用和可观测成本近似随角色和轮次增长；
4. 角色 Prompt 容易制造拟人化权威感、确认偏误和“多数投票即正确”的错觉；
5. 上下文在 Agent 间复制会扩大隐私泄露、Prompt 注入和越权工具调用面；
6. 非确定性对话难以回放、归因和建立稳定 Golden set；
7. 多 Agent 不应承担仓位、费用、风控、账本或订单状态机计算；
8. 对 2～3 人 MVP，单 Agent + 确定性工具 + 反方检查清单通常更简单、便宜、可审计。

L5 准入条件：单 Agent 基线已稳定；离线评估证明净增益；成本/延迟预算可接受；每个结论有独立证据；工具最小权限；可回放；失败可退回单 Agent；禁止多数投票直接形成交易动作。

### 4.3 市场数据与基金估值

- `MarketObservation` 默认质量应为 `UNAVAILABLE`，时间使用 `default_factory`；
- Provider 必须从源记录读取 `as_of`，结合交易日历计算 FRESH/STALE；
- 非正数、缺字段、schema drift、超时和空数据 fail-closed；
- 基金估值必须接收持仓权重、对应行情和剩余资产基准，输出方法版本、覆盖率、上下界和披露日期；
- 没有足够持仓数据时返回 `UNAVAILABLE/ABSTAIN`，禁止固定比例伪估值；
- 黄金/铜/原油比价必须定义统一单位、归一化基期和解释边界，先留在 L4。

### 4.4 账本简化但更诚实的方案

MVP 使用“不可变投资组合事件账本 + 多腿事件 + 可重建投影”，不再无条件宣称会计意义上的双式借贷。每个事件按 event type 校验腿组合和经济效果；未来引入负债、融资、跨账户清算后，再扩展为正式 debit/credit account 模型。

必须补齐：SELL、CASH_OUT、费用/税、现金/红利再投资、冲正、负数校验、UTC 时间、持久幂等和数据库事务。事件/legs/outbox 同事务提交，投影可清空重建。

### 4.5 Migration 可执行性

- `profiles` 与 `auth.users` 使用一致且受约束的 user ID；纯 PostgreSQL 部署提供独立 identity adapter，而非直接依赖 `auth.uid()`；
- 为 `(tenant_id,id)` 建立稳定唯一键和复合外键；
- seed 使用确定 ID/唯一键，重复执行不增加 legs；
- 三个试点 tenant 都应有账户和最小 fixture，真正支持 A/B/C 隔离测试；
- report 补 `job_run_id`，alert fingerprint 建唯一窗口，Outbox 保存渠道 message ID/lease/error；
- migration 必须在临时 PostgreSQL/Supabase 环境分别验证“全新 001～最新版本”和“既有 001～006 升级到最新版本”；seed 必须重复执行无经济副作用。版本 migration 本身按迁移框架只执行一次，不以脚本任意重复执行作为目标。

## 8. 实际修复结果

### 8.1 需求与阶段

- 将唯一当前交付范围固定为 **L0 + L1**：A 股股票、场内 ETF/LOF、场外公募基金、2～3 个用户、企业微信、四时段闭环；
- 保留黄金、债券、港美股、大宗、回测、DSL、券商接入、媒体研究等详细场景，但统一放入 L2～L4 并在场景、全景图、需求表和追溯矩阵标注；
- 新增 L5，把多 Agent 和 Skill 自进化调到最后优先级，默认关闭，且任何前序能力都不依赖它；
- 修正盘后超时语义：`NO_RESPONSE` 不等于“无交易”；自然语言成交先生成草稿，用户校对后才可能入账；
- 修正基金 14:30 报告：保留固定报告会话，但不再假定所有产品申赎截止统一为 15:00；已过产品截止、披露覆盖不足或数据陈旧时必须弃权；
- 修正分红语义：除息日通知不直接改账，到账/份额确认并核对后才追加事实。

### 8.2 架构与选型

- 把 Hermes 从“系统中枢”降为可替换的企业微信/Agent 边缘 PoC，核心采用 FastAPI/Python 模块化单体、PostgreSQL、Worker、Outbox 和 Port/Adapter；
- 明确 `Hermes/WeCom -> scoped Domain API -> PostgreSQL`，Agent、前端和通道不得持有数据库高权限凭据；
- 恢复并重新评价 OpenClaw、LangGraph、OpenAI Agents SDK、CrewAI/AutoGen、Temporal/Restate/DBOS 等路线，给出各自触发条件，不再声称单一框架天然最优；
- 四时段固定流程先用 PostgreSQL 租约 + Outbox；只有长暂停、跨服务编排、恢复复杂度达到量化阈值后才引入耐久工作流框架。

### 8.3 数据库与安全

- 新增 `migrations/007_security_and_integrity_hardening.sql`，兼容已经执行旧 001～006 的环境；
- 增加 `trade_fills`，分离研究建议、用户决策、真实成交和账本事件；
- 把 decision 拆为 `decision_action` 与生命周期状态，修复原先一个 status 同时表达动作和历史状态的问题；
- 移除 active member 对所有表的 blanket CRUD；普通认证用户对金融事实、报告、工作流和审计保持只读，配置写权限按角色和表显式授权；
- 增加同租户组合外键、已确认账本/终态 fill/决策内容/审计 append-only 触发器、Outbox lease 与外部消息 ID、告警去重、绑定码原子消费字段；
- 三个试点 tenant 均有确定 ID 的账户和最小账本 fixture，避免 seed 重跑增加经济事实；
- 数据质量默认值统一 fail-closed 为 `UNAVAILABLE`。
- 取消回撤、单仓和股债金比例的通用默认值；投资政策先为 `DRAFT`，只有用户确认且完整校验后才可用于数量/再平衡候选；
- 新增按基金标的、销售渠道、生效区间和来源版本管理的截止规则，市场日历不再默认所有产品 15:00。

### 8.4 Python 原型与 Skill

- 企业微信 Adapter 改为显式收件人，拒绝空值和 `@all`；凭据缺失返回 `CONFIG_ERROR`，只有显式 `dry_run` 才模拟；异常只记录类别，避免 Corp Secret/access token 出现在日志或响应；
- 绑定码摘要必须注入服务端 secret，不再带源码默认密钥；
- 投资事件账本原型采用 frozen event/leg、tuple、UTC 时间，补齐负费用校验、SELL/超卖、CASH_OUT、独立 FEE/TAX 和只追加 REVERSAL；明确它不是会计级复式总账，也不是生产持久化仓库；
- 行情 observation 默认 `UNAVAILABLE`，时间使用 `default_factory`；基金估值改为显式持仓权重、成分收益、剩余资产基准、覆盖率和不确定区间，覆盖不足时弃权；

## 10. 尚未完成、不得误报为已上线的能力

1. 仓库仍没有完整 FastAPI Application Service、持久 Repository、Worker 租约执行器和 Outbox consumer；当前 Python 代码是领域/Adapter 原型。
2. 企业微信真实应用、回调签名、OAuth/绑定限速、渠道 message ID 对账和网络重试尚未在沙箱或生产环境 E2E。

4. Hermes、OpenClaw、LangGraph、Agents SDK 的对比目前是官方能力核对与架构判断，尚未完成同一 Golden set 的实测 PoC。
5. PostgreSQL 临时验证应固化为 CI 容器测试，并增加并发幂等、事务 kill/retry、备份恢复、RPO/RTO 和性能证据。
6. 多媒体内容接入还需逐来源确认转载、转写、存储、引用和模型训练权利；创作者观点必须与事实、预测及到期校准分开。
7. L5 多 Agent/Skill 实验继续保留，但除非相对单 Agent 基线在关键错误率、引用正确率、人工盲评上有预先定义的显著净增益，且成本、延迟与安全均达标，否则应长期关闭。
