## 一、 重构修改的优劣势全景评估

### 1. 好的地方（核心架构与工程质量的大幅提升）

| 维度 | 重构前 (v1.x) 存在的问题 | 重构后 (v2.0) 的优秀改进 |
| :--- | :--- | :--- |
| **账务严谨性** | `positions` 与 `portfolio` 为可变单表，修改不走原子事务，分红与成交会导致数据分叉、错账。 | **确立不可变账本（Immutable Ledger）**：引入 `ledger_events` 与 `ledger_legs` 作为唯一事实源，持仓和净值变为可重构投影（Projections），彻底杜绝金额与份额对账不平。 |
| **多租户安全** | 存在 P0 级隐患（如建议给 Agent 配置 `service_role`、`profiles.limit(1)` 越权取第一个用户）。 | **严格的多租户隔离边界**：数据库全表启用 RLS；后端统一从 JWT/渠道绑定解析 `tenant_id`；Agent 仅暴露 scoped 业务工具，零直接数据库写权限。 |
| **数据真实性与失败关闭** | 原方案在接口失败时硬编码固定原油、金价、PMI 数据，容易把假数据伪装成实时结论。 | **引入数据质量状态机**：明确定义 `FRESH / ESTIMATED / STALE / CONFLICT / UNAVAILABLE`，数据缺失时明确 `ABSTAIN`（弃权），保证“LLM 不拥有金融事实”。 |
| **测试实事求是** | 仓库中未实现代码却在文档中将 53 个测试全部标为 `PASS`，部分断言与函数参数脱节。 | **测试全部重置为 `NOT_RUN`**：建立了 L0–L4 演进分级与追溯矩阵（`08`），要求每个 `PASS` 必须附带真实的 Commit、环境、Migration 和报告证据。 |
| **渠道与自动化** | 自建 shell 拼接命令调用企业微信，存在注入漏洞。 | **规范化 Adapter 架构**：对接 Hermes 官方 WeCom 适配器 / 安全 SDK，支持一次性 Token 安全绑定与消息幂等去重。 |

### 2. 存在的问题与不足（为什么感觉“少了东西”）

1. **实操可执行性（Executability）下降，缺少开箱即用的脚手架**：
   - 原先的 `03.实战指南` 提供了大量直接复制即可运行的 Python 代码（如 `finance_tools.py`、`wecom_tools.py`、`db_tools.py`）以及具体的 `SKILL.md`；
   - 重构后的 `03` 变成了高度精炼的“架构交付步骤与规范”，开发者无法在 10 分钟内拉起一个可交互的本地 Demo，增加了上手门槛。
2. **生动的投研人机交互场景被过度概括**：
   - 之前详细规划的 **08:30 If-Then 操盘剧本（支撑/阻力/加减仓条件）、14:30 场外基金盘中估算净值申赎决策、15:30 盘后主动质询与 2 小时超时自动归档、周末知行合一行为体检** 等生动场景，在重构中被浓缩为抽象的 Schema 字段，丢失了直观的 Prompt 范例、输入输出卡片和对话体感。
3. **部分特色资产与宏观周期被降级，演进路径略显断层**：
   - 原先设计的“上海金 SGE / 黄金 ETF 避险中枢”、“原油/铜大宗商品晴雨表与金铜比”、“基钦库存周期 4 阶段与美林时钟”是平台极具吸引力的特色；
   - 重构为了收敛 MVP 边界，将它们全部划归到 L2–L4，但在文档中未详细给出“未来如何平滑扩展这些资产的数据模型与计算函数”，导致看起来像被直接删除了。
4. **数据库设计停留在 Markdown 表格，缺少可一键执行的 SQL DDL 脚本**：
   - `06` 详细列出了每个字段和约束，但没有提供标准、可直接导入 PostgreSQL / Supabase 的 `.sql` 脚本文件（包含 Schema 创建、RLS 策略定义、自动更新触发器等）。

### 一、 核心建议：不建议维护“两套完全平行的文档”，推荐采用“单一权威源 + 章节分层详述 + 外挂代码/SQL/Skill 资产”架构

#### 为什么不建议“两套平行体系（简述版 vs 详述版）”？
1. **“双重维护与文档漂移（Doc Drift）”陷阱**：一旦业务逻辑、表字段或 API 契约发生变动，同时维护两套文档极易出现“简述版改了、详述版忘了改”的冲突，重新引发前后端对账不齐与测试脱节问题。
2. **追溯与索引割裂**：需求追溯矩阵（`docs/08`）和自动化校验脚本（`validate_docs.ps1`）在多套文档下难以维护统一的稳定 ID。

#### 推荐方案：“单一基线、深度展开（规范 + 实战手册分工）”
保持 `docs/01` ~ `docs/08` 为唯一的权威体系，在文档内部划分好 **“规约（用于架构设计与追溯）”** 与 **“生动场景与实操（用于学习、理解与实战）”**，并把实际代码、SQL、Prompt SOP 分离到专门的项目目录中：
