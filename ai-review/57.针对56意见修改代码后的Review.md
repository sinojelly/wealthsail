\## Review 结论：方向正确，但现在不建议直接部署 NAS



我检查了提交 `2e0ee8d` 的实际源码、Migration 093、任务恢复逻辑、Docker 配置，以及你提供的测试记录。

\### 问题 1：`claim\_stale\_runs()` 使用了已经离开作用域的数据库连接



P0 · 确定的代码错误



文件：`backend/jobs/runner.py`，约第 125–151 行。



当前代码结构是：



```

async with system\_connection(pool) as conn:    result = await conn.execute(...)# 已离开 async with，连接已归还连接池try:    usage\_res = await reconcile\_stale\_calls(conn)    ...except Exception:    logger.exception(...)

```



`reconcile\_stale\_calls(conn)` 在连接管理器外执行。此时连接已经归还池中，asyncpg 通常会报告连接已释放，或者无法执行操作。



更糟的是，异常被捕获后仅写日志，因此不会阻止 Worker 启动，容易让人误以为恢复流程正常。



建议修法：



```

async with system\_connection(pool) as conn:    result = await conn.execute(...)try:    async with system\_connection(pool) as conn:        usage\_res = await reconcile\_stale\_calls(conn)    ...except Exception:    logger.exception(        "zombie ai usage call reconciliation failed"    )

```



将两项数据库操作分别放在有效连接作用域内，并让 AI 用量对账失败不影响正常 Job 租约恢复。



这是上线前必须修复的问题。



\### 问题 2：Migration 093 的 Worker 身份判断过宽



P0 · 权限边界风险



文件：`migrations/093\_fix\_ai\_usage\_overlap\_json\_and\_role.sql`。



当前判断是：



```

v\_is\_worker := (

&#x20;   current\_setting('role', true) = 'wealthsail\_worker'

&#x20;   OR SESSION\_USER = 'wealthsail\_worker'

&#x20;   OR pg\_has\_role(

&#x20;       SESSION\_USER,

&#x20;       'wealthsail\_worker',

&#x20;       'MEMBER'

&#x20;   )

);

```



问题出在最后一个 `OR`。



WealthSail 的 Worker 登录账户拥有切换到 `wealthsail\_worker` 的权限，但也可能主动降权切换为 `wealthsail\_api`，用来执行租户隔离操作。



即使当前角色已经切换为 `wealthsail\_api`，`SESSION\_USER` 仍然是 Worker 的登录账户，`pg\_has\_role(..., 'MEMBER')` 依然可能返回 true。



这会让某些本应执行租户鉴权的调用绕过检查。



建议只在确实以 Worker 运行角色执行时启用全局任务特权，并且验证实际登录角色有权承担该角色，而不是仅凭登录账户拥有成员资格就放行。



还应该保留普通 API 调用的严格用户、租户关联检查。



至少增加以下 PostgreSQL 真实权限测试：Worker 正常全局执行、Worker 降权到 API、普通 API 租户用户、跨租户调用、缺失 JWT、空 JWT 和非法 JWT。



这属于安全边界问题，不能依靠字符串匹配 SQL 的单元测试判断已经安全。



\## 二、其他需要修复的问题



\### 问题 3：僵尸任务恢复并没有真正实现“持续自动恢复”



P1 · 功能不完整



目前 `reconcile\_stale\_calls()` 挂在 `claim\_stale\_runs()` 下，而实际 Worker 只在启动阶段调用一次 `claim\_stale\_runs()`。



独立的周期恢复循环调用的是 `run\_recoverable\_jobs()`，没有调用新增的 AI 推理对账。



所以即便修复问题 1，也只能做到Worker 启动时恢复，无法保证当天新发生的异常及时恢复。



建议把 AI 用量对账独立为轻量周期任务，每隔几分钟扫描一次，并满足以下条件：



\- 仅对父任务已经结束且经过短暂宽限期的调用执行恢复。

\- 每批限制处理数量，避免对整个历史表执行无边界更新。

\- 保留原始错误类别和恢复记录，保证重复执行幂等。

\- 恢复不触发 Codex、业务任务重跑或额外额度采样。



另外，`aggregate\_task()` 当前只把任务聚合状态显示成 `UNCERTAIN`，并没有同步修改 `calls` 列表里的状态。



这可能造成同一页面中任务显示“结果不确定”，展开后的单次调用仍显示“执行中”。



建议统一接口输出语义，而不是只修正任务级状态。



\### 问题 4：失败重试范围太宽



P1 · 可靠性优化



文件：`backend/ai\_usage/tracker.py`。



现在所有 `finish\_call` 和 `finish\_task` 异常都会再重试一次，包括：



\- `22P02`：无效 JSON 等输入数据错误。

\- `42501`：权限不足。

\- 代码缺陷导致的其他非临时异常。



这些错误并不会因为等 0.5 秒就自行恢复。



建议仅重试明确的临时错误，例如数据库连接短暂断开、死锁或可恢复的事务冲突。权限错误、数据格式错误和确定性程序错误应该直接失败并记录诊断。



同时保留总耗时预算，避免重试让一次研究收尾延迟太久。



\### 问题 5：`\_safe\_failure\_reason()` 不是真正的安全脱敏



P1 · 日志安全与准确性



文件：`backend/jobs/daily\_research.py`。



当前实现：



```

msg = str(exc).strip().replace("\\n", " ")return msg\[:120] if msg else type(exc).\_\_name\_\_

```



截取前 120 个字符并不等于脱敏。



未来异常消息可能包含外部 URL、请求参数、模型输出片段或其他不应该进入普通 Docker 日志的信息。



我更建议使用异常类别 + 固定错误代码 + 阶段的方式，例如：



```

daily\_research\_failed

stage=REPORT\_VALIDATION

error\_class=ValueError

reason\_code=UNKNOWN\_SOURCE\_REFERENCE

```



对项目自己定义的可信校验异常，可以维护固定错误代码；对其他外部异常，仅输出类型和通用类别。



此外，当前通过 `checks is not None` 来推断 `VALIDATION\_FAILED` 或 `SOURCE\_CHECK\_FAILED` 也不够准确。如果错误发生在模型请求阶段，却会被归类成来源校验失败。



应该在每个阶段显式设置 `current\_stage`，而不是根据一个变量是否为空推断出错位置。



\## 三、NAS 审计日志配置还没有闭环



目前提交里新增：



```

DAILY\_RESEARCH\_AUDIT\_DIR=/app/data/research-audit

```



但我检查了 `docker-compose.yml` 和 `external-access/compose.wealthsail.storage.yaml`：



Worker 没有挂载 `/app/data/research-audit` 的持久化目录。



这意味着即使在 NAS 的真实 `worker.env` 中配置了这个变量，诊断文件仍可能只写到容器自己的可写层里，容器重新创建后就无法可靠保留。



建议利用现有的 `NAS\_VOLUME\_WEALTH\_SAIL` 数据根目录，专门增加研究审计子目录，设置合适的 UID 10001 权限和保留期限，并且只挂载给 Worker。



不要把诊断文件放到前端静态目录或暴露给公网。



还有一点：当前 `write\_research\_audit()` 保存了完整的公开研究模型输出与来源核验信息。这对排查很有用，但应该增加文件轮转、占用空间限制和访问控制，避免长期堆积。
