### 一、为什么加了“负面新闻分析”后几乎必败？（两大死循环）

之前几次修复之所以治标不治本，是因为一直在“保持严苛的全量拦截规则不变”的前提下修修补补，导致系统在两个错误之间反复横跳：

1. **死循环 A：跑全量核查 $\rightarrow$ 触发 `TimeoutError`（前天 NAS 上的失败）**
负面新闻分析要求对 **10 个行业 × 5 类风险 = 50 条查询** 做反方核查。如果让 Codex 老老实实把 50 条搜索和网页阅读全部跑完，多轮累计输入就会飙到 116 万 Token 以上，加上生成 2.2 万 Token 的报告，直接撞上 900 秒硬超时。


2. **死循环 B：省流跳过核查 $\rightarrow$ 触发 `ResearchValidationError`（昨天 Windows 上的失败）**
为了不超时，上一轮优化告诉模型“50 条查询是软预算、优先做高价值核查、避免重复搜索”。模型听话了，但后端的 Python 验收器（`value_directions.py` + `research_assurance.py`）**根本不认“软预算”**——只要有任何一个方向关联的行业没把 5 类负面核查全部做完并拿到完美回执，就直接抛 `ResearchValidationError` 炸掉整份报告！

### 二、穿透本次 `d7810690` 失败现场：3 个致命卡点

从 `83.投资研究失败.md` 导出的审计结果中，可以看到这次在 Windows 上跑出的 `d7810690-ef13-44ad-8591-d3699f3f589a` 实际上**模型已经成功跑完并给出了合理的投研结论**，是被后端的 3 个硬伤联手“误杀”的：

#### 1. 致命伤一：CLI 事件解析器因 `UNATTRIBUTED_EVENT` 直接清空了所有搜索凭证

看 PowerShell 导出的执行回执数据：

* `turnCompleted : True`（模型正常跑完了）


* `proofBarrier : UNATTRIBUTED_EVENT`（遇到了一条未归属/未识别的 CLI JSONL 事件）


* `已记录的精确搜索回执数： 0`（所有 `webToolCalls` / `searchQueries` 统计全空）



**原因**：`backend/integrations/research_execution.py` 对 Codex CLI 的 JSONL 事件流做了极其脆弱的“白名单强校验”。只要 Codex CLI 输出了一条不在预期结构内的事件（比如新版本的内部思考事件、心跳或工具包装事件），解析器就立起 `proofBarrier = "UNATTRIBUTED_EVENT"`，并**把整次运行的搜索执行凭证全部作废清零**。
一旦搜索回执清零，所有 `NOT_FOUND`（未发现负面新闻）的核查项就全部失去凭证——这意味着**哪怕某个行业干干净净没有任何负面新闻，也永远不可能通过核查**！

#### 2. 致命伤二：`WATCH`（观察）方向也被强行要求 100% 跑满 5 类负面核查

看本次报错的第 0 个方向 `robotics_mobility`（机器人）：

* 模型已经在 `ROBOT` 行业查出了 2 项负面风险：`FINANCING_COOLING = FOUND`（融资降温）、`LAYOFFS_CLOSURES = FOUND`（裁员或关停）。


* 正因为查出了资金约束风险，模型非常合理地将该方向的信号设为了 **`signal: WATCH`（观察，而非买入）**，标题定为《机器人：控制进展与资金约束并看》，并把其余 3 项（砍单、产能过剩、生产延迟）标为 `UNVERIFIED`。


* **荒谬的地方来了**：既然已经查出 2 个负面风险并降级为 `WATCH`（不建议买入）了，本来就不需要再浪费额度去把剩下 3 个负面项搜到底；但 `backend/macro/value_directions.py`（第 437–444 行）不管你是 `BUY` 还是 `WATCH`，只要 `(review_ids | plan_sectors) - audit_completed_scopes` 非空，一刀切直接 `raise ResearchValidationError("DIRECTION_INDUSTRY_EXECUTION_UNVERIFIED")`！



#### 3. 致命伤三：“单点不合规”直接连坐销毁“整份有效报告”

虽然 `backend/macro/research_batch.py` 里写了 `FORMAL`（正式）、`OBSERVATION_ONLY`（仅观察）、`PENDING_REVIEW`（待核实）的分层逻辑，但 `daily_research.py` 在调 `validate_daily_research_report()` 时，遇到单个方向核查未完成依然是**直接抛异常中断任务（标为 `FAILED`）**，而不是把该方向自动降级为 `OBSERVATION_ONLY` / `PENDING_REVIEW` 后正常保存报告。

#### 4. 附带隐患：Windows 下 `exit_confirmed=False` 导致每次跑完都死锁

日志里出现了 `exit_confirmed=False dispatch_started=True state=UNKNOWN reason=COMPLETED`。
这是因为 `backend/integrations/research_process.py` 在 Windows 下清理进程时硬编码返回了 `return process.returncode is not None, False`（第二个 `False` 代表“未确认后代进程全部退出”）。导致在 Windows 上**哪怕模型正常跑完（`COMPLETED`），系统也认为进程未确认退出，拒绝释放数据库的 `daily_research_model_guards` 互斥锁**，下一次再点研究就会一直卡住等待。

### 三、如何彻底摆脱“一直失败”？（4 步根治改造方案）

附件里另一个 AI 的诊断脚本非常精准地抓出了病灶，但它建议“继续保持严格阻断、只修回执解析”是不够的——**如果不打破“50 条全量精确匹配 + 单项不过整单报错”的枷锁，哪怕修好了一个 `UNATTRIBUTED_EVENT`，下次只要模型改写了一个搜索词，或者少搜了一个子项，研究依然会失败。**

要彻底让每日研究稳定达到 **95%+ 的一次成功率**，同时**不牺牲真正的买入风控**，只需要修改以下 4 处核心逻辑：

#### 1. 【最关键】将“抛异常炸毁整单”改为“未完备方向自动降级为观察（Auto-Downgrade）”

* **修改位置**：`backend/macro/value_directions.py`、`backend/macro/research_assurance.py`、`backend/jobs/daily_research.py`。


* **改造规则**：
1. **`WATCH` / `AVOID` 方向豁免全量完备性要求**：如果模型给出的方向本身就是 `WATCH`（观察）或 `AVOID`（回避），或者已经发现了至少 1 项有效负面风险（`FOUND`），说明风控目的已达成，**直接放行**，不再要求其余 `UNVERIFIED` 子项必须搜完。


2. **拟推荐买入（`BUY` / `POSITIVE`）方向若核查未完备，自动降级而不报错**：如果某个正式方向未完成 5 类负面核查（不在 `audit_completed_scopes` 中），**严禁 `raise ResearchValidationError` 炸毁整份报告**！而是由服务器确定性地将其信号强制降级为 `WATCH`，并归入 `OBSERVATION_ONLY` / `PENDING_REVIEW`（附上原因标签：`行业反方核查未完备，已自动降级为只读观察，不生成买入计划`）。




* **效果**：既 100% 守住了“未经完整负面核查绝不给出正式买入计划”的风控底线，又彻底消灭了 `DIRECTION_INDUSTRY_EXECUTION_UNVERIFIED` 导致的整单失败！



#### 2. 修复 `research_execution.py`：移除 `UNATTRIBUTED_EVENT` 一票否决，支持语义/关键词匹配回执

* **修改位置**：`backend/integrations/research_execution.py`。


* **改造规则**：
1. **未知事件宽容处理**：解析 Codex JSONL 事件流时，遇到未识别的事件类型只记录诊断计数，**不再设置阻断性的 `proofBarrier = "UNATTRIBUTED_EVENT"**`，绝不因为一条无关事件就把已执行的搜索回执全部清零。


2. **搜索回执支持归一化/关键词匹配**：Codex Agent 在调用搜索工具时经常微调查询词。核验 `NOT_FOUND` 的搜索回执时，除了精确匹配 `query` 字符串外，只要实际执行的 `searchQueries` 中包含该任务的**行业核心词 + 风险类别关键词**，即认可该项搜索已执行。



#### 3. 缩减负面核查范围：只对“拟买入/有击球区基金”的重点行业强制要求 5 类核查

* **修改位置**：`backend/macro/daily_research.py` / `model_prompt.py` / `daily_sources.py`。


* **改造规则**：不要让模型在一次会话里去硬啃 10 个行业 × 5 类 = 50 条搜索。在 Prompt 和合同中明确：**仅对当期准备给出正式投资计划（或存在技术面候选基金）的 Top 2~3 个重点行业（最多 10~15 条查询）执行完整五类反方核查**；其余仅做宏观/主题观察的行业标为 `WATCH` 即可。这样单次耗时能直接稳定压在 5~8 分钟以内。



#### 4. 修复 Windows 下的进程树回收与 `exit_confirmed` 解锁逻辑

* **修改位置**：`backend/integrations/research_process.py`。


* **改造规则**：在 Windows 环境（`os.name == "nt"`）下，使用 `taskkill /F /T /PID <pid>` 清理子进程树（或检查以该 PID 为 `ParentProcessId` 的子进程已不存在）；当主进程已退出（`process.returncode is not None`）且无残留子进程时，返回 `(True, True)`（即 `descendants_confirmed = True`），让 Windows 正常结束或超时清理后都能拿到 `exit_confirmed = True` 并自动释放数据库模型锁。
