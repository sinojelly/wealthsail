\## 一、从截图看，已经发现两个异常



这次任务不是简单的“Codex 推理慢”，而是 业务任务状态与 AI 推理状态没有正常闭环。



任务 ID



`194eafbb`



任务名称



基金机会研究（自动）



启动时间



2026-10-29 08:31:55



业务结束时间



2026-10-29 08:36:24

业务：失败

业务从开始到失败约经过 4 分 29 秒。但内部 Codex 推理记录仍是 `RUNNING`，而且显示“尚未结束”。



这说明：



1\. 业务任务已经结束，但 AI 调用记录没有完成终态更新。 不能根据这个 `RUNNING` 就判断 Codex 现在还在持续推理。

2\. 推理前后额度都未采集、Token 未知，可能是采样超时、模型调用被取消、进程异常退出，或收尾更新失败；仅凭页面还无法确定。

3\. 要优先检查是否命中模型执行超时、Worker 被重启或杀死，以及业务异常后推理记录是否被遗留。



我已经查到 WealthSail 的 AI 用量设计确实允许一种情况：进程被强制终止后，推理记录可能永久停留在 `RUNNING`，目前不会自动修复终态。 所以这次需要分别追查真实的业务失败原因和状态遗留原因。



\## 二、我查到的代码关键点



当前 WealthSail 源码中，推理记录与业务记录是分别写数据库的：



start\_task → start\_call



创建任务、推理记录，状态 RUNNING



推理前额度采集 → Codex 执行 → 推理后额度采集



finish\_call



写入推理终态、结束时间、Token



finish\_task



写入业务终态和结束时间



这里有一个很值得怀疑的地方：



`backend/ai\_usage/tracker.py` 的 `Task.write()` 对数据库写入设置了 5 秒超时，但遇到异常只记录：



```

ai\_usage\_write\_failed event=finish\_call error\_class=...

```



然后继续执行，不会因为推理遥测写入失败而直接中断业务。



因此，如果推理的 `finish\_call` 写数据库失败，但随后的 `finish\_task` 写入成功，就会出现你截图里的状态。



这是我目前优先排查的方向。 而且业务结束时间已经写入成功，说明不能简单地把整个问题归因于 Worker 被强杀。



另外，当前源码每日研究模型执行超时的默认值为 900 秒，并不是 4 分多钟。实际 NAS 可以通过下面的命令核对是否覆盖了这个配置。

\## 定位结果：已经找到两个明确的故障点



这次提供的 NAS 日志非常关键。结合数据库记录和 WealthSail 源码，现在可以确认：Codex 请求正常返回，但推理记录写库失败；随后研究报告的业务处理又出现了 `ValueError`。



Codex 模型请求



\&#x20;HTTP 200



08:36:01 返回，未达到配置的 900 秒超时



AI 推理记录入库



已确认失败



08:36:13 — `InvalidTextRepresentationError`



每日研究业务



已确认失败



08:36:24 — `ValueError`



Docker 容器



正常运行



Worker、Runner、API 均未发生重启或 OOM



因此可以排除这次故障的几个主要疑点：不是 Codex 一直运行到现在，不是模型执行达到 900 秒超时，也没有证据表明容器被杀死。



“推理一直执行中”是数据库状态遗留，不是真正的运行状态。



而 `ValueError` 是另一条故障线，需要继续追到报告校验环节。下一步不应再围绕网络连接或 Docker 重启反复排查。

\## 二、再抓两项信息，就能进一步确定根因



\### 1. 查 PostgreSQL 的原始错误类别



`InvalidTextRepresentationError` 对应 PostgreSQL 的数据格式转换错误（SQLSTATE `22P02`）。



可能发生在 `finish\_call` 的 JSONB 更新或随后调用的 `research.mark\_ai\_usage\_overlap()` 数据库函数中。现在应用日志隐藏了异常原文，还不能断言具体是哪个字段。



运行：



```

sudo docker logs postgres \\

&#x20; --since '2026-10-29T00:36:10Z' \\

&#x20; --until '2026-10-29T00:36:17Z' 2>\&1 \\

&#x20; | grep -Ei 'ERROR:|invalid input syntax|CONTEXT:|SQLSTATE' \\

&#x20; | head -n 30

```



如果能看到类似 `invalid input syntax for type uuid` 或 `invalid input syntax for type json`，定位范围就能明显缩小。发送结果前请检查并遮盖可能出现的参数值。



如果没有输出，也不代表 PostgreSQL 没有报错，只说明当前数据库日志不一定记录了对应的详细信息。



\### 2. 查询模型报告有没有保存本地校验诊断



源码支持 `DAILY\_RESEARCH\_AUDIT\_DIR`，如果在 NAS 上启用了该选项，模型原始返回后的校验失败原因可能已经保存在内部审计 JSON 中。

\## 三、源码后续需要修复的地方



基于当前证据，我建议分两个独立问题修改：



P0：修复 AI 用量落库错误



检查 `backend/ai\_usage/repository.py` 的 `finish\_call` SQL、数据库函数 `research.mark\_ai\_usage\_overlap()`，以及 PostgreSQL 18 实际部署环境。补充相同运行角色、真实额度快照和全局研究任务的回归测试，并在失败时记录安全的 SQLSTATE 和阶段信息。



P0：修复研究报告校验失败



根据审计里的具体 `ValueError` 判断是模型违反输出约束、来源引用不一致，还是校验代码存在问题。保留证据真实性要求，不要直接放宽所有校验来让报告通过。



P1：补充推理异常终态恢复



当业务已经结束、推理记录仍为 `RUNNING` 时，通过对账识别异常并提供安全恢复机制。无法证实的结果标记为 `UNCERTAIN`，不能虚构 Token，也不能自动认定为成功。



\### 目前的结论



这次已经不是一个笼统的“NAS Docker 推理卡住”问题，而是两个可明确追查的缺陷：



AI 调用遥测写库失败 + 模型返回后的研究处理失败。



先把上面两个检查的结果发过来，尤其是 `ValueError` 的具体内容和 PostgreSQL 转换错误信息。这样就能针对真实根因制定修复方案，避免盲目调整模型推理强度、超时时间或 Docker 配置。

2026-10-29 08:36:13.415 CST \[1327] ERROR:  invalid input syntax for type json

2026-10-29 08:36:13.415 CST \[1327] CONTEXT:  JSON data, line 1:



Research audit: DISABLED

现在可以进一步锁定根因了。结合 PostgreSQL 错误和 WealthSail 源码，AI 用量记录的问题很可能是数据库函数对空 JWT 信息进行了不安全的 JSON 转换。



\## 一、AI 推理一直显示 RUNNING 的原因



高概率定位到具体代码



在 `migrations/091\_ai\_usage.sql` 中，存在这段逻辑：



```

IF current\_setting('role',true)

&#x20;  IS DISTINCT FROM 'wealthsail\_worker'

&#x20;  AND NOT EXISTS (

&#x20;      SELECT 1

&#x20;      FROM research.ai\_usage\_calls c

&#x20;      JOIN research.ai\_usage\_tasks t

&#x20;        ON t.id = c.task\_id

&#x20;      WHERE c.id = p\_call

&#x20;        AND t.user\_id = auth.uid()

&#x20;        AND t.tenant\_id::text =

&#x20;          current\_setting('request.jwt.claims',true)::jsonb

&#x20;            ->>'tenant\_id'

&#x20;  )

THEN

&#x20;   RAISE EXCEPTION ...

END IF;

```



问题就在：



```

current\_setting('request.jwt.claims',true)::jsonb

```



每日自动研究属于全局后台任务，不具有普通用户请求的 JWT 上下文。



如果 `request.jwt.claims` 是空字符串 `''`，PostgreSQL 会抛出：



```

ERROR: invalid input syntax for type json

CONTEXT: JSON data, line 1:

```



与你提供的错误高度吻合。



实际调用路径是：



Codex 研究完成，HTTP 200



前后额度快照读取成功



finish\_call 数据库事务失败



整个事务回滚，推理记录停留 RUNNING



`finish\_call` 先更新 JSONB，再调用 `research.mark\_ai\_usage\_overlap()`。Python 侧通过 `json.dumps()` 构造合法 JSON，因此数据库函数里的直接强制转换是更可疑的来源，但还需要通过回归测试最终确认。



\### 修复建议



不能仅仅把数据库报错吞掉。应该：



1\. 将 Worker 角色判断和普通用户的权限验证拆成明确的条件分支，不依赖 SQL 的 `AND` 表达式短路。

2\. 将空字符串 JWT 转换为 NULL 后再解析，并确保缺少认证信息的普通用户仍被拒绝。

3\. 在 PostgreSQL 18 测试 Worker 无 JWT、JWT 为空字符串、API 正常租户请求及跨租户拒绝场景。

4\. 新增数据库迁移，通过 `CREATE OR REPLACE FUNCTION` 修复，保留现有 SECURITY DEFINER、权限边界及并发标记机制。



不要直接修改生产表里的 `RUNNING` 状态来掩盖这个问题。



\## 二、业务失败的 ValueError



`Research audit: DISABLED` 说明这次没有开启模型研究结果的本地校验诊断。



所以目前只能确定：



\- Codex 执行成功返回。

\- 后续研究业务发生 `ValueError`。

\- 研究结果没有成功成为有效报告。

\- 具体违反哪一项校验规则仍然未知。



从代码看，`validate\_report()` 会检查来源引用、发布时间、事件日期、投资方向、基金计划、能源数据等。任何关键规则不满足，都可能导致整份报告失败。



这不一定代表模型能力不足，也不应该直接通过降低校验标准解决。



下一版应增加结构化校验诊断，例如失败阶段、错误代码、规则名称及脱敏详情。这样以后无需保存完整原始模型输出，也能快速知道报告为什么失败。
