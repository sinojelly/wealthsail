## 一、 `f993320` 的核心改进与亮点

### 1. 严格清晰的阶段分层治理 (L0–L5 Phased Scope)
- **交付边界清晰化**：明确 **L0（可信底座）+ L1（核心 MVP）** 是当前唯一的交付承诺（A 股股票 + 场内外公募基金、2~3 个试点用户、企业微信自建应用、四时段闭环）。
- **长期愿景不等于 MVP 承诺**：将黄金、大宗商品、宏观库存周期、Backtrader 回测、策略 DSL 准确归入 **L4**；将“多 Agent 红蓝对抗”和“Skill 自进化”归入 **L5（实验性自治，最后优先级，默认关闭）**，并在全景图和每个场景中打上了显式 `[Level]` 标签。

### 2. 决策与成交事实严格解耦 (Decision vs Trade Fill vs Ledger Event)
- **纠正关键金融事实漏洞**：彻底纠正了“用户在微信点确认买入就直接入账成交”的虚假假设。
- **建立了四阶段不可逆生命周期状态机**：
  $$\text{AI建议 (Recommendation)} \longrightarrow \text{用户采纳决策 (Decision: ACCEPTED)} \longrightarrow \text{成交草稿 (TradeFill: DRAFT)} \longrightarrow \text{二次确认/券商回报确认 (Confirmed Fill)} \longrightarrow \text{不可变账本追加 (LedgerEvent)}$$
- 盘后自然语言回复先解析为草稿并由用户校对；超时 2 小时归档为 `NO_RESPONSE`，明确不推断为“今日无交易”。

### 3. 安全凭据与 RLS 深度硬化
- **消除高权限凭据泄露风险**：彻底切断 Hermes / Agent 对 `SUPABASE_SERVICE_ROLE_KEY` 的依赖，明确架构为 `Hermes -> scoped Domain API -> PostgreSQL`，Agent 仅持有限定作用域的 API Token。
- **重构 RLS 授权模型**：移除了原先对所有 active member 开放 blanket UPDATE/DELETE 的漏洞；普通用户对账本、报告、工作流和审计全表保持只读，写入仅允许通过受控后端 API 执行。
- **租户数据完整性防护**：在 [migrations/007_security_and_integrity_hardening.sql](file:///d:/develop/gitee/WealthSail/migrations/007_security_and_integrity_hardening.sql) 中补充了 **55 个同租户复合外键**（`FOREIGN KEY (tenant_id, account_id)`）和 append-only 防篡改触发器，从数据库底层杜绝跨租户关联漏洞。
- **企业微信通道加固**：收件人强制必填，严禁 `@all` 广播；移除假模拟成功；绑定码升级为高熵随机码（如 `WS-8K4P-9Q2M`）、服务端密钥摘要、15 分钟失效、原子单次消费与支持即时撤销。

## 二、 发现的潜在问题与边界风险（需在后续迭代注意）

经过对 `f993320` 提交代码的逐行审查，发现了以下 **4 个潜在边缘情况或生产化鸿沟**，建议在后续进入应用层实现时予以完善：

### 1. 内存原型与持久化数据库之间的工程差距
- **现状**：[modules/ledger/service.py](file:///d:/develop/gitee/WealthSail/modules/ledger/service.py) 和 [adapters/messaging/wecom_adapter.py](file:///d:/develop/gitee/WealthSail/adapters/messaging/wecom_adapter.py) 目前是**内存领域原型（In-Memory Prototype）**，幂等键保存在内存 `set` 中。
- **风险**：进程一旦重启，内存幂等键即清空，无法提供跨进程或崩溃后的幂等保障。
- **改进建议**：下一步应编写真正的 `PostgresLedgerRepository`，把幂等键校验交由数据库 `UNIQUE (tenant_id, idempotency_key)` 唯一约束和事务来保证。

### 2. `rebuild_projection()` 冲正处理的算法扩展性
- **现状**：在 [modules/ledger/service.py: L599-L607](file:///d:/develop/gitee/WealthSail/modules/ledger/service.py#L599-L607) 中，重建持仓投影时，是通过集合过滤跳过被冲正的事件（`if event.event_type is EventType.REVERSAL or event.id in reversed_event_ids: continue`）。
- **分析**：在原型阶段仅冲正最新单条事件时，这种过滤跳过逻辑是成立的；但如果未来演进到多事件历史调整或部分冲正，跳过原事件会导致历史依赖链断裂。
- **改进建议**：在生产级 SQL 投影重建中，建议按时序直接累加反向 Leg（Inverse Legs，即冲正分录直接作为负值参与求和），保持纯粹的事件累加数学模型。

### 3. 企业微信 Access Token 缺少本地 TTL 缓存
- **现状**：[adapters/messaging/wecom_adapter.py: L40-L65](file:///d:/develop/gitee/WealthSail/adapters/messaging/wecom_adapter.py#L40-L65) 的 `get_access_token()` 每次调用都会直接向企业微信发送 HTTP 请求获取新 Token。
- **风险**：企业微信的 `gettoken` 接口有每日调用频次限制，且 Token 本身有效期为 7200 秒。高频调用会导致微信接口报错（45009 频率超限）。
- **改进建议**：在生产 Adapter 中增加基于时间戳的内存或 Redis 缓存（如缓存 7000 秒，过期前自动复用）。

### 4. 完整的 Application API 与 Worker 编排尚未落地
- **现状**：当前仓库具备了完整的领域模型原型、数据库迁移（001~007）、SOP 技能库、文档和测试，但尚未实现 FastAPI Controller 和独立定时 Worker 进程。
- **说明**：文档在 [docs/03.WealthSail-MVP快速构建与实战指南.md](file:///d:/develop/gitee/WealthSail/docs/03.WealthSail-MVP快速构建与实战指南.md) 中已诚实标注当前状态为 `v2.1.0-draft / Review Required`，未夸大上线状态，符合规范要求。
