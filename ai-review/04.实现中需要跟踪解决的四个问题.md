## 2. Tool Loop 修复设计

### 2.1 原问题

`ab279f4` 的方向正确，但示例不足以成为实现契约：

1. 一次模型响应可能包含多个 tool call，完整 assistant message 只能追加一次；逐个重复追加会破坏对话协议。
2. 工具参数修复、终态结构修复、模型重试和总轮次不是同一个预算，必须分别统计。
3. 未明确未知工具、工具异常、输出过大、不可重试 Provider 错误和总 deadline 的终态。
4. tenant/user/correlation 不能从模型参数获得，必须由可信调用上下文注入。
5. 不能用自由文本错误冒充正常投资结论；调用方需要稳定、可观测的类型化状态。

### 2.2 已实施

- 新增 [modules/agent/tool_loop.py](../modules/agent/tool_loop.py)，提供 Provider-neutral、有界、同步的 Loop 原型。
- 工具参数和终态输出使用 Pydantic 模型校验；工具只来自显式 allowlist。
- 独立预算覆盖模型调用、工具调用、schema repair、Provider retry、总 deadline、模型响应和工具输出字节数。
- 可信 `ToolContext` 由调用方注入，不允许模型覆盖 tenant/user/correlation。
- 终态区分 `SUCCESS`、`DATA_UNAVAILABLE`、`MODEL_UNAVAILABLE`、`TOOL_ERROR`、`SCHEMA_INVALID`、`BUDGET_EXCEEDED`、`DEADLINE_EXCEEDED` 和 `ABSTAIN`；确定性工具只能通过受限 `ToolAbort` 返回数据不足/弃权，不能伪造其他故障类别。
- 新增 [tests/unit/test_tool_loop.py](../tests/unit/test_tool_loop.py)，覆盖多 tool call、schema repair 上限、非法参数、未知工具 fail-closed、可重试模型错误上限、retry backoff 不得越过总 deadline、超大模型/工具响应熔断，以及数据不足类别不被误写。

### 2.3 仍待实现

- 接入真实模型 Provider adapter，并记录 model/provider/prompt/schema/tool 版本和 token/cost。
- 增加工具抛错、工具输出过大、不可重试错误和终态 `ABSTAIN` 自动化测试，并补充工具执行本身超过 deadline 的可中断策略。
- 为只读工具与未来副作用工具划分不同权限；MVP 模型不得直接写决策、成交或账本。
- 通过 eval/canary 证明 fallback 模型满足同一 contract 后，才允许启用切换。

## 3. 人机协同与企业微信回调修复设计

### 3.1 正确对象关系

```mermaid
flowchart LR
    R["报告 / 建议"] --> I["interaction_requests: OPEN"]
    I --> O["Outbox 卡片"]
    O --> C["可信回调验证"]
    C -->|"ACCEPTED / IGNORED / DEFERRED"| D["追加 decisions"]
    D -->|"仅在独立成交确认后"| F["trade_fills: CONFIRMED"]
    F --> L["追加 ledger event / legs"]
```

等待用户响应不是一个 decision。`reporting.decisions` 只追加已经发生的用户选择；`ACCEPTED` 只是认知决策，不等于下单或成交。

### 3.2 已实施

- [migrations/004_market_and_research.sql](../migrations/004_market_and_research.sql) 为 fresh install 新增 `workflow.interaction_requests`。
- [migrations/007_security_and_integrity_hardening.sql](../migrations/007_security_and_integrity_hardening.sql) 为已有 004–006 基线提供兼容升级，并加入：
  - 同租户复合外键；
  - RLS/最小 GRANT；
  - `OPEN -> CONSUMED/EXPIRED/CANCELLED` 单向状态机；
  - 终态、身份、绑定、允许动作、token 摘要和业务引用不可篡改；
  - tenant 幂等键和 token 摘要唯一约束。
- PRD、架构、MVP 指南、数据设计和安全设计已统一使用该状态模型。
- 测试规范新增 `WEC-CBK-*` 与 `WF-HITL-*`，覆盖签名、重放、过期、动作篡改、跨租户、并发消费、事务失败和崩溃恢复。

### 3.3 回调实现的强制顺序

1. 验证企业微信签名和允许的时间窗。
2. 验证 timestamp/nonce/message ID 未重放。
3. 解析并验证 active `channel_binding`。
4. 以带密钥摘要查询 action token，验证有效期和 `OPEN` 状态。
5. 从绑定和请求记录推导 tenant/user；忽略客户端提交的身份字段。
6. 验证动作属于 `allowed_actions` 且 payload schema version 受支持。
7. 在一个事务中条件消费请求并追加 decision；重复调用返回相同业务结果。
8. 只有后续独立成交回报或用户二次确认，才允许创建/确认 fill 并写账本。

### 3.4 仍待实现

- FastAPI callback controller、签名验证 adapter、nonce/message ID 存储和安全审计。
- Domain command 的事务实现及并发条件更新测试。
- 真实企业微信回调契约测试、重放测试和故障注入测试。
- 回调 token 轮换、密钥轮换兼容窗口和失权后待请求批量取消。

## 5. 多 Agent 的局限与优先级

多 Agent 继续保留需求，但置于 L5 最后优先级并由 feature flag 默认关闭，原因包括：

- 多角色共享相同模型、来源或检索结果时，投票不是独立证据，可能共同放大同一错误。
- Agent 数量增加会扩大 Prompt 注入面、tenant context 传播、敏感数据复制、工具越权和审计链断裂风险。
- 编排带来额外 token、延迟、超时、循环、部分失败和不可复现性，未必带来相称投资收益。
- “看多/看空角色扮演”容易制造叙事丰富度，不等于预测准确率或风险调整收益改善。
- 在没有单 Agent 基线、离线评测、成本上限和可回退机制前，不应进入 MVP 关键路径。

进入实验的最低条件：单 Agent 基线稳定；角色有独立最小工具集；消息视为不可信输入；共享显式 tenant context；限制深度/token/时间；端到端 trace 可复现；在盲测中相对单 Agent 对引用正确率、弃权准确率或决策质量有显著净提升。任何越权、预算失控或不可复现结论立即关闭并回退。
