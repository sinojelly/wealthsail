\### 1. P0：僵尸调用对账存在覆盖正常推理结果的竞态风险



文件：`backend/ai\_usage/repository.py`，`reconcile\_stale\_calls()`，约第 145–178 行。



目前逻辑：



```

WITH stale AS (

&#x20;   SELECT c.id, t.finished\_at

&#x20;   FROM research.ai\_usage\_calls c

&#x20;   JOIN research.ai\_usage\_tasks t

&#x20;     ON t.id = c.task\_id

&#x20;   WHERE c.status = 'RUNNING'

&#x20;     AND ...

&#x20;   LIMIT $1

)

UPDATE research.ai\_usage\_calls target

SET status = 'UNCERTAIN',

&#x20;   finished\_at = COALESCE(

&#x20;       stale.finished\_at,

&#x20;       statement\_timestamp()

&#x20;   )

FROM stale

WHERE target.id = stale.id;

```



这里存在一个典型的 先查询、后更新 的并发窗口：



1\. 对账任务发现某条推理记录仍为 `RUNNING`。

2\. 与此同时，正常 `finish\_call` 提交成功，把状态更新为 `SUCCEEDED`。

3\. 对账任务继续更新同一条记录，存在将已成功的调用覆盖成 `UNCERTAIN` 的风险。



目前设置了 30 秒宽限期，可以降低发生概率，但宽限期不是数据库并发安全保障。



建议采用 PostgreSQL 行级锁并在更新时重新检查目标状态，例如通过 `FOR UPDATE OF c SKIP LOCKED`、确定性排序和 `target.status = 'RUNNING'` 限制目标行，结合真实并发事务测试确认正确性。



这项要在上线前解决，因为 WealthSail 的 AI 用量记录涉及模型是否完成、Token 统计和额度归因，不应该被后台恢复程序误改。



\### 2. P1：周期性对账会持续扫描不断增长的 AI 用量表



文件：`backend/jobs/runner.py`、`backend/ai\_usage/repository.py`。



这一版已经把对账接入 `run\_recoverable\_jobs()`，连接作用域也修好了，这是正确的。



但我检查了原有 `migrations/091\_ai\_usage.sql`：`research.ai\_usage\_calls` 有任务关联索引和账户索引，没有针对 `status='RUNNING'` 的专门索引。



而新 SQL 每次先执行：



```

WHERE c.status = 'RUNNING'

```



随着用量记录不断积累，周期性扫描可能越来越昂贵。`LIMIT 100` 只限制最终选择的记录数量，并不保证扫描开销也被限制。



建议增加部分索引，并用 PostgreSQL 18 的 `EXPLAIN (ANALYZE, BUFFERS)` 在隔离测试库验证。同时把对账从报告 Job 恢复路径中解耦，避免对账锁等待拖慢正常报告恢复。



\### 3. P1：研究校验日志仍无法定位具体的 `ValueError`



文件：`backend/jobs/daily\_research.py`，约第 47–68 行。



新版加入 `MODEL\_EXECUTION`、`SOURCE\_VERIFICATION`、`REPORT\_VALIDATION` 三个阶段，这是改进。



但对所有 `ValueError` 仍然统一返回：



```

if "JSON" in name or isinstance(exc, ValueError):    return "PAYLOAD\_VALIDATION\_FAILED"

```



假设明天再次出现 10 月 29 日的错误，日志只会是：



```

daily\_research\_failed

error\_class=ValueError

stage=REPORT\_VALIDATION

reason\_code=PAYLOAD\_VALIDATION\_FAILED

```



我们仍然无法知道到底是来源引用、发布日期、投资方向、基金价格计划，还是其他校验失败。



这意味着最初“为什么基金研究失败”的排障目标只完成了一部分。



建议给项目内部可控的校验器增加固定错误代码，例如：



| 代码示例                          | 说明          |

| ----------------------------- | ----------- |

| `SOURCE\_REFERENCE\_INVALID`    | 来源引用不存在     |

| `SOURCE\_DATE\_INVALID`         | 来源时间不合法     |

| `DIRECTION\_VALIDATION\_FAILED` | 投资方向约束不满足   |

| `FUND\_PLAN\_INVALID`           | 基金交易计划校验不通过 |

| `SCHEMA\_VALIDATION\_FAILED`    | 模型输出结构不符合要求 |



这些是建议新增的代码，不是当前项目已经具有的错误码。



实现时应由校验函数明确抛出固定代码，避免从包含模型文本的异常消息中直接提取内容。



这样既保护日志，又能识别具体失败规则。



\### 4. P1：NAS 研究审计持久化尚未真正落地



本次添加的 Compose 卷配置没有明显的 YAML 结构问题，但仍有两个部署条件：



第一，NAS 宿主机目录必须预先存在并可写。



```

${NAS\_VOLUME\_WEALTH\_SAIL}/research-audit

```



Worker 容器以 UID `10001` 运行。如果目录不存在，Docker 本地 bind 卷可能无法正常挂载；如果目录由 root 创建但不可写，则审计保存会失败。



第二，实际 NAS 的 `worker.env` 需要配置：



```

DAILY\_RESEARCH\_AUDIT\_DIR=/app/data/research-audit

```



现在改的是 `.env.example`，不会自动更新已有生产配置。



上线前应该明确校验目录、所有者、权限、卷挂载结果，以及审计文件能否在容器重建后保留。不要通过修改整个数据根目录的所有权来处理单个子目录。



\### 5. P2：Migration 093 的异常 JWT 处理还不完整



文件：`migrations/093\_fix\_ai\_usage\_overlap\_json\_and\_role.sql`。



这版 Worker 角色条件从宽松的 `OR` 改为要求当前实际角色为 `wealthsail\_worker`，方向是正确的。



不过还有一个边界情况：函数中对非法 JSON 有异常处理，RLS 策略中却仍使用：



```

NULLIF(

&#x20;   current\_setting('request.jwt.claims', true),

&#x20;   ''

)::jsonb

```



它能解决空字符串问题，但不能处理非空、格式错误的 JSON。



正常情况下，WealthSail 服务端应当生成合法的 JWT 上下文，因此这不是普通业务请求的高概率问题。不过如果目标是让用量记录的权限错误始终能够安全、清晰地失败，还需要覆盖这个边界。



建议通过真实数据库测试验证缺失、空字符串、非法 JSON、无效 UUID、合法租户以及跨租户请求，确保不会错误放行，也不会导致未预期的转换异常。
