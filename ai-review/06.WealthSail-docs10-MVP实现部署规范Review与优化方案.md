## 2. 总体评价

### 2.1 值得保留的设计

原稿以下方向与既有决策一致，应在优化中保留并展开，而不是删除：

- React SPA + FastAPI 模块化单体 + PostgreSQL/Supabase 的技术路线；
- API 与后台 Worker 进程隔离，但不提前拆成微服务；
- 股票、场内基金、场外基金共用不可变投资事件与可重建投影；
- PostgreSQL RLS、`FORCE ROW LEVEL SECURITY` 和含 `tenant_id` 的复合外键作为纵深防御；
- 金额、份额、价格和收益率使用 Decimal/NUMERIC，前端图表转换不回流业务计算；
- 四时段报告、`workflow.jobs/job_runs`、事务性 Outbox 和持久化 HITL；
- 企业微信使用一次性高熵绑定挑战，拒绝 `@all` 和不可信 tenant/user；
- Agent/模型默认只读，不能取得数据库、账本、政策或订单写权限。

### 2.2 主要不足

原稿更接近“目标架构概览 + 配置片段”，还不是完整的工程和部署规范。主要不足包括：

- 多处将尚不存在的目标目录、路由和容器写成当前事实；
- 企业微信绑定数据无法支持后续主动推送；
- tenant-scoped token 的承诺没有被当前 RLS 策略真正执行；
- API、Worker 共用全部密钥和数据库连接，违反最小权限；
- Supabase 连接模式、异步驱动和 prepared statement 约束未说明；
- 四时段任务被错误压成一条 Cron，时间还提前了 30 分钟；
- Compose/Nginx 缺少构建、迁移、健康检查、安全加固、备份和回滚；
- API 契约、OpenAPI 生成、错误码、幂等和并发控制缺少落地规则；
- 没有把 TDD、异常分支、上线证据和运行验收写进本文。

## 3. 阻断级问题（P0）

### R10-P0-001：企业微信正式绑定只有哈希，主动推送无法取得收件人

**原稿现象**

绑定时序要求正式 `channel_bindings` 只保存外部用户 ID 的“加盐哈希，不存明文”；随后又要求 Worker 在 08:30、14:30、15:30 主动向绑定用户推送。现有 `WeComAdapter.send_markdown_message()` 必须获得明确的 `to_user`，单向哈希无法还原企业微信 UserID。

当前表虽然有 `external_username`，但它既不是明确的路由字段，也没有加密与读取权限约束。如果把 UserID 隐式塞入该列，会造成语义和隐私边界不一致。

**影响**

- 定时报告不能可靠地定向发送；
- 开发人员可能为了跑通功能而在普通字段中保存明文 UserID；
- Web DTO、日志或运维查询可能意外泄漏可识别的外部身份。

**修改方案**

正式 binding 同时保存两种信息：

1. `external_user_hmac`：以服务端密钥生成的确定性 HMAC，用于查找、去重和唯一约束；
2. `external_user_ciphertext`：信封加密后的可逆路由值；API 只拥有 encrypt-only 能力，只有发送 Worker 的最小权限角色拥有 decrypt 能力；自托管 MVP 可用公钥封装，云环境可用 KMS 权限分离；
3. `encryption_key_id`、`nonce`、`algorithm_version`：支持轮换和迁移；
4. Browser DTO、审计摘要和模型上下文只暴露绑定状态及脱敏用户名，不暴露哈希、密文和路由值。

迁移 001–008 尚未包含上述密文字段，因此优化后的 docs/10 必须标记为“后续迁移待实现”，不能伪装成已有能力。

### R10-P0-002：active tenant claim 没有进入实际 RLS 判定

**原稿现象**

原稿在事务中注入 `request.jwt.claims.tenant_id`，并声称数据库上下文已经按活动租户隔离；但当前 `identity.is_tenant_member(target_tenant)` 只检查 `auth.uid()` 是否属于目标 tenant，不检查目标 tenant 是否等于 token 的 active tenant。

当一个用户未来同时加入 tenant A 和 tenant B 时，active tenant=A 的会话仍可能在数据库层读取 tenant B。Repository 如果遗漏 `WHERE tenant_id = :active_tenant`，RLS 无法兜底。

**影响**

- 与 docs/09 的“一枚 access token 只绑定一个 active tenant”决策冲突；
- 未来家庭/团队模式下产生跨活动租户读取风险；
- 文档错误地把“membership 范围”描述成“active tenant 范围”。

**修改方案**

- 由后端从已验证会话和 membership 解析 `TenantContext`，不接受请求 Body、查询参数、模型或企微正文自报 tenant；
- RLS helper 同时验证 `auth.uid()`、active tenant claim 与 membership；
- Repository 方法全部显式接收 `TenantContext` 并带 tenant predicate；
- 新增“用户同时属于 A/B，token 激活 A，查询 B 必须为空或拒绝”的专项测试；
- Worker 使用独立受限角色和显式 tenant job scope，不模拟浏览器会话。

### R10-P0-003：API 与 Worker 共用整套生产环境变量和数据库身份

**原稿现象**

Compose 示例让 API 与 Worker 同时加载 `.env.production`。这会让两个进程同时取得数据库连接、Auth 密钥、企业微信回调密钥、主动发送密钥、模型 API Key 等全部秘密。

**影响**

- 任一进程被攻破时，爆炸半径扩大；
- 无法落实 docs/07 中 API、Worker、Migration role 的职责边界；
- 运行时容器可能意外获得迁移、表所有者或 BYPASSRLS 权限。

**修改方案**

- `api.env`、`worker.env`、`migration.env` 分离；
- API DB role、Worker DB role、Migration role 分离；
- API 只持有认证、回调验签和 API 必需密钥；
- Worker 只持有行情、模型、企微发送及任务处理所需密钥；
- migration 凭据只在一次性迁移命令中注入；
- Secret 使用 Docker Secrets、NAS Secret Manager 或挂载文件，非敏感配置才放 env。

## 4. 高优先级问题（P1）

### R10-P1-001：TARGET 与 AS-IS 混写

原稿头部已经写明 `TARGET / NOT_LIVE`，但正文使用“位于”“标准 Compose”“生产配置”等已实现语气。仓库当前没有 `app/`、`api/`、`infrastructure/`、`deployment/`、Dockerfile、Compose 或企微回调 endpoint；绝对 `file:///d:/...` 链接也不可移植。

优化文档应新增“当前实现、目标实现、验收证据”矩阵，所有尚不存在的路径统一标注 `[TARGET]`，链接全部使用仓库相对路径。

### R10-P1-002：企微入站能力与现有适配器不符

现有适配器只实现 access token、主动 Markdown、绑定码 HMAC；没有首次 GET `echostr` 验证、POST XML 验签/AES 解密、被动回复加密和持久化防重放。

优化文档应把 GET 验证、POST 回调、五秒响应窗口、重复消息处理、签名失败、timestamp 漂移、nonce/message ID 去重完整写出，并把它们标为待实现和待测试。

### R10-P1-003：认证方案未形成唯一决策

既有 PRD 选择 Supabase Auth，原稿又同时出现自定义 `auth.py`、`JWT_SECRET`、`SECRET_KEY`、HttpOnly refresh cookie 和 tenant-scoped access token。缺少 token issuer、audience、算法、JWKS、refresh rotation、撤销和 membership 失效路径。

优化方案采用明确的两阶段边界：Supabase Auth 证明用户身份，FastAPI 验证后选择合法 active membership，并签发短期 WealthSail tenant-scoped application token；refresh cookie 仅由同源 FastAPI 管理，refresh 时重新验证 Supabase 会话和 membership。后续实现必须再以 ADR 和契约测试固化。

### R10-P1-004：Supabase 连接模式说明不完整

原稿把 Transaction Pooler 6543 与 Direct 5432 并列，却没有说明：

- 长驻 NAS/VPS 容器优先 Direct 或 Session Pooler；
- transaction mode 不支持 prepared statements；
- 使用 asyncpg 连接 6543 时需要 `statement_cache_size=0`；
- migration、备份恢复不能共用运行时连接模式；
- API 和 Worker 的池大小必须共同受数据库连接预算约束。

官方依据：

- Supabase：<https://supabase.com/docs/guides/database/connecting-to-postgres>
- Supabase Prepared Statements：<https://supabase.com/docs/guides/troubleshooting/disabling-prepared-statements-qL8lEL>

对 2–3 用户 MVP，建议连接池从每进程 `min=1/max=5` 起步，经负载测试调整，而不是固定 `5/20`。

### R10-P1-005：四时段任务和 Cron 不一致

原稿环境变量 `0 8,14,15 * * 1-5` 实际在 08:00、14:00、15:00 执行，且完全遗漏盘中事件跟踪。四种 session 的触发条件、数据时点、失败语义不同，不应压成一条 Cron。

优化文档应分别定义 PRE_MARKET、INTRADAY、FUND_1430、POST_MARKET，统一使用 `Asia/Shanghai`、交易日历、job lease、幂等 job key、missed-run 补偿和多 Worker 去重。

### R10-P1-006：Outbox 枚举和可靠性描述不一致

原稿写 `DEAD_LETTER`，迁移实际状态为 `DEAD`；1s/2s/4s 后立即判死也无法应对第三方平台短时故障。

优化文档应统一数据库状态，区分 429、5xx、超时和永久 4xx，采用带 jitter 的延迟重试、`Retry-After`、租约回收和人工重放；投递语义应表述为“至少一次 + 业务幂等”，不能暗示绝对 exactly-once。

### R10-P1-007：数据库名称、数量和完成度声明错误

- 原稿写 55 个复合外键；实际迁移文本中共有 44 个 `FOREIGN KEY`，其中 42 个以 `tenant_id` 开头；
- `protect_import_item()` 不存在，实际为 `ledger.protect_portfolio_import_item()`；
- “数据库已部署”“经测试”“无缝恢复”与 `TARGET / NOT_LIVE` 冲突。

优化文档不再用外键数量充当安全证据，改用 Schema introspection、A/B 越权测试、迁移测试和恢复演练作为门禁。

### R10-P1-008：前端真实 API 接入状态未说明

当前 Web UI 和测试框架已存在，但 API 文件仍包含 fixture/TARGET 实现：默认 API base 为 `/api`，没有自动 correlation ID、受控 401 refresh、OpenAPI 自动生成和真实绑定接口。

优化文档应明确：UI 已实现，真实后端联调未完成；目标统一为 `VITE_API_BASE_URL=/api/v1`，补充 API error envelope、幂等键、并发版本、OpenAPI 生成和 mock 禁入生产门禁。

### R10-P1-009：部署片段缺少生产闭环

原稿 Compose 依赖宿主机预构建 `frontend/dist`，引用不存在的两个 Dockerfile，没有 migration job、healthcheck、readiness、graceful shutdown、资源限制、日志轮转、非 root、只读文件系统、备份、回滚和镜像固定。

优化方案使用：

- 一个可复用 backend image，API/Worker 通过不同 command 启动；
- 独立多阶段 frontend image；
- 一次性 migrate service；
- 运行时最小权限和健康检查；
- NAS 反向代理、VPS 直出、Tunnel 三种部署 Profile；
- 可验证的发布、回滚和恢复步骤。

### R10-P1-010：缺少 TDD 与上线证据

原稿没有把 docs/04、docs/05、docs/08 的测试追踪落实到工程命令和部署门禁。优化文档应增加单元、组件、契约、数据库、E2E、安全和运维演练矩阵，并明确测试先行、失败用例先出现、修复后回归的 TDD 过程。

## 5. 中优先级问题（P2）与简化建议

### R10-P2-001：严格横向 DDD 对小规模 MVP 偏重

2–3 用户 MVP 不需要为每个简单类都建立接口和多层转发。建议保留模块化单体和边界原则，但采用“纵向业务模块 + 少量共享基础设施”：每个模块就近组织 `api/service/domain/repository/schemas`，只在数据库、企微、行情和模型等真正可替换边界建立 Port/Adapter。

这样既保留未来拆分能力，又减少一次需求变更跨越 `api/modules/infrastructure/repositories` 多个远端目录的成本。

### R10-P2-002：Compose 与 Nginx 示例使用旧写法

- Compose 顶层 `version: '3.8'` 已是兼容字段，现代 Compose 会忽略并告警：<https://docs.docker.com/reference/compose-file/version-and-name/>；
- `nginx:alpine` 是不可重现的浮动标签；
- Nginx `listen ... http2` 参数已弃用，应使用独立 `http2 on;`：<https://nginx.org/en/docs/http/ngx_http_v2_module.html>；
- TLS 路径在拓扑和 Compose 中不一致；
- `container_name` 会妨碍 Compose 项目隔离和水平扩展。

### R10-P2-003：术语方向容易误解

“微信下行接收”“微信上行推送”取决于观察者，容易混乱。建议统一使用“企业微信回调入站（Ingress）”和“主动消息出站（Egress）”。“边缘适配器”如果不是独立进程，也不应暗示额外边缘服务。

### R10-P2-004：固定绝对安全和高可用措辞过度

触发器、RLS、Outbox 和持久化 HITL 都是重要防线，但数据库 owner、BYPASSRLS、错误密钥、错误恢复程序和未实现消费者仍可能破坏保证。文档应使用“数据库约束下的不可变”“恢复目标”“待演练”，避免“绝对安全”“无缝恢复”等不可证实措辞。

## 6. 文档重构方案

优化后的 docs/10 采用以下结构，既方便首次阅读，也能直接指导实施：

1. 文档定位、范围、阅读路径；
2. 当前实现与目标实现差距；
3. 架构决策、拓扑和信任边界；
4. 前端工程、会话和 API Client；
5. 后端模块化单体和依赖规则；
6. API 契约、错误、幂等和并发；
7. Auth、TenantContext 与 RLS；
8. 企业微信入站、绑定和出站；
9. 四时段 Worker、Outbox 与故障恢复；
10. 数据库连接、角色、迁移和备份；
11. dev/staging/prod/NAS/VPS 部署 Profile；
12. Compose、Nginx 和环境变量权威示例；
13. 安全、可观测性、SLO/RPO/RTO；
14. TDD、异常矩阵和上线门禁；
15. 发布、回滚和运维手册；
16. 分阶段实施清单与未决事项。

每个关键示例都需要说明“当前是否存在、实现前置条件、如何验收”，避免示例代码被误认为已经上线。

## 8. 建议实施顺序

### 第一批：实现前必须冻结的安全与契约决策

1. 冻结 Auth/token/refresh/active tenant ADR；
2. 增加 active tenant RLS helper 与多 membership 测试；
3. 增加企业微信可逆加密路由字段和最小权限读取路径；
4. 冻结 API error envelope、幂等键、版本冲突和 OpenAPI 生成方式；
5. 统一环境变量名称，删除双重 `SECRET_KEY/JWT_SECRET` 歧义。

### 第二批：最短可运行后端

1. FastAPI 装配、health endpoint 和配置加载；
2. Auth/session、portfolio、report、risk、identity 基础 endpoint；
