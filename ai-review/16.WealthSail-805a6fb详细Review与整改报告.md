## 1. 结论摘要

本提交试图一次完成身份领域统一、研究决策 API、成交 API、密码重置和租户创建，功能方向中有一部分是合理的，例如：密码重置令牌只保存 HMAC 摘要、重置函数使用行锁保证一次消费、成交与决策增加不可变状态保护、Worker 不再持有密码重置密钥等。

但是，当前实现**不能按原样发布**。它存在 1 个 P0、多个 P1 数据一致性与安全问题，并重新引入了此前 `ai-review/14` 已经整改过的“双生产栈”架构。最严重的实际结果包括：

1. 登录或刷新虽然返回 200，但新签发 JWT 无法通过真实 HTTP 鉴权，后续受保护请求全部 401；
2. 登录审计、成交、决策等新增写入把 `dict` 直接绑定到 JSONB，真实 asyncpg 连接会报错并回滚；
3. 两笔不同成交复用同一确认幂等键时，可以被错误关联到同一个账本事件；
4. 成交确认不校验现金、持仓和买入出局条件，也不刷新持仓/NAV 投影；
5. 新增匿名注册和任意登录用户创建 tenant，直接违反 MVP 封闭邀请制；
6. 密码重置令牌进入 URL query、浏览历史和 Nginx 日志，且重置后旧 access token 仍可继续使用；
7. migration 022–024 已加入代码，但部署文档、readback 和测试仍停留在 021。

因此本次整改采用“保留正确能力、恢复既定边界”的策略：密码重置、研究决策和成交草稿/确认继续保留；公开注册、自助建 tenant 在 L1 删除；新增生产代码归并回 `backend/` 纵向领域模块；补充前向 hardening migration、readback、部署文档及回归测试。

## 4. 发现明细

### R16-01 — P0：新签发 JWT 无法通过真实 HTTP 鉴权

- 位置：`modules/identity/jwt.py:76-100`、`modules/identity/service.py` 登录/刷新/切租户、`backend/dependencies.py:58-64`
- 触发：正常登录或刷新后，用返回的 access token 调用任意受保护 API。
- 根因：新 issuer 把 `iat`、`exp` 序列化为 ISO 8601 字符串；生产鉴权仍由 `backend.common.auth` 的 python-jose 负责，后者要求 JWT NumericDate。
- 实证：使用项目虚拟环境执行“新 issuer → 真实 decoder”稳定得到 `JWTClaimsError: Issued At claim (iat) must be an integer.`。
- 影响：登录显示成功，但所有后续请求 401，是阻断全站的认证契约断裂。
- 测试缺口：现有测试只验证新模块“自编自解”，没有验证生产 issuer/consumer 组合。
- 整改：身份领域复用 `backend.common.auth` 唯一 JWT 实现；补登录签发 token 经真实 decoder 解码的回归测试。

### R16-02 — P1：重新形成 `backend/` 与 `modules/` 两套生产实现

- 位置：`backend/domain.py`、`backend/identity/service.py`、`backend/market/api.py`、`backend/portfolio/api.py`、`backend/worker.py`、根 `modules/*`
- 现象：identity 几乎整体迁到根 `modules`，market/portfolio 只迁一部分，research/trading 又采用另一种组合；同一领域同时存在新旧 Service、Repository、错误、数据库事务和 JWT。
- 影响：接口行为、缓存、事务、JSON 编码、错误码和测试使用的实现不一致；本次 JWT、JSONB、搜索缓存退化正是这种双栈漂移的直接结果。
- 历史证据：`ai-review/14` 已明确删除同一批影子生产文件，并约定新能力正式实现到 `backend/`；`modules/agent/tool_loop.py`、`modules/ledger/service.py`、`modules/market_data/providers.py` 才是保留的原型。
- 整改：将新增身份、成交、决策代码归入 `backend/<domain>/`；market/portfolio 恢复原有已验证 Service；删除重复 database/errors/JWT/生产 Service；保留明确原型。

### R16-03 — P1：审计 JSONB 参数在真实 asyncpg 下失败

- 位置：新增 identity `_write_audit`、ledger draft/confirm、research record/retract。
- 根因：把 Python `dict` 直接绑定到 JSONB；项目连接池没有注册自定义 JSONB codec，asyncpg 默认需要 JSON 字符串。既有 `backend.dependencies.write_audit` 已明确 `json.dumps`。
- 影响：登录审计、成交、决策会 DataError/500 或事务回滚。企业微信绑定还可能先提交绑定、后在独立审计事务失败，形成“响应失败但绑定已生效”。
- 整改：所有领域审计统一使用 `write_audit` 或等价 JSON 序列化；状态变更与审计放在同一事务；增加断言参数为 JSON 字符串的测试。

### R16-04 — P1：成交确认幂等冲突会错绑经济事件

- 位置：新增 ledger repository 的 `persist_event` 与 `confirm_trade_fill`。
- 触发：同 tenant、account、side、trade_date 的两个不同 fill 使用同一确认 Idempotency-Key。
- 根因：重放仅比较 account、event type、date、reversal，不比较 fill、instrument、quantity、price、fee、description 或 legs；随后第二个 fill 仍被改为 CONFIRMED 并指向第一个 event。
- 影响：fill、ledger event、audit 三者表达不同经济事实，破坏账本与归因。
- 整改：确认命令的 event description 强制包含 fill ID；重放比较完整规范化 event + legs；数据库增加一个 event 只能确认一个 fill 的唯一约束；不同命令同 key 返回 `IDEMPOTENCY_CONFLICT`。

### R16-05 — P1：成交确认不校验现金/持仓，也不刷新投影

- 位置：`backend/trading/api.py` 直接调用 Repository。
- 触发：确认正常成交、超卖 SELL 或余额不足 BUY。
- 影响：正常成交后 portfolio 仍读旧 position/NAV；超卖和负现金可以成为 CONFIRMED 账本事实，直到未来重放才暴露。
- 整改：新增 trading application Service；同一 tenant 事务中锁账户/草稿，读取未被 REVERSAL 的 confirmed ledger，校验可用现金和当前标的数量，写 event/fill/audit，再调用公开投影重建服务。任一步失败全部回滚。

### R16-06 — P1：BUY 确认没有强制出局条件

- 位置：成交草稿 DTO/确认服务。
- 影响：可形成没有任何失效条件的持仓，与产品最核心的“纪律化投资”价值冲突。
- 整改：BUY 确认前检查同 tenant、instrument、account 范围内存在 ACTIVE thesis，且 `invalidation_conditions` 为非空数组；SELL 不受此规则影响。

### R16-07 — P1：匿名注册和自助 tenant 创建违反 L1 封闭试点

- 位置：`POST /auth/register-with-tenant`、`POST /auth/tenants`、migration 022/024 对应函数、前端“自助注册”。
- 影响：互联网匿名请求可创建用户、tenant、OWNER，绕过邀请准入并无界消耗 bcrypt、数据库和运维资源；任意登录用户也可重复创建 tenant。
- 整改：删除 L1 API 和 UI；继续保留 `/auth/register` 一次性邀请流程；前向 migration 撤销并删除相应 SECURITY DEFINER 函数，避免已升级环境继续保留能力。

### R16-08 — P1：切换 tenant 时 refresh token 泄露到 JSON

- 位置：`backend/identity/api.py` switch-tenant。
- 根因：领域 payload 含私有 `_refreshToken`，该路由未像 login/refresh 一样 pop 并写回 HttpOnly Cookie。
- 影响：长期凭据可被页面 JavaScript、浏览器扩展或 XSS 读取。
- 整改：显式剥离私有字段，只通过 Secure/HttpOnly/SameSite Cookie 返回；响应契约测试禁止 token 出现在 JSON。

### R16-09 — P1：密码重置 token 进入 URL query、历史、Referer 和访问日志

- 位置：`backend/integrations/email.py`、`LoginPage.tsx`、`frontend/nginx.conf`。
- 触发：用户点击 `/login?token=...`。
- 影响：原始 capability 进入 Nginx 请求行、浏览历史及同源 Referer；有效期内日志读取者可能接管账号。
- 整改：邮件链接使用 `#reset-token=...` fragment；前端读取后立即 `history.replaceState` 清理，兼容一次旧 query 链接；Referrer-Policy 调整为 `no-referrer`；增加 URL 清理测试。

### R16-10 — P1：密码重置未立即撤销已签发 access token

- 位置：migration 024 reset 函数、`backend.common.auth`、`backend.dependencies`。
- 根因：只撤销 refresh session；JWT 仅验签名与 exp。
- 影响：已窃取 bearer 在密码重置后默认还能使用一小时。
- 整改：profiles 增加 `auth_version`；JWT 携带该版本；鉴权依赖每次使用 API 角色读取当前版本并 fail closed；密码重置函数在撤销 refresh session 的同一事务递增版本。旧版本 token 立即 401。

### R16-11 — P2：密码重置请求可被滥用并存在时序枚举

- 位置：password-reset request Service/API。
- 问题：已知邮箱同步等待 SMTP，未知邮箱立即返回；重复请求先作废旧 token 且没有来源/账号限速，攻击者可邮件轰炸并持续让链接失效。
- 本轮安全修复：邮件改后台发送，旧 token 在新请求时不再立即失效，消费任一 token 时才统一作废；增加短窗口账号级抑制。
- 剩余工作：生产级 IP + email 双维度限速、持久 Outbox 和投递重试需要独立设计与容量策略，不能用单进程内存计数器冒充分布式控制。

### R16-12 — P2：研究决策更正未形成 SUPERSEDED 链

- 位置：Decision Service `record_decision`。
- 触发：请求包含 `previousDecisionId`。
- 影响：旧、新记录都保持 RECORDED；跨用户旧 decision 也未被应用层验证；当前有效版本不唯一。
- 整改：同事务 `FOR UPDATE` 锁定旧记录，校验 tenant、user、状态及关联对象，插入新记录后将旧记录标记 SUPERSEDED；列表返回 previous link；覆盖跨用户、终态和并发冲突。

### R16-13 — P2：`confirmed_by` 缺少同租户复合外键

- 位置：migration 023。
- 问题：只引用 `identity.profiles(id)`，API 角色可把 tenant B 用户写成 tenant A fill 的确认人。
- 整改：前向 migration 改为 `(tenant_id, confirmed_by) -> identity.tenant_members(tenant_id,user_id)`，同时要求确认时 `confirmed_by = auth.uid()`；补 readback 与跨 tenant 数据库负例。

### R16-14 — P2：标的搜索退化为每次下载三套全市场数据

- 位置：portfolio API 被切到新 `modules.portfolio.service`。
- 根因：新实现生成 cache key 却未使用缓存或 single-flight；旧 `backend.portfolio.service` 已有 300 秒 TTL 和逐数据集锁。
- 影响：前端连续输入或 2–3 用户并发也会重复触发全量拉取，延迟、上游限流和雪崩风险显著增加。
- 整改：恢复原有 backend 搜索服务和缓存，不保留重复实现。

### R16-15 — P2：migration、readback 与部署文档漂移

- 位置：`scripts/migrate.py`、`docs/04`、`docs/08`、`docs/10`、`docs/11`、migration runner 测试。
- 问题：代码实际需要 022–024，文档与 readback 仍以 021 为当前目标；新 RLS、函数权限、触发器、复合 FK 和密码重置约束未验证。
- 影响：按文档部署会错误停止或漏配生产环境；迁移程序即使关键安全约束损坏仍可能报告成功。
- 整改：更新目标版本、环境变量、dry-run 预期、执行命令和 forward-fix；readback 覆盖新增列/函数/FORCE RLS/权限/触发器及本轮 hardening migration。

### R16-16 — P3：新增登录模式前端校验不完整

- 位置：`LoginPage.tsx`。
- 问题：`form noValidate`，按钮主要只看密码；邮箱、tenant 名等无模式化提交前校验。服务端 fieldErrors 未映射到具体控件。
- 整改：删除自助注册后，分别为登录、邀请注册、重置请求/确认建立派生 `formValid` 和字段级提示；非法值不允许提交。

## 7. 整改结果、验证和部署影响

### 7.1 已完成的代码整改

1. **恢复唯一生产代码树。** 将本次真正新增的身份、成交和研究决策能力归并到
   `backend/identity`、`backend/trading`、`backend/research`，恢复原有 market/portfolio
   Service 与搜索缓存；删除重复的 database、errors、JWT 和影子生产 Service。`modules/`
   仅保留 Agent tool loop、内存账本和 Provider 契约原型，避免同一业务存在两套实现。
2. **统一身份协议。** 登录、刷新和切租户全部使用 `backend.common.auth` 的 NumericDate JWT；
   切租户响应剥离 refresh token，只写入 HttpOnly Cookie。移除匿名自助注册和登录用户自建
   tenant 的 API、前端入口及数据库 RPC，恢复 L1 一次性邀请码准入。
3. **让密码重置真正撤销会话。** 新增 `profiles.auth_version`；access JWT 携带版本，受保护请求
   以 API 角色回读当前版本并 fail closed；重置密码在同一数据库事务中递增版本、撤销 refresh
   session、消费 reset token 和写审计。邮件链接改用 fragment，前端读取后立即清除 fragment/
   兼容旧 query，Nginx 使用 `Referrer-Policy: no-referrer`。
4. **修复 asyncpg JSONB 写入。** 身份、成交、决策审计字段在绑定前统一序列化为 JSON 字符串，
   避免真实 asyncpg 连接因直接绑定 Python `dict` 而报 DataError。
5. **补齐金融命令不变量。** 成交确认先锁 fill 和 account，再校验 BUY 的 ACTIVE thesis/
   出局条件、含费用的可用现金，或 SELL 的可用持仓；随后在同一事务写入完整 event + legs、
   更新 fill、写审计并重建持仓/NAV 投影。幂等重放比较完整经济命令，并以 fill ID 绑定事件，
   数据库再用唯一索引禁止一个 ledger event 被多个 fill 复用。
6. **修复冲正和费用口径。** 现金余额纳入 CASH/FEE/TAX 等所有非空 amount legs，同时显式排除
   REVERSAL 事件及其被冲正目标；交易前现金/持仓校验采用同一口径，避免冲正的反向 legs
   被再次计入形成“双重冲正”。
7. **补齐决策修订链。** 修订时锁定并校验原决策的 tenant、user、subject 和状态，在同一事务将
   原记录转为 `SUPERSEDED`；列表返回 `previousDecisionId`，幂等冲突比较完整命令。
8. **增加前向数据库加固。** 新增 `025_identity_session_and_trade_integrity_hardening.sql`，不改写
   已可能执行的 022～024 checksum；撤销越界 RPC，新增会话版本、确认人同租户复合外键、
   event 唯一关联和 `confirmed_by = auth.uid()` RLS 检查。迁移前会检测历史脏数据并拒绝静默上线。
9. **同步实现、测试和部署文档。** `docs/04`、`docs/08`、`docs/10`、`docs/11` 均以 025 为当前

### 7.3 部署影响

本次版本**不能只更新应用并重启**。新鉴权依赖 `identity.profiles.auth_version`，新成交约束依赖
025 的复合外键、唯一索引和 RLS，因此必须按 `docs/11`：备份数据库 → 使用迁移管理员执行
dry-run → 正式迁移到 025（正式命令会自动 readback）→ 手工回读 → 再重启 API/Worker。
025 的 preflight 如果发现跨租户 `confirmed_by` 或同一 event 被多个 fill 引用会主动中止；应先
人工确认经济事实并用新的前向 migration 清理，禁止删 migration ledger、改历史 checksum 或
强行跳过约束。

## 8. 剩余风险与后续建议

1. **尚未取得真实 PostgreSQL/Supabase 执行证据。** 当前机器没有目标数据库凭据和 Docker，
   因而本轮完成的是 runner、SQL 契约和应用层自动化验证，不能替代生产/隔离库执行 022～025、
   RLS 角色、函数 owner/search_path、并发冲突和 readback。上线前必须保留命令输出和脱敏证据。
2. **密码重置的分布式防滥用仍需平台能力。** 当前已改为后台投递、保留旧 token、60 秒账户级
   抑制；下一阶段应在外层网关增加 IP + email 双维度限速，并建设持久化邮件 Outbox、退避重试、
   投递状态和告警。单进程内存限流不适合作为多实例安全边界。
3. **每个受保护请求增加一次身份版本回读。** 对 MVP 的 2～3 位用户成本可接受，换来密码重置
   后 access token 立即失效；扩容前应监控数据库延迟与连接池占用。若未来做短缓存，必须有
   reset 事件主动失效或严格短 TTL，不能牺牲会话撤销承诺。
4. **成交不变量需要真实并发集成测试。** 应覆盖两个进程对同 account 并发 BUY/SELL、并发修订
   同一 decision、重复 Idempotency-Key、冲正后重试和投影重建失败回滚，并验证 PostgreSQL
   行锁、唯一索引、触发器与 RLS 的最终行为。
5. **BUY 出局条件的用户体验仍不完整。** 后端已经 fail closed，但前端成交确认流程应在按钮前
   展示匹配 thesis、失效条件和缺失原因，并提供有权限的快捷补录入口，避免用户只看到通用 400。
6. **原型代码仍有小额技术债。** `modules/ledger/service.py` 的 7 个 E741 命名告警可在独立提交中
   机械修复；同时应给 `modules/README.md` 增加更醒目的“非生产、不可被 API/Worker import”边界，
   防止后续再次形成双生产栈。
