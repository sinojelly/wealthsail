## 1. 结论摘要

### 1.1 总体结论

本提交**不建议直接作为“企业微信验证已修复”的可发布版本合入生产**，建议结论为：

> **Request changes / 有条件拒绝发布。**

原因不是实现思路完全错误，而是修改同时出现了三类问题：

1. **凭据泄露与高权限部署风险**：Git 中新增了两个环境备份、脚本内固定凭据、固定数据库角色密码和固定演示账户；必须优先按安全事件处理，而不能只做代码清理。
2. **核心投递链路仍未闭环**：报告 Outbox 生产者没有写入本提交消费者要求的 `touser`，正常报告仍会投递失败；并发认领和失败回退还可能造成重复发送。
3. **实现与既定设计发生偏离**：文档要求通过租户绑定解析收件人、加密保存路由值、API/Worker 密钥分离、前向迁移和可审计回执；本提交改为从通用 `payload` 读取明文收件人，并通过运维脚本把凭据复制到多个运行环境。

因此，这个提交解决的是“部分企业微信协议调用和排障能力”，还没有解决“多租户投资报告安全、可靠地送达正确用户”这一产品目标。

### 1.2 风险等级统计

| 工程级别 | 数量 | 说明 |
|---|---:|---|
| P0 | 7 | 发布阻断：凭据事件、正常投递失败、重复发送、迁移固定凭据等 |
| P1 | 11 | 应在进入 MVP 联调前完成：路由设计、协议边界、生命周期、性能和测试等 |
| P2 | 7 | 可维护性与工程治理改进 |

安全差异扫描另确认了 4 个可报告发现：1 个 Medium、3 个 Low。这里的安全等级受“凭据是否仍有效、脚本是否已在生产执行、外部可达性尚未验证”影响；从项目发布管理角度，**已进入 Git 历史的疑似真实凭据仍应按 P0 处理**，不能因为外部可达性未知而降低处置优先级。

### 1.3 本提交值得保留的部分

修复时不要把以下正确方向一并删掉：

- 对 Supabase pooler 的 `statement_cache_size` 兼容问题进行了显式处理，方向正确，但实现还不完整。
- 企业微信应用消息与智能机器人作为两种发送通道进行了概念区分。
- 主动发送已经具备超时、Access Token 缓存、请求 ID、WebSocket 心跳和待响应请求表等基本骨架。
- Outbox 失败时仍保留失败状态，没有伪造 `SENT`。
- 新增 `/verify` 的校验过程仍包含签名、时间戳、AES 解密和 CorpID 校验；应复用到唯一规范入口，而不是丢失这些校验。
- `websockets` 使用固定版本，具备最基本的依赖可重复性意识。

## 4. P0：发布阻断问题

### P0-01：Git 中新增疑似真实凭据，必须先做轮换和泄露响应

**证据**

- `.env.bak:3-36`
- `.env.bak.20260825:3-36`
- `scripts/fix_wecom_verify.sh:19-22`
- `.gitignore` 只覆盖 `.env` 和 `*.env`，没有覆盖 `.env.bak*`

两个环境备份包含非占位格式的数据库连接、模型提供商 Key、企业微信配置以及应用运行密钥。修复脚本还把企业微信相关配置写成仓库内常量，并输出服务进程环境、systemd 环境文件和备份路径。

**影响**

- 删除当前文件并不能使 Git 历史中的值失效。
- 仓库克隆、CI 缓存、日志、Review 工具和备份都可能已经复制这些值。
- 若数据库 Worker 凭据、模型 Key 或企业微信密钥仍有效，可能导致跨租户数据访问、费用损失、伪造消息或数据泄露。

**立即处置顺序**

1. 暂停把当前提交分发到更多环境，不要先等待代码修复完成。
2. 盘点并轮换所有可能真实的数据库、模型、JWT/HMAC、企业微信回调/发送/Bot 凭据；优先轮换高权限和可远程使用的值。
3. 检查 Supabase、模型提供商、企业微信和 CI 日志，确认是否存在异常访问。
4. 从当前树移除环境备份和脚本常量；新增 `.env*` 默认忽略，仅显式放行脱敏的 `.env.example`。
5. 在轮换完成后，再协调执行 Git 历史清理和强制更新；历史重写会影响所有协作者，不能在未协调时擅自执行。
6. CI 增加 secret scanning，并阻断高熵密钥、私钥、数据库 URL 和企业微信密钥进入提交。

**验收标准**

- 旧凭据全部失效，有轮换记录和访问日志检查结果。
- `git grep`、历史扫描和 CI Secret Scan 不再发现真实值。
- 运维自检只输出“存在/缺失、长度是否合法、配置版本”，不输出值、前后缀或整个进程环境。

### P0-02：正常报告生产者没有 `touser`，主动发送仍然不可用

**证据**

- `backend/jobs/outbox.py:88-93`：发送时强制从 `payload` 读取 `touser`，缺失即失败。
- `backend/reports/service.py:451-458`：`REPORT_PUBLISHED` 事件只写入 `report_id`、`session`、`version`。
- 现有 Seed Outbox 也没有提供符合新消费者约定的目标字段。

**实际结果**

盘前简报、盘中跟踪、基金 14:30 报告和盘后复盘即使成功生成，进入 Outbox 后仍会因缺少 `touser` 重试，最终进入 `DEAD`。因此“主动发送代码存在”不等于“产品链路可用”。

**设计问题**

不能简单要求所有报告生产者把企业微信 UserID 塞进通用事件：

- 这会把渠道隐私和报告领域耦合。
- 同一报告面向多个用户时会产生不清晰的一对多语义。
- 用户解绑、换绑、停用、跨租户误绑时难以在发送前重新校验。
- 后续增加邮件、短信、App Push 时会继续膨胀 `payload`。

**建议方案**

- 报告发布事件只表达 `tenant_id + report_id + report_type + audience_policy`。
- 通知编排层根据订阅和有效 `channel_binding` 展开一人一条 delivery/outbox 记录。
- Outbox 保存 `channel_binding_id`、模板/内容引用和幂等键，不保存可由 API 任意写入的明文接收者。
- Worker 在发送前以 `tenant_id + binding_id + status=ACTIVE` 回读绑定，解密路由密文并发送。
- 用户解绑后，未发送记录应进入 `CANCELLED/DEAD` 并记录可解释原因。

### P0-03：Outbox 认领不是原子的，多 Worker 会重复发送

**证据**

- `backend/common/database.py:107-115` 的 `system_connection` 只获取连接，没有包裹事务。
- `backend/jobs/outbox.py:28-38` 执行 `SELECT ... FOR UPDATE SKIP LOCKED`。
- 随后在 `backend/jobs/outbox.py:46-55` 更新状态，`57` 发起外部网络请求，`63-72` 标记 `SENT`。

在 PostgreSQL 中，行锁只在事务内有效。当前查询在没有显式事务的连接上执行，语句结束后锁就可能释放；两个 Worker 可以先后选中同一条记录，并分别发送。外部平台已接收、进程却在写 `SENT` 前崩溃时，下一次重试也会再次发送。

对投资报告而言，重复推送会直接损害用户信任，尤其是盘中风险提示或需要用户操作的消息。

**建议状态机**

1. 短事务内通过 `UPDATE ... WHERE status IN (...) AND lease_expired ... RETURNING` 原子认领，写入 `lease_token`、`leased_until`、`attempt_no`。
2. 提交事务并释放数据库连接。
3. 执行外部发送，不在网络等待期间占用数据库事务和连接。
4. 用 `id + lease_token` 条件更新最终状态，避免旧 Worker 覆盖新租约。
5. 为企业微信请求建立业务幂等键、provider request/receipt ID 和“不确定结果”状态。
6. 对超时后无法确认的请求先查回执或进入人工/定时对账，不盲目换通道或重发。

### P0-04：应用消息失败后无条件回退 Bot，可能一次生成两条消息

**证据**

- `backend/integrations/wecom.py:105-114` 捕获宽泛异常后立即改走 Bot。

如果应用 API 已经接收消息，但响应在网络中超时，调用方看到的是异常；当前实现会立即通过 Bot 再发一次，Outbox 之后还可能继续重试。一次报告最多可能经多个路径重复到达。

**建议**

- 区分“明确拒绝”“调用前失败”“结果不确定”三类错误。
- 只有明确、可证明未接收且产品规则允许时才做通道降级。
- 超时、连接中断、5xx 等不确定结果进入 `UNKNOWN`/`RECONCILING`，不可自动切换通道。
- 通道选择应由通知策略层完成，发送客户端只负责一个明确通道，避免在底层偷偷改变用户体验。

### P0-05：Supabase 迁移脚本把固定密码、高权限角色和演示用户带入目标环境

**证据**

- `scripts/supabase_migrate.sh:39-59` 创建带固定仓库已知密码的运行角色，其中包含 `BYPASSRLS` 权限。
- `scripts/supabase_migrate.sh:80-103` 插入固定密码并已确认的演示 Auth 用户。
- 脚本依次执行 001–012，其中包括开发 Seed 和演示认证数据。
- 没有部署目标白名单、交互确认、迁移账本、逐版本 readback 或“生产禁止 Seed”保护。

**影响**

- 任何能读仓库的人都知道运行角色和演示账号口令。
- `BYPASSRLS` 凭据一旦暴露，所有租户边界同时失效。
- 在生产误执行时，开发数据、演示账号与运行权限一起落库。
- 失败后重新运行可能处于部分完成状态，`SKIP_MIGRATIONS=1` 只是全部跳过，并不能安全恢复。

**建议**

- 角色凭据由 Secret Manager/部署平台生成和注入，迁移 SQL 不包含口令。
- Runtime Role、Migration Role、Owner Role 分离；日常 Worker 不持有 schema owner。
- Seed 与 schema migration 完全分开，生产部署默认且强制禁用 demo seed。
- 采用 Alembic 或 Flyway 风格的版本账本、checksum、单版本事务和 drift 检测。
- 部署前打印脱敏目标信息并要求显式确认环境；CI/CD 用受保护环境审批代替脚本内默认值。
- 部署后 readback：角色权限、RLS、函数 owner/search_path、表结构、迁移版本和演示账户不存在。

### P0-06：认证函数向普通认证角色返回密码哈希

**证据**

- `scripts/fix_login_authenticate_credentials.sql:18-40` 定义可按任意 Email 查询的 `SECURITY DEFINER` 函数，并返回密码哈希和成员关系。
- `scripts/fix_login_authenticate_credentials.sql:90-95` 将 schema 使用权和函数执行权授予普通认证运行角色。
- `scripts/supabase_migrate.sh:109-123` 又定义了第二份相似实现，已经出现漂移。

这等价于给调用者一个“按 Email 取离线破解材料”的接口。bcrypt 能提高破解成本，但密码哈希本身仍是敏感认证材料，不应返回给普通调用角色。

**建议**

- 首选统一到成熟的 Supabase Auth，不再维护第二套密码认证边界。
- 若确需自有认证：函数放入不暴露的私有 schema，只授权专用 Auth Service Role；在数据库/服务端完成密码校验，只返回非敏感 subject、tenant membership 和认证结果。
- `SECURITY DEFINER` 固定 `search_path`，显式 owner，撤销 `PUBLIC` 权限，并增加跨租户与枚举测试。

### P0-07：迁移脚本不能保证从清洁 Supabase 成功构建

**证据**

- `scripts/supabase_migrate.sh:69` 对 `public.profiles` 执行 `ALTER TABLE`，注释却表示将创建它。
- 仓库迁移中没有找到 `CREATE TABLE public.profiles`。
- 主设计使用的是 `identity.profiles` 等领域 schema，与该临时 `public.profiles` 修复路径不一致。

空库执行到这里会因为目标表不存在而中断，留下前面已经创建的扩展、角色或部分 schema。它既不是确定性迁移，也不是可靠的修复脚本。

**建议**

- 选定唯一身份模型：MVP 使用 Supabase Auth 映射到 `identity.profiles`，或完全自建 Auth；不要并行维护 `public.profiles` 临时模型。
- 在一次临时修复前，先生成正式的、版本化的前向迁移。
- 清洁数据库 CI 必须从零执行全部生产迁移，再执行 schema/权限契约测试。

## 5. P1：高优先级工程问题

### P1-01：DSN 修复只提取参数，没有可靠地从 DSN 移除

`backend/common/database.py:31-41` 解析了 `statement_cache_size`，并在建池时作为参数传入；但 `backend/common/database.py:60-69` 仍把原始 DSN 传给 `asyncpg.create_pool`。如果 URL 中仍保留客户端专用 query 参数，pooler 连接问题可能继续存在。

`scripts/supabase_migrate.sh:30-31` 用字符串替换清理 query 参数，也无法正确覆盖参数位于首位、中间、末位以及后面还有其他参数的所有情况。

建议用 URL 解析器构造“清洁 DSN”和 `connect_args`，并为以下形式做参数化测试：

- 无 query；
- 目标参数为唯一参数；
- 位于首位、中间、末位；
- URL 编码用户名/密码；
- IPv6、特殊字符、多个重复参数；
- Session Pooler 与 Transaction Pooler。

### P1-02：重复 `/verify` 路由扩大公开接口面，没有解决配置根因

`backend/integrations/wecom.py` 已经有 `/callback`，本提交新增几乎相同的 `/verify`。修复脚本自身又判断根因是企业微信后台 URL/Token/AESKey 配置，而不是原算法缺失。

建议：

- 选定文档规定的唯一规范入口 `/api/v1/integrations/wecom/callback`。
- 校验逻辑抽成一个纯函数/服务，由 GET 验证和 POST 消息共同复用。
- 若线上确实已经配置 `/verify`，把它做成有截止日期、指标和告警的兼容别名；不要复制整个实现。
- 文档、反向代理、企业微信控制台、自检和测试全部引用同一 URL。

### P1-03：路由明文与绑定设计不符合多用户扩展目标

MVP 虽然只有 2–3 个用户，也必须按“多租户、多用户、一人多通道”建立正确模型。直接在通用 JSON Payload 使用 `touser` 会让以后增加邮件、微博私信、App Push、群聊和个人聊时不断增加渠道字段。

更简洁且可扩展的数据关系建议为：

```text
notification_intent
  └── notification_delivery（每个用户/通道一条）
        ├── channel_binding_id
        ├── content_snapshot_id / template_id
        ├── idempotency_key
        ├── status / lease / attempt
        └── provider_receipt

channel_binding
  ├── tenant_id / user_id / channel_type
  ├── routing_hmac（查重/匹配）
  ├── routing_ciphertext（仅 Worker 可解密）
  └── status / verified_at / revoked_at
```

这样当前只有企业微信时结构并不复杂，后续增加渠道也不需要修改报告领域表或 Outbox Payload 约定。

### P1-04：企业微信模块承担过多变化原因

`backend/integrations/wecom.py` 同时包含：回调签名、AES 协议、入站绑定、Access Token 缓存、应用消息发送、Bot 回退和 FastAPI 路由。文件从约 215 行增长到约 360 行，职责边界变得模糊。

不建议为了“分层”机械拆很多空目录，建议按三个真正独立的变化原因拆分：

- `wecom_callback.py`：签名、时效、AES、CorpID、回放控制。
- `wecom_app_client.py`：Token 和应用消息 API。
- `wecom_bot_client.py`：WebSocket Bot 生命周期。
- `wecom.py`：只保留路由装配和依赖注入。

再通过一个小而明确的 `DeliveryPort` 返回类型化结果，例如 `ACCEPTED / REJECTED / UNKNOWN`，不要以宽泛 Exception 决定业务降级。

### P1-05：Bot 客户端是进程级单例，不支持多租户和密钥轮换

`backend/integrations/wecom_bot.py` 的模块级 `_client` 会永久缓存第一次传入的 Bot ID/Secret：

- 第二个租户或第二个 Bot 会错误复用第一个连接。
- 密钥轮换后进程不重启就不会生效。
- 无法按租户隔离配额、断路器、日志和故障。

建议由 Worker 生命周期持有 `BotClientRegistry`，以 `tenant_id + credential_version` 为键，支持上限、LRU/空闲回收、显式关闭和轮换事件。MVP 只有 2–3 个用户时也可以只开一个租户客户端，但接口不能写死为全局首个实例。

### P1-06：WebSocket 断线生命周期存在自取消和悬挂请求

`_reader_loop` 在断线后调用 `_teardown`，而 `_teardown` 会取消 `self._reader_task`；当调用者就是 reader 自身时，会把自己取消。与此同时：

- 已放入 `_pending` 的 Future 没有在断线时统一失败。
- 代码没有形成清晰的持续重连循环和退避/抖动策略。
- Worker 关闭时没有明确调用客户端 `close()`。
- `max_size=None` 允许不受限的消息帧。
- 入站事件主要被记录，缺少严格 schema、大小和频率控制。

建议把连接状态机明确为 `DISCONNECTED → CONNECTING → READY → DRAINING`，由一个 supervisor task 独占重连；reader 不负责取消自己。断线时以明确的 `DeliveryUnknown` 结束所有 pending，并对帧大小、心跳、指数退避、连接上限和关闭超时设硬限制。

### P1-07：HTTP 客户端和 Token 缓存缺少生命周期与并发控制

当前每次取 Token、每次发送都新建 `httpx.AsyncClient`，无法复用连接池和 TLS 会话。Token 缓存没有并发锁，同一租户在过期边界会发生刷新风暴；以 Secret 字符串作为缓存键也不利于轮换和内存敏感数据治理。

建议：

- Worker 启动时创建共享 `AsyncClient`，关闭时统一释放。
- 缓存键使用 `tenant_id + credential_version`，不使用 Secret 本身。
- 每个键增加 single-flight 锁，提前带抖动刷新。
- 识别 token 失效错误，只允许一次受控刷新重试。
- 设置连接池、DNS、读写超时、并发和企业微信速率限制。

### P1-08：Outbox 在外部请求期间长期占用数据库连接

`run_outbox_once` 在一个 `system_connection` 上选出最多 20 条记录，然后串行执行外部发送。若单次上限 15 秒，理论上连接可被占用约 300 秒。随着股票、场内/场外基金四个时段报告集中产生，连接池会被慢外部服务拖住。

应采用“短事务认领—释放连接—有界并发外发—短事务确认”。并发数不能无限提高，要按租户和渠道做速率控制，避免一个租户占满整个 Worker。

### P1-09：运维修复脚本混合过多职责，且可能产生部分成功状态

`scripts/fix_wecom_verify.sh` 同时做配置覆盖、环境备份、systemd 重启、进程环境检查、网络自检和临时脚本执行；还硬编码路径、服务名、端口、外部时间来源和部署平台假设。

这类脚本很难安全重试，也很难判断失败前已经改变了什么。建议拆成：

1. 只读诊断命令；
2. 生成建议配置差异；
3. 需要显式确认的应用步骤；
4. 独立 readback；
5. 可记录的回滚步骤。

自检逻辑只保留 `scripts/wecom_selftest.py` 一份，Shell 不再内嵌第二份 40 行 Python。

### P1-10：日志暴露用户路由信息，且异常可能携带敏感参数

`backend/integrations/wecom.py:148`、`backend/integrations/wecom_bot.py:126-130,192` 会记录完整用户标识或入站标识；`scripts/wecom_selftest.py:98-101` 还输出配置指纹。根据 `docs/07`，外部渠道标识属于受限数据。

建议日志仅记录 `tenant_id`、内部 binding ID、不可逆短哈希、request ID、错误分类和耗时；不要记录外部 UserID、密钥指纹、完整 URL Query 或原始响应体。日志模板应通过单元测试验证脱敏。

### P1-11：仓库新增 87.96 MiB 无来源证明的隧道二进制

三个 ngrok 压缩包内容完全相同，且仓库没有发现对这些二进制的受控调用。问题包括：

- Git 永久膨胀，Clone、CI、扫描和备份成本提高。
- 不知道具体版本、下载来源、许可证、校验和和 CVE 状态。
- 无自动更新或回滚路径。
- 临时隧道容易绕过既定 HTTPS 入口、WAF、域名和审计设计。

建议从源码仓库移除，开发环境按需通过受控脚本下载固定版本并验证 SHA256/签名；生产使用正式反向代理、域名和证书。若确实需要作为运维工具，放入独立工具镜像或制品仓库并生成 SBOM。

### P2-01：提交应该按可独立回滚的主题拆分

建议至少拆成：

1. DSN pooler 兼容 + 测试；
2. 企业微信回调兼容 + 测试；

企业微信请求、响应、Outbox Payload 和 Bot 回包大量依赖字符串键。建议使用轻量 dataclass/Pydantic Model/TypedDict，至少明确：

- `DeliveryCommand`
- `DeliveryResult`
- `WeComAppResponse`
- `BotFrame`
- `ReportPublishedPayload`
- `OutboxLease`

类型化不是为了增加抽象，而是让缺少 `touser` 这类生产者/消费者契约错误在测试或类型检查阶段暴露。

独立 SQL 和 `supabase_migrate.sh` 内嵌 SQL 对 `crypt` schema 的引用不同，函数 owner 也依赖执行上下文。应该只有一个正式迁移文件；修复脚本调用迁移工具，不再复制函数定义。

### P2-04：配置模型未体现 Secret 所属进程

所有配置进入同一个 `Settings`，容易让 API 和 Worker 获得彼此不需要的密钥。建议最小化为：

- `ApiSettings`：回调验证、公网 API、租户受限数据库连接。
- `WorkerSettings`：发送凭据、路由解密、跨租户 Worker 连接。
- `MigrationSettings`：只存在于部署任务，不进入常驻服务。

共享的非敏感配置可以组合复用，但 Secret 字段不能因为“方便”而进入共同基类。

### P2-05：Bot 是实验性能力，应通过 Feature Flag 隔离

应用消息是 MVP 可控的首选路径。智能机器人协议、群聊/个人标识、回调、配额和可用性尚未建立契约测试，不应默认作为应用消息异常后的自动兜底。

建议 `WECOM_BOT_ENABLED=false` 默认关闭，只在独立测试租户逐步启用，并记录成功率、重复率、延迟、断线和配额指标。

### P2-06：依赖治理仍不是可重复构建

虽然新增的 `websockets` 固定了版本，但项目仍使用单一 `requirements.txt` 混合运行和测试依赖，当前环境缺少 `bcrypt`、`httpx` 就无法收集测试。建议：

- 使用 `pyproject.toml` + lock 文件，或至少拆分 runtime/dev requirements。
- CI 从空环境安装锁定依赖后运行测试。
- 对 `websockets`、`asyncpg`、`httpx` 做协议/版本契约测试。
- 不把 pytest 等测试工具装进生产镜像。

### P2-07：缺少变更记录、运行手册和弃用说明

新增外部通道时，应同步补充：

- 企业微信控制台配置的唯一回调 URL；
- 应用消息与 Bot 的适用场景和限制；
- Secret owner、轮换步骤和失败回滚；
- Outbox 状态解释和人工重放条件；
- `/verify` 若保留时的弃用期限；
- 隧道仅开发可用的明确约束。

## 7. 性能与容量分析

MVP 只有 2–3 个用户，吞吐量不是主要瓶颈，但错误的生命周期和事务边界会在低流量下同样造成故障。

| 问题 | 2–3 用户时的影响 | 扩展后的影响 | 优化方向 |
|---|---|---|---|
| 每次发送新建 HTTP Client | 延迟和资源浪费 | TLS/端口耗尽 | Worker 级共享 Client |
| 网络期间占用 DB 连接 | 一次企业微信卡顿即可占池 | 报告集中时连接池枯竭 | 短事务 + 释放连接 |
| 20 条串行发送 | 基金 14:30 或盘后批次延迟 | 队头阻塞 | 有界并发 + 租户公平调度 |
| Token 无 single-flight | 过期边界偶发重复刷新 | 刷新风暴和限流 | 按凭据版本加锁 |
| Bot 单例串行等待回包 | 单租户尚可 | 多租户相互阻塞 | Registry + 限速 + 背压 |
| WebSocket `max_size=None` | 恶意/异常帧可占内存 | DoS 风险放大 | 限制帧和消息 schema |
| 87.96 MiB Git 二进制 | Clone/扫描变慢 | CI 缓存持续膨胀 | 制品仓库/按需下载 |

建议先保证正确性和可观测性，再增加并发。对金融消息，“慢但不重复、不串租户”比“快但不确定”更重要。

### 8.2 必须补齐的测试矩阵

#### A. 回调验证与入站安全

- 正确签名、错误签名、空参数、重复参数。
- 时间戳刚好在边界内/外、未来时间、非数字时间。
- AESKey 长度错误、Base64 错误、Padding 错误、CorpID 不匹配。
- 超大请求、XML/JSON 畸形、重复回调、Nonce/消息 ID 回放。
- 绑定 Token 过期、已消费、跨租户、被撤销、并发消费。
- `/callback` 与临时兼容 `/verify` 行为一致；弃用指标可统计。
- IP/租户级限速、日志不包含签名参数和外部 UserID。

#### B. 报告到通知的业务闭环

- 四类 MVP 报告生成后，都能为已订阅用户展开 delivery。
- 股票、场内基金、场外基金的报告受众与时段正确。
- 一个租户 2–3 用户分别绑定，消息只到自己的账号。
- 用户无绑定、绑定未验证、解绑、停用、换绑时结果正确。
- 同一用户多通道的优先级和降级规则明确。
- 生产者无需知道企业微信 `touser`，Worker 从有效 binding 解析。

#### C. Outbox 并发与故障注入

- 两个 Worker 同时认领同一批记录，单条只允许一个有效 lease。
- 认领后崩溃、发送前崩溃、平台接收后崩溃、最终写库前崩溃。
- 网络超时、DNS 错误、429、5xx、明确 4xx、Token 过期。
- 租约过期接管和旧 Worker 条件更新失败。
- `UNKNOWN` 状态不会自动跨通道重复发送。
- 幂等键冲突、回执重复、人工重放审计。

#### D. 企业微信应用客户端

- Token 缓存命中、提前刷新、并发刷新 single-flight。
- 失效错误只刷新一次；权限错误不得重试。
- 响应缺字段、非 JSON、超大响应、慢响应。
- HTTP Client 生命周期、连接池配置和关闭。
- 收件人来自可信 binding，不能由通用 payload 注入。

#### E. Bot WebSocket

- 鉴权成功/失败、订阅失败、断线和指数退避重连。
- reader 退出不会自取消 supervisor。
- 断线后所有 pending Future 得到明确结果并被清理。
- 心跳超时、帧大小上限、未知 frame、重复 request ID。
- 进程优雅关闭、密钥轮换、多租户 Registry 隔离。
- 速率限制、背压和队列上限。

#### F. 数据库与迁移

- 空库从零迁移成功。
- 单版本失败后安全重试；checksum drift 被阻断。
- 生产环境不能执行 demo seed，不能创建固定演示用户。
- 角色无仓库已知密码；Worker 权限最小化。
- RLS、函数 owner、固定 `search_path`、schema grant 的 readback。
- 普通角色无法取得密码哈希或任意租户成员关系。
- `workflow` schema 未经设计不得由 Data API 暴露。

#### G. 运维脚本与供应链

- ShellCheck、`bash -n`、容器内 dry-run。
- 临时文件位于私有 `mktemp -d`，有 trap 清理，不跟随符号链接。
- 脚本输出快照经过 Secret Scan，确保无敏感值。
- 目标环境需要显式确认，失败返回非零且给出已完成步骤。
- 外部二进制固定版本、来源、SHA256/签名和 SBOM。

#### H. DSN 兼容

- 不同 query 顺序和 URL 编码下，传给 asyncpg/psql 的 DSN 均正确。
- Transaction Pooler 明确禁用 prepared statement cache。

## 13. 最终评价

`c1db39f` 的积极意义是把企业微信从“只有回调验证/占位发送”推进到了“存在应用 API 和 Bot 客户端骨架”。但当前修改把**协议可调用**误当成了**业务可交付**：报告生产者、用户绑定、收件人隐私、Outbox 原子性、幂等、回执、配置隔离和自动测试没有形成同一条可靠链路。

最重要的优化不是继续在 `_deliver` 中增加更多 if/else，而是先建立以下单向、可审计的主干：

```text
报告发布
  → 按租户订阅展开通知意图
  → 绑定解析生成逐用户 Delivery
  → 原子租约认领
  → 单一明确通道发送
  → 回执/不确定结果对账
  → 可观测状态与审计
```

在这个主干稳定后，应用消息、智能机器人、邮件和其他媒体才是可插拔通道；否则每增加一个通道都会放大重复发送、串租户和凭据扩散风险。
