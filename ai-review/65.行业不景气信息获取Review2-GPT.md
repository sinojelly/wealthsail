\## 二、新发现的高优先级问题



\### P1-1：风险“已确认”仍可能不代表经济事实已经确认



位置： `backend/macro/industry\_cycle.py:323-345`



当前逻辑大致是：



```

if (    check\["verification"] == "SOURCE\_CHECKED"    or check\["independentSourceCount"] >= 2):    check\["strength"] = "CONFIRMED"

```



问题在于，`SOURCE\_CHECKED` 只证明引用内容确实出现在网页原文中，并没有校验这段内容是否真正支持当前风险结论。



例如，模型错误地把一篇“机器人融资仍在增长，但个别公司融资困难”的文章标记为 `FINANCING\_COOLING`。只要原文引用通过校验，该项就可能成为 `CONFIRMED`。



同样，两个不同域名、标题不同的文章，也可能来自同一个原始报道，或者讲的是不同国家、不同细分行业、不同时间段。



目前独立来源计数器只检查域名与标题指纹，不能真正证明内容独立，更不能证明经济结论一致。



影响： 错误的 `CONFIRMED` 可触发20分扣减和1倍风险折价。



建议明确区分：



\- `SOURCE\_CHECKED`：原文引用已核实。

\- `CLAIM\_SUPPORTED`：原文确实支持具体风险判断。

\- `INDUSTRY\_CONFIRMED`：证据范围、趋势和行业代表性达到行业级确认条件。



这三个概念不能合并。



\### P1-2：商业化早期仍可能被错误升级为“已确认风险”



位置：



\- `industry\_cycle.py:350-395`

\- `industry\_cycle.py:437-469`



当前代码判断 `EARLY\_COMMERCIALIZATION` 时，主要检查是否存在相关 `evidence.kind`，但没有要求这些证据必须完成原文核验。



随后，风险策略中有：



```

early = cycle.get("stage") == "EARLY\_COMMERCIALIZATION"if confirmed or early or declared == "CONFIRMED":    level, scale = "CONFIRMED", 1.0

```



结果是：



模型把行业归为商业化早期，即使依据尚未核实，也可能形成：



\- `stage = EARLY\_COMMERCIALIZATION`

\- `riskLevel = CONFIRMED`

\- `leftDiscountScale = 1.0`



而且这里存在更深层的经济概念问题。



商业化早期不等于行业风险已经确认，更不等于泡沫出清。



例如，一个商业化早期但订单快速增长、现金充足、估值合理的行业，不一定应该受到最高等级的行业风险扣分。



建议：



1\. 产业兑现阶段仍独立展示。

2\. 商业化早期可以限制左侧建仓信心。

3\. 但不应自动等同于 `CONFIRMED` 行业衰退风险。

4\. 对未经核验的商业化阶段证据，阶段也应保持待核验。



这是本次 Gemini 设计本身需要修正的地方，不只是代码实现问题。



\### P1-3：财报盈利核验仍可能出现语义误判



位置： `industry\_cycle.py:98-149`



我检查了 `\_earnings\_fact\_clauses()` 的判定方式。



当前利润增长验证主要依赖同一句中同时出现：



\- 利润相关词；

\- 增长相关词；

\- 没有命中某些预测和否定关键词。



例如：



> 本季度公司净利润下降30%但营业收入增长5%。



这句话包含“净利润”和“增长”，所以现有正则表达式可能将其识别为 `PROFIT\_GROWTH`。



我用相同的关键词匹配条件做了独立验证，确实同时匹配。



如果同一份来源的另一句又描述了实际回款，那么两个不同子句就可能满足 `earningsVerified=True`，即使公司的利润实际上在下降。



另外，两句证据是否属于同一家企业、同一报告期、同一业务板块，也没有被结构化验证。



这是一个实际的事实判定漏洞，而不是仅仅缺少更多媒体。



建议改为抽取和验证明确的财务事实：



| 字段     | 例子        |

| ------ | --------- |

| 企业     | 某上市公司     |

| 指标     | 归母净利润     |

| 报告期    | 2026年三季度  |

| 当前值    | 具体金额      |

| 同比变化   | -30%      |

| 实际现金回收 | 独立指标      |

| 证据来源   | 财报或权威原始披露 |



不能用“同一子句里有利润、有增长”来认定净利润增长。



如果暂时无法结构化识别，应保留 `UNKNOWN`，不能自动升级为绿色业绩兑现。



\### P1-4：行业风险的解除条件过于宽松



位置：



\- `backend/macro/industry\_cycle.py:629-687`

\- `backend/macro/daily\_research.py:1227-1254`

\- `backend/macro/daily\_research.py:1803-1827`



这是本轮另外一个重要发现。



在 `persist\_industry\_risk()` 中，存在这样的条件：



```

if not isinstance(previous, dict) or result.get("earningsVerified") is True:    return result

```



也就是说，只要本次研究满足 `earningsVerified=True`，就不再继承此前确认的风险观察。



但这在经济上并不严谨。



例如：



\- 10月20日：机器人初创企业融资明显收缩，系统确认行业融资降温。

\- 10月21日：某家上市零部件企业披露净利润增长、实际回款良好。

\- 系统可能因此解除之前的融资降温风险延续。



一家上市公司盈利改善，不能证明一级市场融资已经恢复。



盈利兑现与融资降温可以同时存在。



正确的风险解除机制应该按风险类别独立处理：



| 原风险     | 应要求的解除依据           |

| ------- | ------------------ |

| 融资降温    | 同口径融资金额、笔数、融资成功率恢复 |

| 企业倒闭或裁员 | 行业企业经营及生存情况改善      |

| 下游砍单    | 真实新增订单、交付及复购恢复     |

| 产能过剩    | 库存、利用率、价格及毛利率改善    |

| 量产延期    | 实际量产、交付和客户验收       |



当期利润增长可以降低某些企业的投资风险，却不能直接清除所有行业风险。



建议将 `earningsVerified` 从统一解除条件改为辅助恢复证据，按 `riskFlag` 分别维护解除条件。



\### P1-5：缺失发布时间的风险证据仍有升级空间



位置： `industry\_cycle.py:77-92, 159-195, 323-345`



`\_source\_recency()` 在缺少发布时间时返回 `UNVERIFIED`。



但后续只有历史过期状态会强制把 `FOUND` 改为 `UNVERIFIED`。



因此，一条发布时间不明但完成原文核验的材料，仍有可能因为 `SOURCE\_CHECKED` 而成为 `CONFIRMED`。



这会导致旧文章被误当成近期行业降温的证据。



建议行业风险确认至少检查：



\- 发布时间；

\- 事件实际发生时间；

\- 财务数据所属报告期；

\- 对比基期；

\- 是否属于近90天的新变化。



特别是融资数据，必须比较同口径的时间区间。不能拿一篇2026年发表、讨论2024年融资困难的文章，直接证明2026年当期行业降温。



\## 三、还有哪些非阻断性但值得改进的问题？



\### P2-1：技术趋势参与评分与买区折价的规则不完全一致



`opportunity\_scoring.py:260-265` 已经把 `weakening` 和 `trendWeakening` 都纳入技术风险扣分。



但 `actionable\_zones.py:752-757` 只有在 `weakening=True` 时，才把0.5倍风险折价升级到1.0倍。



如果 Lower Highs 与20/60日负超额收益触发 `trendWeakening=True`，但 `weakening=False`，就可能出现：



\- 技术风险扣8分；

\- 左侧买区仍只折价0.5倍。



这不一定是错误的投资规则，但与“技术走弱和产业风险共振加大折价”的整体意图不完全一致。



应明确是只允许MA60破位升级折价，还是所有确认的技术走弱都可以升级。不要让两个模块隐含不同定义。



另外，三个20日窗口最高价依次下降，只能严格称为区间高点下移，不能直接证明出现了三个真正的反弹高点。



\### P2-2：最多10个赛道可能遗漏最重要的负面风险



现在的优先级主要考虑：



1\. 当日存在催化新闻。

2\. 基金已经进入买区。

3\. 距离买区较近。



但最需要发现的行业衰退风险，并不一定伴随着当日正面催化或接近买点。



例如，某行业连续出现负面产业新闻，但不在当前10个候选里，仍可能被遗漏。



建议增加独立的风险优先级，尤其关注持有中的基金、已有高风险观察的赛道，以及上一轮未完成核查的行业。



而且要在日报中展示被跳过的赛道数量及原因，不能只把 `omittedCandidateCount` 留在研究任务内部。



\### P2-3：50次搜索与24条来源的容量仍不协调



目前最多产生50个查询，但最终报告仍限制24条来源。



即使模型进行了所有搜索，也可能无法保留充分的行业证据。



可以考虑将行业反方搜索结果独立于日报正文来源预算保存。



这样既不用增加主报告长度，又能保留完整检索证据。



\### P2-4：风险强度阈值缺乏历史验证



当前采用：



\- 已确认行业风险：扣20分。

\- 待核实或未兑现：扣10分。

\- 技术走弱：扣8分。

\- 总扣分封顶25分。

\- 买区下移0.5倍或1.0倍风险尺度。



实现本身是明确且可测试的，但这些数字仍属于经验规则，不是经过验证的市场统计规律。



特别是降低买区并不一定降低风险。泡沫出清期间，企业盈利预期和合理估值可能持续下降，原来用历史波动率计算的支撑位也可能失效。



建议历史回测比较：



\- 无行业风险保护。

\- 只有评分扣减。

\- 评分扣减加0.5倍折价。

\- 评分扣减加1.0倍折价。

\- 高风险时暂停左侧买入，等待右侧确认。



评估最大回撤、错误抄底次数、风险调整后收益，以及错失反弹机会的比例。



不能预先认定1.0倍一定比0.5倍更安全、更有效。



\### P2-5：前端风险标记仍可能让用户误解



前端现在已经能够显示五项核查、来源和证据强度，这是实质性进步。



但 `IndustryCycle.tsx` 把 `NONE` 显示成：



`行业风险：未触发`



对于未真正证明五次搜索执行、或者资料不足的行业，这个提示容易被理解为“行业没有风险”。



建议显示：



`本轮未确认行业风险 · 检索覆盖待核实`



同时把 `searchExecutionVerified` 显示出来，让用户清楚区分研究覆盖情况和风险判断结果。



\## 四、可靠性和性能的评价



新缓存比原先的建议实现更谨慎。



`live\_fund\_plans.py:284-329` 不只依据基金代码、日期和样本数量判断缓存，还计算价格及基准数据指纹。这样能避免同日期价格修订后继续使用旧指标。



同时，缓存命中时返回深拷贝，进程缓存最多256项；价格时效与申购限制等规则在后续读取流程中重新应用。



这些都属于正确的工程防护。



14天风险延续也有相应的原始时间戳保护，避免单纯通过重复继承持续延长有效期。



所以我没有发现必须推翻新缓存和风险延续机制的理由。



但完整生产可靠性仍未验证。尤其需要重点测试：真实日报历史数据、连续多日未找到结果、跨周末到期、报告读取时重新评分，以及风险解除后各页面是否保持一致。



测试方面，仓库里已经补充了 `test\_industry\_cycle\_strength.py`、`test\_relative\_strength\_risk\_tiers.py`、`test\_industry\_research\_performance.py` 等针对性测试。



不过这些测试中有些逻辑与现有实现具有相同的假设，例如测试明确允许“商业化早期加待核实融资报道”最终形成 `riskLevel=CONFIRMED`。所以测试通过不能证明这个经济分类合理。



你提供的4164项后端通过、509项前端通过属于本次提交的验证报告；我检查了连接工作区的执行记录，当前没有可读取的测试执行输出，不能把这些数字说成我已独立复跑验证。真实生产联网和数据库联调也尚未完成。

\## 六、Review 结论



\## 本轮仍建议修改，但不需要推倒重来



设计符合度



较高



代码组织与测试覆盖



较好



经济风险判断准确性



仍需加强



生产数据可靠性



尚未验证



相比 `d001286` 和 `6cc81d6`，现在这两个新提交值得保留。没有从静态审查中发现需要立即撤销提交的系统级问题。



但我不建议现在就部署为可信的自动行业风险判别系统。



目前最危险的已经不是评分计算和买区下移代码，而是前端显示“行业风险已确认”时，底层经济证据未必真的足以支持这种结论。



我的建议是先集中修复上面五项 P1 的证据和经济语义问题，再补上实际搜索执行凭证。真实持仓暴露模型可以作为后续单独迭代，不必为了它再次改动整个投研框架。



这次整改的核心原则应当是：



没有证据不能认定安全；有负面新闻不能认定整个行业衰退；有一家企业盈利也不能认定整个行业风险解除。



这样才能让 WealthSail 从“带风险关键词的投研系统”，进一步成为真正具有经济证据判断能力的投资研究工具。
