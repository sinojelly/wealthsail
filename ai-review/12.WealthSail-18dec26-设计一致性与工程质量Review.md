## 1. 结论摘要

`18dec26` **不建议作为可部署、可验收的独立提交发布**。它不是单纯的“企业微信绑定”改动，而是同时引入了企业微信绑定 UX、数据库角色切换、手工持仓增删改、标的搜索、市场情绪、AI 操作建议、调度时间变更、临时推送、Supabase Provision、开发启动脚本和 UI 冒烟脚本，共修改 46 个文件、增加约 4,068 行。提交标题与真实范围严重不匹配，导致评审、回滚和故障定位成本显著上升。

总体判断如下：

| 维度 | 结论 | 说明 |
| --- | --- | --- |
| 可发布性 | **不通过** | `18dec26` 同时存在两个 `014` migration，CI migration discovery 必然失败；Python lint 也失败 |

## 3. 做得正确、应保留的设计

这次提交并非全部需要推翻，下列实现方向是正确的，后续修复时应保留：

1. **显式 API 运行时角色**：`backend/common/database.py:134-150` 新增 `api_system_transaction`，把登录、注册、刷新令牌等身份操作收敛到事务级 `SET LOCAL ROLE wealthsail_api`，比依赖连接默认角色更稳定，也能避免事务池连接的残留会话状态影响身份操作。
2. **本人绑定状态与软解绑**：`backend/identity/api.py:193-219` 和 `backend/identity/service.py:592-664` 使用登录态 tenant/user 过滤，解绑要求口令二次认证，采用 `REVOKED` 软撤销并写审计，符合“本人管理、保留历史”的主线。
3. **外部行情 I/O 放在持仓写事务外**：`add_position` 先抓行情再进入 tenant transaction，避免把不可控网络等待放入写事务；这一原则应推广到 AI 建议和情绪抓取。
4. **金融数值继续使用 Decimal/NUMERIC**：持仓数量、成本、价格和收益没有改用二进制 float，API 继续返回十进制字符串。
5. **行情不可用时不虚构价格**：新增持仓在行情失败时返回 `UNAVAILABLE` 和空价格，而不是用成本价冒充实时价。
6. **持仓变更写审计并重建投影**：虽然事件语义选错了，但“不可直接改 snapshot、通过领域事件重建投影”的方向正确。
7. **Outbox retry 权限修复合理**：`014_wecom_binding_push_fix.sql` 把重试路径实际更新的 `available_at` 补入 Worker 列级授权，与 `_cas_retry_or_dead` 的行为一致。
8. **前端沿用统一 API/React Query/Dialog 体系**：新增功能没有绕过现有 client、私有 query key 和无障碍 Dialog 基础组件。

后续应在这些正确骨架上修正领域语义、安全边界和性能实现，而不是把丰富的功能说明或现有模块化单体结构整体删除。

## 4. P0：立即处置/发布阻断问题

### P0-01：仓库包含疑似真实账号明文口令，并通过 HTTP 登录且写入持仓

**位置**：`frontend/scripts/ui-smoke.cjs:4,17,21-22,35,41-43`
**当前 master**：仍存在。

脚本把公网地址、账号和明文口令直接提交到 Git，并使用明文 HTTP 登录。成功后脚本还会选择具体股票、写入数量和成本并点击“确认添加”。这同时造成三类风险：

- Git 历史、镜像、备份、协作者副本均可取得登录凭据；
- HTTP 链路可能泄露账号、口令、access/refresh token 和返回的个人资产信息；
- 每次运行都会向疑似真实环境追加持仓，污染不可变账本、现金流、收益和后续 AI 分析。

这不是普通测试代码可读性问题，而是必须立即响应的凭据与数据完整性事件。

**立即措施**：

1. 立即修改该账号口令、撤销全部 refresh session，并检查登录、持仓、审计和绑定记录；
2. 将真实环境强制切换 HTTPS，禁止脚本访问 `http://`；
3. 从当前文件移除地址、账号和口令，只接受环境变量或 CI Secret，并要求测试账号为可丢弃的专用 tenant；
4. smoke 默认只做只读断言；若必须写数据，使用专用 fixture、固定幂等键和可靠清理/冲正，不触碰真实组合；
5. 在协调备份与协作者后，再决定是否使用 history rewrite 清理历史。历史重写有破坏性，本次 Review 不直接执行；
6. CI 增加 secret scan 和“测试代码不得包含公网生产目标/明文口令”的规则。

报告中不复述明文口令，避免二次扩散。

### P0-02：两个 `014` migration 使该提交无法部署

**位置**：`migrations/014_tmp_2130_test_push.sql`、`migrations/014_wecom_binding_push_fix.sql`
**当前 master**：重复编号已由后续提交修复；`18dec26` 快照仍不可部署。

`scripts/migrate.py::load_migrations` 明确拒绝同一版本号。本次快照运行 CI 同款命令稳定得到 `duplicate migration version: 014`，因此 `015` 和 `016` 也不可能进入部署流程。

## 5. P1：发布前必须修复的问题

### P1-01：手工持仓被伪造成真实 `BUY + CASH_IN`，破坏经济事实与收益率

**位置**：

- `backend/portfolio/service.py:479-500`：新增持仓写 `CASH_IN` 和 `BUY`；
- `backend/portfolio/service.py:654-695`：编辑先清旧、虚构 `CASH_OUT`，再重建并虚构 `CASH_IN`；
- `backend/portfolio/service.py:757-775`：删除持仓写清仓 adjustment 和成本额 `CASH_OUT`；
- `backend/portfolio/repository.py:247-436`：直接创建 `CONFIRMED` BUY/CASH/ADJUSTMENT。

这与既定设计直接冲突：`docs/03` 与 `docs/06` 要求新用户持仓录入先形成 `portfolio_import_batches/items(DRAFT)`，用户确认后形成期初 `ADJUSTMENT` 基线，**不得虚构 CASH_IN、BUY 或 fill**。当前实现把“用户告诉系统现在持有 100 股、平均成本 1,500”解释成“系统确认在某日真实买入并入金”，这是不能从输入推出的事实。

后果包括：

- 本金、现金余额、累计收益、TWR/IRR 前置数据和交易复盘失真；
- 编辑成本价会制造退出旧本金、注入新本金的假历史；
- 删除持仓会按历史成本制造现金流出，既不是卖出回款，也不是冲正；
- AI 建议和报告会在错误的经济事实之上继续推理。

**正确方案**：

1. “初始化/手工对账”采用 `portfolio_import_batch(DRAFT) -> preview -> CONFIRMED opening ADJUSTMENT`；
2. “真实发生的交易补录”采用 `trade_fill(DRAFT) -> 用户二次确认 -> BUY/SELL ledger event`；
3. 更正已确认基线采用 `REVERSAL + 新 ADJUSTMENT`，保留来源、操作者、原因、版本和前后关联；
4. 不自动创建与该事实无关的 `CASH_IN/CASH_OUT`；现金未知时显式标记账户起始现金/本金口径未知；
5. API/UI 明确区分“初始化持仓”“补录真实成交”“更正持仓”“冲正”，不能统一称为“添加/编辑/删除持仓”。

### P1-02：VIEWER 也可以新增、编辑和删除持仓/账本

**位置**：`backend/portfolio/api.py:104-150`、`migrations/016_manual_holdings.sql:26-37`
**当前 master**：仍存在。

`TenantContext` 已提供 `require_roles`，但三个持仓写接口没有调用。Migration 的 INSERT policy 只检查 `identity.is_tenant_member(tenant_id)`，没有检查 OWNER/ADMIN/EDITOR。只要是 active member，包括 VIEWER，就能调用 Domain API 写入不可变账本并重算资产。

这违反 `docs/06`“active member 可读、EDITOR 以上才修改允许资源”的权限基线，也让应用层授权和 RLS 同时缺失角色约束。

**修复**：

- command 入口统一 `ctx.require_roles("OWNER", "ADMIN", "EDITOR")`；
- 数据库 policy 使用可复用的 role-aware helper，避免只验证 membership；
- VIEWER 的 POST/PATCH/DELETE 全部做 API + PostgreSQL 集成测试；
- 审计记录真实 command/event UUID，不使用幂等字符串冒充 `resource_id`。

### P1-03：绑定能力从 ≥128 bit 降为约 30 bit，且“每挑战 5 次”对错误猜测不生效

**位置**：

- `backend/common/security.py:30-41`、`backend/identity/service.py:438`；
- `migrations/011_identity_privileged_helpers.sql:48-67`；
- `docs/10` 本提交将 128-bit 章节改为 6 位短码。

其他权威文档仍要求至少 128-bit 一次性能力：`docs/03`、`docs/06`、`docs/07`、`docs/09`。`docs/10` 不能在没有 ADR、威胁分析和跨文档同步的情况下静默降低安全基线。

更关键的是，现有 `consume_binding_challenge` 先按 `token_hash` 查找 challenge。错误猜测查不到任何 challenge，直接抛 `BINDING_TOKEN_INVALID`，不会增加某个 challenge 的 `attempt_count`。只有猜中正确 token 后才会加 1，而第一次猜中已经完成绑定。因此“15 分钟 + 每挑战 5 次”的风险计算并不成立。

**推荐**：

- MVP 继续使用 ≥128-bit 可复制 token/二维码/深链，Web 提供一键复制；
- 若必须使用短码，协议必须加入公开 challenge identifier、按 external user/IP/tenant/global 的持久限速、失败计数、防重放消息 ID、告警与熔断，并重新计算总体在线猜测概率；
- 绑定回调补 `MsgId + nonce + timestamp` 去重，不能只校验 5 分钟时间窗；
- 增加 token 大小写/空格归一化、过期、并发消费、错误猜测、限速、撤销后重绑的真实数据库测试。

### P1-04：未认证的市场情绪 GET 会触发慢外部抓取和高权限数据库写

**位置**：`backend/market/api.py:35-49`、`backend/market/service.py:428-469`、`backend/integrations/market_data.py:944-1046`
**当前 master**：仍存在。

`GET /api/v1/market/sentiment` 没有 `get_tenant_context` 或其他认证依赖，却会：

1. 拉取全市场 AkShare 快照；失败时并发翻页访问新浪，注释承认可能耗时 10～20 秒；
2. 每次继续尝试北向资金抓取；
3. 使用 API pool 的 `system_connection` 写 `market.market_sentiment`，没有显式切换 `wealthsail_api`；
4. 前端每个登录用户每 5 分钟自动调用一次。

任意网络访问者都可反复触发 Provider、线程、CPU、连接和数据库资源消耗。若 API 登录凭据仍是 `postgres`，`system_connection` 还会直接使用超出 API 边界的默认数据库权限。

**修复架构**：

- Worker 按交易时段或固定 TTL 单飞刷新并写 source snapshot/observation；
- API 只认证后读取最近快照，使用显式 least-privilege API role，不在 GET 请求里做 Provider 写刷新；
- 增加 Redis/进程级 single-flight、TTL、超时、并发和频率预算；
- 返回 `quality/source/asOf/retrievedAt/coverage/methodVersion`，过期时明确 STALE；
- 对匿名请求、并发 50/100 请求、Provider 超时、部分分页失败做负载与降级测试。

### P1-05：Provision 默认把 API 与 BYPASSRLS Worker 能力都授予 `postgres`，分权只剩自我约束

**位置**：`scripts/provision_supabase_roles.sql:14-70`、`docs/10` 新增 8.1.1
**当前 master**：仍存在。

脚本把 `wealthsail_api` 和 `wealthsail_worker` 都授予同一个 `postgres` 登录，并把它作为默认用法。`wealthsail_worker` 具有 BYPASSRLS；同一登录凭据同时被 API 和 Worker 使用时，API 进程实际上持有切换到 Worker 的能力，`SET LOCAL ROLE wealthsail_api` 只是代码自我降权，不能构成可靠的凭据边界。

**正确方案**：

- 创建独立 `wealthsail_api_login`、`wealthsail_worker_login`、`wealthsail_migration_login`；
- API login 只能 SET API role，绝不能成为 Worker role 成员；
- Worker login 只持 Worker 所需能力，不持用户 JWT secret；
- Migration login 不用于运行时；
- API/Worker 使用不同 Secret、连接串、pooler 模式和容器 env；

## 6. P2：下一轮重构应完成的问题

### P2-01：搜索和投影重算存在明显的请求放大

- 前端每输入一个字符立即发 search 请求，没有 debounce/minimum useful length；
- 每个请求在后端并发运行 A 股、ETF、场外基金三次全量 AkShare DataFrame 拉取，单次最长 15 秒；输入 `600519` 可能产生 6 × 3 份抓取；
- `_ak_spot_cached` 没有 single-flight lock，缓存失效瞬间会并发回源；
- 每次持仓增删改在写事务内重放该 tenant 全部确认事件并重建全部当日 position/NAV snapshot，复杂度随历史和账户增长。

应增加 300～500 ms debounce、代码搜索最小长度、服务端缓存/single-flight、Provider 专用搜索接口、取消/限速；投影改为 command 写事件后按受影响 account/instrument 增量更新或投递异步 projection job，并保留全量 replay 作为校验/修复工具。

### P2-02：`market_sentiment` 数据表和计算缺少金融数据治理字段

`migrations/015_market_sentiment.sql` 只有每日数值，没有 `source_id/snapshot_id/as_of/retrieved_at/quality_status/coverage/method_version/revision`，也没有非负、score 0～100、up/down/flat 一致性等 CHECK。一天只有一条记录，多个 Provider 会互相覆盖且无法复现。

算法又用统一 ±9.8% 近似涨跌停，无法处理 ST 5%、主板 10%、创业板/科创板 20% 和新股规则；新浪部分分页失败会得到不完整样本，但仍被当成 live；`date.today()` 依赖服务器时区而不是 Asia/Shanghai 交易日。

建议复用 `source_snapshots + market_observations`，情绪作为带版本的 derived observation；保存样本总数/覆盖率/板块规则版本/Provider；数据不完整时标记 STALE/UNAVAILABLE 或弃权，不输出貌似精确的 score。

### P2-03：前端错误、刷新和幂等语义不完整

- Dashboard 全局错误只收集 summary/positions/nav，忽略 sentiment/advice；Provider/模型失败会被误显示为“暂无建议/暂无评分”；
- 持仓变更只 invalidate positions/summary/nav，没有 invalidate advice，用户改完持仓后可能继续看到旧建议；
- add/update 每次点击提交才生成新的 UUID，网络结果不明后再次点击会使用新键，无法阻止重复命令；delete 完全没有幂等键；
- `todayIso()` 使用 UTC，上海时间 00:00～07:59 会得到前一天；
- 删除只用浏览器 `window.confirm`，没有展示账户、影响、冲正语义和二次认证；
- 搜索 listbox 缺完整键盘选择/`aria-selected` 语义。

建议为一次用户意图在表单初始化时生成并复用 idempotency key；服务端保存请求摘要并对同键同 payload 返回原结果、同键异 payload 冲突；明确 error/empty/stale/abstain；持仓/报告/政策变更联动失效 recommendation query。

### P2-04：Outbox 从“租户内有效绑定逐用户展开”改成只发 acting user，需求语义未澄清

`backend/reports/repository.py` 新增 `user_id` 过滤，测试也从两个用户应生成两条 delivery 改成只验证一人。定时任务使用 tenant OWNER 作为 acting user，因此同一 tenant 的其他有效成员可能永远收不到四时段报告。这与 `docs/10`“按有效 binding 展开逐用户 Outbox”表述不一致。

需要先明确产品模型：

- 如果每个试点用户各自一个 tenant：明确 job/report recipient 就是该 tenant 的 owner；
- 如果一个家庭 tenant 有多个成员：增加 per-user subscription、可见账户范围、个性化报告和 recipient 选择，不能用“acting owner”隐式代替所有收件人。

测试至少覆盖 A/B 用户、撤销 binding、一个用户多个 binding、群聊/`@all`、部分投递失败和不同订阅偏好。

6. 同标的跨账户、同代码跨市场、并发创建和冲正后的账本/投影对账通过；
7. 绑定 ≥128-bit，或短码具备经测试的持久失败计数、限速、防重放和并发单次消费；
8. sentiment API 不触发外部刷新；Provider 失败/部分数据明确 STALE/UNAVAILABLE；
9. recommendation 每条都有关联 evidence、as_of、policy/model/method version，陈旧或缺政策时 ABSTAIN；
10. 模型/Provider 调用不持有数据库事务；连接池并发和超时测试通过；
11. 真实企业微信 2～3 用户完成绑定、撤销、定向收件人、重复回调、UNKNOWN 和 Outbox 恢复 E2E；
12. 四时段实际运行时间与需求一致：08:30、盘中、14:30、15:30，不再包含临时 session。

---

## 11. 最终判断

`18dec26` 的积极价值在于：它把企业微信绑定状态、本人软解绑、显式 API 角色、手工持仓 UI、市场情绪和建议卡片快速串成了可见功能，并延续了模块化单体、tenant transaction、Decimal、审计和投影重建等正确骨架。

但当前实现把“功能跑通”放在了“金融事实可信、安全边界和正式工作流”之前。尤其是明文真实凭据、虚构 BUY/CASH_IN、VIEWER 可写账本、无效的 30-bit 绑定码控制、公开慢刷新、高权限角色共用以及未经风控/证据校验的加减仓建议，都会直接影响真实用户资产数据和投资判断。

因此建议结论为：**保留正确骨架，暂停扩展新功能，按阶段 0～2 先修复安全与可信数据主线；这些 Gate 通过后，再进行性能与可维护性拆分。**
