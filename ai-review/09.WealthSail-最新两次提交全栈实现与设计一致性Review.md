## 1. 结论先行

### 1.1 总体结论

这两个提交已经搭起了一个可运行的“模块化单体 API + 独立 Worker + React Web + PostgreSQL/Supabase”骨架，`backend/` 的方向是正确的，也比重新回到根级 `modules/`、`adapters/` 或全局 controller/service/repository 横向分层更符合当前 2–3 用户 MVP。

但当前只能评价为：**结构方向基本遵循设计，核心业务语义、权限边界、任务可靠性和生产部署尚未遵循设计，不能按 MVP 完成或可发布状态验收。**

最需要警惕的不是“功能少”，而是若干页面和数据链路已经显示“已确认、已入账、已投递、数据新鲜”，实际却只修改浏览器状态、使用不完整投影或根本没有外部投递。这会直接损害投研助手最重要的可信度。

| 维度 | 结论 | 是否可按 MVP 验收 |
|---|---|---|
| 后端目录与模块化单体 | 方向正确，实际目录比旧方案更简洁 | 部分可验收 |
| 股票、场内基金组合读取 | 已有 API/行情/组合骨架，但金融事实重建有错误 | 不可验收 |
| 场外基金与 14:30 报告 | 只取最近披露净值，没有盘中估值、覆盖率和不确定性 | 不可验收 |
| 四时段报告 | 有调度与生成骨架，但交易日、时区、幂等、恢复均不可靠 | 不可验收 |
| 企业微信交互 | 回调/绑定有原型，主动投递始终 `NotImplementedError` | 不可验收 |
| 多用户/多租户 | RLS 基础已接入，但角色、缓存、数据库 GRANT 存在边界缺陷 | 不可验收 |
| 数据可信与证据链 | 后端和前端都存在伪造/默认提升 provenance 的行为 | 不可验收 |
| Docker/生产部署 | 有 Compose 骨架，但与 docs/10 的凭据、TLS、入口设计冲突 | 不可验收 |
| 自动化测试 | 前端单测/构建可运行；Python 测试当前无法完成收集，无 CI | 不可验收 |

### 1.2 做得正确、建议保留的部分

以下内容是正确的“血肉”，后续修复时不应删除：

1. `backend/main.py` 与 `backend/worker.py` 分开在线 API 和后台任务进程，符合 docs/10 的运行进程划分。
2. `backend/identity`、`portfolio`、`market`、`risk`、`reports`、`chat`、`operations`、`jobs`、`integrations` 按领域组织，比过度拆分的小服务更适合 MVP。
3. 普通 API 请求通过 `tenant_transaction()` 设置事务级角色与租户声明，RLS 作为第二道隔离防线，方向正确。
4. 报告生成把“读取上下文”和“外部模型调用”分成两个阶段，报告路径没有长期占用数据库连接；这个模式应复用于 Chat。
5. 金额 DTO 大部分以 Decimal 字符串输出，图表转换集中在前端适配层，基础金融精度意识是正确的。
6. 报告、模型运行、Outbox、审计在同一持久化事务内创建，保留了可靠事件发布的正确雏形。
7. 前端目录、lazy route、API hooks、功能页面组织基本符合 docs/09 的组件结构；没有把 access token 写入 localStorage/sessionStorage。
8. 外部行情不可用时已有 `UNAVAILABLE` 数据结构，而不是直接伪造实时值。问题主要出在后续聚合和投影没有完整保留它。

### 1.3 两个提交分别带来的结果

这是主体实现提交，新增 117 个文件、约 1.3 万行。优点是一次性补齐了 API、Worker、迁移、前端对接和测试骨架；问题是提交粒度过大，需求、权限、金融口径、部署和测试没有逐 Gate 收敛，导致“页面看起来完整”和“领域事实真实完成”混在同一提交中。

该提交引入了本文绝大多数 P0/P1 问题：数据库角色过宽、公开注册、演示凭据进入正式迁移、行情投影口径、调度与 Outbox、假确认 UI、前端缓存隔离、部署凭据不分离等。

该提交只改动 4 个文件，主要增加新闻聚合、Chat 新闻上下文、新闻相关单测和一张头像文件。它没有修复 `97a5413` 的核心 Gate，反而新增或扩大了以下风险：

- 头像在生产 Nginx 路由下仍不可访问，且容器重建会丢失，提交图片只掩盖了存储设计缺失。

## 2. 是否遵循 docs/10 及相关设计

### 2.1 设计一致性矩阵

|---|---|---|
| 单一 `backend/` 模块化单体 | 基本遵循 | 实际目录已经采用纵向领域切片，方向正确 |
| API/Jobs → Service → Repository/Integration | 部分遵循 | 多数模块遵循；`risk/service.py`、`chat/service.py` 等仍直接写大量 SQL，`risk/service.py:20` 还导入 portfolio 私有 `_d` |
| `Decimal`/`NUMERIC` 全链路 | 未完全遵循 | `chat/service.py:266-274,314` 用 `float` 格式化金融值；docs/10:125 明确禁止 |

| API/Worker 凭据隔离 | 不遵循 | docs/10:447-476 要求 `api.env`/`worker.env` 分权；Compose 两者都加载 `.env`，注册 API 还直接使用 `worker_database_url` |

### 2.2 后端目录是否符合“更少拆分”的建议

**基本符合。** 当前实际目录比 docs/10:81-109 的目标树更适合 MVP，不建议为了形式一致再创建空的 `research/`、`deployment/` 或把每个领域强制拆成 `schemas/service/repository` 三件套。

建议把权威 MVP 目录统一为：

```text
backend/
├── main.py
├── worker.py
├── config.py
├── common/
├── identity/
├── portfolio/
├── market/
├── risk/
├── reports/
├── chat/
├── operations/
├── jobs/
└── integrations/
```

需要修正的是：

- docs/10 写的是 `reporting/`，实现是 `reports/`，必须选一个；建议保留已经落地的 `reports/`；
- `research/` 是 L3/L4 扩展点，MVP 不应创建空壳；
- 部署文件目前在仓库根和 `frontend/`，docs/10 却写 `deployment/`，应选择并统一，不应同时维护两套路径；
- 只有当 DTO/SQL 复杂度明显增加时再增加领域内 `schemas.py`、`repository.py`；不要回到全局横向分层。

## 3. P0：发布前必须修复的问题

> 这里的 P0 是 MVP 发布 Gate 优先级，不等同于安全漏洞 CVSS 严重度。

### REV-P0-01：数据库信任边界被 migration 009 破坏

**证据**

- `migrations/009_domain_api_write_policies.sql:41-48` 对所有列出的系统表创建只检查 tenant membership 的 INSERT policy；
- `migrations/009_domain_api_write_policies.sql:78-106` 直接给 `authenticated` 报告、模型、任务、Outbox、审计、binding、持仓和 NAV 写权限；
- 文件注释声称生产浏览器角色“no-op”，但 SQL 没有任何环境条件；
- docs/06:502 明确要求投影、报告、Workflow 和审计只能由 Domain API/Worker 写入。

**影响**

在 Supabase Data API/RPC 可达的部署中，普通 tenant member 可以伪造本 tenant 的报告、审计、Outbox 或资产投影。即使不造成跨租户泄漏，也会彻底破坏投资数据可信度。

**修改方案**

1. 建立 `wealthsail_browser`、`wealthsail_api`、`wealthsail_worker` 三类数据库身份；
2. 浏览器角色只拥有明确 DTO 所需的最小 SELECT，且生产前端不直连系统事实表；
3. API 角色只执行受控 Domain command，Worker 才拥有跨 tenant 调度和投影能力；
4. migration 中不能靠注释表达环境差异，必须由不同角色、不同迁移入口或显式环境脚本实现；
5. 部署后执行 GRANT、RLS、FORCE RLS、function owner 的自动 readback。

**验收**

- 浏览器 JWT 对所有系统事实表 INSERT/UPDATE 均失败；
- API/Worker 只能完成各自职责内的操作；
- 每个新增 tenant 表缺 RLS/GRANT 测试时 CI 失败。

### REV-P0-02：认证、封闭试点与演示凭据互相冲突

**证据**

- docs/07:19 规定 2–3 用户封闭试点、只允许受邀用户、禁止公开注册；
- `backend/identity/api.py:46-58` 暴露无认证 `/register`；
- `backend/identity/service.py:145-200` 在 API 进程中用 Worker DSN 创建 tenant 和 OWNER；
- migration 012 把固定演示口令写入正式编号迁移，并把 credential helper 授权给 `authenticated`；
- `frontend/LoginPage.tsx:59-63,191-195` 在生产 bundle 中公开演示凭据；
- `migrations/012_identity_password_auth.sql:27-58` 的 `SECURITY DEFINER` 函数向 `authenticated` 返回任意邮箱的 password hash。

**修改方案**

- MVP 只实现 invitation/allowlist 注册；邀请必须一次性、过期、限 tenant、可审计；
- API 不持有 Worker DSN，注册写入通过最小权限 bootstrap command 完成；
- password hash 验证留在私有认证边界，不把 hash 返回给浏览器数据库角色；
- `010/012` 中演示用户、演示密码移入 `seeds/dev/`，生产 migration 和生产 bundle 不包含；
- 生产启动检测默认 JWT secret、演示账号、开发模式和错误数据库角色并 fail closed。

### REV-P0-03：资产投影不是从已确认经济事实可靠重建

**证据**

- `backend/market/repository.py:153-162` 从旧 `position_snapshots` 取数量/成本，而不是从不可变 ledger/fill/import facts 重建；
- 缺报价时 `repository.py:165-167` 直接 `continue`，当日快照中该持仓消失；
- `repository.py:228-241` 把 `PENDING` ledger event 计入现金和本金，违反“只有 CONFIRMED 产生经济效果”；
- `unavailable_value` 被查询但没有用于 NAV 完整性判断；缺价资产被遗漏后，剩余子集甚至可能被标成 `FRESH`；
- 账户列表来自 position snapshot，纯现金账户不会生成 NAV；
- docs/09:170、191 要求缺失估值时整体 `UNAVAILABLE` 且不得按零或遗漏。

**正确方案**

投影输入应统一为“已确认 ledger/import/fill + 当前有效 instrument + 最新估值 observation”。每一个已确认持仓都必须产生当日 projection row：

- 有报价：写价格、市值及来源质量；
- 无报价：保留数量/成本，价格和市值为空，质量 `UNAVAILABLE`；
- NAV 返回可估值金额、不可估值资产数、覆盖率和整体质量；
- 任何 `PENDING/DRAFT` 不影响资产、现金、收益率；
- 同一算法可从零重放得到同一 projection。

### REV-P0-04：MVP 必需的场外基金 14:30 报告没有实现

`backend/integrations/market_data.py:618-681` 只读取东方财富最近披露净值。文件顶部也承认盘中估值接口未使用。这不能支持基金 14:30 报告，尤其缺少：

- 当日估值涨跌、估值时点和 method；
- 基金持仓披露日期、持仓覆盖率和现金/未知仓位；
- 估值区间/不确定性、停牌或跨市场时差；
- 与最近正式 NAV 的偏差；
- 场外基金申赎截止时间、报告有效期；
- 数据不可用时的 ABSTAINED/UNAVAILABLE 分支。

建议 MVP 先做可解释的 deterministic estimator，不要直接让模型猜净值：`最近披露持仓 × 标的当日收益 + 现金/未知仓位保守项`，输出 coverage、as_of、method、uncertainty；覆盖率不足时弃权。

### REV-P0-05：四时段 Scheduler/Job lease 不可靠

**证据**

- `scheduler.py:64-76` 定义了 `is_trading_day()`，但 `_tick()` 从未调用；
- `scheduler.py:118` 使用 naive `datetime.now()`，容器时区改变会错 8 小时；
- `_last_fired` 只在内存，重启或多 Worker 会重复执行；
- `runner.py:28-29` 的 job key 包含秒，重启后的同一业务时段会产生不同 key；
- `claim_stale_runs()` 只是把任务置 `FAILED`，没有恢复/重试同一业务 key，也没有 heartbeat/lease owner CAS。

**修改方案**

- 使用 timezone-aware Asia/Shanghai 时间和权威交易日历；
- 持久化业务唯一键：`tenant_id + job_id + trade_date + session`；
- job_run 使用 `lease_owner/lease_until/heartbeat_at/attempt/next_retry_at`；
- claim 用单条原子 SQL，完成/失败用 lease token CAS；
- 重启扫描 due/misfired 任务并按 policy 补跑，非交易日明确 SKIPPED；
- 多 Worker 并发测试只允许一个有效运行。

### REV-P0-06：Outbox 既不能安全 claim，也没有企业微信主动投递

**证据**

- `outbox.py:27-41` 的 `FOR UPDATE SKIP LOCKED` 不在显式 transaction 中；SELECT 结束后锁可能已经释放，多 Worker 可重复处理；
- 外部投递在同一连接循环内执行，锁和慢网络耦合；
- `outbox.py:76-87` 无论是否配置 CorpSecret 都最终抛 `NotImplementedError`；
- binding 只保存不可逆 HMAC，没有 docs/10:146 要求的 Worker 可解密路由值；
- 因而盘前、盘中、14:30、盘后报告无法主动送达企微。

**推荐状态机**

1. 短事务原子 `UPDATE ... WHERE ... FOR UPDATE SKIP LOCKED RETURNING`，把记录改为 SENDING 并写 `claim_token/lease_until`；
2. 提交事务并释放连接；
3. 调用企微，使用 tenant/topic/business idempotency key；
4. 用 `id + claim_token` CAS 标为 SENT 或 PENDING/DEAD；
5. 对“请求发出但响应未知”先按外部幂等/readback 判断，不直接盲重试；
6. routing ciphertext 只允许 Worker 解密，API/浏览器不可读。

### REV-P0-07：前端把演示状态伪装成真实金融事实

这是投资产品的信任红线。

- Dashboard 使用硬编码 pending fills 和现金，确认只在浏览器 `filter()` 删除行（`DashboardPage.tsx:29-41,120-123`），却会让用户理解为已经入账；
- Risk preview 生成 `sha256:demo-*`，任意非空口令即可显示“策略已确认并启用”（`RiskPolicyPage.tsx:39-51,65-69`）；
- WeCom “模拟确认”由浏览器自行生成 external ID；“解除绑定”只修改本地 state（`WeComBindingCard.tsx:64-76,243-249`）；
- 后端 risk API 只有 GET（`backend/risk/api.py:16,29`），不存在正式 preview/confirm command。

接口未实现前，应禁用按钮并明确显示“演示/尚未接入”，不能显示“已入账、已确认、已撤销、消息已停止”。正式实现必须由服务端返回版本、审计、幂等结果和 projection cursor。

### REV-P0-08：多用户会话可能展示上一个 tenant 的缓存

docs/09:431 要求 Query Key 第一维包含 API major 和 active tenant subject。当前 `hooks.ts:40-118` 使用 `['portfolio', ...]`、`['reports', ...]` 等全局 key；`auth-session.ts:65-69` logout 只清 token/session，不 cancel、remove 或 clear cache。

同一 SPA 中 A 退出、B 在 30 秒 staleTime 内登录时，B 可能先看到 A 的组合、报告、风险或运维缓存；A 的延迟请求也可能在 B 登录后写回。

修复必须是原子会话边界：先 cancel 请求、使旧 response 失效、清所有私有 cache/chat state，再发布 logout/login/tenant switch；Query Key 统一为 `['v1', subject, domain, ...]`。

### REV-P0-09：生产部署与 docs/10 的安全拓扑不一致

| docs/10 目标 | 当前实现 |
|---|---|
| `api.env`、`worker.env` 分离 | API/Worker 都加载 `.env` |
| API 不持有模型/CorpSecret/Worker DSN | 一个 `Settings` 包含所有 secret，注册还使用 Worker DSN |
| Worker 不持有 JWT secret | 同一 `.env` 注入 |
| 单一 TLS Nginx 入口 | Compose 暴露 API `8000` 和 HTTP 前端 `8080` |
| API 内网可达 | 直接发布宿主端口 |
| migration 有环境选择和 readback | 注释要求手工执行 `migrations/*.sql`，会包含 dev seed |
| 安全 Header、Cookie Secure | `frontend/nginx.conf` 无 CSP/HSTS/nosniff/referrer/frame 防护 |

此外，生产 Nginx 不代理 `/static`，后端返回的头像 URL 会被 SPA fallback 成 `index.html`；API 容器没有头像 volume，重建会丢失。

## 4. P1：核心正确性、可维护性和可信度问题

### REV-P1-01：报告 provenance 和质量状态不可信

- `_parse_llm_draft()` 接受任意 item type/severity，并把每条模型输出质量写成 `FRESH`（`reports/service.py:284-303`）；
- report 默认 `quality_status=FRESH`、`policy_check_status=PASSED`（`reports/service.py:437-441`），并没有对应完整校验；
- 输入 snapshot hash 是 `sha256:ctx-{持仓条数}`，不是内容 hash（`reports/service.py:400-402`）；
- Worker 生成报告仍构造人类 OWNER context，审计 actor 可能写 USER，`job_run_id` 始终为空；
- 前端把每个 report item 伪造成来源“模型生成”、URL `#`、hash=item id、modelRunId=模型名称（`ReportViewer.tsx:25-40,198-203`）。

应建立真实的 `evidence_refs`、claim type、source snapshot、retrieved/published/as_of、content hash、model run id 和 policy check result。没有直接证据的自然语言必须标成解释/推断，不能制造“证据外观”。

### REV-P1-02：风险政策没有实现设计中的生命周期

- API 只有读取，没有 create/update/preview/confirm/retire；
- `POLICY_FIELDS` 和 DTO 仍包含 bond/gold，违反 L1 不提交、不参与求和的约束（docs/09:64、docs/06:363）；
- 查询只找 `CONFIRMED`，但没有验证 completeness、confirmation provenance、适用资产和 legacy 状态；
- 规则中“现金低于目标 50% 才违规”的阈值没有设计依据；
- policy hash 没有覆盖全部影响计算的字段。

建议先完成最小状态机 `DRAFT -> PREVIEW -> CONFIRMED -> RETIRED`，所有变更带 expected version、Idempotency-Key 和重新认证；L1 DTO 完全去掉 bond/gold，而不是传 0。

### REV-P1-03：组合读取在多账户和不可用估值场景下有错误

- `portfolio/repository.py:84-99` 按 instrument 去重，没有包含 account，导致同一标的分布在多个账户时丢账户；
- `portfolio/service.py:136` 对已格式化金额字符串做字典序排序；
- `_d(None)` 返回 0，缺估值容易被显示成 `0.00`；
- summary 的 `asOf` 使用请求时间，不是最弱/最新事实快照时间；
- `dailyPnlRate` 没有处理外部现金流，不是可靠的 TWR/资金流调整收益。

### REV-P1-04：关键页面把错误伪装成空数据

Reports、Risk、Settings、Operations 和 Dashboard 的多个 query 使用 `data ?? []`、默认 VIEWER 或“暂无数据”；只有个别主 query 显示 error。结果是：持仓失败显示“暂无持仓”、风险失败显示“未配置”、运维失败显示 0。

必须统一 `QueryStateBoundary`，区分 loading、empty、stale、estimated、unavailable、401、403、429、5xx；组合页面需要聚合其所有 query 状态，不能只看 summary。

### REV-P1-05：401、refresh、撤权和 tenant 切换没有闭环

- `onAuthFailure()` 只挂到少数 identity mutation，组合、报告、风险、运维、头像和 SSE 的 401 不会统一清会话；
- 应用启动没有 refresh/bootstrap，浏览器刷新必回登录；
- 设置页却宣称已有 HttpOnly refresh cookie；
- membership 被撤销或角色改变后，没有清 cache、停止 stream、重新加载 role；
- header tenant switch 与 docs/09 的 token-bound tenant 冲突。

### REV-P1-06：Chat 独立实现绕过了已有模型治理设计

- `chat/api.py:50-59` 在整个外部新闻/模型流期间持有 tenant DB transaction；默认 10 个连接，约 10 个慢请求即可耗尽 pool；
- caller 可以任意覆盖 model，没有 allowlist、并发、速率和花费预算；
- `chat/service.py:266-274,314` 把金融 Decimal 转为 float；
- provider error body 被日志记录，异常文本可能返回客户端；
- 完整持仓、报告、新闻和用户问题送往外部模型，缺少最小化、授权、保留期和敏感字段治理；
- 新闻/网页内容直接拼到 system prompt，未标记为不可信数据，存在 prompt injection；
- 没有统一 `model_runs`、prompt/schema 版本、token/cost、evidence refs 和可重放 input hash；
- 每次请求创建多个 AsyncClient，行情/新闻也串行拉取，延迟和连接复用较差。

建议 Chat 复用统一 `ModelGateway + ToolLoop + ModelRunRecorder`，短事务读取 immutable context DTO 后释放连接，再并行执行有限外部数据调用，最后流式生成。

### REV-P1-07：头像存储、校验与生命周期不完整

- `identity/api.py:119-136` 先读完整文件再检查 2 MiB，可造成内存压力；
- 只信任扩展名/MIME，没有解码验证图片 magic、尺寸、像素数和重编码；
- 文件先写磁盘再更新 DB，DB 失败会留下 orphan；旧头像不清理；
- 容器本地存储不持久；生产 Nginx 无 `/static` 路由；
- 已把两张运行时头像提交到 Git，存在隐私、仓库膨胀和环境污染风险。

MVP 可使用受控 volume + 独立 media route，正式版迁对象存储。任何方案都要 server-side filename、解码/重编码、像素和体积限制、旧对象回收、隐私访问策略和生命周期测试。

### REV-P1-08：迁移和 seed 流程不可用于生产

- `010_dev_seed_workbench.sql` 明确是开发 seed，却处于正式编号迁移链；
- `012` 同时改 schema、创建 credential helper、初始化演示密码、授权 Worker，多种责任混在一个 migration；
- Compose 没有 migration service、schema version ledger 或启动 readback；
- `scripts/seed_wangfang_tenant.sql:31-59` 不是幂等：第一次插入事件 101，第二次发现 101 后会插入“修正”事件 105，第二次运行改变经济余额。

建议拆为 `migrations/schema/`、`seeds/dev/`、`ops/backfill/`，使用单向 migration ledger；seed 的第二次运行必须是严格 no-op，修正脚本必须独立命名、显式确认和审计。

### REV-P1-09：依赖、测试和 CI 无法证明当前实现可回归

- 当前 `.venv` 运行 `pytest -q` 在 collection 阶段因缺 `bcrypt/httpx` 失败；
- `requirements-dev.txt` 仍写“后端实现引入后再分离”，已过期；
- `requirements.txt` 把 pytest 放进 runtime，包含当前未实际采用的 SQLAlchemy/Alembic/passlib，并让 `akshare>=1.18.0` 无上限漂移；
- `pytest.ini` 选项在当前环境报 unknown warning；
- 没有 GitHub/Gitee CI；
- smoke script 依赖手工数据库和 seed，不属于自动化验收；
- 没有真实 PostgreSQL RLS/GRANT/migration、任务并发、Outbox 并发或 WeCom 协议测试。

### REV-P1-10：docs/10 的 AS-IS、目录和部署示例已经过期

- docs/10:65-68 仍说只有 migration 001–008、后端尚未收口，实际已经新增 backend 和 009–012；
- docs/10:96 写 `reporting/`，实现为 `reports/`；docs 中有 `research/`、`deployment/`，实现没有；
- docs/10:133 的链接文字指向新路径，URL 却仍是旧 `file:///.../adapters/...`；
- docs/08 追溯矩阵和 docs/04 测试没有加入 Chat、新闻、头像、注册等新增需求与异常分支；
- docs/01 的“注册新账户”和 docs/07 的“禁止公开注册”仍未统一。

文档应更新为“当前实现状态 + 目标状态 + 明确差距”，不能继续把目标示例当成已实现部署。

## 5. P2：可读性、扩展性、性能与工程质量

### 5.1 文件和模块边界

以下文件已经超过适合单职责维护的规模：

- `backend/integrations/market_data.py`：约 717 行，混合股票、ETF、基金、热点、缓存、解析和多个 provider；
- `backend/identity/service.py`：约 530 行，混合登录、注册、binding、profile、avatar；
- `backend/reports/service.py`：491 行，混合上下文、prompt、模型解析、fallback、持久化；
- `backend/chat/service.py`：约 374 行，且与统一 model gateway 重复；
- `frontend/src/index.css`：3293 行，跨 feature 全局耦合；
- `frontend/src/api/types.ts`：348 行，所谓 generated client 实际仍是手写 re-export。

建议按稳定变化原因拆分，不按机械层数拆分：

- `integrations/market/{akshare,sina,eastmoney,fund}.py`；
- identity 内分 `auth_service`、`binding_service`、`profile_service`；
- reports 内分 `context_builder`、`draft_generator`、`publisher`；
- Chat 只做 conversation orchestration，复用 model/news/market ports；
- 前端按 feature CSS module 或 feature stylesheet；
- OpenAPI 生成 DTO/client，入口做 runtime schema validation。

### 5.2 SQL 与 Repository 边界

当前不少 service 直接执行 SQL，返回值大量使用 `dict`/`asyncpg.Record`，跨模块还导入私有函数。这会使 schema 变化只能在运行时暴露。

建议：

- 高风险写命令必须在 repository/domain command 中完成，并用类型化输入/输出；
- Service 只编排事务、授权、幂等和外部端口；
- 禁止跨领域导入 `_d`、`ZERO` 这类私有实现；通用金融类型放 `common/money.py`；
- SQL 不必引入 ORM 才算可维护，保留 asyncpg 完全可行，但要有 typed row mapper、契约测试和迁移校验。

### 5.3 外部调用和缓存性能

- `market_data.py` 多处每次创建 `httpx.AsyncClient`，应使用应用级连接池；
- `_spot_cache` 没有锁，同一过期时刻会 cache stampede；
- 基金逐只串行请求，应有有界并发、批量或 provider 限速；
- Chat 上下文的持仓、情绪、新闻可并行，但必须有总 deadline 和部分失败质量状态；
- `MarketHot` 是公开且昂贵的外部调用，缺少服务端跨进程缓存和 rate limit；
- Chat 每个 token 更新整段 React message 并重新解析 Markdown，长回答趋近二次开销；建议 lazy-load、批量 delta、memo message。

### 5.4 前端契约、权限和可访问性

- generated client 不是实际生成，`request()` 对 JSON 直接强制断言，后端字段漂移不被发现；
- 前端只隐藏 Operations 导航，直接输入 `/operations` 仍会挂载页面；需要 `RoleGuard/Can`，但后端授权仍是最终边界；
- 多个活跃按钮没有行为，应 disabled + “尚未接入”，不能静默无响应；
- 市场表格行使用 `tr onClick`，不能键盘触发；Chat Drawer 缺少焦点管理、Escape、aria-live 和 label；
- Operations 声称 30 秒刷新，但 hooks 没有 `refetchInterval`；
- Nginx 缺安全 Header，Dockerfile 注释给出的 root-context build 命令会找不到 frontend package 文件；
- E2E 脚本收集 console/page errors，却不据此返回失败，且没有加入 package script/CI。

### 5.5 仓库卫生

- 删除 `nohup.out`；
- 不提交 `backend/static/avatars/*` 运行时文件，保留 `.gitkeep` 即可；
- `git diff --check` 当前报告 `frontend/src/api/portfolio.ts:55` 多余 EOF 空行；
- 为日志、上传、构建产物、测试截图和临时 SQL 输出补 `.gitignore`；
- 大提交拆成可验证的垂直切片，提交说明包含 requirement/test IDs 和 migration/deploy 影响。

## 7. 推荐的详细修改方案

### Phase 0：冻结错误能力，先恢复可信边界

1. 暂停对外部署当前 Compose；
2. 禁用公开注册、演示登录、浏览器企微模拟确认、假解绑、假成交确认、假风险确认；
3. 前端未接入命令统一显示“尚未接入”，不显示成功事实；
4. 撤销 `authenticated` 系统写权限和 credential helper 执行权；
5. 把 dev seeds/default credentials 移出 migration；
6. 修复 Query cache 的 subject/tenant 隔离。

### Phase 1：收敛认证、租户和数据库角色

1. 明确唯一身份方案：MVP 可继续本地 bcrypt/JWT，但必须实现 invite、refresh、logout、revoke、membership version；不要一边声称 Supabase Auth 一边实现另一套协议；
2. 一个 token 只绑定一个 active tenant；切换必须服务端重验 membership/role 并签新 token；
3. API、Worker、Migration、Browser 数据库角色彻底分离；
4. 注册 bootstrap 使用最小权限 command，不把 Worker DSN 注入 API；
5. 对真实 PostgreSQL 跑 RLS/GRANT 集成测试。

### Phase 2：重做组合投影和基金 14:30 最小闭环

1. 只以 CONFIRMED ledger/import/fill 为经济事实；
2. 建立 deterministic position projector，可全量重放与增量更新；
3. 缺报价保留持仓并输出 coverage/UNAVAILABLE；
4. 多账户维度保留 `(tenant, account, instrument, as_of)`；
5. 实现场外基金估值 observation、持仓披露 coverage、uncertainty 和 ABSTAINED；
6. 所有报告引用同一批 `input_snapshot_hashes/evidence_refs`。

### Phase 3：完成四时段任务、Outbox 与企业微信

1. 用持久化 job schedule + business key 取代内存 `_last_fired`；
2. timezone-aware 交易日调度、misfire/补跑策略；
3. lease token/heartbeat/CAS；
4. Outbox 短事务 claim、事务外投递、CAS 完成；
5. 实现 Worker-only routing decrypt 和企微主动消息 adapter；
6. 绑定只能从已验签回调消费，解绑必须是后端状态变更；
7. 四个 session 做独立 E2E：盘前、盘中、14:30、盘后交互复盘。

### Phase 4：报告/Chat 可信模型治理

1. 统一 ModelGateway、模型 allowlist、timeout/retry/circuit breaker；
2. 建立 model run、prompt/schema 版本、输入内容 hash、token/cost、provider response hash；
3. 外部媒体只作为不可信 evidence data，claim pipeline 无工具执行权限；
4. 事实、观点、推断、预测明确标签；
5. 报告 item 只能引用真实 evidence ref，没有证据则显式说明；
6. Chat 在 DB 短事务外执行，限制并发/花费/上下文最小化。

### Phase 5：前端真实对接与全状态验收

1. OpenAPI 生成 client/DTO，并在核心边界 runtime validate；
2. 统一 AuthBoundary、QueryStateBoundary、RoleGuard 和 Command client；
3. 每个 mutation 统一 Idempotency-Key、If-Match、错误恢复和 unknown-result readback；
4. 删除所有会伪装服务端成功的本地状态逻辑；
5. 补键盘、读屏、移动端和流式响应性能；
6. 运行 docs/04、docs/08 的 Test ID 追溯。

### Phase 6：生产部署和 CI Gate

1. 统一部署目录和权威 Compose；
2. API/Worker 分 env/secret recipient，API 不发布宿主端口；
3. 单一 TLS ingress、安全 Header、CORS/CSRF、body/rate limit；
4. migration job + schema/grant readback + backup/restore 演练；
5. Python lock、Node lock、镜像 digest、SBOM/依赖扫描；
6. CI 顺序至少包括 docs validator、format/lint/typecheck、unit、PostgreSQL integration、E2E、Docker build、migration dry-run、安全回归。
