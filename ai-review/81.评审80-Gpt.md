\## 一、总体审查结论



我已读取第 80 号 Review，并对照最新 WealthSail 工作区的实际实现。



当前代码版本为 `master@39c8b08`，领先 `origin/master` 9 个提交。另外还有 7 个已修改文件和新增的主题优先级代码尚未提交。因此，当前工作区并不等于已经部署的版本，也不是完全冻结的待发布版本。



这次改造确实实现了第 80 号 Review 最重要的功能：AI 发现机会后，可以独立寻找相关基金，不再因为正式 `valueDirections=\[]` 就完全没有基金结果。



但还不能认定“AI 总能找到最合适的基金”。我发现的主要剩余问题集中在匹配准确性、查询性能、归档刷新和机会优先级，而不是原来的负面风险硬门槛。

这比此前“正式方向没有通过就不给用户看基金”的设计合理得多。



\## 二、剩下最值得修复的 4 个问题



\### P1：全量基金匹配可能成为新的数据库性能瓶颈



位置：`backend/investment/opportunity\_fund\_recall.py`，`\_LOOKUP\_SQL`、`recall\_topic\_funds()`。



新版采用一条较大的 SQL：



```

FROM catalog c

CROSS JOIN unnest($2::text\[]) k

```



然后对基金名称、跟踪指数进行模糊查询：



```

c.fund\_name ILIKE '%' || k || '%'

```



同时还有 `LATERAL` 查询、申购状态排序和窗口排名。



虽然最终每个关键词最多返回 12 个候选基金，但限制发生在匹配和排名之后，并不能保证数据库前面的计算量很小。



当前最多支持 72 个主题，每个主题最多 8 个直接关键词，还会增加兜底关键词。



这意味着基金库和主题数增加后，数据库可能产生较大的中间匹配工作量。



尤其值得注意：这个查询是在用户打开页面时执行的，不是每日 AI 研究结束后预先计算的。



建议：



\- 对实际 PostgreSQL 基金主库运行只读 `EXPLAIN (ANALYZE, BUFFERS)`。

\- 检查基金名称、指数名称是否有适合模糊检索的索引。

\- 将稳定的主题—基金候选关系进行有界缓存，申购状态单独按时效刷新。

\- 给查询设置明确超时和性能监控，避免基金推荐拖慢整个投资机会页面。



这是我建议部署前优先验证的问题。当前没有真实生产 SQL 执行计划，因此不能直接断定它已经慢。



\### P1：基金匹配成功，不代表找到了最合适的基金



这个问题更接近你最初的真实需求。



目前 `\_terms()` 从主题标题、行业词和文本中提取关键词，而 `\_LOOKUP\_SQL` 可以通过基金名称包含关键词来形成 `DYNAMIC\_MATCH`。



例如，一个主题写的是：



> AI 硬件盈利兑现与估值重估



模型可能提取“AI”“芯片”“半导体”等关键词。



但名称包含这些词的基金，未必拥有相同的实际投资敞口。



当前实现已经区分“基金名称匹配”和“已核验跟踪指数匹配”，这是正确的；但最后的排序仍主要考虑申购状态、匹配层级、量化分数。



缺少对主题实际敞口的独立质量评估。



还有一个更明显的边界：`\_fallback()` 在未识别海外市场和特定资产类别时，默认尝试中证 A500、沪深 300、中证 500。



对于部分国内细分产业主题，这些宽基确实可以作为间接观察对象；但宽基中究竟有多少相关资产敞口，代码并未验证。



因此，容易出现：



> AI 发现了一个很具体的机会，系统却给它匹配一个泛泛的宽基基金。



这虽然比完全没有基金好，却未必符合“最合适”的要求。



建议增加匹配可信等级：



| 关联依据             | 建议展示等级       |

| ---------------- | ------------ |

| 已核验跟踪指数与机会主题直接对应 | 高关联          |

| 有可靠产品分类或投资范围支持   | 中高关联         |

| 基金名称关键词匹配        | 候选关联，待核实     |

| 宽基或其他大类资产兜底      | 间接观察，不称为主题推荐 |



这里不需要让 AI 猜测基金持仓，也不必马上新增模型调用。先利用现有基金主数据、指数关系和投资范围资料即可。



\### P2：没有区分“有利投资机会”和“负面经济事件”



`project\_topic\_recommendations()` 当前主要排除 `QUARANTINED` 主题，其余主题都可进入基金推荐链。



这意味着“机器人商业化取得进展”和“机器人企业倒闭潮”都可能匹配机器人基金。



后者当然也值得研究，但它更可能是风险观察或退出评估，而不是新的正向机会。



新版会展示风险徽章，但还没有完整区分机会的投资方向。



建议给主题增加独立的、可解释的经济影响分类：



\- `POSITIVE\_OPPORTUNITY`：有依据的正向机会假设；

\- `NEGATIVE\_RISK`：经营恶化、风险或退出观察；

\- `MIXED`：正反因素并存；

\- `MACRO\_OBSERVATION`：重要经济变化，但不直接对应某类投资机会；

\- `UNDETERMINED`：证据不足。



这只是研究展示分类，不授予交易资格。



首页可以分别显示“值得关注的机会”“主要风险和退出观察”“经济事件与市场影响”，而不是把所有相关基金统称为推荐基金。



这也能避免为了凑推荐数量，让负面新闻不断匹配出基金。



\### P2：新推荐接口缺少自动归档完成刷新



位置：`TopicFundRecommendations.tsx`。



后端在归档尚未结束时会返回 `UNAVAILABLE` 和 `TOPIC\_ARCHIVE\_PENDING`，这是合理的。



但前端 `useQuery()` 当前只有手动重新检查，没有类似主题目录的有界自动轮询。



```

retry: false,

staleTime: 60\_000,

refetchOnWindowFocus: false,

refetchOnReconnect: false,

```



如果用户在 AI 刚完成、主题尚未归档时打开页面，可能首先看到“匹配资料尚不完整”，随后归档完成，页面却没有自动显示新推荐。



这与你之前遇到的“研究成功但页面没有显示”属于同类体验问题。



建议复用现有归档轮询机制：只在明确处于 `AUDIT\_PENDING` 或 `ARCHIVING` 时有限轮询，完成后停止，绝不重新调用 AI。



\## 三、还有两项设计没有完全闭环



\### 1. “当日新机会优先审核”只能覆盖模型运行前已知的新闻



现在 `current\_opportunity\_industries()` 会从模型调用前的公开新闻中提取正向催化，并优先分配行业审核名额。



这实现了第 80 号 Review 的一部分。



但是AI 在本次研究中临时发现的新行业主题，并不能反过来改变本次已经冻结的 10 个审核名额。



这是单次模型调用、先冻结搜索预算的架构所决定的，并不是代码漏调用一个函数。



这不妨碍新主题获得只读基金推荐。但如果要让它在下一次具备正式投资资格，应该将确有证据的动态主题纳入后续有界审核队列，而不是无限追加搜索。



另外，个人持仓行业优先的接口已经有了，但文档明确说明本轮没有把私有持仓直接接入共享研究任务，原因是避免暴露个人偏好。这部分应保持隐私隔离，不建议直接塞进公共 Prompt。



\### 2. AI 仍可能输出 0 个正式投资方向



这次新增的是：



```

AI 主题 → 基金匹配候选 → 只读推荐

```



它没有把这些候选自动转换成严格合格的 `valueDirections`。



我认为这个边界应该保留。



否则为了消除 0 个正式方向，可能重新引入错误的投资资格放行。



正确的成功标准应当分别统计：



| 指标              | 未来希望看到的结果   |

| --------------- | ----------- |

| AI 主题数量         | 有实质研究内容，不凑数 |

| 有真实基金关联的主题      | 尽可能高        |

| 有直接、可靠基金敞口依据的主题 | 持续提高        |

| 申购状态已核实的候选      | 明确展示        |

| 价格和技术位置可评估的候选   | 明确展示        |

| 获得严格正式投资资格的方向   | 可以为 0，但原因透明 |



不要只看“匹配基金数量”。应特别观察“高可信基金关联率”。



\## 四、最新未提交代码还需要注意



当前工作区正在实现主题重点排序功能，涉及：



`backend/macro/research\_topic\_priority.py`



`ResearchTopicRegistry.tsx`



以及相关 API、数据库和前端测试。



这部分采用独立的排序侧栏，不改写历史主题顺序，方向是对的。



但它目前还属于未提交工作区改动，不能和 `39c8b08` 已提交实现混为一谈。



而且页面上可能同时存在两套重点展示：



1\. 新闻机会与匹配基金；

2\. 值得关注的 AI 投资主题。



两者排序逻辑不同，可能造成同一个主题在页面重复出现。



建议最终把二者整合成一张真正的“机会卡片”：主题故事、相关基金、关联可信度、量化状态和风险统一呈现；完整主题目录继续作为详细研究入口。



\## 五、我的部署建议



最新代码审查



建议补充针对性验证



不需要推翻第 80 号方案，也不建议重新收紧基金召回。



重点先确认真实全量库查询性能，再降低弱关联基金被当成最佳推荐的风险，补齐归档刷新和机会/风险分类。完成后进入受控灰度。



我建议下一轮让 Codex 集中完成以下工作：



1\. P1：检查全量基金召回 SQL 的实际执行计划。 通过索引、分阶段查询及有界缓存控制延迟和数据库负载。

2\. P1：提高基金匹配质量。 已核验跟踪指数优先于基金名称关键词；宽基兜底必须明确为间接敞口，不能和直接主题基金混同。

3\. P2：区分正向投资机会、负面风险和中性经济观察。 不允许仅凭新闻出现产业词就宣称找到正向机会。

4\. P2：增加新推荐接口的归档完成自动刷新。 完成后立即展示，但绝不触发新的模型调用。

5\. P2：合并重复的首页重点主题展示。 保留一次用户可读的主题—基金—风险卡片及完整目录入口。



验收时应加入几类真实业务案例：AI 硬件机会找到可信芯片 ETF 联接基金、海外利率主题不会错误匹配中国债基、负面机器人新闻不会被包装成买入机会、没有直接基金时宽基不会假装纯主题敞口、归档延迟后能自动显示，以及 72 主题下的数据库压力测试。



测试方面，我检查了源码和现有回归用例，相关单元及独立 PostgreSQL 测试已有覆盖；但当前连接没有独立执行记录，不能确认最新 HEAD 加上尚未提交修改后的全量测试已经通过。



最终判断：第 80 号 Review 的核心目标已基本实现——有 AI 洞察时，不再必须等正式投资方向审核通过才能找到真实相关基金。



接下来最值得投入的，不是继续增加基金推荐数量，而是让系统做到：



推荐的基金确实与机会有关、优先展示最合适的产品、能说明当前价格和风险位置，而且不会拖慢整个页面。



做到这一步，WealthSail 才真正从“发现机会后凑基金”升级为“发现机会后可靠地筛选投资载体”。
