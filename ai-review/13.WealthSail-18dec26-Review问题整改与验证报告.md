## 1. 整改原则与最终边界

本次没有简单删除新增功能，也没有退回只剩目录和接口名称的“骨架文档”。整改保留了股票、场内基金、场外基金、四时段报告、企业微信、多用户、标的搜索、市场情绪和投研候选的产品价值，但重新建立以下边界：

1. 用户输入的期初持仓是**待核对输入**，不是已发生的交易或现金流；
2. 读取型 API 不得在请求链中偷偷执行高权限写入或即时生成投资建议；
3. 投研候选必须经过持久化、证据、有效期和投资政策门禁；无合格结果时明确弃权；
4. API 与 Worker 使用独立数据库登录；API 永远不能升级为 BYPASSRLS Worker；
5. 四时段正式调度只包含 08:30、盘中、14:30、15:30，临时推送不得混入长期 scheduler；
6. 同一租户的每个有效企业微信 binding 都拥有独立 Outbox delivery；
7. 安全冒烟脚本只能从环境变量取得测试凭据，远程目标必须使用 HTTPS，流程只读。

## 3. 期初持仓设计的具体变化

### 3.1 新的 Web/API 流程

```text
搜索并选择服务端可核验标的
  → POST /api/v1/portfolio/imports
  → portfolio_import_batches/items = DRAFT
  → Web 展示规范化名称、类型、数量、成本和基线日期
  → 用户再次确认
  → POST /api/v1/portfolio/imports/{batch_id}/confirm
  → CONFIRMED ADJUSTMENT + INSTRUMENT leg
  → 刷新 position/NAV projection
```

创建和确认分别使用稳定的 `Idempotency-Key`。DRAFT 阶段不生成 ledger event，也不刷新经济事实。确认事务对 batch 加锁；重复确认返回同一结果，不重复写事件。已确认内容不允许直接 UPDATE/DELETE，后续纠错应实现正式 `REVERSAL` UI，而不是恢复“编辑持仓”。

### 3.2 主数据可信与并发边界

表单 `name` 只用于展示，后端不采信。已有标的从本地主数据解析；缺失标的必须由 Provider 精确匹配代码、类型和市场后才允许建档。market+ticker advisory lock 解决同一新标的的并发创建；alias 查询不再只按六位代码跨市场碰撞。

### 3.3 Migration 兼容策略

没有修改已经可能落库的 `016_manual_holdings.sql`，避免已应用 migration checksum 漂移。新增 `017_portfolio_import_authorization.sql` 以前向方式覆盖不安全 RLS，并授权正式 import 表。这符合仓库的 forward-only migration 约束。

## 4. 行情、投研候选与多 Agent 边界

### 4.1 市场情绪

Worker 按正式 session 刷新快照，API 只读。快照现在能回答“来源是什么、源时点是什么、何时抓取、覆盖多少、质量如何、算法版本是什么”。页面同时展示这些字段，Provider 失败不再伪装成正常的空数据。

### 4.2 投研候选

新增的 `backend/research` 不是又一个在线 Agent，而是已持久化 recommendation 的门禁读模型。模型运行失败、证据缺失/冲突、政策拒绝或过期都会被过滤；没有合格结果时明确 ABSTAIN。它保留未来的加仓候选、减仓候选和反方论据价值，但不把任何候选直接转换成交易或账本写入。

### 4.3 多 Agent 的局限性和优先级

多 Agent 需求继续保留，但仍应排在单 Agent/确定性工作流之后：

- 多 Agent 会增加调用成本、尾延迟、失败组合和结果不稳定性；
- “多角色讨论”不自动等于独立证据，不同 Agent 可能共享相同模型偏差和错误上下文；
- 上下文交接会丢失时间、来源、质量和版本语义，容易出现引用漂移；
- 并行 Agent 对工具权限、幂等、预算、停止条件和审计提出更高要求；
- 投资场景最终仍需确定性的 evidence/policy/publication gate 与人类确认。

因此当前代码只提供受治理的只读结果，不为 Agent 暴露账本写连接。未来只有在单 Agent 基准、
离线评测、成本上限、超时/熔断、Prompt 注入防护和 feature flag 齐备后，才逐步启用多 Agent。

## 5. 数据库登录、RLS 与部署变化

### 5.1 最终角色关系

```text
wealthsail_api_login
  └─ SET wealthsail_api
     └─ tenant_transaction + JWT claims + RLS

wealthsail_worker_login
  └─ SET wealthsail_worker (BYPASSRLS group role)
     └─ 单向 SET wealthsail_api，用于按租户生成报告
```

关键不变量是：API 登录绝不能 SET Worker；Worker 是更高信任进程，可以主动降权到 API。启动时
`verify_runtime_login_boundary` 会检查 session/current user、superuser、BYPASSRLS 和 SET
能力，配置错误直接拒绝启动。

### 5.2 生产升级顺序

1. 立即轮换曾出现在 Git/HTTP 冒烟脚本中的账号口令，撤销其 refresh sessions；
2. 审计该账号历史持仓、账本、audit、企业微信 binding 和登录日志；必要时人工冲正；
3. 备份数据库，用 migration 管理员执行 017、018、019 并完成 readback；
4. 执行 `scripts/provision_supabase_roles.sql`，为两个 LOGIN 设置不同随机密码；
5. 分别更新 API `DATABASE_URL` 与 Worker `WORKER_DATABASE_URL`；
6. 先启动 API 并验证 `/healthz`，再启动 Worker；
7. 用 OWNER/EDITOR/VIEWER 与两个有效企业微信用户完成真实 E2E。

注意：旧凭据已经进入 Git 历史，仅删除当前文件不能让它失效。是否重写远端历史需要单独协调所有
clone；无论是否重写，口令轮换、会话撤销和历史审计都必须先做。

4. 2–3 个真实用户的企业微信绑定、撤销、重复回调、多 recipient delivery、单用户失败隔离；
5. 公网 HTTPS、Secure Cookie、外层代理回调/SSE 配置和限速；
6. Provider 超时、分页缺失、交易日/节假日、基金 14:30 低覆盖率的 staging 契约测试；
7. 已确认期初导入的 REVERSAL 纠错 UI；在其实现前，录错数据必须通过受审计的运维流程冲正；
8. Worker 生成并发布 governed recommendations 的完整生产流水线；当前无合格记录时会安全弃权，
   不会恢复即时无证据建议。

完成这些外部验证后，才能把本次整改从“仓库级通过”提升为“生产可验收”。
