这张图片里有一句极其核心且充满工程智慧的话：**“按场景复杂度选档，拒绝一步到位”**。

结合我们之前为您设计的**智能量化投研中台**（包含数据抓取、Skill/Plugin 调度、多空 Agent 辩论、实盘交易确认等复杂环节），如果直接生扑最高难度的架构，很容易陷入无尽的 Debug 中。

根据这张图的选型路线，我建议您的投资辅助系统采取“L5 起步，L7 托底”的演进策略：

### 第一阶段（MVP 与基建）：L5 Route + Skill（技能系统首选）

* **为何契合**：您系统底层的核心资产是各种独立的模块，比如 `AkShare 数据抓取 Plugin`、`威科夫量价分析 Skill`、`RAG 历史复盘记忆`。
* **落地形态**：系统此时像一个聪明的**路由器（Router）**。当用户输入“帮我查一下腾讯的技术面”，Router 精准将其路由到对应的“技术分析 Skill”和“行情 Plugin”上，得出结论后返回。这个阶段代码最轻，见效最快，且极度契合您之前提出的“Skill 与 Plugin 分离”的架构理念。

### 第二阶段（认知进阶）：L4 多 Agent + L6 Blackboard（共享状态）

* **为何契合**：当您的系统需要引入“**红蓝沙盘多空辩论**”（多头、空头、风控裁判）时，单一路线就不够用了。
* **落地形态**：引入 **L6 黑板模式（Blackboard）**。将最新的宏观数据和腾讯的 K 线数据挂在“黑板”上，多头 Agent 和空头 Agent 围绕黑板上的公共数据各自输出观点，最后由风控裁判 Agent 综合黑板上的所有信息，给出最终的买卖仓位建议。

### 第三阶段（终极生产态）：L7 Graph Workflow（工业级上生产）

* **为何契合**：金融交易系统对**状态可控**和**容错**的要求是极其苛刻的。大模型不能处于“黑盒探索”状态。
* **落地形态**：当系统进化到需要接入**真实交易接口**时，必须采用 **L7 图工作流（Graph Workflow）**。比如，系统走到“生成交易指令”这个节点时，图工作流必须**强制挂起（中断状态）**，等待用户在 Web 页面点击“确认执行”后，再恢复状态流转，进入下一个“调用券商 API”的节点。这正是图编排（如 LangGraph 或自研状态机）在工业级场景下的终极价值。

---

**总结来说：**
不要一开始就去写复杂的 Graph 节点。用 **L5 (Route + Skill)** 的架构把数据抓取、回测跑通，沉淀好你的工具库；等准确率达标了，再用 **L7 (Graph Workflow)** 把它们像串珍珠一样串起来，加上交易风控和状态恢复，推向“工业级生产”。

如果您准备从 L5 (Route + Skill) 开始动手，您是打算用自然语言意图识别来做 Router，还是采用更稳定的函数调用（Function Calling）来做底层路由？

---

在构建 Agent 的路由层（Router）时，**自然语言意图识别**与函数调用（Function Calling）是两种截然不同的技术流派。

对于金融投资这种对**精确度、参数提取要求极高**的场景，**结论是：函数调用（Function Calling）绝对是更好的选择，它是目前工业级 Agent 的标准做法。**

以下是对这两种方式的深度拆解与对比：

### 一、 方式一：自然语言意图识别 (Semantic / Prompt Routing)

这种方式把大模型当做一个“分类器”，通过文字交流让模型决定去哪。

* **实现原理**：
通常有两种做法：
1. **Prompt 强算**：给大模型一段提示词：“你是一个路由节点，用户输入了【帮我查腾讯的财报】，请从 [查财报, 查K线, 下单] 中选择一个输出”。然后用正则表达式去提取模型的文本输出。
2. **向量检索 (Semantic Router)**：将所有 Skill 的描述转化成向量（Embedding），再将用户的提问也向量化，计算余弦相似度，哪个分数最高就路由给哪个 Skill。


* **特点与优势**：
* **极度灵活**：不需要定义严格的数据结构，适合闲聊或宽泛的知识库问答。
* **速度快（仅限向量法）**：如果用本地轻量级 Embedding 模型做余弦相似度计算，甚至不需要调用大模型 API 就能瞬间完成路由。


* **致命缺陷（在金融场景）**：
* **参数提取极其困难**：如果用户说“帮我买 100 股茅台，价格不超过 1400”，意图识别只能告诉你“他想交易”，但你需要另外写一套极其复杂的逻辑去把“茅台”、“100股”、“1400元”准确提取出来，且极易出错。
* **格式幻觉**：大模型有时会多嘴，输出“好的，我帮您选择【查财报】”，导致后端的正则解析直接崩溃。



---

### 二、 方式二：函数调用 (Function Calling / Tool Calling)

这是 OpenAI、DeepSeek 等主流大模型原生支持的高级特性，让大模型直接输出结构化的机器代码指令。

* **实现原理**：
开发者在调用大模型 API 时，把系统里所有的 Plugin/Skill 以 **JSON Schema (数据结构描述)** 的形式作为 `tools` 参数传给模型。
例如定义一个名为 `get_kline` 的函数，明确告诉大模型它需要 `symbol` (股票代码, 字符串) 和 `days` (天数, 整数) 两个必填参数。大模型理解用户意图后，不会回复自然语言，而是直接返回一个标准的 JSON 对象：`{"name": "get_kline", "arguments": {"symbol": "00700", "days": 20}}`。
* **特点与优势**：
* **自带参数提取（最核心价值）**：大模型不仅知道该调哪个功能，还会极其精准地从用户的自然语言里抠出股票代码、价格、时间等参数，并强制转换为你在 Schema 里定义的类型（如整数、浮点数）。
* **确定性极高**：输出的是标准 JSON，后端代码反序列化后可以直接运行，彻底告别正则解析。
* **多工具并发支持**：如果用户说“对比一下腾讯和阿里的技术面”，Function Calling 可以一次性返回两个函数调用指令（并行调用两次 `get_kline`），极大提升效率。


* **劣势**：
* 强依赖底层模型的能力。如果用了参数量较小或未经过专门指令微调的开源模型，可能会出现输出 JSON 格式残缺的情况。



---

### 三、 为什么 Function Calling 更适合您的投资中台？

在您的 L5 (Route + Skill) 架构中，系统底层挂载了大量具体的工具（AkShare 数据接口、策略回测脚本）。

1. **容错性要求**：金融交易不允许“大概率正确”。将 `买入("00700", 100, 380.5)` 解析成一串标准的 JSON 给到后端，比依靠大模型的自然语言解析安全一万倍。
2. **代码工程化**：在 Python 后端（如 FastAPI 配合 Pydantic），将后端的 Python 函数一键转换为 Function Calling 所需的 JSON Schema 已经有了极度成熟的库（如 Pydantic 本身的 `schema_json()`，或者 Instructor 库）。这种“代码即契约”的开发体验极其丝滑。
