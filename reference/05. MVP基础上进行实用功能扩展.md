基于您对 MVP 的大幅扩展要求，这个系统已经从一个简单的“提醒工具”进化为一个**全栈架构的智能量化投研中台**。

结合您的需求，以下是为您量身定制的技术选型与详细方案设计。

### 一、 核心架构与技术栈选型

针对支持 Web 跨端访问、本地化部署以及量化回测的需求，传统的单体脚本已无法满足。建议采用**前后端分离 + 微服务**的现代化架构：

* **数据库 (Supabase)**：极佳的选择。Supabase 底层是 PostgreSQL，天然支持关系型金融数据（持仓、订单）存储，自带的 `pgvector` 可用于存储 AI 复盘的记忆向量，且 Realtime 功能可用于前端的异动预警推送。
* **后端计算与 AI 层 (Python FastAPI)**：Python 是量化金融与 AI 的绝对主场。使用 FastAPI 构建接口，集成 `Backtrader` 或 `Qlib` 作为量化回测引擎。
* **数据同步引擎 (Go)**：面对高频的 K 线轮询和多源宏观数据抓取，可以利用 Go 语言的高并发协程特性开发独立的数据抓取服务，将清洗后的数据落入 Supabase。
* **前端交互端 (React / Next.js)**：复用 React 体系的组件化优势，构建自适应的 Web UI。手机浏览器与电脑端均可完美访问，后续若需打包独立 App，也能低成本迁移至 React Native 架构。
* **NAS 部署方案**：在极空间（ZSpace）等具备 Docker 能力的 NAS 平台上，通过 `docker-compose` 将 Supabase 官方镜像、Python 后端、Go 数据服务一键容器化部署。NAS 的全天候运行特性完美契合早晚定时分析与夜盘监控的需求。

### 二、 关于开源项目 `earendil-works/pi` 的评估

**结论：不适合作为本系统的基础框架。**

* **定位差异**：`pi` 是一个极简的**终端/命令行（CLI）编码 Agent 框架**，核心机制是利用大模型读写本地文件（`read`, `write`, `bash` 工具），并通过 TUI（终端用户界面）与开发者交互。
* **架构冲突**：您需要的是一个具备 Web UI 页面、能处理关系型数据库（Supabase）、跑量化回测并支持多端访问的金融系统。如果硬改 `pi`，相当于把一辆赛车强行改成跨海大桥，改造成本远大于基于 Python/FastAPI 从零搭建原生 API。

### 三、 核心需求详细设计

#### 1. 策略、Skill 与 Plugin (插件) 的解耦与承载

要让系统灵活且严谨，必须明确这三者的边界：

* **Plugin (插件/工具)**：**连接外部世界的“手眼”**。
* *承载内容*：获取宏观指数、拉取 AkShare/Tushare 的 K 线数据、对接未来的真实券商交易 API。
* *实现方式*：Python 函数，通过 OpenAI 的 Function Calling / Tool Use 机制注册给大模型。


* **Skill (技能/认知 SOP)**：**AI 的“分析思维模型”**。
* *承载内容*：例如“如何进行威科夫量价分析”、“如何解读非农数据”、“如何诊断财报造假”。
* *实现方式*：结构化的 Prompt 模板（System Instructions）。当用户提问特定领域时，系统动态将该 Skill 注入上下文。


* **操作策略 (Trading Strategy)**：**绝对理性的“量化法则”**。
* *承载内容*：均线交叉、RSI 超买超卖、动态止盈止损线。
* *实现方式*：必须以 **Python 代码 (如 Backtrader 策略类)** 或 **JSON 结构化参数** 承载。不要让大模型用自然语言直接“猜”回测结果。当用户在前端配置策略后，后端调用量化引擎进行硬核回测，然后**把真实的回测收益率和夏普比率作为数据（Data）喂给大模型**，由大模型总结结论。



#### 2. 仓位管理与收益统计

系统不再只是给方向，而是给出精确的交易指令。

* 在 Supabase 中建立 `accounts`（总资产）和 `positions`（当前持仓）表。
* AI 在生成建议时，通过 Plugin 获取用户的可用资金和风险偏好，计算出具体的买入股数。计算逻辑在后端严格约束：

$$\text{目标股数} = \lfloor \frac{\text{可用总资金} \times \text{建议仓位比例}}{\text{当前股票市价}} \rfloor$$


* 前端展示模块根据 Supabase 记录的买入均价和最新市价，自动绘制持仓资产走势图和累计收益率（类似券商的账户分析功能）。

#### 3. AI 建议与人类真实操作的“复盘沉淀”机制

这是提升投资胜率的最核心功能（闭环反馈）。建议采用“向量化记忆（Vector Memory）”的方式沉淀，而不是修改底层代码。

* **数据记录**：当 AI 给出“建议在 380 元卖出”后，系统监听用户的实际操作。如果用户“在 350 元才割肉卖出”，这两条数据（AI 建议 vs 实际操作）同时存入 `trade_logs` 表。
* **复盘过程**：周末或月末触发复盘 Task。Agent 对比这两组数据，分析用户的“认知偏差”（如：过于贪婪导致利润回撤、扛单不设止损）。
* **结果沉淀（关键）**：Agent 将诊断出的教训总结为一段经验（例如：“用户在科技股暴跌时倾向于死扛，往往导致 -20% 以上回撤”），并将其进行 Embedding 向量化，存入 Supabase 的 `vector_memory` 表中。
* **提取与修正**：在下一次大模型给出操作建议前，先通过 RAG（检索增强生成）查询用户的“历史亏损记忆”。动态拼接进系统提示词中：“*警告：根据过去的复盘记忆，你在此类形态中曾因犹豫导致重大亏损，请严格执行本次建议的止损线。*”

#### 4. 模型参数配置化

在 Supabase 中建立 `user_preferences` 表，或直接在 Web UI 的“系统设置”页面提供可视化表单。

* **可选参数**：支持切换底层模型（如 OpenAI 适合复杂逻辑推演，DeepSeek 适合高频且低成本的日常数据总结）、设定 `Temperature`（逻辑回测要求 0，发散性新闻分析可设为 0.5）。
* 通过 API 请求拦截器，在每次调用 LLM 前动态读取这些配置。

### 四、 未来演进：自动交易 (Auto-Trading) 接口设计

为了日后平滑对接自动交易（如 A 股的 QMT/MiniQMT、美股的 Interactive Brokers），需要提前预留接口抽象层：

设计一个基础的 `BrokerInterface` 类：

```python
class BrokerInterface:
    def get_balance(self) -> float: pass
    def get_positions(self) -> dict: pass
    def submit_order(self, symbol: str, action: str, qty: int, price: float) -> str: pass

```

在当前阶段，可以将接口实现为 `PaperTradingBroker`（模拟盘），所有的 `submit_order` 只是在 Supabase 数据库中做增删改查。等未来跑通实盘接口后，只需实现一个 `QMTBroker` 或 `FutuBroker` 继承该类，替换依赖注入即可，上层的 AI Agent 逻辑完全不需要修改。
