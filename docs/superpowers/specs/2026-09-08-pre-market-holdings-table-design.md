# 盘前个性化简报持仓表格设计

## 目标

在不改变四时段调度、报告审计数据模型和现有推送链路的前提下，为 08:35 的 `PRE_MARKET_PERSONALIZED` 报告增加持仓表格：Web 研报审计页面展示完整、可着色的 Markdown 表格；企业微信展示适配其能力的紧凑持仓摘要，并继续链接到完整报告。

本功能只消费已经持久化的持仓、组合汇总和行情事实，不在报告生成过程中调用外部行情源或 AI。没有可靠行情的数据必须显示 `--`，不得根据成本价、累计盈亏或其他字段推算当日涨跌幅。

## 范围边界

- 08:30 的 `PRE_MARKET_MACRO` 是全租户复用内容，保持不含任何用户持仓或关注数据。
- 08:35 的 `PRE_MARKET_PERSONALIZED` 承载持仓表格及用户级内容。
- 有持仓用户的完整报告增加表格；只有关注列表、没有持仓的用户显示“暂无持仓，今日市场概况”。
- 没有持仓且没有关注的用户继续只接收 08:30 宏观简报，不额外生成 08:35 空报告。
- 不修改公共 API 地址、响应结构、数据库结构和订阅语义，不需要新增 migration。
- 不把企业微信的自建应用消息声明为 `markdown_v2`。当前链路和接口支持的是 `markdown`；企业微信端采用兼容的紧凑文本行，完整标准 Markdown 表格在 Web 报告中展示。

## 现有数据链路

报告服务 `backend/reports/service.py` 的 `build_report_context()` 已按当前用户和租户读取：

- `backend/portfolio/service.py` 的 `get_positions()`：从 `ledger.position_snapshots` 返回代码、名称、数量、平均成本、最新价格、仓位和质量状态；
- `get_summary()`：返回组合总资产等汇总；
- `backend/reports/repository.py`：读取已经入库的行情观察事实。

现有持仓记录尚未提供可靠的普通股票/ETF 当日涨跌幅。基金盘中估值偶尔包含 `intradayEstimate.changePct`，但 08:35 通常没有当日估值，不能作为通用字段。行情表的 `metadata.changePct` 可用，但现有 `latest_day_change_pct()` 仅返回百分比，缺少价格对齐、质量和事实时间，不能直接复用。

## 后端设计

### 行情对齐查询

在 `backend/reports/repository.py` 新增盘前持仓行情查询。输入为当前持仓的 `instrument_id`、持仓快照价格和报告时点，输出至少包含：

- `instrumentId`
- `changePct`
- `qualityStatus`
- `sourceAsOf`

查询只使用报告时点之前已持久化的 `market.market_observations`。优先选择与持仓快照价格对应的最新观察；没有可验证匹配时不返回涨跌幅，避免把不同日期的价格与变化率拼接。数据质量沿用系统既有 `FRESH / ESTIMATED / STALE / UNAVAILABLE` 语义。

`backend/reports/service.py` 仅在盘前个性化上下文中调用该查询，并按 `instrumentId` 合并到持仓条目。此数据为报告内部扩展，不改变 `/api/v1/portfolio/*` 的公共返回契约。

每行的最终质量取持仓估值质量与行情变化质量中的较差者。`STALE` 或 `UNAVAILABLE` 时在名称后追加 `⚠️`；其他质量不追加该标记。

### 标准化表格模型

在 `backend/reports/pre_market.py` 增加纯函数，用于构造和渲染盘前持仓表格。`backend/reports/pre_market_personalized.py` 复用该函数，避免新旧盘前代码出现两套格式规则。

表格列固定为：

| 列名 | 取值与格式 |
| --- | --- |
| 代码 | `position.symbol` |
| 名称 | `position.assetName`，质量异常时加 `⚠️` |
| 持仓 | `quantity` + 单位；A 股为“股”，ETF、基金及其他份额资产为“份” |
| 成本价 | `avgCost`；缺失显示 `--` |
| 最新价 | 与持仓快照一致的 `price`；缺失显示 `--` |
| 当日 | 对齐行情的 `changePct`，显示带正负号的百分比；缺失显示 `--` |
| 仓位 | 使用组合投影已经计算的 `weight`，显示百分比；缺失显示 `--` |

排序规则为仓位从高到低，空仓位排最后；仓位相同或为空时按代码升序，确保同一事实集输出稳定。价格和成本保留能表达原数据的合理小数位，不因格式化产生新的计算精度含义。

代码和名称在写入 Markdown 单元格前必须转义反斜杠、竖线和换行，防止资产名称破坏表格结构或注入额外 Markdown。报告不允许嵌入原始 HTML。

### 完整报告

`backend/reports/pre_market_personalized.py` 的 `build_report()` 在现有完整摘要最前面加入：

```markdown
## 持仓概览

| 代码 | 名称 | 持仓 | 成本价 | 最新价 | 当日 | 仓位 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 600036 | 招商银行 | 8,500股 | 38.82 | 39.15 | +0.84% | 34.85% |
```

随后保留现有“持仓今日影响、关注标的动态、今日操作提醒”等内容以及现有报告条目和证据链接结构。表格只进入 `reporting.reports.summary`，无需新增数据库字段。

没有持仓但有关注列表时，`持仓概览` 下显示“暂无持仓，今日市场概况”，随后继续展示关注标的与提醒。

### 企业微信摘要

`backend/reports/pre_market_personalized.py` 的 `format_push_content()` 保持 200 字以内，并输出企业微信 `markdown` 能稳定展示的紧凑内容，而不是 GFM 表格：

```text
**盘前持仓概览**
600036 招商银行 34.85%｜+0.84%
510300 沪深300ETF 29.68%｜-0.31%
另1项见完整报告
```

最多展示仓位最高的两项。内容按完整行进行预算，不能先拼接后粗暴截断导致行或 Markdown 标记残缺。空间允许时追加一条操作提醒；完整报告链接继续由 `backend/jobs/outbox.py` 追加。消息类型继续为 `markdown`，`backend/integrations/wecom.py` 的合法消息类型范围不变。

## Web 渲染设计

`frontend/src/features/reports/components/ReportViewer.tsx` 使用项目已安装的 `react-markdown` 与 `remark-gfm` 渲染 `report.summary`，从而支持 GFM 表格。不开启 `rehypeRaw`，报告内容中的 HTML 按普通文本处理，避免扩大 XSS 攻击面。

为表格单元格提供受控渲染：文本严格匹配带符号百分比时，正值增加上涨样式，负值增加下跌样式，零值保持中性；不根据任意字符串或 HTML 设置颜色。按照 A 股展示习惯，上涨为红色、下跌为绿色。

报告样式文件增加独立的 Markdown 容器和表格样式：

- 容器允许横向滚动，窄屏不撑破页面；
- 表头、边框、数值对齐和行间距与现有审计页一致；
- 不复用仅作用于聊天抽屉的 `.chat-markdown` 选择器；
- 普通段落、标题和已有报告内容保持现有可读性。

## 预计修改文件

- `backend/reports/repository.py`：增加与持仓快照对齐的盘前行情查询。
- `backend/reports/service.py`：为盘前个性化上下文合并涨跌幅、行情质量和事实时间。
- `backend/reports/pre_market.py`：增加持仓表格标准化、排序、单位、转义和 Markdown 渲染纯函数。
- `backend/reports/pre_market_personalized.py`：完整摘要接入表格；企微生成紧凑摘要。
- `frontend/src/features/reports/components/ReportViewer.tsx`：接入 GFM Markdown 渲染和涨跌单元格组件。
- 研报审计页面对应样式文件：增加响应式表格和涨跌颜色。
- 相关后端与前端测试文件：覆盖新契约和回归边界。

实现阶段以实际测试组织为准定位既有测试文件，不新建重复测试套件。

## 失败与降级规则

- 行情查询失败按现有报告错误边界处理，不调用外部数据源补偿。
- 单个标的缺少价格、涨跌幅或仓位时只将相应单元格显示为 `--`，其他行仍正常展示。
- 数据过期或不可用时显示 `⚠️`，但报告仍可生成、保存和推送。
- 企业微信不支持表格不会影响 Web 完整报告；推送始终提供现有报告详情链接。
- 无持仓分支不构造空表，不改变共享宏观报告内容。

## 测试策略

实施遵循先红后绿：

1. 后端纯函数测试：字段格式、A 股/基金单位、仓位排序、稳定次序、空值、质量标记、Markdown 转义和无持仓文案。
2. Repository 测试：只读取报告时点前事实、价格对齐、质量和 `sourceAsOf`，不匹配时不伪造涨跌幅。
3. Service 测试：仅盘前个性化上下文执行行情增强，不改变公共持仓 API 契约。
4. 报告测试：完整摘要包含标准 Markdown 表格并保留原有章节、条目和证据。
5. 推送测试：最多两项、完整行、总长度不超过 200 字，Outbox 仍使用 `markdown` 并追加详情链接。
6. 前端测试：GFM 表格真实渲染为 `table`，正负百分比分别获得上涨/下跌样式，缺失值中性，原始 HTML 不被执行。
7. 回归验证：后端目标测试、完整后端测试、前端单元测试、类型检查和生产构建。

## 验收标准

- 有持仓用户的 08:35 审计报告显示七列表格，按仓位降序排列。
- 表格价格、涨跌幅和质量均来自已持久化且时间一致的事实；不可用值明确显示 `--`。
- `STALE` 与 `UNAVAILABLE` 标的名称带 `⚠️`。
- 无持仓但有关注的用户看到“暂无持仓，今日市场概况”。
- Web 上涨红、下跌绿，移动端可横向浏览表格。
- 企微消息不超过 200 字、可正常送达，并可通过既有链接进入完整报告。
- 08:30 共享宏观简报不泄露任何用户级信息，其他报告时段与订阅行为无回归。
