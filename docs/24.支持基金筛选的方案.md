# WealthSail 项目评估：建议继续开发，不要完全重做

建议：基于现有项目扩展

我已经通过连接到 WealthSail 工作区的代码工具，读取了项目需求文档、架构设计，以及部分前后端实现。

初步结论很明确：WealthSail 非常适合承载我们刚才讨论的基金投资决策系统。

它并不是一个简单的基金展示程序，而是已经具备资产管理、市场数据采集、基金筛选、风险政策、投研报告、定时任务和消息推送等能力的完整平台。

因此，我建议：

保留 WealthSail 作为主项目，在现有架构中新增一个相对独立的「智能基金投资决策引擎」，而不是再建一套独立的 Web 系统。

不过，现有项目的重点更偏向于管理已经持有的资产、市场观察与投研复盘；我们现在希望新增的重点是：

> 在全市场中寻找有投资价值的基金，综合经济周期、估值、技术指标和风险，在适合的时机给出可解释、可验证的买卖决策参考。

这两部分彼此互补，完全值得整合。

## 三、源码审查发现的五个关键问题

这些问题直接关系到系统能不能真正帮你提高决策质量。

问题 1：历史低估指标容易产生误导

`backend/integrations/fund_nav_ranges.py` 的 `current_percentile` 实际计算的是：

\\[ \frac{当前累计净值-历史最低累计净值}{历史最高累计净值-历史最低累计净值} \\]

它不是历史 PE/PB 估值分位，也不是时间分布意义上的百分位数。

然而，页面将这类结果用于“历史低估”分类。

建议：改名为“历史净值区间位置”，单独新增真正的指数估值分位。不能直接以基金净值处于低位作为低估买入的理由。

问题 2：历史行情数据不足以支撑全面择时

`backend/jobs/fund_nav_sync.py` 对新纳入同步的已持有场外基金，初次默认回填约 60 个交易日。

这远远不够进行 MA200、长期动量、完整市场周期及多年回测。

此外，当前基金筛选的区间缓存主要保存最高、最低、最新净值等汇总数据，不是可直接供技术分析使用的完整日线序列。

建议：建立统一历史时序数据服务，覆盖指数、场内 ETF 的复权 OHLCV，以及场外基金的可比净值/收益序列。

问题 3：筛选池还不是真正的全市场机会池

`backend/funds/service.py` 的快速筛选只使用已经缓存的基金，单类默认最多返回 20 条。基金净值缓存主要通过用户搜索或现有持仓逐步积累。

因此，当前没有实现全市场完整的机会排名。

建议：先建稳定的指数与基金主数据关系，再分批更新候选基金的历史数据和评分，而不是依赖用户搜索才触发分析。

问题 4：宏观简报还不是经济周期决策引擎

`backend/reports/pre_market_macro.py` 已经支持经济数据摘要，包括 PMI、CPI 的基本解释。

但是它主要解释单期数据，并未建立完整的增长、通胀、信用、流动性趋势与资产预期收益的关系模型。

建议：保留现有简报，新建具有历史数据版本、指标发布日、趋势得分和情景不确定性的宏观分析服务。

问题 5：现有风控还需要组合层面的增强

`backend/risk/service.py` 已经能检查单只持仓比例、现金比例以及最近约 60 个交易日的组合回撤等。

但还需要完善基金相关性、行业集中度、因子暴露、流动性、波动率和情景压力测试。

建议：在已有投资政策机制上扩展，不重新建设账户和风险政策系统。

这五项中，我认为历史数据、指标语义和回测真实性最值得优先解决。否则界面做得再漂亮，结论也未必可靠。

## 四、推荐的技术架构：主项目不变，新增独立分析内核

不推荐另建一个完整的 Streamlit 项目，也不推荐现在将整个项目拆分为很多微服务。

最适合的是「模块化单体 + 独立计算模块 + 现有 Worker」。

WealthSail React Web 工作台

基金机会排行榜 · 指数分析 · 买卖信号 · 回测结果 · 投资组合

现有 FastAPI

权限控制 · 数据查询 · 用户投资政策 · 分析任务提交

新增：基金投资决策引擎

宏观周期引擎

增长、通胀、流动性

基金选优引擎

估值、成本、质量

技术择时引擎

MACD、KDJ、MA、动量

回测评估引擎

交易成本、收益、回撤

组合优化引擎

仓位、相关性、再平衡

投资信号引擎

解释、风控、提示

复用现有基础设施

PostgreSQL · Worker · 行情适配器 · 企业微信 · 审计 · Outbox

这里最重要的设计原则是：每一个算法都能独立测试，所有投资信号都可以追溯到所使用的数据、参数和策略版本。

大模型负责分析、解释、比较不同情景；不要让大模型直接计算技术指标、决定仓位或凭空生成回测收益率。

### 代码建议怎么组织？

建议沿用现有目录，并新增：

```
WealthSail/
├── backend/
│   ├── funds/            # 保留现有基金主数据和净值查询
│   ├── market/           # 扩展历史日线与宏观数据
│   ├── indicators/       # 新增 MA/MACD/KDJ/RSI
│   ├── investment/       # 新增基金评分与信号决策
│   ├── backtest/         # 新增回测与基准对比
│   ├── risk/             # 扩展仓位和组合风控
│   └── jobs/             # 新增日终批量分析任务
├── frontend/src/features/
│   ├── fund-screener/    # 升级基金筛选
│   ├── investment/       # 新增投资决策工作台
│   └── backtest/         # 新增策略验证页面
├── migrations/           # 新增数据表与访问权限
└── tests/                # 新增算法和回测测试
```

建议优先统一 `reference.instruments` 与基金主数据之间的标的映射，避免场内 ETF、场外基金、联接基金、跟踪指数之间产生重复或模糊关联。

已有的 `market.market_observations` 可以继续管理有来源、版本和质量状态的观测数据；新增高频访问的历史行情、指标快照和回测结果时，再根据查询性能设计专用存储结构。

## 五、建议的实际改造顺序

我建议分五个阶段，而不是同时建设全部功能。

P0：可信基金与指数数据底座

统一 ETF、场外基金、指数和联接基金关系；建立完整日线；修正历史分位语义；补充交易日、复权、披露时间和缺失状态。

验收标准： 能稳定取得足以计算长期指标的历史序列，且异常数据不能进入买卖评分。

P1：技术指标与基金机会筛选

实现 MA、MACD、KDJ、RSI、动量、ATR；显示趋势状态和原因；建设候选基金排行榜。

验收标准： 指标可与独立计算结果核对，评分可复现，不将评分误称为胜率。

P2：回测与策略评价

对比买入持有、定投、MA 趋势和多指标策略，包含实际费用及成交时差，并加入样本外验证。

验收标准： 不存在前视偏差，能清楚看到策略是否真正优于简单基准。

P3：宏观经济、估值与组合优化

整合经济周期、指数估值和基金费用与跟踪质量，补充仓位、相关性、行业重叠、风险预算和再平衡。

验收标准： 能区分“基金值得长期配置”“近期技术趋势适合建仓”“当前组合还能增加多少风险”。

P4：全自动数据更新与人工决策闭环

按数据实际公布时间自动计算信号、生成分析报告、微信推送风险变化，并记录用户决策及后续表现。

验收标准： 每个信号能解释、能追溯、能复盘；数据不足时不发出确定性交易信号；不自动下单。

## 七、继续开发与重新开发，怎么比较？

| 方案                    | 优点            | 缺点                 | 结论     |
| --------------------- | ------------- | ------------------ | ------ |
| WealthSail 内直接堆功能     | 集成最快          | 容易使现有大模块变得臃肿       | 不推荐    |
| WealthSail + 独立投资分析模块 | 复用基础设施，模块边界清晰 | 需要认真设计数据接口         | 最推荐    |
| 新建一套完整 Web 系统         | 完全独立、自由度高     | 重做账户、持仓、权限、通知、数据治理 | 暂不推荐   |
| 独立 Python 研究沙盒        | 算法实验灵活        | 无法自然整合用户资产和完整产品工作流 | 适合辅助研究 |

之前我做的那个 Python/Streamlit ETF 观察台，可以用作算法实验原型；经过验证的指标和策略逻辑再迁移进 WealthSail。不需要长期维护两个独立的投资工作台。

## 八、还有一项必须完成的工程验证

目前已确认工作区是 `master` 分支，提交 `6e7870e`，Git 工作区干净。

仓库中已有大量单元测试，并且 `.github/workflows/ci.yml` 配置了后端测试、前端检查以及 PostgreSQL 环境中的全栈冒烟测试，这是继续扩展的有利条件。

但本次连接提供的是源码读取与测试状态查询，没有执行新测试。测试状态接口返回没有可用执行记录，因此我不能据此断言当前分支所有测试通过，更不能证明真实行情源与生产部署正常。

正式实施前，仍应跑一次完整测试基线，确认数据库迁移、行情同步及现有业务不受新模块影响。

## 最终判断

# WealthSail 应该继续做，而且值得作为长期投资决策平台。

我不建议推倒重来，也不建议简单地给基金筛选页面加 MACD 和 KDJ 就算完成。

最合适的工程方向是：

WealthSail = 投资资产与决策管理平台 + 新增量化基金研究与策略引擎。

新引擎要形成一条可靠的链路：

可信历史数据 → 选指数 → 选基金 → 趋势及估值分析 → 风险检查 → 回测验证 → 生成信号 → 人工决策 → 追踪结果。

我建议下一步先以当前仓库为基线，形成一份正式的 《WealthSail 智能基金投资决策系统扩展设计》，明确复用哪些现有模块、需要新增哪些数据库表/API/计算任务，以及每个阶段的测试验收标准。

其中最先动手的部分，应当是修正基金筛选的估值语义、补齐 ETF/指数历史行情，并建立可独立验证的技术指标引擎。这三项完成以后，后续的择时评分、回测和自动提醒才能有可信的基础。
