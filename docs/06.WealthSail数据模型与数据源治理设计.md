# WealthSail 数据模型与数据源治理设计（v2.0）

> 目标：为 L0/L1 提供最小、可信、可执行的数据内核，并能通过兼容 migration 扩展到 L2–L5
>
> 原则：稳定标识、不可变事实、可重建投影、来源/时点透明、租户默认隔离
>
> 相关文档：[PRD](./01.WealthSail投研平台需求文档.md) · [架构](./02.WealthSail投研平台全栈技术选型与架构评估.md) · [Web 工作台](./09.WealthSail-MVP-Web投研工作台设计与实现规范.md) · [安全](./07.WealthSail安全隐私与合规设计.md)

## 1. 设计目标与边界

### 1.1 本设计解决什么

- 2–3 用户和未来更多用户的数据隔离；
- 股票、场内基金、场外基金共享标的和账本内核；
- 现金、交易、费税、分红和公司行动的可审计记录；
- 行情、净值、基金估值、公告和媒体内容的来源/时点/质量；
- 四时段报告、证据、用户决策和企业微信交互；
- 幂等任务、Outbox、模型运行和审计；
- L2–L5 的多账户、基金穿透、多媒体、回测、多市场和实验性 Agent 扩展。

### 1.2 本设计不做什么

- 不把可变 `positions.quantity/avg_cost` 当唯一事实；
- 不以 symbol 单独标识证券；
- 不用一张超宽宏观表承载所有指标；
- 不把模型聊天记忆当正式决策或成交；
- 不把 secret 明文存入业务 JSON；
- 不为每个资产类型复制一套账户、建议和报告表；
- 不在 L1 建设完整券商订单数据库，但保留明确扩展点。

## 2. Schema 与所有权

建议使用 PostgreSQL schema 表达模块私有边界；应用层不得跨模块直接修改私有表。

| Schema | L0/L1 表 | 后续扩展 |
|---|---|---|
| `identity` | tenants, profiles, tenant_members, accounts, channel_bindings, secret_refs | household/team roles, organizations |
| `reference` | instruments, instrument_aliases, trading_calendars, instrument_cutoff_rules, data_sources | currencies, exchanges, fee schedules |
| `ledger` | ledger_events, ledger_legs, trade_fills, position_lots, position_snapshots, account_nav_snapshots | tax lots, liabilities, margin |
| `market` | source_snapshots, market_observations, corporate_actions | fund disclosures, exposure projections |
| `research` | theses, recommendations, evidence_refs, model_runs | media claims, backtest artifacts |
| `reporting` | reports, report_items, decisions, conversations | report templates, behavior insights |
| `risk` | investment_policies, alert_rules, alert_events | factor models, stress tests |
| `workflow` | jobs, job_runs, interaction_requests, outbox | durable workflow adapter state |
| `audit` | audit_log | compliance retention/export index |
| `media` | L3 不启用 | source_registry, media_items, transcripts, media_claims |
| `execution` | L4 不启用 | broker order_intents, approvals, order status；L1 的用户确认成交事实保存在 `ledger.trade_fills` |

全局标的/数据源表无 `tenant_id`；任何用户资产、研究、报告、风险、消息和审计表必须有 `tenant_id uuid NOT NULL`。

## 3. 稳定标识与通用字段

### 3.1 稳定 ID

| ID | 稳定性 |
|---|---|
| `tenant_id` | 用户/家庭/组织数据边界，L0–L4 不改变 |
| `user_id` | 登录主体，允许一个用户属于多个 tenant |
| `account_id` | 券商/基金/手工账户，不随导入批次改变 |
| `instrument_id` | 全球唯一标的，代码变更/市场别名不改变 |
| `ledger_event_id` | 唯一经济事件，冲正通过新事件引用 |
| `source_id` | 数据/媒体 Provider 稳定标识 |
| `snapshot_id` | 一次可复现来源抓取 |
| `evidence_id` | 报告可引用的证据单元 |
| `model_run_id` | 一次模型执行，包含模型/Prompt/Skill 版本 |
| `report_id` | 一次报告版本，不因消息重发改变 |

建议主键使用 UUIDv7/ULID 以兼顾全局唯一和时间局部性；数据库不支持时使用 `gen_random_uuid()`。

### 3.2 通用时间字段

| 字段 | 语义 |
|---|---|
| `created_at` | WealthSail 首次写入时间 |
| `updated_at` | 可变元数据最后更新时间，不代表市场时点 |
| `published_at` | 来源首次公开内容时间 |
| `as_of` | 数据实际代表的市场/报告时点 |
| `observed_at` | Provider 观察到数值的时间 |
| `retrieved_at` | WealthSail 获取内容时间 |
| `revised_at` | 来源更正或修订时间 |
| `effective_from/to` | 规则/别名/绑定的有效区间 |

所有跨市场时刻使用 `timestamptz`；交易日另存市场本地 `date`。禁止用 `created_at` 代替 `as_of`。

### 3.3 数据质量状态

```text
FRESH       在产品定义的新鲜度窗口内，可用于对应报告
ESTIMATED   模型/组合估算，必须给区间、方法和误差说明
STALE       超出新鲜度窗口，只能作为历史背景
CONFLICT    主备源或版本冲突，需并列/人工或规则解决
UNAVAILABLE 缺失或许可/接口不可用，关键结论应弃权
REVISED     来源已修订，需触发受影响报告重评估
```

## 4. 身份、租户与账户

### 4.1 `identity.tenants`

| 字段 | 类型/约束 | 说明 |
|---|---|---|
| id | uuid PK | tenant_id |
| name | text NOT NULL | 个人/家庭/组织名称 |
| status | text CHECK | ACTIVE/SUSPENDED/CLOSED |
| base_currency | char(3) | MVP=CNY |
| created_at | timestamptz | 创建时间 |

### 4.2 `identity.profiles` 与 `identity.tenant_members`

在 Supabase 部署画像主键 `profiles.id` 必须与 `auth.users.id` 相同，`tenant_members(tenant_id, user_id, role)` 的 `user_id` 引用该稳定认证 subject。MVP 每 tenant 一个 OWNER，但模型允许未来家庭/团队 VIEWER/EDITOR。纯 PostgreSQL 部署通过 `IdentityProvider` Adapter 提供等价 subject，不直接伪造 `auth.uid()`；`006` 中的 profile 仅是数据库隔离 fixture，不是可登录 Auth 用户。

L1 的 Web access token 只绑定一个活动 tenant。用户登录后，Identity/Application 层根据 active membership 生成 `TenantContext(tenant_id, user_id, role, membership_version)`；repository 方法必须显式接收该上下文。`identity.is_tenant_member(target_tenant)` 只是数据库 membership predicate，不负责选择 tenant。后续支持同一用户加入多个 tenant 时，切换动作必须重新校验 membership、签发新的 tenant-scoped token，并使旧 tenant 的浏览器缓存、WebSocket subscription 和后台请求失效。

### 4.3 `identity.accounts`

| 字段 | 约束 | 说明 |
|---|---|---|
| id, tenant_id | PK + FK | 稳定账户与租户 |
| account_type | CHECK | BROKERAGE/FUND_PLATFORM/MANUAL |
| name | NOT NULL | 用户可识别名称 |
| base_currency | char(3) | MVP=CNY |
| provider_ref | text nullable | 外部账户脱敏引用 |
| status | CHECK | ACTIVE/CLOSED |
| opened_on/closed_on | date | 生命周期 |
| version | integer | 乐观锁 |

唯一约束：`(tenant_id, id)`；外部账号原文不落日志。

### 4.4 `identity.binding_challenges`

绑定 challenge 与正式渠道绑定是两个对象。challenge 在已登录用户请求绑定码时创建，记录 tenant/user、channel、`token_hash`、过期时间、尝试次数上限、状态（PENDING/CONSUMED/EXPIRED/CANCELLED）、消费/解决时间、生成幂等键和版本；原 token 只返回一次，不写数据库、日志、URL、分析 SDK 或模型上下文。Web 只能通过 Domain API 读取不含 hash 的本人状态。

WeCom Adapter 校验渠道签名、时间窗、nonce/message ID、allowlist、消息长度和来源限速后，才调用受控 Domain command。消费时对 challenge 加行锁或条件更新，在同一事务中创建正式 binding、写 `binding_id` 并把状态转为 CONSUMED；并发重放只有一个成功。过期、取消和终态 challenge 不可修改或删除。

### 4.5 `identity.channel_bindings`

只记录已经验证成功的 tenant/user、channel、`external_user_hash`、状态、绑定/撤销时间、最后使用和版本，不再承载尚未验证的 binding token。外部用户 ID 可按业务需要加密，索引使用 keyed hash。解绑是 `ACTIVE -> REVOKED` 的软撤销，保留历史引用和追加式审计；普通用户只能管理自己的 binding，跨用户恢复由重新认证的 OWNER/ADMIN 通过受控 Domain API 执行。普通 JWT 使用本人 RLS 加列级 GRANT，只能读取状态 DTO 所需字段，不能读取 `external_user_hash` 或任何新旧 token/hash 列。

现有 `channel_bindings.binding_token_hash/token_expires_at/token_consumed_at/token_attempt_count` 是 002 早期模型的兼容列，008 起不再写入；经过读取统计、双读窗口和升级验证后再在未来 contract migration 删除，不能原地修改已部署 migration。

### 4.6 `identity.secret_refs`

只保存 `secret_name`、Vault/KMS URI、用途、权限范围、版本、轮换时间和 owner，不保存 secret value。Vault/KMS URI 本身仍是敏感基础设施元数据，浏览器 JWT 不具备 `secret_refs` 的表级读取权限；仅受控后端按用途解析。

## 5. 标的主数据

### 5.1 `reference.instruments`

| 字段 | 约束 | 说明 |
|---|---|---|
| id | uuid PK | instrument_id |
| asset_type | CHECK | CN_STOCK/EXCHANGE_FUND/OFF_EXCHANGE_FUND；后续可新增 |
| primary_market | text | SSE/SZSE/FUND_CN 等 |
| trading_currency | char(3) | MVP=CNY |
| canonical_name | text | 标准名称 |
| isin | text nullable | 可得时记录 |
| lifecycle_status | CHECK | ACTIVE/SUSPENDED/DELISTED/LIQUIDATED/MERGED |
| inception_date/end_date | date | 生命周期 |
| metadata | jsonb | 只放非核心、低查询扩展信息 |

### 5.2 `reference.instrument_aliases`

表达 `instrument_id + alias_type + alias_value + market + effective_from/to`，支持代码变更、基金简称和不同 Provider symbol。唯一约束覆盖有效区间，避免跨市场同 symbol 错配。

### 5.3 `reference.trading_calendars`

按 market/date 记录交易、半日市、可选的市场级回退截止和时区。四时段任务依赖日历，不以服务器工作日判断；`fund_cutoff_time` 为空时不能擅自使用 15:00，且该字段不能覆盖标的/销售渠道规则。

### 5.4 `reference.instrument_cutoff_rules`

按 `instrument_id + sales_channel + effective_from/to + rule_version` 保存截止时间、时区和来源。14:30 报告先解析用户实际销售渠道的有效规则，再考虑有证据的市场级回退；规则缺失、冲突或已过截止时明确提示/弃权，不生成“仍可申赎”的确定性结论。

### 5.5 `reference.data_sources`

记录 Provider 名称、类型、许可模式、允许用途、商业/再分发状态、SLA、频率限制、优先级、备用源、状态和 owner。

## 6. 不可变投资组合事件账本与投影

MVP 采用“不可变事件 + 多腿经济效果 + 可重建投影”。它解决投资组合现金/份额事实、幂等和冲正问题，但当前模型没有完整会计科目、借方/贷方和本位币平衡字段，因此不把它误称为通用会计总账。未来融资、负债、跨账户清算需要正式 debit/credit account 时，通过新增 posting/account 表扩展，稳定 event ID 不变。

### 6.1 `ledger.ledger_events`

核心字段：

```sql
CREATE TABLE ledger.ledger_events (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id uuid NOT NULL REFERENCES identity.tenants(id),
    account_id uuid NOT NULL REFERENCES identity.accounts(id),
    event_type text NOT NULL CHECK (event_type IN (
        'CASH_IN', 'CASH_OUT', 'BUY', 'SELL', 'DIVIDEND_CASH',
        'DIVIDEND_REINVEST', 'FEE', 'TAX', 'SPLIT', 'MERGER',
        'TRANSFER_IN', 'TRANSFER_OUT', 'ADJUSTMENT', 'REVERSAL'
    )),
    status text NOT NULL CHECK (status IN ('PENDING', 'CONFIRMED', 'REVERSED')),
    trade_date date NOT NULL,
    occurred_at timestamptz NOT NULL,
    source_id uuid REFERENCES reference.data_sources(id),
    external_event_id text,
    idempotency_key text NOT NULL,
    reverses_event_id uuid REFERENCES ledger.ledger_events(id),
    description text,
    schema_version integer NOT NULL DEFAULT 1,
    created_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, idempotency_key)
);
```

业务事件确认后不可 UPDATE/DELETE 经济字段。元数据更正或错误用新 `REVERSAL`/更正事件表达。除单列外键外，正式 migration 使用 `(tenant_id, account_id)` 复合外键，防止 tenant A 的有效事件引用 tenant B 的有效账户。

### 6.2 `ledger.ledger_legs`

```sql
CREATE TABLE ledger.ledger_legs (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id uuid NOT NULL REFERENCES identity.tenants(id),
    event_id uuid NOT NULL REFERENCES ledger.ledger_events(id) ON DELETE RESTRICT,
    leg_type text NOT NULL CHECK (leg_type IN ('CASH', 'INSTRUMENT', 'FEE', 'TAX')),
    instrument_id uuid REFERENCES reference.instruments(id),
    currency char(3),
    quantity numeric(28, 10),
    amount numeric(28, 8),
    unit_price numeric(28, 10),
    lot_ref uuid,
    created_at timestamptz NOT NULL DEFAULT now(),
    CHECK (
        (leg_type = 'INSTRUMENT' AND instrument_id IS NOT NULL AND quantity IS NOT NULL)
        OR
        (leg_type <> 'INSTRUMENT' AND currency IS NOT NULL AND amount IS NOT NULL)
    )
);
CREATE INDEX ledger_legs_event_idx ON ledger.ledger_legs(tenant_id, event_id);
```

正式 migration 使用 `(tenant_id, event_id)` 复合外键引用 `ledger_events(tenant_id,id)`；仅验证当前 leg 自身的 RLS 不足以阻止跨租户关联。

应用服务按 event_type 验证腿组合：

- BUY：正证券数量 + 负现金 + 可选负费用/税；
- SELL：负证券数量 + 正现金 + 可选负费用/税；
- CASH_IN/OUT：单现金腿；
- DIVIDEND_REINVEST：分红应收/现金语义 + 正证券数量，方法和 NAV 可追溯；
- REVERSAL：与原事件经济效果相反并引用原事件。

数据库事务确保事件和全部腿原子提交；应用 property test 验证现金/证券和事件规则守恒。

### 6.3 `ledger.trade_fills`：决策与真实成交之间的边界

`reporting.decisions` 只表达用户是否采纳研究建议，不能产生持仓变化。用户对一笔已经发生的真实买卖进行自然语言补录、导入对账文件或接收券商回报时，先形成 `trade_fills(DRAFT)`，包含 tenant/account/instrument、side、quantity、unit_price、fee、trade_date、occurred_at、source_type、created_by 与幂等键。用户校对或回报验证后，领域服务在同一事务中创建该成交对应的账本事件并把 fill 置为 `CONFIRMED`、关联 `ledger_event_id`；拒绝/取消不会入账。单笔 fill 不携带初始入金，也不能在确认时隐式创建无关 CASH_IN。

确认、拒绝或取消后的 fill 不可修改/删除。`(tenant_id, account_id/decision_id/ledger_event_id/created_by)` 使用组合外键，防止跨租户引用。L1 的 `USER_CONFIRMED` / `STATEMENT_IMPORT` 与 L4 的 `BROKER_FILL` 复用同一事实表；L4 订单意图、报单与撤单状态另建 execution 模块，不污染已成交事实。

### 6.4 `ledger.portfolio_import_batches` / `portfolio_import_items`

新用户初始化需要同时表达期初可用现金和多个股票/基金持仓，不能伪装成一笔成交。`portfolio_import_batches` 保存 tenant/account、创建人、来源类型（MANUAL/CSV/NATURAL_LANGUAGE）、状态（DRAFT/CONFIRMED/CANCELLED）、输入摘要 hash、幂等键、版本和确认/取消时间；`portfolio_import_items` 保存 CASH_BALANCE 或 POSITION 项、instrument、数量、单位成本、基线日期、来源行号和结构化校验错误。CASH_BALANCE 的 `cash_amount` 表示基线日的可用现金，不代表发生了一笔入金；用户同时提供的“总资产”只用于 `现金 + 持仓成本` 差额校验，不直接入账。

只有 DRAFT 可校正。确认命令以 `(tenant_id,idempotency_key)` 去重并带 expected version，在一个事务中锁定批次、重新检查所有项目和当前 membership，为每个 item 创建一条 `ADJUSTMENT` 期初事件及分录、重建投影，再将批次置为 CONFIRMED；`ledger_events.import_batch_id + import_item_id` 提供不可变来源链和每 item 唯一原始 effect。期初导入不创建 `CASH_IN/BUY` 或 `trade_fills`，因此不会虚构历史资金流/成交；组合收益从基线日开始。任一步失败全部回滚。终态批次不可修改/删除，撤销已确认批次按来源链逐项追加 REVERSAL。原始自然语言/CSV 是否保留由隐私策略决定，默认只保存受控摘要和行级错误，不进入模型长期记忆。

### 6.5 `position_lots` 和快照

- `position_lots`：从确认账本派生的开放批次，包含 acquired_at、quantity_open、cost_amount、currency、projection_version；
- `position_snapshots`：按 account/instrument/as_of 的数量、成本、行情/估值、价值、状态；
- `account_nav_snapshots`：按 account/as_of 的现金、资产、负债、NAV、基准和数据状态。

它们均带 `source_ledger_cursor`，可删除后从账本重建。用户纠错不能直接修改投影。

### 6.6 对账

导入/Provider 余额与投影比较，生成 reconciliation run 和差异项。差异经用户确认后产生 ADJUSTMENT，而不是覆盖余额。MVP 可在 `audit_log` 保存运行摘要；L2 增加正式 reconciliation 表。

### 6.7 `ledger.account_performance_baselines`：累计收益跟踪边界

当前持仓快照只知道剩余份额和成本，不能证明导入前完整入金、出金与已实现收益。累计收益因此使用
独立的账户级起点，而不复用容易误导的 `account_nav_snapshots.cumulative_pnl` 遗留列。每个版本保存
`tenant_id/account_id`、`baseline_as_of`、`baseline_total_asset`、
`initial_cumulative_pnl`、`source`、`version`、`created_by`、幂等键、请求哈希和创建时间。

- 首次完整账户 NAV 自动建立 version 1，历史累计收益默认为 0；既有完整 NAV 在 migration 039
  取最新快照建立 `AUTO_MIGRATION` 起点，未来账户由 `AUTO_NAV` 触发器初始化；
- 用户只在能从旧平台确认导入前历史累计盈亏时追加 `USER` 版本。新版本继承起点日期与起点资产，
  只修订历史累计收益；禁止 UPDATE/DELETE，避免重写已展示过的收益口径；
- 当前累计收益按账户计算
  `initial_cumulative_pnl + current_total_nav - baseline_total_asset - net_external_flow`；
  `net_external_flow` 只汇总起点后、当前 NAV 日之前已确认且未被 REVERSAL 的
  `CASH_IN/CASH_OUT` 现金腿，现金流金额保留正负号；
- BUY/SELL、分红、费用、税和期初 ADJUSTMENT 都不是外部入金，不能进入净外部资金流；
- 当前作用域内任一账户缺完整 NAV 或基线时，组合累计收益返回空值，不发布部分账户汇总；
- 累计收益率/TWR 需要按现金流切分时间区间，当前仍不发布，不能用累计收益除以静态本金近似。

RLS 允许 API 租户成员读取，追加版本还要求 OWNER/ADMIN/EDITOR、`created_by=auth.uid()` 且用户是
该账户当前 `BENEFICIAL_OWNER/JOINT_OWNER`。浏览器数据库角色不能直读，Worker 不能插入用户版本。
API 以 `If-Match` 校验 version、以 `(tenant_id,idempotency_key)` 防重，并在同一事务写审计日志。

## 7. 市场、基金与公司行动数据

### 7.1 `market.source_snapshots`

记录 `source_id`、retrieval key、origin URI、published_at、as_of、retrieved_at、revised_at、content_hash、schema version、quality status、许可标签、对象存储引用和解析错误。原始 payload 可按许可/隐私决定是否保存，业务表不保存未经验证的大 JSON。

### 7.2 `market.market_observations`

长表而非每个指标一列：

| 字段 | 说明 |
|---|---|
| subject_type/id | INSTRUMENT/INDEX/MACRO_SERIES/FUND |
| field_code | CLOSE/NAV/ESTIMATED_NAV/FX/PMI 等版本化定义 |
| value/lower_value/upper_value | 点值或估值区间 |
| unit/currency | 单位与币种 |
| observed_at/as_of | 观察与代表时点 |
| snapshot_id/source_id | 来源和可复现快照 |
| quality_status | FRESH/ESTIMATED/STALE/CONFLICT/UNAVAILABLE/REVISED；缺省为 UNAVAILABLE，必须由校验逻辑显式提升 |
| method_version | 估值/计算方法 |

唯一约束：`(subject_type, subject_id, field_code, as_of, source_id, revision)`。

### 7.3 基金 14:30 数据

场外基金报告至少引用：

- 最新确认 NAV 与净值日期；
- 盘中估值 lower/upper/value、方法版本和 `ESTIMATED`；
- 最近基金持仓披露报告期、公告日期和覆盖率；
- 相关指数/行业观测；
- 基金申赎规则和截止时间来源。

持仓披露超过产品新鲜度阈值时，估值质量降级；不可用时不写固定默认值。

### 7.4 `market.corporate_actions`

表达现金/股票分红、拆合股、配股、合并、代码变更、退市/清盘。唯一外部事件 ID + revision；更正产生新 revision 并触发受影响投影重建。

## 8. 研究、证据和模型运行

### 8.1 `research.theses`

按 tenant/account/instrument 保存用户论点：summary、horizon、catalysts、risks、invalidation_conditions、target/valuation assumption、status、version、有效期和 owner。修改采用乐观锁，历史版本进入审计或 thesis_versions（L2）。

### 8.2 `research.model_runs`

记录 provider/model、Prompt template/version、Skill/version、input snapshot hashes、tool calls、structured output hash、Token、成本、开始/结束、状态、error class 和 correlation ID。敏感输入只保存脱敏引用。

### 8.3 `research.recommendations`

推荐是研究对象，不是订单：

- tenant/instrument/account optional；
- recommendation_type：HOLD/OBSERVE/REVIEW/REDUCE_CANDIDATE/ADD_CANDIDATE/ABSTAIN；
- horizon、benchmark、confidence、valid_until；
- thesis_id、model_run_id、policy_check_status；
- summary、counter_case、invalidation_conditions；
- status：DRAFT/VALIDATED/PUBLISHED/EXPIRED/RETRACTED。

MVP 避免 `BUY/SELL + 精确点位` 作为默认输出；未来具体订单必须进入 execution 模块和人工审批。

### 8.4 `research.evidence_refs`

每条证据关联 recommendation/report/model_run，包含 source snapshot、origin locator、excerpt（在许可范围内）、claim type、published_at/as_of、quality、content hash 和 relevance。证据删除/撤权后可标记不可用并触发受影响报告重评估。

## 9. 报告、对话与决策

### 9.1 `reporting.reports`

核心字段：tenant、report_session、trade_date、version、status、as_of、quality_status、summary、model_run、policy check、valid_until、job_run、supersedes_report。唯一约束：`(tenant_id, trade_date, report_session, version)`。

状态：DRAFT/VALIDATED/PUBLISHED/PARTIAL/ABSTAIN/EXPIRED/RETRACTED。

### 9.2 `reporting.report_items`

按报告承载事实/风险/待办/提醒/组合贡献等条目：item_type、subject、severity、title、body、evidence coverage、data status、sort order。避免把多资产日报塞进单 symbol/action 表。

### 9.3 `reporting.decisions`

记录 report/recommendation、user_id、`decision_action`（ACCEPTED/IGNORED/DEFERRED）、生命周期 status（RECORDED/RETRACTED/SUPERSEDED）、reason、correction、decided_at、idempotency_key 与 previous_decision_id。`decisions` 只记录已经发生的用户选择，不保存“等待用户选择”的 `PENDING` 占位；采纳只代表认知决策，绝不等同于订单或成交。用户纠正追加新记录并把旧记录标为被替代，不覆盖历史。

### 9.4 对话

MVP 可保存结构化会话消息的脱敏摘要和工具调用引用，不默认永久保存全部原始聊天。会话消息必须 tenant scoped；任何模型记忆均是派生索引，可删除/重建，不能包含其他 tenant 内容。

## 10. 风险和提醒

### 10.1 `risk.investment_policies`

账户/tenant 级：目标、期限、基准、最大回撤、现金需求、允许资产、单标的/资产上限、提醒预算、版本、生效区间、确认人/时间和 `policy_status`。所有百分比缺省为空，禁止把示例性的 15% 回撤、30% 单仓或股债金比例当作通用政策。

L1 Web 只提交基准、期限、最大回撤、单标的上限、提醒预算、静默和当前股票/基金范围内可验证的约束；黄金、债券和大宗目标字段只是空扩展点，不进入 L1 DTO、完整性求和或建议计算。用户明确确认且通过后端完整性/适用资产校验后，Domain API 以 expected version 原子创建新的 CONFIRMED 版本并退役旧版本；新确认必须记录 `confirmation_provenance=USER_CONFIRMED`、确认人和确认时间，已确认内容不得原地覆盖。Migration 008 之前已有但无法证明确认人/时间的政策标记为 `LEGACY_MIGRATED`，不得伪造确认元数据；它可以在同一事务中退役并由用户重新确认的新版本替代。只有当前有效且适用的 CONFIRMED 政策可参与数量、报告和再平衡候选计算，DRAFT 只用于预览；legacy 政策在重新确认前应在 API/UI 明示来源不完整。

### 10.2 `risk.alert_rules`

绑定 tenant + account/instrument/thesis，包含 rule_type、条件 schema version、严重度、静默窗口、有效期、状态和 version。规则条件使用受控 DSL/JSON Schema，不执行任意代码。

### 10.3 `risk.alert_events`

保存 fingerprint、triggered_at、source snapshot、状态（OPEN/SUPPRESSED/DELIVERED/ACKNOWLEDGED/EXPIRED/CANCELLED）、抑制/取消原因和 Outbox 引用。应用生成稳定 `dedupe_key = tenant + rule + reason + window`，数据库以 `(tenant_id,dedupe_key)` 唯一索引防止同一窗口重复。

## 11. Workflow、Outbox 与审计

### 11.1 `workflow.jobs` / `job_runs`

job 定义 schedule、calendar、tenant、report session、model/provider pin、enabled、version；run 保存 job_key、planned/start/end、status、attempt、lease、input/output references、error_class。`job_key` 唯一。

### 11.2 `workflow.interaction_requests`

卡片发送前，报告/建议、待交互请求和 Outbox 必须在同一数据库事务中提交。待交互请求保存 `tenant_id`、`user_id`、`channel_binding_id`、report/recommendation 引用、`request_type`、`allowed_actions`、带密钥摘要后的 `action_token_hash`、有效期、状态、消费动作、payload schema version 与幂等键。原始 action token 仅发送给绑定用户，不写数据库、日志或模型上下文。

状态机只有以下单向迁移：

```text
OPEN --合法回调--> CONSUMED(action, resolved_at)
OPEN --到期任务--> EXPIRED(resolved_at)
OPEN --撤销/失权--> CANCELLED(resolved_at)
```

终态不可再次更新或删除；身份、绑定、允许动作、token 摘要和业务引用在创建后不可修改。回调事务以行锁或条件更新消费 `OPEN` 请求，并在同一事务追加 `reporting.decisions`；重复回调返回第一次结果，不产生第二条有效决策。`ACCEPTED` 不创建成交，成交仍须由券商回报或独立二次确认进入 `trade_fills`。

数据库使用 `(tenant_id, idempotency_key)` 和 `(tenant_id, action_token_hash)` 唯一约束，并用以下同租户复合外键闭合对象图：

- `(tenant_id, user_id) -> identity.tenant_members`；
- `(tenant_id, channel_binding_id) -> identity.channel_bindings`；
- `(tenant_id, report_id) -> reporting.reports`；
- `(tenant_id, recommendation_id) -> research.recommendations`。

普通 JWT 只能读取 `user_id = auth.uid()` 的本人请求，不能读取其他 tenant 成员的请求，也没有 `action_token_hash`、内部幂等键列权限；不能直接插入、消费或删除。只有受控 Domain API/Worker 可执行状态迁移。

### 11.3 `workflow.outbox`

```sql
CREATE TABLE workflow.outbox (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id uuid NOT NULL REFERENCES identity.tenants(id),
    topic text NOT NULL,
    aggregate_type text NOT NULL,
    aggregate_id uuid NOT NULL,
    payload jsonb NOT NULL,
    schema_version integer NOT NULL,
    idempotency_key text NOT NULL,
    available_at timestamptz NOT NULL DEFAULT now(),
    status text NOT NULL CHECK (status IN ('PENDING', 'SENDING', 'SENT', 'DEAD')),
    attempt_count integer NOT NULL DEFAULT 0,
    last_error_class text,
    locked_at timestamptz,
    locked_by text,
    external_message_id text,
    sent_at timestamptz,
    created_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, topic, idempotency_key)
);
```

业务对象和 Outbox 同事务提交。Consumer 通过 lease/lock 抢占任务，发送后记录渠道消息 ID；发送超时但结果未知时先查回执/按 idempotency key 重试。Python Adapter 的进程内 `set` 只用于本地原型，不能作为生产幂等依据。

### 11.4 `audit.audit_log`

append-only：tenant、actor type/id、action、resource type/id、request/correlation、before/after hash 或受控差异、reason、IP/device（按隐私策略）、created_at。账本/决策/绑定/权限/模型/Skill/订单相关审计保留期由合规模式决定。

## 14. RLS 与权限基线

### 14.1 成员检查函数

```sql
CREATE OR REPLACE FUNCTION identity.is_tenant_member(target_tenant uuid)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
STABLE
SET search_path = identity, public
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM identity.tenant_members tm
    WHERE tm.tenant_id = target_tenant
      AND tm.user_id = auth.uid()
      AND tm.status = 'ACTIVE'
  );
$$;
```

函数 owner、execute privilege 和 search_path 必须锁定并测试，防止 SECURITY DEFINER 注入。

### 14.2 tenant 表模板

```sql
ALTER TABLE reporting.reports ENABLE ROW LEVEL SECURITY;
ALTER TABLE reporting.reports FORCE ROW LEVEL SECURITY;

CREATE POLICY reports_select_member
ON reporting.reports
FOR SELECT
USING (identity.is_tenant_member(tenant_id));
```

正式 migration 对 SELECT/INSERT/UPDATE/DELETE 分别按角色设计：active member 可读本人 tenant；EDITOR 只修改允许的账户、论点和风险配置；决策、成交、账本、投影、报告事实、Workflow 和审计由受控 Domain API/Worker 写入。审计、分录和已确认账本对普通用户不可 UPDATE/DELETE。`secret_refs`、原始 `jobs/job_runs/outbox/audit_log` 对所有浏览器 JWT 撤销 SELECT，OWNER/ADMIN 也只能经 Domain API 获取脱敏运维 DTO。RLS 是逻辑行隔离而不是物理分库，必须与表/列级 GRANT、所有 tenant 子资源的复合外键、应用鉴权和外部缓存/队列 tenant scope 共同使用。CI 检测任何含 `tenant_id` 的表是否启用并强制 RLS、是否有适用 policy。

### 14.3 后端角色

- 浏览器：用户 JWT + RLS；
- Agent/Hermes：调用 scoped API，无 DB 凭据；
- Worker：最小权限数据库角色，仅所需 schema/函数；
- service role：仅受控后端管理任务，绝不进入通用 Agent、前端、日志或教程示例；
- migration role：独立部署凭据，不用于运行时。

## 16. Migration 与兼容

### 16.1 规则

- migration 文件只前进，不手工修改已部署版本；
- schema/API/event 都有版本；
- 默认 additive change；
- 新 NOT NULL 列先 nullable/默认，回填验证后收紧；
- 索引并发创建；大回填可恢复、限速并记录 cursor；
- 破坏性删除经过读取统计、双读对比、回滚窗口和审批。

仓库以 `scripts/migrate.py` 和数据库 migration ledger 管理 `migrations/` 内的 schema migration；runner 按编号执行、记录 SHA-256 checksum，并拒绝已应用文件发生漂移。当前 schema 演进覆盖 001–019，其中原 006/010 演示数据已移入 `seeds/dev/`，不得进入生产 ledger。007/008 保留既有安全与 Web 基础升级语义，009 收敛 Domain API 写权限，011/012 增加受控身份能力，013 补齐会话轮换、邀请、Worker/Outbox lease、投影完整性、基金披露和报告证据，014–016 为已发布的企业微信、情绪与早期手工持仓增量，017 用正式导入状态机取代虚构交易写法并收紧角色，018 为市场情绪增加来源/时间/覆盖率/质量/方法版本，019 允许 Domain API 在 TenantContext 内为全部有效 binding 展开独立投递。任何历史跨租户引用在增加复合外键前都必须使 migration 失败并要求人工调查，不静默改写经济事实；旧 binding token 兼容列暂不删除，旧版已确认政策仍以 `LEGACY_MIGRATED` 保留未知事实，不得回填虚构确认人。

### 16.2 expand–migrate–contract 示例

为 L2 基金穿透增加 `fund_holding_disclosures`：

1. Expand：新表和 projection version，旧 portfolio API 不变；
2. Migrate：导入历史披露，计算新 exposure，与旧行业估算并行比较；
3. Switch：新增可选 `lookthrough` API 字段，客户端容忍缺失；
4. Contract：只删除被证明无消费者的临时比较字段，ledger/instrument 不变。

### 16.3 投影重建

每个 projection 保存 code/schema version 和 source cursor。重建在影子表完成，校验数量/金额/抽样后原子切换；原投影保留回滚窗口。

## 17. 数据质量与治理运行

### 17.1 Provider 上线 Gate

- 商业/研究用途和再分发许可明确；
- 字段、单位、复权、时区、交易日历和错误码 contract fixture；
- 新鲜度/完整性阈值；
- 限流、SLA、成本和备源；
- schema drift 告警；
- 退出和数据删除计划。

### 17.2 冲突处理

主备源冲突时保留双方 observation，不直接覆盖。解析单位/复权/时区差异；无法自动解决则 `CONFLICT`，报告弃权或并列说明。后续解决写 resolution/audit，不删除原值。

### 17.3 修订传播

来源 revision 触发影响分析：受影响的 market observation、报告、建议、评估和投影进入重算队列；已发送报告标注修订并通过新版本纠正。

## 18. 测试不变量

必须自动验证：

1. 任意 tenant 表均无跨租户读写；
2. 相同 idempotency key 只产生一次经济效果；
3. 任意进程崩溃点恢复后账本投影一致、同一成交只有一个经济效果、Outbox 不重复产生业务副作用；
4. BUY/SELL/分红/费税/公司行动/冲正的投影结果符合手算 fixture；
5. 投影清空重建与原结果一致；
6. 陈旧/冲突/不可用数据不会产生伪实时建议；
7. 基金 14:30 输出始终带估算、区间、方法和时点；
8. schema v1 消费者容忍 v1 新增可选字段并拒绝未知 major；
9. RLS migration 新增 tenant 表遗漏 policy 时 CI 失败；
10. binding challenge 过期、暴力尝试、并发消费、撤权和重放不会创建第二个 binding；
11. 初始化导入批次任一步失败全部回滚，相同幂等键只产生一次现金和持仓效果；
12. DRAFT 政策不参与计算，确认并发由 version 拒绝，L1 不能提交黄金/债券/大宗目标；
13. 媒体来源撤权后不可再生成新报告引用，历史审计按策略保留。
