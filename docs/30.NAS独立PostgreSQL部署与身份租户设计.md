# NAS 独立 PostgreSQL 部署与身份租户设计

日期：2026-10-22。适用于现有 PostgreSQL 18 NAS 服务和 WealthSail 独立部署。

## 1. 目标与已确认条件

- 数据库使用用户现有的 `postgres:18-bookworm` 容器，不部署 Supabase。
- 数据库容器名/网络 DNS 为 `postgres`，容器端口 `5432`，管理员名为 `admin`。
- 已有跨 Compose 网络为 `global-postgres-network`。
- 现有默认库 `prismscore_db` 属于其他应用；WealthSail 使用独立的 `wealthsail` 库。
- 保留当前登录页、邀请注册、设置页、租户成员、平台管理员和账户归属体验。
- 不复制 PostgreSQL Compose 中的管理员密码进源码、示例、镜像或运行时 API/Worker。
- 本机没有 Docker。执行可运行的本地测试，NAS 上完成 PostgreSQL 18 与容器端到端验收。

用户已确认：空库首装，不迁移原 Supabase 数据；Web 使用 HTTPS 域名或 NAS 反向代理。初始化工具不得覆盖已有用户、业务数据或重置既有密码。

2026-10-23 补充：采用 `wealth.sinojelly.kdns.fr` + Cloudflare Tunnel/Access；前端额外加入独立 edge 网络，API/Worker 的数据库边界不变，详细方案见 [外网接入设计](../external-access/DESIGN.md)。

模型配置更新：聊天、普通报告的模型分析和每日公共研究统一使用 Codex，详见 [Codex 统一模型与 NAS 认证指南](./32.Codex统一模型与NAS认证操作指南.md)。下述安装流程包含 Codex Runner 和独立认证卷。

## 2. 核心决策

### 2.1 继续使用已有认证，不引入新的身份服务

项目实际已经自行完成 bcrypt 密码校验、HS256 JWT 签发、HttpOnly refresh cookie、会话撤销和邀请注册。浏览器只访问同源 `/api/v1`，不依赖 Supabase SDK。

`identity.profiles` 存用户资料和密码哈希；`identity.tenants` 存租户；`identity.tenant_members` 存成员角色。`identity.platform_roles` 与租户 OWNER/ADMIN 分离。

保留 `auth.uid()`、`authenticated` 等数据库对象名称：它们是现有 RLS 的内部兼容协议，migration 001 会在普通 PostgreSQL 中创建，不代表仍连接 Supabase。保留历史迁移 checksum；不改写旧 migration。

### 2.2 独立数据库与运行身份

| 连接方 | 数据库登录 | 权限 |
|---|---|---|
| 一次性安装/升级工具 | NAS `admin` | 建库、迁移、运行角色预置、首管理员初始化 |
| API | `wealthsail_api_login` | 只能切换 `wealthsail_api`，受 RLS 限制 |
| Worker | `wealthsail_worker_login` | 激活 `wealthsail_worker`，必要时降权至 API 角色 |

API/Worker 密码独立生成。二者均非超级用户，不直接具有 BYPASSRLS、建库或建角色权限。不能把 NAS 的 `admin` 连接串用于应用运行。

PostgreSQL 角色属于整个集群。安装器必须在新建库前检查 WealthSail 专用角色冲突；同名角色存在而目标库没有可信的 WealthSail migration ledger 时拒绝初始化，避免修改其他库使用的同名角色。进一步验证账本 checksum/所有者/结构、安装标记、跨库角色依赖、角色属性和成员白名单；`authenticated` 不得携带额外权限。仅设置 `wealthsail` 自身 ACL，不改变 `prismscore_db` 的授权。

### 2.3 接入已有 Docker 网络

根 `docker-compose.yml` 继续定义通用服务；`docker-compose.nas.yml` 作为 NAS overlay：

- API 和 Worker 同时加入应用网络与已有 PostgreSQL 网络。
- 前端仅加入应用网络，通过 Nginx 访问 API。
- 一次性 `db-init` 服务复用后端镜像，仅在显式运行时启动。
- 不新增 PostgreSQL 服务、不挂载现有 PG 数据目录、不改变已有 PG Compose。
- 前端宿主绑定地址和端口可配置，默认仍为 `127.0.0.1:8080`。
- API/Worker 另加入独立 `codex` 网络，通过内部令牌访问 `codex-runner:8090`；Runner 不加入数据库、应用入口或外网 edge 网络，不发布宿主端口。
- 仅 Runner 与一次性 `codex-auth` 工具挂载可刷新认证的 `codex_auth` 卷。API/Worker 无 `auth.json`，Runner 无数据库、会话、邮件、企微凭据。

正式浏览器入口沿用 HTTPS 反向代理，Secure refresh cookie 行为保持。外部网络到库的默认连接为 `postgres:5432`；Docker 同机桥接默认使用 `sslmode=disable`，跨主机时应显式配置受信任 TLS。

### 2.4 第三方集成可显式关闭

新增 `WECOM_ENABLED` 与 `PASSWORD_RESET_EMAIL_ENABLED`，默认均为 `true`，保持既有部署行为。NAS 首装生成的配置显式设为 `false`，使账号登录、租户管理和 Web 报告不必等待企微/SMTP 配置。

- 关闭企微时不领取/消耗投递任务，不创建新的绑定挑战，回调与正式应用/群 webhook 发送均明确不可用；原实验 Bot 仍由独立开关管理。
- 关闭邮件找回时，找回请求明确返回功能未配置，不生成无法投递的重置令牌；不影响登录、邀请注册和已有重置令牌确认。
- JWT、refresh、邀请 HMAC、routing key、数据库运行身份检查仍是强制安全边界。
- 配置真实的企微/SMTP 参数并开启相应开关后，恢复现有完整功能；Web 页面结构和接口协议不变。

## 3. 配置与安装工具

### 3.1 `scripts/configure_nas.py`

仅使用 Python 标准库，生成 `deployment/env/api.env`、`deployment/env/worker.env`、`deployment/env/codex.env` 和 `deployment/nas.env`。生成稳定、独立随机密钥与数据库登录口令；routing key 两进程共享，其余 API 会话/邀请密钥不进入 Worker。Runner 只接收独立内部令牌和 Codex 参数，该令牌与数据库、会话密钥分离。

已经生成旧三文件配置时，使用 `scripts/configure_codex.py` 仅追加缺失的 Runner 配置，保留原数据库和身份密钥；不重新运行首装生成器，不导出认证文件内容。Codex CLI 由后端镜像安装，账号认证在 NAS 用 `codex-auth login --device-auth` 完成。

参数至少包括 `--web-base-url`、可选 DB host/port/name、网络名和 Web 监听地址/端口。默认数据库 `wealthsail`、host `postgres`、port `5432`、网络 `global-postgres-network`。拒绝覆盖已有目标文件，运行前完成参数校验，文件权限尽量收紧为 0600。命令输出只显示文件路径和后续动作，不显示密码。

配置文件加入 Git 与 Docker build context 排除规则。生产 HTTPS/CORS、Worker direct pooling 和现有应用安全校验保持生效。

### 3.2 `scripts/initialize_postgres.py`

通过 `db-init` 容器运行，读取 API/Worker 配置中的目标和各自口令，交互读取 NAS 管理员密码。必须指定准确 `--confirm-target postgres:5432/wealthsail`。管理员密码不持久化、不进入命令行参数或应用容器。

依次执行：

1. 校验两个运行 DSN 指向同一目标且角色名正确，确认目标、管理权限与版本。
2. 检查目标库与集群级 WealthSail 专用角色，拒绝不明冲突。
3. 仅在不存在时创建目标库；已存在的非 WealthSail 非空库必须拒绝。
4. 使用现有 `scripts.migrate.migrate` 应用全部迁移和 readback。
5. 预置两套运行登录身份与独立密码，验证 API 不能提升到 Worker。
6. 若指定 `--bootstrap-email`，调用首管理员 bootstrap。
7. 以真实 API/Worker 登录连接，执行生产角色边界验证。

首次安装在迁移前建立受所有者/结构校验的 `public.wealthsail_nas_installation` 单例标记，维护库 advisory lock 串行化整个安装。迁移后，只有该标记仍为初次清理待完成时，才执行 `scripts/fresh_install_data.py`：锁住个人业务与穿透表、确认无用户/资产且仅有 053/054 的近似来源，删除近似权重。清理、bootstrap、标记完成在同一事务提交，支持失败重试。已有安装没有首装标记时不会自动清理。

所有 `seeds/dev` 演示脚本均不执行；生产迁移中的公开产品、来源和研究分类目录保留。053 包含必要 metadata DDL，因此不得直接跳过 053/054。旧 migration 文件保持原样，清理不改变 checksum。

重复执行不得重新建用户或重置 Web 密码。升级前应先备份；现有迁移 runner 的 dry-run 会创建 migration ledger，不应宣传为完全只读。

### 3.3 `scripts/bootstrap_admin.py`

仅为 CLI/安装器提供 `bootstrap_admin(conn, *, email, password, nickname, tenant_name)`，不暴露公网首次注册接口。

在同一事务和 advisory lock 下：

- 空身份库创建 bcrypt profile、活动个人租户、OWNER membership。
- 建立 `default_tenant_id`、`MINE` 资产作用域和 `PLATFORM_ADMIN`（granted_by 为本人）。
- 复用 `scripts.standard_report_jobs` / `insert_standard_report_jobs` 建立四时段标准任务。
- 追加审计，不创建样例账户、持仓、交易或虚假净值。
- 已有同一管理员且关系完整则返回已初始化，不重置密码；已有其他用户/管理员或关系不完整则报清晰冲突，交给独立修复流程。

密码使用交互隐藏输入，首装要求至少 12 字符且不超过 bcrypt 72 字节上限。

## 4. 后续租户与用户操作

首管理员登录后，在“设置 → 租户与成员”中：

- “邀请成员”：邀请新邮箱加入当前租户，指定 ADMIN/EDITOR/VIEWER。
- “创建独立租户邀请码”：由平台管理员邀请新邮箱注册独立租户；注册事务同时创建 OWNER、偏好和四时段任务。
- 新用户仍在原登录页选择接受邀请，设置自己的密码。
- 多租户成员继续使用现有活动租户选择；RLS 与服务端成员复核保持。
- 忘记密码的邮件功能需要 SMTP。未配置时不能承诺发送成功。

已有 Supabase 数据迁移属于单独流程：保留用户 UUID、密码哈希、租户、成员和外键；不能仅改连接串就期望空库出现旧数据。禁止导入整套 Supabase 系统 schema/角色来替代受控的应用迁移。切换 JWT 密钥会使旧会话失效，用户需重新登录。

## 5. 验证与交付

本机：配置生成行为、拒绝覆盖、DSN 目标限制、bootstrap 冲突/幂等、可选集成开关、现有认证测试、前端登录/设置测试、迁移 SQL 检查。若可使用仓库已有便携式 PG16，可加跑隔离空库真实集成；不能据此宣称 PG18/NAS 已验收。

NAS：Compose 合并配置验证、既有网络检查、独立库完整迁移、非 postgres 管理员建库、API/Worker 角色边界、首管理员幂等、登录/刷新/登出、两种邀请、跨租户拒绝、账户导入与报告任务、容器重启后数据与会话恢复。实施计划记录已执行证据和 NAS 待验收项。
