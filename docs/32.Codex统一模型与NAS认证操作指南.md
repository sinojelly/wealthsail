# Codex 统一模型与 NAS 认证操作指南

本文对应当前仓库的独立 PostgreSQL、Cloudflare Access / Tunnel 和 Codex runner 部署。即时聊天、常规报告中的模型生成、每日公开投研都通过 Codex；部署时不需要准备 `MODEL_API_KEY` 或 `OPENAI_API_KEY`。Codex CLI 固定为 `0.160.1`，构建时安装到后端镜像，NAS 宿主机无需另外安装 Node.js、npm 或 Codex CLI。

完整部署顺序、Cloudflare 和数据库初始化仍以 [外网部署详细步骤](../external-access/DEPLOYMENT.md) 与 [NAS 部署及验证操作手册](31.NAS独立PostgreSQL部署与验证操作手册.md) 为准。本文补充模型服务、登录文件和后续维护；首次空库部署仍需按上述手册创建数据库角色、结构、管理员和租户。

## 1. 哪些功能使用 Codex

| 功能 | 发起服务 | 送入模型的内容 | 是否受每日研究开关控制 |
| --- | --- | --- | --- |
| Web 即时聊天 | API | 当前用户有权访问的聊天和业务上下文 | 否 |
| 常规报告中的模型生成 | Worker，或相应报告调用链 | 当前用户、租户有权访问的报告上下文 | 否 |
| 每日公开机会研究 | Worker | 独立的公开研究数据包与公开信息 | 是 |

原有报告的规则计算、数据校验及既有降级逻辑继续保留；页面出现规则生成的降级报告，不等于 Codex 模型调用成功。即时聊天使用 Codex app-server 的真实文本增量，再由 API 转成前端流式响应。

官方目前将 app-server 标为实验功能。本部署固定 CLI 版本；升级时需要回归登录、流式事件和取消处理，NAS 首次上线也需要实际验收。本机 Mock 协议测试无法证明账号端和长期运行的稳定性。[OpenAI app-server 文档](https://learn.chatgpt.com/docs/app-server)

两类输入使用独立策略：私有聊天、报告允许使用服务端已经授权的用户上下文，关闭联网搜索和执行工具；每日研究只使用公开研究包及公开来源，不携带个人持仓、成本或账户数据。模型子进程使用临时工作目录、只读沙箱和临时会话，关闭 shell、应用、插件、多代理及 MCP；请求取消或超时会回收子进程。业务数据的租户权限仍由应用层和 PostgreSQL 权限负责。

## 2. 容器与认证的关系

```text
浏览器 → Cloudflare Access / Tunnel → frontend → API
                                              │
                             Worker ──────────┤ 私有 Codex 网络 + 独立令牌
                                              ↓
                                        codex-runner → Codex 服务
                                              │
                                        codex_auth 卷
                                              ↑
                                     codex-auth 一次性工具
```

| 服务 / 文件 | 作用 | 是否持有 Codex 登录文件 |
| --- | --- | --- |
| `api` / `deployment/env/api.env` | Web、用户与租户权限、即时聊天；只配置 runner URL 和令牌 | 否 |
| `worker` / `deployment/env/worker.env` | 报告任务、可选每日研究；只配置 runner URL 和令牌 | 否 |
| `codex-runner` / `deployment/env/codex.env` | 统一调用 Codex，限制并发和超时 | 是，挂载 `codex_auth` |
| `codex-auth` | 首次登录、状态检查、无模型预检和可选初次导入；没有应用 `env_file` | 是，与 runner 使用同一卷 |
| `deployment/nas.env` | Compose 文件路径、网络等部署设置 | 否 |

runner 仅加入私有 Codex 网络，不加入 PostgreSQL 或 Cloudflare 入口网络，不发布 NAS 端口，也不加载数据库、JWT、企业微信等凭据。API 和 Worker 通过 `http://codex-runner:8090` 访问它，使用专门生成的 `CODEX_RUNNER_TOKEN`。这个令牌只用于内部服务认证，与用户会话密钥、Cloudflare Token、Codex 登录文件各自独立。

`codex-auth` 显式运行时即可启用其 `tools` profile；无需单独 `up` 它。登录容器使用镜像中的非 root 用户 UID/GID `10001`，没有特权、Docker socket 或宿主机目录挂载。设备登录只需 NAS 能向外连接认证服务，不需要开放 OAuth 回调端口或添加 Tunnel 域名。

## 3. 部署前准备

准备完整的最新源码、可用的 NAS Docker / Docker Compose，以及可以使用 Codex 的 ChatGPT 账号。模型可用性、额度和工作区策略由实际登录账号决定；镜像包含 CLI 不代表账号已经登录或具有某个模型的权限。

下面命令在 NAS 的 SSH 终端执行。将源码目录替换成实际路径；保留原部署使用的 Compose 项目名。如果原来使用了 `-p` 或 `COMPOSE_PROJECT_NAME`，下面每次操作也沿用它，避免另建一套卷和容器。

```bash
WEALTH_ROOT="/path/to/WealthSail"
ACCESS_DIR="$WEALTH_ROOT/external-access"
cd "$WEALTH_ROOT"
```

命令统一叠加以下三个文件，文件名都无需修改：

1. `docker-compose.yml`：API、Worker、runner、认证工具及前端。
2. `docker-compose.nas.yml`：连接 NAS 已有 PostgreSQL 网络及数据库初始化工具。
3. `external-access/compose.wealthsail.yaml`：Cloudflare 入口网络和 Web 暴露设置。

`external-access/.env`、Tunnel 入口网络及 NAS 的 PostgreSQL 网络应按外网部署手册准备好。此部署已有 Compose `!override` 用法，需要 Docker Compose `2.24.4+`。不要把完整 `docker compose config` 输出公开，它会展开私有环境变量；验证语法可使用 `config --quiet`。

### 3.1 全新部署：生成四份环境文件

尚未生成部署配置时运行：

```bash
python3 scripts/configure_nas.py \
  --web-base-url https://wealth.sinojelly.kdns.fr
```

脚本按命令参数和默认值生成 `deployment/env/api.env`、`deployment/env/worker.env`、`deployment/env/codex.env` 和 `deployment/nas.env`，文件权限为 `0600`；数据库主机、端口、网络等非默认设置按 NAS 部署手册传入参数，数据库管理员密码不会写入配置。runner 令牌会自动生成，并同步写入需要它的三个服务配置。默认关闭每日公开研究，先完成认证和人工验收。

若 NAS 没有 Python，可使用临时 Python 容器执行相同脚本：

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$WEALTH_ROOT:/workspace" -w /workspace python:3.12-slim \
  python scripts/configure_nas.py \
  --web-base-url https://wealth.sinojelly.kdns.fr
```

两种方式选择一种。已有配置时脚本会拒绝覆盖，不要为了接入 Codex 删除原环境文件重新生成。

### 3.2 旧部署：保留原数据库和登录密钥

此前已经生成三份环境文件、尚无 Codex runner 配置时运行：

```bash
python3 scripts/configure_codex.py
```

没有宿主机 Python 时改用：

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$WEALTH_ROOT:/workspace" -w /workspace python:3.12-slim \
  python scripts/configure_codex.py
```

这个补齐脚本保留原数据库、JWT、刷新会话等配置，只补缺失的 runner URL、独立令牌、`CODEX_ENV_FILE`，并创建缺失的 `codex.env`；重复执行不会旋转已有密钥。若已有 Codex 设置互相冲突，脚本停止并保留原配置，需要先核对三个服务使用的令牌是否一致。

从旧模型方案升级时，删除 `api.env`、`worker.env` 中不再使用的 `MODEL_API_KEY` / `OPENAI_API_KEY`，不要将它们移入 `codex.env`。补齐脚本不修改既有每日研究开关；首次接入认证时请先确认 API 和 Worker 中的 `DAILY_RESEARCH_ENABLED=false`，避免 Worker 启动就消耗当日研究执行槽位。

## 4. 构建、登录、检查、启动

### 4.1 构建镜像

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  build api frontend
```

后端的多个服务共用 `wealthsail-backend:latest`，因此构建 `api` 即已准备好 Worker、runner 和认证工具。构建阶段通过 npm 获取固定版本并提取当前 `amd64` / `arm64` 的 Linux 原生 CLI 及配套文件，最终 Python 镜像不需要 Node.js。构建包含 `codex --version` 检查；版本或二进制不适配时应先解决构建错误。

### 4.2 在 NAS 发起设备登录

先在个人账号的 ChatGPT 安全设置，或工作区管理员的权限设置中启用设备代码登录；运行命令后，用可信电脑上的浏览器打开 CLI 给出的官方地址，完成登录并输入一次性代码。设备代码不要发送给他人。官方说明见 [OpenAI Docs：认证与无浏览器设备登录](https://learn.chatgpt.com/docs/auth)。

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  run --rm --no-deps codex-auth login --device-auth
```

`--no-deps` 使这次操作只运行认证工具，不拉起 API、Worker 或任何每日研究任务。成功后该一次性容器退出，登录文件留在卷中。无需在 NAS 宿主机安装 Codex 或手工创建 `auth.json`。

### 4.3 检查登录状态和 CLI 兼容性

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  run --rm --no-deps codex-auth login status
```

再执行项目的无模型预检：

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  run --rm --no-deps --entrypoint python codex-auth \
  -m scripts.codex_admin check
```

预检检查可执行文件、版本、所需命令和功能开关、登录状态，成功输出包含 `ok: true` 的 JSON；它不会调用模型，也不会占用每日研究执行槽位。`selectedModel` 为空可以表示使用 CLI 默认选择，并不等于认证失败。预检不证明实际推理额度、联网或指定模型权限已经可用，实际模型请求仍需通过 Web 验收。

### 4.4 启动运行服务

已按空库部署手册完成数据库初始化及管理员创建后运行：

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  up -d codex-runner api worker frontend
```

Compose 等待 runner HTTP 健康检查后再启动 API，随后启动 Worker。runner 的 `/healthz` 只证明 HTTP 进程存活，不证明 Codex 已登录；不要跳过前面的认证预检。

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  ps
```

验收顺序：通过 `https://wealth.sinojelly.kdns.fr` 完成 Cloudflare Access 和应用登录；发送一次即时聊天，检查文本持续增量出现；按现有流程生成一份常规报告并查看生成状态。确认其他租户用户仍看不到当前用户的私有数据。不要使用每日研究作首次登录测试。

需要排查时查看有限日志，避免公开业务内容或认证信息：

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  logs --tail=100 codex-runner api worker
```

## 5. 模型、超时和每日研究

### 5.1 模型设置

不指定 `CODEX_MODEL` 时交给 Codex CLI 默认选择。需要固定模型时，使用账号实际可用的模型标识，在以下三个文件中把 `CODEX_MODEL` 设为同一个值：

- `deployment/env/api.env`
- `deployment/env/worker.env`
- `deployment/env/codex.env`

runner 会拒绝与其允许模型不一致的请求。不要把电脑上整个 `config.toml` 复制进容器来配置模型；只设置上述明确需要的变量。

若每日公开研究需要单独的模型，在 `worker.env` 和 `codex.env` 中将 `DAILY_RESEARCH_MODEL` 设置为相同值；留空则沿用 `CODEX_MODEL` / CLI 默认选择。这里不预设某个账号一定具有的模型名。

默认普通生成超时 `90` 秒、聊天 `900` 秒；相应变量为 `CODEX_TIMEOUT_SECONDS` 和 `CODEX_CHAT_TIMEOUT_SECONDS`。如确有需要再调整调用端和 runner，避免调用端提前超时。runner 默认 `CODEX_RUNNER_MAX_CONCURRENT=2`，具有队列限制；忙碌、超时或认证失败会返回可处理的错误，不自动反复重试模型请求。

### 5.2 开启每日公开研究

即时聊天、常规报告验收通过后，如需每日 `08:30`（上海时区）的公开机会研究，将 `api.env` 和 `worker.env` 中的 `DAILY_RESEARCH_ENABLED` 都改为 `true`。当前研究调度按自然日执行，区别于常规报告各自的交易时段规则。API 控制对应功能可见性，Worker 控制任务执行。保持生产环境 `DAILY_RESEARCH_DEBUG_ENABLED=false`。

该开关默认 `false`，也统一控制交易日 08:30/08:35 盘前报告和晨间机会推送。14:30 基金估值与
15:30 盘后复盘分别由 `FUND_1430_ENABLED`、`POST_MARKET_REVIEW_ENABLED` 控制，均默认关闭；
配置文件位置、自动恢复与手动操作边界见 [NAS 部署手册 7.1](31.NAS独立PostgreSQL部署与验证操作手册.md#71-关闭自动日报基金估值盘后复盘和盘中检查)。

修改模型、超时或每日研究设置后，重新创建相应服务加载环境文件；仅 `restart` 不会重新读取环境变量：

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  up -d --force-recreate codex-runner api worker
```

Worker 已包含调度，无需再配置 NAS 计划任务或新增 cron 容器。每日研究有持久化的每日执行约束；真正触发研究后，即使预检或模型失败，也可能记录当日失败并占用当日执行槽位。因此使用 `scripts.codex_admin check` 做登录预检，避免为检查配置反复执行实际每日研究。

## 6. `auth.json` 在哪里、如何持久化

容器内的 `CODEX_HOME=/home/appuser/.codex`，登录缓存自动写为 `/home/appuser/.codex/auth.json`。镜像仅提供最小配置 `cli_auth_credentials_store = "file"`，由独立 `codex_auth` 命名卷持久化。官方说明中，`file` 使用文件，`keyring` 使用操作系统凭据库，`auto` 优先使用凭据库并回退到文件；本部署显式使用文件以适配无桌面容器。[OpenAI Docs：凭据存储](https://learn.chatgpt.com/docs/auth)

目录由 UID/GID `10001` 使用，初始目录权限 `0700`。登录缓存包含可刷新凭据，运行时需要可写；不要将卷改为只读。正常重建容器、更换镜像、`up -d --force-recreate` 都会复用同一项目的命名卷。

请保留同一 Compose 项目名、源目录定位方式和卷：`docker compose down -v` 会删除包括登录缓存、头像在内的本项目命名卷，不用于常规升级。不要根据猜测的卷名手工创建或删除目录。需要查看卷归属时使用 NAS Docker 管理界面的项目/卷信息即可，不需要打开文件内容。

`auth.json` 应按密码管理，不入 Git、不写入 `.env`、不加入镜像、不粘贴到聊天或工单，也不对公网提供下载。ChatGPT 登录凭据会在使用中刷新；保留 runner 写回后的同一份卷。[OpenAI Docs：登录缓存](https://learn.chatgpt.com/docs/auth)

StudyOS 应使用自己的 Codex 目录或卷，并在其项目中独立登录。可以按账号和工作区允许的方式使用同一账号，但两个项目不要共同写同一份 `auth.json` 或整个 `.codex` 目录，避免刷新令牌和配置相互覆盖。两个应用中的租户、用户登录仍由各自应用管理，与基础模型服务账号分开。

## 7. 备选：从 Windows 导入已有 ChatGPT 登录缓存

优先使用 NAS 上的设备登录。设备登录不适用、且 Windows 已经存在文件形式的 ChatGPT Codex 登录缓存时，可使用这一备用流程。若本机使用操作系统凭据库而没有 `auth.json`，直接使用设备登录；不要从凭据管理器提取或手写 token。

导入仅用于目标卷尚无 `auth.json` 的首次初始化。工具拒绝覆盖已有文件，避免用旧缓存覆盖 NAS 已刷新的凭据；它只接受包含 ChatGPT access / refresh token 的缓存，拒绝 API Key 登录缓存。不要复制整个 `.codex` 目录、`config.toml`、历史会话、`AGENTS.md`、skills、插件或 MCP 配置。

### 7.1 安全传到 NAS 源码目录以外

先在 NAS 创建当前 SSH 用户专用的临时目录：

```bash
umask 077
mkdir -p "$HOME/.wealthsail-auth-import"
chmod 700 "$HOME/.wealthsail-auth-import"
```

在 Windows PowerShell 中替换 SSH 用户和 NAS 地址后执行；此处只复制单个文件，不展示内容：

```powershell
$NasUser = 'YOUR_NAS_SSH_USER'
$NasHost = 'YOUR_NAS_SSH_HOST'
$AuthFile = Join-Path $env:USERPROFILE '.codex\auth.json'
if (-not (Test-Path -LiteralPath $AuthFile -PathType Leaf)) {
    throw '没有文件形式的 auth.json，请使用 NAS 设备登录。'
}
scp $AuthFile "${NasUser}@${NasHost}:.wealthsail-auth-import/auth.json"
```

确认 SSH 主机身份后传输，不要把认证文件先放入 WealthSail 源码或共享下载目录。NAS 端继续：

```bash
AUTH_FILE="$HOME/.wealthsail-auth-import/auth.json"
test -f "$AUTH_FILE" && chmod 600 "$AUTH_FILE"
```

### 7.2 停止 runner，并通过标准输入导入空卷

确认前文的 `WEALTH_ROOT`、`ACCESS_DIR` 变量已设置，且镜像已经构建：

```bash
docker compose --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  stop codex-runner

cat "$AUTH_FILE" | docker compose \
  --env-file "$WEALTH_ROOT/deployment/nas.env" \
  --env-file "$ACCESS_DIR/.env" \
  -f "$WEALTH_ROOT/docker-compose.yml" \
  -f "$WEALTH_ROOT/docker-compose.nas.yml" \
  -f "$ACCESS_DIR/compose.wealthsail.yaml" \
  run --rm --no-deps -T --entrypoint python codex-auth \
  -m scripts.codex_admin import-auth
```

`-T` 关闭 TTY，文件经标准输入传入，不出现在命令行参数中；导入工具校验格式，使用当前非 root 用户以 `0600` 独占创建文件。出现“文件已存在”或校验失败时，不删除卷或强行覆盖，应改用原认证状态检查或正常设备登录。

成功后按第 4.3 节执行 `login status` 和无模型 `check`，确认通过后按第 4.4 节重新 `up -d codex-runner api worker frontend`。确认导入完成后删除这份临时传输副本：

```bash
rm -- "$AUTH_FILE"
rmdir -- "$HOME/.wealthsail-auth-import"
```

此处只删除源码外的临时副本，运行中的登录缓存仍保存在命名卷。不要继续定期把 Windows 旧文件同步到 NAS。

## 8. 常见问题与验收记录

| 现象 | 检查与处理 |
| --- | --- |
| `codex-auth` 找不到服务 | 使用最新完整源码及第 3 节的三个 Compose 文件，检查服务名是 `codex-auth`。 |
| 设备登录不可用 | 检查账号/工作区设备代码登录权限及 NAS 出站网络；按第 7 节使用已有文件缓存作首次备用导入。 |
| `login status` 未登录 | 确认登录和运行使用相同 Compose 项目及 `codex_auth` 卷；在同一项目执行设备登录。 |
| 状态已登录，但模型请求失败 | 检查账号额度、模型权限、工作区限制和出站网络；登录状态不能证明这些条件。 |
| runner 返回认证或模型不匹配 | 核对三个服务 `CODEX_RUNNER_TOKEN` 相同；指定模型时，三份 `CODEX_MODEL` 相同，公开研究专用模型在 Worker 和 runner 一致。不要公开粘贴配置内容。 |
| 修改 `.env` 后行为没变 | 使用第 5 节的 `up -d --force-recreate` 重新创建服务。 |
| 认证文件不可写 | 使用当前镜像和项目自动创建的卷，核对 UID/GID `10001`；不要用 root 手工覆盖文件，也不要全目录 `chmod 777`。 |
| runner healthy，但聊天仍不可用 | 先执行无模型预检，再在 Web 发起一次真实聊天；HTTP 存活和模型可用是不同检查。 |
| 没看到每日机会研究 | 核对 API 和 Worker 都启用开关、Worker 正常、调度时间及当日任务记录；不要通过调试强制重跑绕过每日约束。 |

本机没有 Docker，本轮代码验证不能代替 NAS 的镜像构建和账号端到端验证，也没有执行真实模型或读取真实登录凭据。NAS 验收请记录：镜像构建成功、`0.160.1` 预检通过、同卷登录可持久化、Web 即时聊天真实流式响应、常规报告正常、用户/租户隔离保持，以及可选每日研究在预期时段成功。
