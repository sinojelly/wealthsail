## 1. 目标与非目标

本测试用于尽早发现“单元测试通过，但系统已经不能登录或页面无法工作”这一类基础破坏。它实际启动
FastAPI、生产构建后的 React 前端和 Chromium，覆盖登录、核心页面、刷新会话与注销，而不是只检查
文件是否存在或函数能否导入。

它不是完整生产验收，以下内容仍由专项测试承担：企业微信真实收发、四时段 Worker、行情 Provider、
大模型、天天基金写入、性能压测、备份恢复和多租户对抗测试。冒烟成功只说明核心链路可运行，不能证明
全部金融业务正确。

## 2. 两层流水线门禁

| 层级 | 触发时机 | 数据库 | 是否可阻止合并 | 主要作用 |
|---|---|---|---|---|
| PR/Push 全栈冒烟 | workflow 定义为每次 Push、每个 Pull Request；平台触发状态未验证 | 临时 PostgreSQL 16，自动迁移并 readback 到 027 | 只有平台启用且设为保护分支必过检查时才能阻止合并 | 验证迁移、数据库角色、API、前端生产包和登录旅程 |
| 远程 Supabase 冒烟 | workflow 定义为受保护 `master` Push 或 `master` 人工触发；需另行启用 | 专用远程 Supabase 项目；必要时才使用生产项目的隔离空租户 | 通常是合并后的兼容性告警，不是 PR 门禁 | 验证真实网络、TLS、Supabase Pooler、目标 schema 与 API 登录角色 |

状态术语必须严格区分：`DEFINED` 表示 YAML/脚本在仓库中；`ENABLED` 表示平台已经识别并允许
执行；`REQUIRED` 表示分支保护把具体 job 设为必过；`PASSING` 表示能提供目标 commit 的成功
Run URL/ID。本文只能从仓库确认 `DEFINED`，没有外部平台证据时不得把后三种写成 CURRENT。

不能把远程数据库 DSN 注入普通 PR。PR 中的代码尚未经过审核，一旦获得 DSN，就可以主动读取环境变量、
连接数据库或把秘密发送到外部。即使数据库账号权限较小，这仍是不必要的供应链风险。因此，合并前使用
无秘密的临时数据库拦截代码破坏；远程数据库任务只运行受保护分支中已经评审的代码。

如果团队必须在合并前验证托管 PostgreSQL，应单独准备无真实用户、无生产数据的 CI Supabase 项目，
仍不得把生产项目 DSN 暴露给 PR。

## 3. 自动化旅程及不变量

### 3.1 临时数据库旅程

GitHub Actions 的 `full-stack-smoke` Job 会执行：

1. 启动一次性 PostgreSQL 16 Service；
2. 通过正式 `scripts/migrate.py` 应用全部 migration 到当前 027 并执行 migration readback，覆盖
   026 企业微信回调防重与 027 Worker-owned market-hot 权限；
3. 运行 `scripts/provision_supabase_roles.sql`，建立与生产一致的
   `wealthsail_api_login -> wealthsail_api` 单向角色边界；
4. `scripts/prepare_ci_smoke_db.py` 创建一个无持仓的 `VIEWER` 测试用户；该脚本强制要求
   `postgres` 管理员连接指向显式 loopback，任何远程目标都会失败关闭；
5. 构建前端生产包，启动本地 API 和 `vite preview`；
6. Chromium 执行“登录页 → 登录 → 资产看板 → 账号安全 → 页面刷新恢复会话 → 注销”；
7. 保存前端构建日志、API 日志、Preview 日志、Playwright 日志和截图。

测试用户和数据库密码是一次性 CI 容器内的公开 fixture，不是 Secret，也不能复用于任何远程环境。

### 3.2 远程 Supabase 旅程

`remote-supabase-smoke` 使用同一个 `scripts/full_stack_smoke.py`，但有额外防线：

- DSN 登录角色必须是 `wealthsail_api_login`；兼容 Supabase Pooler 的
  `wealthsail_api_login.PROJECT_REF` 写法；
- 禁止 `postgres`、`service_role`、`wealthsail_worker_login` 或其他账号；
- 数据库 hostname 必须与 `WS_SMOKE_DATABASE_EXPECTED_HOST` 完全一致；
- 非 loopback 数据库必须显式设置 `sslmode=require` 或更强模式；6543 端口还必须包含
  `statement_cache_size=0`；
- 启动 HTTP 服务前，调用应用自身的 `verify_runtime_login_boundary`，确认 API 能切换
  `wealthsail_api`、不能切换 `wealthsail_worker`，且登录账号不是 Superuser/BYPASSRLS；
- API 子进程采用最小环境，数据库连接池限制为 1–2；不向它传入 Worker DSN、企微发送 Secret、
  大模型 API Key；前端进程完全拿不到数据库 DSN；
- 不启动 Worker，关闭天天基金导入开关，避免四时段调度、Outbox、行情回填和基金任务产生副作用。

本地 API 使用 `APP_ENV=staging`，是为了让 Chromium 在 loopback HTTP 上测试 HttpOnly Refresh Cookie；
生产角色边界不依赖这个配置跳过，而是在启动前单独强制验证。JWT 和各类 HMAC Key 每次 Run 临时生成，
不需要复制线上服务的会话密钥。

### 3.3 只读业务边界

浏览器路由层允许所有同源 GET/HEAD/OPTIONS，但只允许以下三个 POST：

- `/api/v1/auth/login`
- `/api/v1/auth/refresh`
- `/api/v1/auth/logout`

任何持仓、报告、策略、邀请、绑定、资料或导入写请求都会在浏览器发出前被阻断，并使测试失败。
身份链路本身不是“数据库零写入”：登录/刷新会建立或轮换 `refresh_sessions`，注销会撤销会话，系统还会
保留必要审计记录。因此远程测试必须使用专用账号；不能把普通投资者账号密码放入 CI。

## 4. GitHub Actions 启用步骤

仓库配置文件是 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)。从 YAML 定义看，
`backend`、`frontend`、`full-stack-smoke` 没有额外 job 条件，平台接收 Push/PR 后应运行；
`remote-supabase-smoke` 在显式启用前保持跳过。这只是仓库定义，不代表当前 Gitee remote 会执行
GitHub Actions，也不代表某个 GitHub mirror 已启用 Actions 或配置 branch protection。

### 4.1 先启用合并门禁

在 GitHub 仓库 `Settings → Branches → Branch protection rules` 中保护 `master`：

1. 要求通过 Pull Request 合并；
2. 启用 “Require status checks to pass before merging”；
3. 将 `backend`、`frontend`、`full-stack-smoke` 设为必过检查；
4. 禁止绕过保护规则直接 Push，至少仅仓库管理员可在事故流程中绕过。

这一步不需要任何生产 Secret。配置后必须用测试 PR 验证三个 check 实际出现且不能绕过，并保存
Run URL/ID 与 branch protection 截图；完成这些证据前，状态仍是 `DEFINED`，不能写“门禁已启用”。

### 4.2 配置远程 Supabase 冒烟

在 `Settings → Environments` 创建 `production-smoke`：

- 只允许 `master` 分支部署；
- 建议配置 Required reviewers；
- 添加 Environment Secrets：
  - `WS_SMOKE_DATABASE_URL`：只允许使用 `wealthsail_api_login` 的 DSN；
  - `WS_SMOKE_EMAIL`：专用测试用户邮箱；
  - `WS_SMOKE_PASSWORD`：专用测试用户密码；
- 添加 Environment Variable：
  - `WS_SMOKE_DATABASE_EXPECTED_HOST`：只写 hostname，不带协议、端口和路径。

然后在仓库级 `Settings → Secrets and variables → Actions → Variables` 添加：

```text
WS_REMOTE_SMOKE_ENABLED=true
```

在 GitHub 平台确已启用 workflow、Environment 和变量后，每次 `master` Push 才会自动运行远程冒烟；也可以在 Actions 页面选择 `ci`，通过
`Run workflow` 对 `master` 人工重跑。远程 Job 使用并发锁，不会让两个 Run 同时轮换同一账号的
Refresh Session。

推荐顺序是：优先使用独立的预生产 Supabase 项目；如果确实要连接生产项目，先建立没有持仓、报告、
绑定和个人资料的隔离租户，把测试用户设为 `VIEWER`。该账号不得同时属于真实家庭租户，也不得拥有
OWNER/ADMIN 权限。

## 5. 本地运行远程冒烟

先安装依赖和 Chromium：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Set-Location frontend
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
Set-Location ..
```

在当前 PowerShell 会话注入变量。不要把真实值写进仓库、命令历史截图或工单：

```powershell
$env:WS_SMOKE_DATABASE_URL = '<wealthsail_api_login DSN>'
$env:WS_SMOKE_DATABASE_EXPECTED_HOST = '<exact database host>'
$env:WS_SMOKE_EMAIL = '<dedicated smoke email>'
$env:WS_SMOKE_PASSWORD = '<dedicated smoke password>'

.\.venv\Scripts\python.exe scripts\full_stack_smoke.py
```

执行期间固定占用 `127.0.0.1:8000` 与 `127.0.0.1:5173`。脚本会先检查端口，发生冲突时直接退出，
不会结束不属于本次 Run 的进程。结束后会清理自己启动的 API/Preview 进程，证据写入
`artifacts/full-stack-smoke/`，该目录已被 Git 忽略。

若只想检查无秘密逻辑，运行：

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests\unit\test_full_stack_smoke.py tests\unit\test_prepare_ci_smoke_db.py
Set-Location frontend
pnpm run test:smoke-config
```

## 6. Gitee Go 接入方式

项目当前 Git 远端是 Gitee。Gitee Go 的流水线由仓库“流水线”页面创建，官方支持 YAML 编排、Push/PR
触发、环境变量和阶段权限；其插件名称、云端镜像与 Service 能力由租户版本决定，因此不要直接把
GitHub Actions YAML 改后缀复制过去。参考 [Gitee Go 任务编排](https://help.gitee.com/gitee-go/pipeline/scheduling)
和 [Gitee Go 功能说明](https://gitee.com/features/gitee-go)。

当前仓库没有受版本控制的 Gitee pipeline 文件，仓库内容也无法读取 Gitee UI 中是否已经创建流水线、
最近一次运行结果或 master 保护规则。因此本节是 `[TARGET / MANUAL SETUP]`，不是已启用状态说明。
若团队在 Gitee UI 配置成功，应把流水线名称、触发规则、必过阶段和脱敏 Run URL/ID 记录到发布
证据，而不是反向把平台私有 Secret 或渲染后配置提交进 Git。

推荐在 Gitee Go 建立两个阶段：

1. **PR Gate**：Push 和 PR 自动触发。Agent 准备 Python 3.12、Node 20、pnpm、Chromium 与临时
   PostgreSQL 16，依次执行 `pip install -r requirements-dev.txt`、前后端常规检查、
   `python scripts/prepare_ci_smoke_db.py`、
   `python scripts/full_stack_smoke.py --allow-loopback-database`；将 `artifacts/full-stack-smoke`
   作为构建制品保存。
2. **Remote Supabase Smoke**：只允许 `master` 自动触发或授权人员手工触发，配置阶段权限；通过
   Gitee 环境变量管理注入四个 `WS_SMOKE_*` 变量，执行 `python scripts/full_stack_smoke.py`。
   该阶段不得由 PR 触发，也不得向任务注入 Worker/迁移管理员凭据。

如果 Gitee 云端任务不能提供 PostgreSQL Service，可使用一次性 Docker PostgreSQL 或专用的空测试库；
不要为了方便而把生产管理员 DSN 配给 PR。无论选择 GitHub 还是 Gitee，核心命令和安全检查都在仓库脚本
内，不依赖 CI 平台私有实现。

## 7. 失败定位与维护规则

| 证据文件 | 说明 | 常见失败 |
|---|---|---|
| `frontend-build.log` | TypeScript 与 Vite 生产构建 | 类型错误、依赖或打包失败 |
| `backend.log` | FastAPI 启动和 HTTP 请求边界日志 | schema 不兼容、权限、API 500 |
| `frontend-preview.log` | 生产静态包服务和代理 | 端口、静态资源、代理失败 |
| `ui-smoke.log` | Playwright 每一步与最终断言 | 登录、Refresh、账号接口、注销失败 |
| `wealthsail-ui-smoke.png` | 成功末态或失败现场截图 | 页面渲染与路由问题 |

日志不得输出 DSN、Cookie、口令、Authorization、请求正文和投资数据。失败时先看 `ui-smoke.log`，再按
请求 ID 对照 `backend.log`。远程测试失败不要立即改生产数据；先用同一 commit 在隔离数据库复现，确认
是代码、migration、角色、网络还是目标环境漂移。

维护冒烟旅程时必须遵守：

- 测试先失败再修改实现；
- 选择稳定的可访问名称，不依赖 CSS 层级或随机 ID；
- 增加业务写操作必须经过单独设计评审，不得扩大现有允许列表；
- 页面新增合法的认证生命周期端点时，同时补配置契约测试；
- Worker 永远不属于本冒烟进程集合；
- 远程测试账号、DSN 或目标 host 变化后，必须由第二人复核环境配置。
