# WealthSail 累计收益与标准报告任务设计及运维

> 文档版本：v1.1 · 2026-09-01
> 实现基线：migration 043、`/api/v1/portfolio/performance-baselines`、
> `scripts/backfill_standard_report_jobs.py`

## 1. 本次解决的两个问题

第一，当前持仓导入后可以可靠计算“持仓收益”，但不能把当前市值全部当成“累计收益”。系统现在
为每个账户建立独立收益起点，从该点自动跟踪，并允许用户可选补充导入前已经发生的历史累计盈亏。

第二，migration 033 只在“个人租户邀请码注册”路径创建四个报告任务，既有租户以及通过运维脚本
迁移出的个人租户可能没有任务。当前注册与运维迁移路径都已补齐创建逻辑；对已经存在的租户，提供
允许全空或“现有记录为标准定义精确子集”的受控回填脚本。

## 2. 用户看到的两个收益不是同一个概念

### 2.1 当前持仓收益

```text
当前持仓收益 = Σ(当前市值 − 当前持有份额 × 剩余成本价)
```

它回答“现在仍持有的这些资产浮盈浮亏多少”。它不包含已经卖出的历史收益，也不受出入金影响。
任何当前持仓缺少可靠估值时，组合持仓收益不发布部分结果。

### 2.2 累计收益

每个账户独立计算：

```text
跟踪以来收益 = 当前总资产 − 跟踪起点总资产 − 跟踪期净外部入金
账户累计收益 = 用户填写的跟踪前历史累计收益 + 跟踪以来收益
组合累计收益 = 当前查看范围内所有账户累计收益之和
```

净外部入金只包含已确认、未被冲正的 `CASH_IN/CASH_OUT`。`CASH_OUT` 现金腿是负数，因此直接
求和得到净入金。BUY、SELL、分红、费税和期初 ADJUSTMENT 都是账户内部经济变化，不能当作新增
本金。累计收益率/TWR 本阶段不发布；系统不会用累计收益除以静态本金得到一个貌似精确的百分比。

示例：起点资产 100,000 元，之后净入金 10,000 元，当前资产 118,000 元，用户确认起点前历史
累计收益 -2,000 元，则跟踪以来收益为 8,000 元，累计收益为 6,000 元。

## 3. 普通用户需要做什么

默认不需要做任何事：

1. 首次导入并完成可靠估值；
2. 系统以首个完整 NAV 自动建立账户收益起点，历史累计收益默认 0；
3. 后续确认的出入金和资产估值变化自动进入累计收益；
4. 资产看板新增“累计收益”卡片，并显示从哪天开始跟踪。

只有用户能从天天基金、券商或旧账本明确确认“跟踪起点之前的累计盈亏金额”时，才进入
“账号安全 → 累计收益起点（可选）”，按账户填写正数或负数并保存。用户填写的是金额，不是收益率，
也不是当前市值。系统保存后会自动刷新资产总览；持仓、成本、账本事件和起点日期都不会改变。

多个账户的收益起点日期可能不同。组合卡片副文案显示最早起点，但每个账户仍按自己的起点独立
计算。当前作用域内任一账户缺完整估值或收益起点时，组合累计收益显示不可用，避免把部分账户结果
冒充完整组合。

## 4. 数据与权限设计

`ledger.account_performance_baselines` 是追加式版本表，关键字段如下：

| 字段 | 含义 |
|---|---|
| `tenant_id/account_id` | 租户与投资账户边界 |
| `baseline_as_of` | 自动跟踪起始日 |
| `baseline_total_asset` | 起始日完整账户总资产 |
| `initial_cumulative_pnl` | 用户已知的起点前历史累计盈亏，默认 0 |
| `source` | `AUTO_MIGRATION`、`AUTO_NAV` 或 `USER` |
| `version` | 同账户严格递增版本 |
| `created_by` | USER 版本的确认用户；自动版本为空 |
| `idempotency_key/request_hash` | 命令防重及同键异内容冲突检查 |

表禁止 UPDATE/DELETE。用户修改历史累计收益时，服务端锁定最新版本，校验 `If-Match`，继承原起点
日期和资产并追加新版本，同时写入 `PERFORMANCE_BASELINE_REVISED` 审计。RLS 要求当前租户成员；
插入还要求租户 OWNER/ADMIN/EDITOR、本人身份以及账户 `BENEFICIAL_OWNER/JOINT_OWNER` 归属。
浏览器数据库角色不能直读，Worker 不能插入用户版本。

migration 039 为已有完整 NAV 账户建立 `AUTO_MIGRATION` version 1。未来账户的首个完整 NAV 通过
数据库触发器建立 `AUTO_NAV` version 1；部分估值、已知金额或 0 值占位都不能代替完整 NAV。

## 5. API 与前端契约

- `GET /api/v1/portfolio/summary`：返回 `cumulativePnl`、空的 `cumulativePnlRate`、
  `performanceBaselineAsOf` 和 `performanceBaselineMixed`；
- `GET /api/v1/portfolio/performance-baselines`：只返回当前用户归属账户的最新版本；
- `PUT /api/v1/portfolio/performance-baselines/{accountId}`：请求体为
  `initialCumulativePnl`，必须带 `If-Match` 与 `Idempotency-Key`；
- 资产看板同时显示“持仓收益”和“累计收益”，正收益为红色、负收益为绿色；
- 账号安全页的历史收益设置是可选项，值不变、正在提交或角色无权时保存按钮不可用。

## 6. 四个标准报告任务

| 任务 | session | 默认计划（Asia/Shanghai） | 用户价值 |
|---|---|---|---|
| `pre_market_brief` | `PRE_MARKET` | 工作日 08:30 | 盘前简报 |
| `intraday_tracking` | `INTRADAY` | 工作日 09:30–11:30、13:00–15:00 每 5 分钟 | 盘中跟踪与风险变化 |
| `fund_1430_estimate` | `FUND_1430` | 工作日 14:30 | 基金 2:30 报告 |
| `post_market_review` | `POST_MARKET` | 工作日 15:30 | 盘后交互复盘 |

新个人租户注册和新的 `migrate_user_to_personal_tenant.py --apply` 都在创建租户/迁移身份的同一事务
写入这四条记录，任一失败整笔回滚。运行时 API 没有 `workflow.jobs` INSERT 权限，避免普通接口
绕过治理创建任意定时任务。

`PRE_MARKET` 在内部进一步拆成 08:30 宏观（`PRE_MARKET_MACRO`，受众 `NULL`）与 08:35 个性化
（`PRE_MARKET_PERSONALIZED`，受众为成员）两个阶段，但 `workflow.jobs` 仍只有一条 `PRE_MARKET`
记录，四时段完整性监控不受影响；变体、受众与共享缓存的细节见 §11。

已经存在的租户使用 `scripts/backfill_standard_report_jobs.py`。脚本默认只读：目标租户四类任务
全空或只缺少部分标准任务时返回 `READY`，已完整等于标准定义时返回 `ALREADY_APPLIED`。现有记录
只有在名称、时段、Cron 和启用状态均与标准定义精确一致时才会被保留，脚本只插入缺失项；发现
禁用、改名、改时或重复配置时立即停止，要求人工判断，不自动覆盖。`--apply` 还要求数据库目标、
租户 UUID 和租户名称三重精确确认；缺失任务与 `REPORT_JOBS_BACKFILLED` 审计在一个事务中提交并
回读验证。结果与审计同时记录 `existingSessions` 和 `insertedSessions`，便于区分保留项和新增项。
migration 040 还在数据库层保证同一租户同一 `report_session` 最多一条记录；发现历史重复时迁移
主动停止，不会擅自选择或删除任务。

运行监控只对“ACTIVE 且存在有效企微绑定”的租户检查四时段完整性。完全没有启用任务时发送
`TENANT_NO_ENABLED_JOBS`，存在部分任务、重复或非标准配置时发送
`TENANT_INCOMPLETE_REPORT_JOBS`；未绑定渠道的演示/虚拟租户不会因此产生推送告警。

完整生产命令、readback SQL 和 Jelly 租户示例见
[11.数据库升级方法.md](./11.数据库升级方法.md) 的“已有租户受控补齐四个标准报告任务”。

## 7. 上线顺序与验收

1. 更新 `master` 代码，确认 migrations 041–043 存在；
2. 使用 migration/admin DSN 执行 `scripts/migrate.py`，看到 043 `APPLIED` 或 `SKIP` 且 readback 成功；
3. 对既有 so、Jelly 租户逐一预检、再执行标准任务回填，分别回读恰好四条启用任务；
4. 重启 API 与 Worker，重新构建并发布前端；
5. 登录后确认资产看板有独立“持仓收益/累计收益”卡片，账号安全页可看到自动起点；
6. 不填写历史累计收益时累计收益从 0 历史值正常跟踪；填写后只改变累计收益，不改变持仓收益；
7. 登记一笔 CASH_IN/CASH_OUT 后，累计收益应扣除净入金影响；普通买卖不应改变外部入金；
8. 运维页与数据库确认四个 report job 可被 Worker lease，监控不再发送“无启用报告任务”。

migration 043 不改变任务计划，因此已有租户任务完整时无需再次回填。上线订阅与调试入口还必须
重启 API、Worker 并重新构建前端；只重启后端不会让账号安全页出现新开关。

若 039 已提交但 readback 失败，停止发布并新增 forward-fix migration，不删除 migration ledger，
也不改写已执行的 039。若标准任务回填报告冲突，先导出当前四类任务和审计记录，由人工决定保留
定制计划还是另写受审计修正，禁止直接删行后重跑。

关注列表与盘前双阶段拆分另需 migration 044/045，发布顺序与验收见 §11.7；它不改变本节的
四时段任务定义，因此 `workflow.jobs` 仍恰好四条，无需再次回填。

## 8. 推送内容的持仓/无持仓双模式

四时段任务的触发时间和报告 API 不变，生成阶段按当前有效持仓数量自动选择内容：

- 有持仓：除盘前简报和基金 14:30 报告外，完整报告继续调用原个性化提示词；企微摘要不增加模型调用，而是从组合汇总、持仓质量、
  已确认风险政策和 Worker 持久化市场情绪中确定性生成“一句话总结、持仓健康度、具体行动建议、
  今日市场信号”四段，正文不超过 300 字；
- 无持仓：除盘前简报和基金 14:30 报告外，生成市场观察版，报告和企微正文固定包含“今日大盘风向、值得关注的板块、今日数据解读、
  投资思考、添加自选或导入持仓”五部分，并明确“不构成投资建议”。

两种模式发布后均通过企业微信 Markdown 通知触达，正文末尾的“查看完整报告”链接指向
`/reports?reportId=<report_id>`。有持仓模式使用四段式结构化摘要，无持仓模式保留共享市场观察正文；
链接只改变触达和回看方式，不改变报告生成、共享缓存、Outbox 幂等键或租户隔离语义。用户会话已
过期时先进入登录页，认证成功后再回到对应报告。

当前组合投影只提供当日盈亏金额，`dailyPnlRate` 尚无现金流调整后的可靠口径，也没有逐标的当日
贡献字段。有持仓推送因此不得用累计浮盈亏冒充当日贡献：缺少可靠字段时明确显示“当日涨跌幅暂不
可用”和“主要贡献标的暂无法可靠归因”。估值过期仅依据持仓 `quality=STALE`；仓位过高仅依据已
确认政策的 `single_position_limit`。市场信号只读取 `market.market_sentiment` 的持久化快照，
非实时或缺失数据必须标明，不在报告事务内调用外部 Provider。

无持仓模式读取 Worker 已持久化的 `market.market_sentiment`，仅在当日缓存不存在时并行获取一次
主要指数与行业板块快照。五段正文全部由结构化、带时效标记的数据确定性生成，不调用模型，因此
无持仓模式的 token 成本为零，也不会把模型措辞误当成行情事实或买卖建议。通过
`reporting.shared_market_briefs.trade_date` 唯一约束、受控 API 角色事务和 transaction-pool 安全的
`pg_advisory_xact_lock`，全系统每天只生成一份；其他租户直接复用，但仍各自生成租户内报告、审计记录
和独立 outbox。外部行情失败时，缺失数据明确标为不可用；上一交易日数据会标明日期和“非今日实时”。

migration 041 创建追加式 `reporting.shared_market_briefs`。`wealthsail_api` 和
`wealthsail_worker` 只有 SELECT/INSERT，不能 UPDATE/DELETE；`authenticated` 和 PUBLIC 无访问权。
迁移 readback 会检查表、追加式触发器及最小权限边界。上线后可用以下 SQL 验证每日复用：

```sql
SELECT trade_date, generation_status, provider, model, quality_status,
       token_usage, cost_cny, generated_at
FROM reporting.shared_market_briefs
ORDER BY trade_date DESC
LIMIT 7;
```

同一交易日应只有一行。审计事件 `REPORT_GENERATED.details` 中，个性化模式记录
`generationMode=PERSONALIZED`；无持仓模式记录 `generationMode=NO_HOLDINGS_SHARED`、
`sharedBriefId` 与 `sharedCacheHit`，可据此核对复用是否生效。

### 8.1 盘前简报确定性生成

`PRE_MARKET` 对有持仓和无持仓租户统一使用结构化、零 token 的确定性生成器，审计记录为
`generationMode=PRE_MARKET_DETERMINISTIC`、`generatorVersion=pre-market-deterministic-v1`；因为没有
发生模型执行，报告的 `model_run_id` 保持为空，不计入模型调用次数。完整版在报告摘要中按“隔夜市场
速览、今日重点关注、持仓今日影响、今日操作提醒、一句话总结”五段展示，企微正文压缩为不超过
200 字的同口径摘要；报告、条目、Outbox、企业微信链接和版本链路保持不变。

当前系统尚无受治理的美股指数、A50 期货和经济日历采集器，这些字段必须明确显示“暂无”，不得
用 A 股盘中行情代替隔夜数据，也不得由模型补写。持仓公司行动只读取
`market.corporate_actions` 当日除权日的最新修订；基金操作提醒只读取生效中的
`reference.instrument_cutoff_rules`，并明确该时间只是截止规则参考，不能据此声称产品当前可申购或
可赎回。市场情绪只读取 Worker 持久化快照。migration 042 仅向 `wealthsail_api` 授予上述两表的
SELECT 权限；Worker 生成报告时通过租户事务切换到该受限角色，`wealthsail_worker` 本身、PUBLIC 和
`authenticated` 均无直接访问权。

### 8.2 基金 14:30 报告确定性生成

`FUND_1430` 对有持仓和无持仓租户统一使用结构化、零 token 的确定性生成器，审计记录为
`generationMode=FUND_1430_DETERMINISTIC`、`generatorVersion=fund-1430-deterministic-v1`；报告的
`model_run_id` 保持为空。完整版摘要固定展示“今日估值概览、估值可信度、申赎提醒、操作建议、
一句话总结”五段，并为每条已持久化估值保留独立的证据条目。企微正文使用相同数据源压缩为五行、
不超过 200 字，报告详情链接、Outbox 幂等、版本审计和页面结构不变。

估值涨跌幅及区间以最近正式净值为基准，由 `ESTIMATED_NAV` 的估值点位和上下界计算，来源标为
“基于估值系统”；持仓覆盖率、估值时间和最近正式净值日期只读取观测元数据。操作建议由规则引擎
生成：预估涨跌幅严格超过 `+3%` 或低于 `-3%` 才触发，恰好 `±3.00%` 不触发。系统当前没有受治理的
实时申购、赎回状态源，因此只能展示生效中的渠道截止时间，并明确“状态：暂无；默认渠道 15:00
截止参考，实际能否申赎以销售渠道为准”。缺少正式净值、估值区间、覆盖率或截止规则时均显示
“暂无”，不得调用模型补齐，也不得加入外盘、隔夜市场或明日展望。

## 9. 用户推送订阅

账号安全页向 OWNER、ADMIN、EDITOR、VIEWER 一致展示四个开关，默认全部开启：

- `PRE_MARKET`：盘前简报；
- `INTRADAY`：盘中跟踪；
- `FUND_1430`：基金 2:30 报告；
- `POST_MARKET`：盘后复盘。

读取入口是 `GET /api/v1/auth/me` 的 `reportSubscriptions`。部分更新示例：

```http
PATCH /api/v1/auth/report-subscriptions
Content-Type: application/json

{"FUND_1430": false}
```

请求只允许已知布尔字段且至少包含一个字段。服务端始终以访问令牌中的用户 ID 更新本人偏好，不能
代改他人；每次变更追加 `REPORT_SUBSCRIPTIONS_UPDATED` 审计。开关仅在报告展开为企业微信 Outbox
时生效，不影响报告生成、报告版本、证据和研报审计页面。关闭某时段后，该时段仍会按计划生成，
只是不会为该用户创建投递；同租户其他用户不受影响。`PRE_MARKET` 开关同时控制 08:30 宏观与
08:35 个性化两阶段的 Outbox 展开（见 §11.6）。

## 10. OWNER/ADMIN 一次性调试触发

调试入口不依赖定时任务，适合部署后验证单一用户的“生成 → Outbox → Worker”链路：

```http
POST /api/v1/debug/reports/trigger/POST_MARKET
```

仅当前租户 OWNER/ADMIN 可调用，目标固定为调用者本人，不能代替其他成员生成个人报告或发送通知。
接口强制生成一个新报告版本，但不写入生产 `workflow.jobs` 或 `workflow.job_runs`。`PRE_MARKET`
默认触发 08:30 宏观阶段；可加 `?phase=PERSONALIZED` 验证调用者自己的 08:35 个性化阶段，
无持仓无关注时返回 `{reportId: null, outboxId: null}` 且不写生产 job（详见 §11.7）。响应示例：

```json
{"data":{"reportId":"<uuid>","outboxId":"<uuid-or-null>"},"meta":{"...":"..."}}
```

`outboxId` 非空表示当前调用者的通知已排队，仍需等待 Worker 投递；报告非空而 `outboxId=null` 表示
报告已成功生成，但当前用户没有活动企微绑定、已关闭该时段订阅或没有可投递内容。此结果不是报告生成失败，也不应通过手工插入任务或修改
Outbox 绕过用户选择。生产启动继续拒绝 `AUTH_DEV_MODE=true`，调试权限不能由开发模式放宽。

手动触发只消费已经持久化的数据，不执行 Worker 的行情、热点与情绪刷新。盘前宏观使用当天受治理的
`source_context` 重新运行当前渲染逻辑，不覆盖共享缓存，也不代表重新采集了最新行情。

## 11. 盘前双阶段拆分运维（08:30 宏观 / 08:35 个性化）

migration `045_split_pre_market_reports.sql` 在不破坏现有四时段订阅、过滤与 API 枚举的前提下，把单个
`PRE_MARKET` 拆成两个内部阶段，分别落库、分别投递、分别出现在研报审计中。关注列表（migration 044）是
个性化阶段的数据来源，必须先于双阶段调度代码发布。

### 11.1 两个变体与公开会话不变

- 公开 `report_session` 仍为 `PRE_MARKET`，`workflow.jobs` 每个租户仍恰好一条 `PRE_MARKET` 记录；
  **不得**为个性化插入第五条任务，否则四时段完整性监控与 migration 040 的每租户每时段唯一约束都会失守。
- 内部变体由 `reporting.reports.report_variant` 区分：`PRE_MARKET_MACRO`（宏观，08:30）与
  `PRE_MARKET_PERSONALIZED`（个性化，08:35）。允许的变体量还包括既有 `STANDARD`（用于 INTRADAY /
  FUND_1430 / POST_MARKET 等无受众会话）。
- `audience_user_id` 在宏观阶段为 `NULL`（租户全体活动成员可读），在个性化阶段必须等于目标成员；
  `(tenant_id, audience_user_id)` 复合外键约束其为当前租户成员。版本唯一索引从
  `(tenant_id, trade_date, report_session, version)` 调整为受众感知的
  `uq_reports_variant_audience_version`。

### 11.2 调度与幂等

scheduler 用两个内部 dispatch key 派发：`PRE_MARKET_MACRO` 于 08:30，`PRE_MARKET_PERSONALIZED` 于
08:35。runner 把二者映射到同一条 `PRE_MARKET` job，但持久化 job key 携带内部变体与受众：

- 宏观：`job:<job-id>:<trade-date>:PRE_MARKET_MACRO`，每租户每天一次；
- 个性化：`job:<job-id>:<trade-date>:PRE_MARKET_PERSONALIZED:<user-id>`，每租户、每用户、每天一次。

租约、失败分类、恢复与重试沿用 `workflow.job_runs` 状态机。Worker 重启后从持久化 key 通过
`parse_business_job_key()` 严格还原阶段与受众 UUID，绝不会把个性化 run 误重放为租户级 `PRE_MARKET`
路径；key 形状非法时直接 `ValueError` 失败关闭，不猜测。

### 11.3 隐私与跨成员隔离

- 宏观报告 `audience_user_id IS NULL`：同租户任意活动成员均可读；
- 个性化报告只允许 `audience_user_id` 本人通过报告列表、详情、条目与版本历史读取；另一成员读取同一
  `report_id` 时 API 返回 **404**（而非 403），避免受众枚举；
- RLS 同时约束 `reporting.reports` 与其子表 `report_items`：父报告 `audience_user_id IS NULL OR =
  auth.uid()` 才可见；`authenticated` 与 PUBLIC 都不能跨成员读取个性化内容；`wealthsail_api` 通过事务内
  `app.user_id` 强制本人边界。审计 `details` 记录 `variant`、`audienceUserId`、`deliveryCount`、
  `cacheHit` 与 `sharedBriefId`，但不输出关注原始搜索词或数据库凭据。

### 11.4 共享缓存并发

宏观阶段写入追加式 `reporting.shared_pre_market_briefs`（按 `trade_date` 唯一）。首个执行者在
advisory transaction lock 内基于权威结构化数据生成并写入；同一天后续租户只读取缓存，不重复调用模型或
外部生成流程。生成失败时不写半成品，后续 catch-up tick 可重试；`wealthsail_api` 与 `wealthsail_worker`
只有 SELECT/INSERT，不能 UPDATE/DELETE。

### 11.5 四种分支与跳过

08:35 个性化阶段按成员枚举：有持仓、仅关注、两者都有均生成一条受众为该用户的
`PRE_MARKET_PERSONALIZED`；持仓与关注**均为空**为正常 `SKIPPED:NO_PERSONAL_CONTEXT`，不记作失败、
不写报告、不创建 Outbox。两阶段均不新增 AI 调用；无可靠字段时明确显示“暂无”，不得推断或伪造。

### 11.6 订阅与投递

账号安全页的 `PRE_MARKET` 开关同时控制宏观与个性化两阶段的企微 Outbox 展开；关闭后两阶段仍按计划生成，
只是不向该用户投递，Outbox 数量为 0。订阅开关只作用于 Outbox，不影响报告生成、版本链与研报审计。

### 11.7 上线顺序与验收

1. 执行并回读 044（关注列表）：表、主键 `(user_id, symbol)`、RLS、`wealthsail_api` 仅 SELECT/INSERT/
   DELETE、`authenticated`/PUBLIC 无越权；
2. 部署关注列表 API 与前端（重启 API、重建前端），验证关注增删、空列表与报告上下文读取；
3. 执行并回读 045（变体/受众/共享缓存）：`report_variant` 与 `audience_user_id` 列、复合外键、
   `uq_reports_variant_audience_version`、追加式缓存表与防写触发器、`wealthsail_api`/`wealthsail_worker`
   仅 SELECT/INSERT、个性化 RLS 收紧；
4. 重启 API 与 Worker，重建并发布前端；
5. **不**回填第五条 `workflow.job`，确认每个活动租户仍恰好四条标准报告任务；
6. 交易日观察 08:30 宏观与 08:35 个性化自然调度、两篇独立审计报告及对应 Outbox；
7. 用 §10 调试入口联调：
   - `POST /api/v1/debug/reports/trigger/PRE_MARKET` 默认触发宏观，返回单 `{reportId, outboxId}`；
   - `POST /api/v1/debug/reports/trigger/PRE_MARKET?phase=PERSONALIZED` 生成调用者自己的个性化新版本；
     当前用户非本租户 ACTIVE 成员返回 404；无持仓无关注返回 `{reportId: null, outboxId: null}` 且不写生产 job；
8. 跨成员隔离验证：成员 A 以本人令牌读取成员 B 的个性化 `report_id` 必须 404；宏观 `report_id` 两人均可读。

### 11.8 回滚仅向前

任何发布问题都暂停部署并新增 forward-fix migration；**绝不**编辑 migration ledger 行，也**绝不**手工改写
已执行的 044/045。个性化报告隔离或变体约束发现缺陷时，新增迁移收紧并回读，不删除或涂改既有迁移。

### 11.9 盘中跟踪改为条件触发（减少推送噪音）

migration `046_intraday_alert_throttle.sql` 在保持四时段调度结构不变的前提下，把**盘中跟踪（INTRADAY）**
从“每 5 分钟无条件推送”改为“**阈值触发 + 30 分钟去重**”，解决用户被高频推送淹没的问题。基金 14:30 报告
（`FUND_1430`）保持每天 14:30 一次，**不改动**。

- 调度形态不变：INTRADAY 仍是每 5 分钟一次的内部 dispatch tick，但 tick 本身只是**评估节奏**，不再等于推送；
  只有命中阈值才生成并投递报告，未命中直接 `SKIPPED:INTRADAY_NO_ALERT`，不写报告、不创建 Outbox。
- 触发条件（任一命中即推送）：
  - 单只持仓当日涨跌幅 `|changePct| ≥ 3%` → 告警键 `HOLDING:<instrument_id>`；
  - 组合整体当日涨跌幅 `|组合涨跌幅| ≥ 2%` → 告警键 `PORTFOLIO`。
- 组合整体涨跌幅的口径：`get_summary` 刻意返回 `dailyPnlRate = NULL`（不伪造比率），由告警评估侧按
  `(dailyPnl / (totalAsset − dailyPnl)) × 100` 推导；缺字段或分母为 0 时视为无法判定、不触发。
- 单只 `changePct` 取自 `market.market_observations.metadata -> 'changePct'`（由 Worker 刷新），告警评估阶段
  **不实时拉行情**，直接读最新快照；无快照的持仓跳过该条阈值判断。
- 30 分钟去重：新增 `workflow.intraday_alert_throttle(tenant_id, user_id, alert_key, last_sent_at)`，主键
  `(tenant_id, user_id, alert_key)`，RLS 强制；`repository.claim_intraday_alert` 以
  `INSERT ... ON CONFLICT DO UPDATE` 原子占位，若 `last_sent_at ≥ now − 30min` 则返回 `False`（冷却中，跳过）。
  同一用户对同一条告警 30 分钟内不重复触发。
- 报告落库：新增变体 `INTRADAY_ALERT`，`audience_user_id` 必填且等于目标成员；migration 046 同步放宽为
  `report_variant` 与 `(report_variant, audience_user_id)` 复合 CHECK 允许该变体（在 045 基础上增量修改，
  未删除既有约束）。推送内容经由 `generate_report(..., push_content_override=...)` 覆盖，明确写出触发条件、
  当前涨跌幅与“数据截至 HH:MM”，便于用户判断。
- runner 编排：INTRADAY 与 `PRE_MARKET_PERSONALIZED` 一致，按 `_active_tenant_members` 逐成员扇出，
  每成员独立租约键 `job:<job-id>:<trade-date>:INTRADAY:<HHMM>:<user-id>`；无受众时回退租户 owner。
- 调试入口：`POST /api/v1/debug/reports/trigger/INTRADAY?phase=ALERT` 评估并（命中时）生成调用者自己的
  盘中异动报告；该次调试绕过 30 分钟冷却，但不会修改自动告警冷却记录。当前用户非本租户 ACTIVE 成员
  返回 404；未命中阈值返回 `{reportId: null, outboxId: null}` 且不写生产 job。
- 新增/改动文件：`backend/reports/intraday.py`（纯函数评估 + 编排）、`migrations/046_intraday_alert_throttle.sql`、
  `backend/reports/repository.py`（两个新查询）、`backend/reports/service.py`（透传 `push_content_override`）、
  `backend/jobs/runner.py`（INTRADAY 扇出分支）、`backend/debug/{api,service}.py`（ALERT 调试入口）。

#### 11.9.1 上线顺序与验收

1. 执行并回读 046（节流表 + 变体放宽）：表、主键、RLS、`wealthsail_api` 仅 SELECT、`wealthsail_worker` 读写、
   `report_variant` CHECK 仅增量放宽；
2. 重启 API 与 Worker，重建并发布前端；
3. 交易时段观察：正常波动下盘中不再每 5 分钟推送；单只急拉/急跌破 ±3% 或组合破 ±2% 时收到“盘中异动提醒”；
4. 去重验证：连续两次 5 分钟 tick 命中同一告警，第二次应 `SKIPPED:INTRADAY_NO_ALERT`，30 分钟后方可再次触发；
5. 确认 `FUND_1430` 14:30 推送频率与内容未受影响；
6. 用 §10 入口联调 `?phase=ALERT`：命中返回真实 `reportId`，未命中返回 `{reportId: null, outboxId: null}`。

#### 11.9.2 回滚仅向前
