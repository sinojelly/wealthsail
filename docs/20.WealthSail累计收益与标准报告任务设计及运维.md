# WealthSail 累计收益与标准报告任务设计及运维

> 文档版本：v1.0 · 2026-08-30
> 实现基线：migration 040、`/api/v1/portfolio/performance-baselines`、
> `scripts/backfill_standard_report_jobs.py`

## 1. 本次解决的两个问题

第一，当前持仓导入后可以可靠计算“持仓收益”，但不能把当前市值全部当成“累计收益”。系统现在
为每个账户建立独立收益起点，从该点自动跟踪，并允许用户可选补充导入前已经发生的历史累计盈亏。

第二，migration 033 只在“个人租户邀请码注册”路径创建四个报告任务，既有租户以及通过运维脚本
迁移出的个人租户可能没有任务。当前注册与运维迁移路径都已补齐创建逻辑；对已经存在的租户，提供
允许全空或“现有记录为标准定义精确子集”的受控回填脚本。

## 2. 用户看到的两个收益不是同一个概念

### 2.1 当前持仓收益

```text
当前持仓收益 = Σ(当前市值 − 当前持有份额 × 剩余成本价)
```

它回答“现在仍持有的这些资产浮盈浮亏多少”。它不包含已经卖出的历史收益，也不受出入金影响。
任何当前持仓缺少可靠估值时，组合持仓收益不发布部分结果。

### 2.2 累计收益

每个账户独立计算：

```text
跟踪以来收益 = 当前总资产 − 跟踪起点总资产 − 跟踪期净外部入金
账户累计收益 = 用户填写的跟踪前历史累计收益 + 跟踪以来收益
组合累计收益 = 当前查看范围内所有账户累计收益之和
```

净外部入金只包含已确认、未被冲正的 `CASH_IN/CASH_OUT`。`CASH_OUT` 现金腿是负数，因此直接
求和得到净入金。BUY、SELL、分红、费税和期初 ADJUSTMENT 都是账户内部经济变化，不能当作新增
本金。累计收益率/TWR 本阶段不发布；系统不会用累计收益除以静态本金得到一个貌似精确的百分比。

示例：起点资产 100,000 元，之后净入金 10,000 元，当前资产 118,000 元，用户确认起点前历史
累计收益 -2,000 元，则跟踪以来收益为 8,000 元，累计收益为 6,000 元。

## 3. 普通用户需要做什么

默认不需要做任何事：

1. 首次导入并完成可靠估值；
2. 系统以首个完整 NAV 自动建立账户收益起点，历史累计收益默认 0；
3. 后续确认的出入金和资产估值变化自动进入累计收益；
4. 资产看板新增“累计收益”卡片，并显示从哪天开始跟踪。

只有用户能从天天基金、券商或旧账本明确确认“跟踪起点之前的累计盈亏金额”时，才进入
“账号安全 → 累计收益起点（可选）”，按账户填写正数或负数并保存。用户填写的是金额，不是收益率，
也不是当前市值。系统保存后会自动刷新资产总览；持仓、成本、账本事件和起点日期都不会改变。

多个账户的收益起点日期可能不同。组合卡片副文案显示最早起点，但每个账户仍按自己的起点独立
计算。当前作用域内任一账户缺完整估值或收益起点时，组合累计收益显示不可用，避免把部分账户结果
冒充完整组合。

## 4. 数据与权限设计

`ledger.account_performance_baselines` 是追加式版本表，关键字段如下：

| 字段 | 含义 |
|---|---|
| `tenant_id/account_id` | 租户与投资账户边界 |
| `baseline_as_of` | 自动跟踪起始日 |
| `baseline_total_asset` | 起始日完整账户总资产 |
| `initial_cumulative_pnl` | 用户已知的起点前历史累计盈亏，默认 0 |
| `source` | `AUTO_MIGRATION`、`AUTO_NAV` 或 `USER` |
| `version` | 同账户严格递增版本 |
| `created_by` | USER 版本的确认用户；自动版本为空 |
| `idempotency_key/request_hash` | 命令防重及同键异内容冲突检查 |

表禁止 UPDATE/DELETE。用户修改历史累计收益时，服务端锁定最新版本，校验 `If-Match`，继承原起点
日期和资产并追加新版本，同时写入 `PERFORMANCE_BASELINE_REVISED` 审计。RLS 要求当前租户成员；
插入还要求租户 OWNER/ADMIN/EDITOR、本人身份以及账户 `BENEFICIAL_OWNER/JOINT_OWNER` 归属。
浏览器数据库角色不能直读，Worker 不能插入用户版本。

migration 039 为已有完整 NAV 账户建立 `AUTO_MIGRATION` version 1。未来账户的首个完整 NAV 通过
数据库触发器建立 `AUTO_NAV` version 1；部分估值、已知金额或 0 值占位都不能代替完整 NAV。

## 5. API 与前端契约

- `GET /api/v1/portfolio/summary`：返回 `cumulativePnl`、空的 `cumulativePnlRate`、
  `performanceBaselineAsOf` 和 `performanceBaselineMixed`；
- `GET /api/v1/portfolio/performance-baselines`：只返回当前用户归属账户的最新版本；
- `PUT /api/v1/portfolio/performance-baselines/{accountId}`：请求体为
  `initialCumulativePnl`，必须带 `If-Match` 与 `Idempotency-Key`；
- 资产看板同时显示“持仓收益”和“累计收益”，正收益为红色、负收益为绿色；
- 账号安全页的历史收益设置是可选项，值不变、正在提交或角色无权时保存按钮不可用。

## 6. 四个标准报告任务

| 任务 | session | 默认计划（Asia/Shanghai） | 用户价值 |
|---|---|---|---|
| `pre_market_brief` | `PRE_MARKET` | 工作日 08:30 | 盘前简报 |
| `intraday_tracking` | `INTRADAY` | 工作日 09:00–14:59 每 5 分钟 | 盘中跟踪与风险变化 |
| `fund_1430_estimate` | `FUND_1430` | 工作日 14:30 | 基金 2:30 报告 |
| `post_market_review` | `POST_MARKET` | 工作日 15:30 | 盘后交互复盘 |

新个人租户注册和新的 `migrate_user_to_personal_tenant.py --apply` 都在创建租户/迁移身份的同一事务
写入这四条记录，任一失败整笔回滚。运行时 API 没有 `workflow.jobs` INSERT 权限，避免普通接口
绕过治理创建任意定时任务。

已经存在的租户使用 `scripts/backfill_standard_report_jobs.py`。脚本默认只读：目标租户四类任务
全空或只缺少部分标准任务时返回 `READY`，已完整等于标准定义时返回 `ALREADY_APPLIED`。现有记录
只有在名称、时段、Cron 和启用状态均与标准定义精确一致时才会被保留，脚本只插入缺失项；发现
禁用、改名、改时或重复配置时立即停止，要求人工判断，不自动覆盖。`--apply` 还要求数据库目标、
租户 UUID 和租户名称三重精确确认；缺失任务与 `REPORT_JOBS_BACKFILLED` 审计在一个事务中提交并
回读验证。结果与审计同时记录 `existingSessions` 和 `insertedSessions`，便于区分保留项和新增项。
migration 040 还在数据库层保证同一租户同一 `report_session` 最多一条记录；发现历史重复时迁移
主动停止，不会擅自选择或删除任务。

运行监控只对“ACTIVE 且存在有效企微绑定”的租户检查四时段完整性。完全没有启用任务时发送
`TENANT_NO_ENABLED_JOBS`，存在部分任务、重复或非标准配置时发送
`TENANT_INCOMPLETE_REPORT_JOBS`；未绑定渠道的演示/虚拟租户不会因此产生推送告警。

完整生产命令、readback SQL 和 Jelly 租户示例见
[11.数据库升级方法.md](./11.数据库升级方法.md) 的“已有租户受控补齐四个标准报告任务”。

## 7. 上线顺序与验收

1. 更新 `master` 代码，确认 migration 041 存在；
2. 使用 migration/admin DSN 执行 `scripts/migrate.py`，看到 041 `APPLIED` 或 `SKIP` 且 readback 成功；
3. 对既有 so、Jelly 租户逐一预检、再执行标准任务回填，分别回读恰好四条启用任务；
4. 重启 API 与 Worker，重新构建并发布前端；
5. 登录后确认资产看板有独立“持仓收益/累计收益”卡片，账号安全页可看到自动起点；
6. 不填写历史累计收益时累计收益从 0 历史值正常跟踪；填写后只改变累计收益，不改变持仓收益；
7. 登记一笔 CASH_IN/CASH_OUT 后，累计收益应扣除净入金影响；普通买卖不应改变外部入金；
8. 运维页与数据库确认四个 report job 可被 Worker lease，监控不再发送“无启用报告任务”。

若 039 已提交但 readback 失败，停止发布并新增 forward-fix migration，不删除 migration ledger，
也不改写已执行的 039。若标准任务回填报告冲突，先导出当前四类任务和审计记录，由人工决定保留
定制计划还是另写受审计修正，禁止直接删行后重跑。

## 8. 推送内容的持仓/无持仓双模式

四时段任务的触发时间和报告 API 不变，生成阶段按当前有效持仓数量自动选择内容：

- 有持仓：继续调用原个性化提示词，生成持仓分析、市场情绪、AI 建议和宏观解读；企微仍发送原有
  “报告已发布”通知，用户进入 WealthSail 查看完整报告；
- 无持仓：生成市场观察版，报告和企微正文固定包含“今日大盘风向、值得关注的板块、今日数据解读、
  投资思考、添加自选或导入持仓”五部分，并明确“不构成投资建议”。

两种模式发布后均通过企业微信 Markdown 通知触达，正文末尾的“查看完整报告”链接指向
`/reports?reportId=<report_id>`。有持仓模式保留原个性化摘要，无持仓模式保留共享市场观察正文；
链接只改变触达和回看方式，不改变报告生成、共享缓存、Outbox 幂等键或租户隔离语义。用户会话已
过期时先进入登录页，认证成功后再回到对应报告。

无持仓模式读取 Worker 已持久化的 `market.market_sentiment`，仅在当日缓存不存在时并行获取一次
主要指数与行业板块快照。五段正文全部由结构化、带时效标记的数据确定性生成，不调用模型，因此
无持仓模式的 token 成本为零，也不会把模型措辞误当成行情事实或买卖建议。通过
`reporting.shared_market_briefs.trade_date` 唯一约束、受控 API 角色事务和 transaction-pool 安全的
`pg_advisory_xact_lock`，全系统每天只生成一份；其他租户直接复用，但仍各自生成租户内报告、审计记录
和独立 outbox。外部行情失败时，缺失数据明确标为不可用；上一交易日数据会标明日期和“非今日实时”。

migration 041 创建追加式 `reporting.shared_market_briefs`。`wealthsail_api` 和
`wealthsail_worker` 只有 SELECT/INSERT，不能 UPDATE/DELETE；`authenticated` 和 PUBLIC 无访问权。
迁移 readback 会检查表、追加式触发器及最小权限边界。上线后可用以下 SQL 验证每日复用：

```sql
SELECT trade_date, generation_status, provider, model, quality_status,
       token_usage, cost_cny, generated_at
FROM reporting.shared_market_briefs
ORDER BY trade_date DESC
LIMIT 7;
```

同一交易日应只有一行。审计事件 `REPORT_GENERATED.details` 中，个性化模式记录
`generationMode=PERSONALIZED`；无持仓模式记录 `generationMode=NO_HOLDINGS_SHARED`、
`sharedBriefId` 与 `sharedCacheHit`，可据此核对复用是否生效。
