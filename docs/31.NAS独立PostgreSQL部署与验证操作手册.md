# NAS 独立 PostgreSQL 部署与验证操作手册

日期：2026-10-22。方案：空库首装，使用已有 PostgreSQL 18，Web 通过 HTTPS 域名或 NAS 反向代理访问。

2026-10-23 补充：实际域名为 `wealth.sinojelly.kdns.fr`，采用 Cloudflare Tunnel + Access 对指定成员开放 LAN/WAN。**此部署方式直接按 [外网接入操作手册](../external-access/README.md) 执行**，其中 `ws` 前缀包含本手册的 NAS 配置和额外入口 overlay；不要混用下面仅有两文件的 `dc up` 命令丢失入口防护。本手册仍作为数据库、首装数据、用户/租户及备份的详细说明。

## 1. 数据库与测试数据

保留 NAS 现有 PostgreSQL Compose。该服务的 DNS 是 `postgres`、容器端口 `5432`、管理员名 `admin`、共享网络 `global-postgres-network`。当前 `prismscore_db` 不作为 WealthSail 数据库；安装器仅创建/使用 `wealthsail`。

正式安装会执行 `migrations/` 中全部生产迁移，编号中有历史缺号。**不要按编号拼接 SQL，也不要跳过含有 DDL 的迁移。**

以下开发种子全部不执行：

- `seeds/dev/006_mock_seed_data.sql`
- `seeds/dev/010_dev_seed_workbench.sql`
- `seeds/dev/seed_zhangming_tenant_supabase.sql`
- `seeds/dev/seed_wangfang_tenant.sql`

编号 006/010 已不在正式 migration 目录；migration runner 会拒绝生产账本出现这两个版本。不要运行 `scripts/local_dev.py`、`scripts/prepare_ci_smoke_db.py` 或旧 `scripts/local_supabase_compat.sql` 初始化 NAS，它们是本地/CI 专用入口。

生产迁移本身不创建测试用户、演示租户或虚拟资金。但 053/054 历史上会填入基金穿透近似权重；安装器会在**首次空库**完整迁移后、创建管理员前移除这组近似数据。清理受持久化首装标记保护，只接受空用户/账户/账本，且检查近似数据来源；升级既有库不会执行此清理。052/054 中的公开基金/股票目录、数据源与研究分类等基础目录保留，它们不等于用户自选或持仓。

首装完成且尚未操作 Web 时，预期：1 个指定管理员、1 个个人租户、1 个 OWNER 成员、4 个标准报告任务；账户/交易/持仓/净值/近似穿透均为 0。不会创建测试账号。

## 2. 上传源码与生成配置

把本次修改后的整个项目放到 NAS 的应用目录，以下命令在该目录执行。例如：

```bash
cd /你的NAS应用目录/WealthSail
```

生成配置只需要 Python 标准库。NAS 已安装 Python 时：

```bash
python3 scripts/configure_nas.py --web-base-url https://wealth.sinojelly.kdns.fr
```

NAS 没有 Python 时，使用临时 Python 容器：

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/workspace" -w /workspace python:3.12-slim \
  python scripts/configure_nas.py --web-base-url https://wealth.sinojelly.kdns.fr
```

把示例域名替换为你的实际 HTTPS 入口。生成：

- `deployment/env/api.env`：受限 API DSN、JWT/会话/邀请密钥。
- `deployment/env/worker.env`：独立 Worker DSN、共享 routing key。
- `deployment/env/codex.env`：Codex Runner 的内部调用令牌、超时参数，不包含数据库口令或 Web 会话密钥。
- `deployment/nas.env`：Compose 网络名、管理员名、Web 监听地址等。

这些文件不应提交 Git；生成器不会显示口令，也拒绝覆盖已有文件。重启/升级必须保留这些文件，不能每次重新生成。数据库管理员密码不会存进这些文件。

此前已生成前三份旧配置、缺少 `codex.env` 时，执行 `python3 scripts/configure_codex.py` 补齐，已有数据库和身份密钥保持。无 Python 时复用上方临时容器，将脚本替换为 `scripts/configure_codex.py`。详细命令见 [Codex 统一模型与 NAS 认证指南](./32.Codex统一模型与NAS认证操作指南.md)。

默认反向代理在 NAS 宿主机上，访问 `127.0.0.1:8080`。若反向代理在另一个容器/主机，它无法访问此宿主机回环地址：在 `deployment/nas.env` 中将 `WEB_BIND_ADDRESS` 改为 NAS 的受控局域网 IP，再让反向代理指向该 IP:8080。端口冲突时修改 `WEB_PORT`。API 和数据库端口不需要新增映射。

**浏览器始终访问 HTTPS 域名。** 直接使用 `http://NAS-IP:8080` 不能保证 Secure refresh cookie 保存，刷新页面后的登录体验会不同。无需为测试把 `APP_ENV` 改成 development。

## 3. 检查已有网络与构建

在当前 shell 定义一个简写，后面命令都用它：

```bash
dc() {
  docker compose --env-file deployment/nas.env \
    -f docker-compose.yml -f docker-compose.nas.yml "$@"
}
```

新开 SSH shell 后需要重新定义。该简写也可替换为完整的 `docker compose ...` 前缀。

```bash
docker network inspect global-postgres-network >/dev/null
docker exec postgres pg_isready -U admin -d postgres
dc config --quiet
dc build api frontend
```

预期：网络存在，数据库 accepting connections，Compose 校验无错误，两个镜像构建成功。`api`、`worker`、`codex-runner`、`codex-auth`、`db-init` 复用同一后端镜像，镜像包含 Linux 原生 Codex CLI。不需要在 NAS 安装宿主 Codex，也不需要重建已有 PostgreSQL 容器。

`dc config` 完整输出包含解析后的秘密，日常只使用 `--quiet`，不要把完整配置粘贴到日志或聊天。

## 4. 创建独立数据库和首位管理员

```bash
dc run --rm --no-deps db-init \
  --confirm-target postgres:5432/wealthsail \
  --bootstrap-email 你的登录邮箱@example.com \
  --nickname 管理员 \
  --tenant-name 我的投研工作台
```

按提示依次隐藏输入：

1. NAS PostgreSQL 的 `admin` 密码。
2. 新 Web 管理员密码（至少 12 字符、最多 72 UTF-8 字节）。
3. 再次输入 Web 密码。

数据库口令和 Web 口令是不同身份。不要把口令作为命令行参数传入。

工具会检查目标、集群级角色冲突、管理员权限，创建独立库、应用完整迁移、设置独立运行口令、清理首次近似种子、创建管理员和任务，再用真实 API/Worker 身份验证权限。

预期末尾包含：

```text
READBACK OK: ...
Runtime API/Worker login boundaries verified. No development seeds were executed.
Ready: postgres:5432/wealthsail
Web administrator created.
First-install approximate holdings removed: ...
```

如果提示角色冲突，不要删除其他库或执行 blanket GRANT/REVOKE；先检查这个 PG 集群是否已有其他 WealthSail 安装。`wealthsail_*` 角色属于整个集群，不能由多个独立数据库各自轮换同名账号密码。

如果某份迁移失败，停止启动应用，保留原 env、查看报错的迁移名称后处理；不要手工跳版本、删除账本或改 checksum。修复后可重复运行安装器。首次清理标记只有清理及可选 bootstrap 事务提交后才完成，避免失败重试留下近似数据。

## 5. 启动与基础检查

先完成 Codex 设备登录和无模型请求的预检；使用上文两文件 `dc` 前缀的部署可执行：

```bash
dc run --rm --no-deps codex-auth login --device-auth
dc run --rm --no-deps codex-auth login status
dc run --rm --no-deps --entrypoint python codex-auth -m scripts.codex_admin check
```

浏览器按终端的一次性设备码完成授权。Cloudflare 部署使用 [完整三文件部署步骤 5.4](../external-access/DEPLOYMENT.md#54-为-wealthsail-完成-codex-登录) 中对应命令。预检不调用模型；认证文件只保存在独立 `codex_auth` 命名卷内，不与 StudyOS 共用。

```bash
dc up -d codex-runner api worker frontend
dc ps
dc logs --since=10m api worker
dc exec -T api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=5).status)"
```

预期：API 与 Codex Runner healthy，健康端点 200；Worker 日志包含数据库连接与 running。Worker 没有 HTTP 服务，因此禁用了共用镜像中只适用于 API 的 HTTP healthcheck。Runner 健康检查只检查进程，模型权限仍须在 Web 聊天验证。

NAS 反向代理配置 HTTPS 域名转发到前端入口，保留 Host、X-Forwarded-For、X-Forwarded-Proto。浏览器打开你在配置中设置的 HTTPS 域名。

首次市场数据下载受 NAS 联网和数据源状态影响。用户/租户登录可先验收，采集和报告可在随后配置真实数据源及模型服务后验收。

## 6. Web 用户和租户验收

- 使用你刚创建的邮箱/密码登录；进入设置能看到平台管理员能力。
- 刷新页面、关闭后重新打开，仍能恢复会话；登出后刷新不能继续进入工作台。
- “设置 → 租户与成员 → 邀请成员”：邀请另一个新邮箱，指定 VIEWER；退出或使用无痕窗口，在原登录页接受邀请，确认属于原租户。
- 管理员创建“独立租户邀请码”：第三个新邮箱接受邀请，确认得到独立租户 OWNER 身份，不能看到管理员账户数据。
- 普通租户 OWNER/ADMIN 不应获得平台管理员创建独立租户邀请的权限。
- 初次资产为空是正确行为。通过原开户/导入流程加入真实账户和基金持仓，不导入开发 SQL。
- 导入后观察数据任务状态、Worker 日志和报告结果；重启容器，确认真实数据仍保留。

可在 pgAdmin 连接 `wealthsail` 只读核对首装数量。下面的数量应在第 4 步完成、执行上述邀请/导入前检查：

```sql
SELECT 'profiles' AS item, count(*) FROM identity.profiles
UNION ALL SELECT 'tenants', count(*) FROM identity.tenants
UNION ALL SELECT 'accounts', count(*) FROM identity.accounts
UNION ALL SELECT 'ledger_events', count(*) FROM ledger.ledger_events
UNION ALL SELECT 'positions', count(*) FROM ledger.position_snapshots
UNION ALL SELECT 'nav', count(*) FROM ledger.account_nav_snapshots
UNION ALL SELECT 'fund_lookthrough', count(*) FROM market.fund_lookthrough
UNION ALL SELECT 'report_jobs', count(*) FROM workflow.jobs;
```

预期依次为 `1 / 1 / 0 / 0 / 0 / 0 / 0 / 4`。管理员账号只在 `identity.profiles`，不需要 Supabase `auth.users`。

## 7. 企微、邮件与模型配置

NAS 生成配置默认显式关闭尚未配置的企微和邮件找回，不妨碍登录、邀请和租户管理。原页面保留；点击未配置功能会明确提示不可用。

- 企微：按 `deployment/env/*.env.example` 填写两进程分别需要的参数，再在两个运行 env 中设置 `WECOM_ENABLED=true`。API 不得收到 Worker 的发送 secret。关闭时，待发 Outbox 不被领取或消耗重试次数。
- 邮件：在 API env 配真实 SMTP 配置，并设置 `PASSWORD_RESET_EMAIL_ENABLED=true`；启用生产 STARTTLS 后，原“忘记密码”流程恢复。未开启时不生成无法投递的找回令牌。
- 模型：聊天、普通报告的模型分析、每日公共研究全部走 Codex Runner；无需 `MODEL_API_KEY`。API/Worker 只有访问 Runner 的内部令牌，没有 Codex 认证文件。可选 `CODEX_MODEL` 在 API、Worker、Runner 中保持一致，留空沿用账号默认；确定性计算和模板逻辑继续保留。
- 每日AI流水线默认关闭，启用后默认每天07:00公共采集→质量检查→Codex研究，包含周末；`DAILY_RESEARCH_SCHEDULE_MODE=DAILY|WEEKDAYS`及`DAILY_RESEARCH_SCHEDULE_TIME=HH:MM`可调整，WEEKDAYS仅周一至周五。聊天继续可用。旧08:30/08:35简报与AI晨间推送改为另外两个默认关闭的开关。登录预检和Web聊天通过后，需要时将API与Worker运行env的每日研究开关**都**改为`true`，并保持日程配置一致，再重建两服务。不要用`--once`试登录，真实模型仍受当日唯一名额约束，结果不确定不自动重试。

```bash
dc up -d --force-recreate codex-runner api worker
```

### 7.1 关闭自动日报、基金估值、盘后复盘和盘中检查

以下业务开关均默认`false`。在`deployment/env/worker.env`与`deployment/env/api.env`中保持以下值一致；
如果部署指定了其他 `WORKER_ENV_FILE` / `API_ENV_FILE`，修改这两个变量实际指向的文件。已有文件中的
显式 `true` 会覆盖代码默认值；项目根目录 `.env` 里的同名变量不会自动传入运行容器。

```dotenv
DAILY_RESEARCH_ENABLED=false
DAILY_RESEARCH_SCHEDULE_MODE=DAILY
DAILY_RESEARCH_SCHEDULE_TIME=07:00
DAILY_RESEARCH_START_WINDOW_MINUTES=120
DAILY_RESEARCH_PIPELINE_TIMEOUT_SECONDS=7200
PRE_MARKET_REPORTS_ENABLED=false
MORNING_OPPORTUNITY_PUSH_ENABLED=false
FUND_1430_ENABLED=false
POST_MARKET_REVIEW_ENABLED=false
INTRADAY_TRACKING_ENABLED=false
```

- `DAILY_RESEARCH_ENABLED=false`：停止自动AI流水线；开启时不需要同时开启`ALPHA_PUBLIC_ENABLED`。DAILY包含周末；WEEKDAYS仅周一至周五，不含行政调休。
- `PRE_MARKET_REPORTS_ENABLED=false`：停止旧08:30宏观、08:35个性化简报自动生成、恢复及对应消息发送。
- `MORNING_OPPORTUNITY_PUSH_ENABLED=false`：停止当日AI研究结果的晨间群推送，不影响14:30机会检查。
- `FUND_1430_ENABLED=false`：停止 14:30 标准基金估值报告和机会服务中的基金/持仓买卖点检查与推送。
- `POST_MARKET_REVIEW_ENABLED=false`：停止 15:30 盘后复盘。
- `INTRADAY_TRACKING_ENABLED=false`：停止每五分钟持仓异动检查，包括显式 `phase=ALERT` 告警评估。

关闭后自动调度和旧自动任务的失败恢复均跳过相应时段，Worker 不会为该关闭时段刷新行情、创建新的
租约或报告运行记录。历史记录保留。页面手动盘前/盘后报告仍按既有权限执行；明确提交的基金手动刷新
请求仍由 Worker 消费。运维脚本 `scripts/manual_trigger_post_market.py` 走统一任务入口，使用时须在
该进程环境显式设置 `POST_MARKET_REVIEW_ENABLED=true`。

`ALPHA_PUBLIC_ENABLED`保留给独立无模型采集场景；每日AI开启时，采集是流水线内部强制步骤，不注册另一条并行早间采集循环。企业行为、基金主数据与官方净值等全局同步保持独立。旧盘前待发送消息在开关关闭时保留队列但不领取或发送；发送历史不删除。

此次升级的`095_daily_research_pipeline.sql`在上线前已移除内部事务，由迁移器保证DDL与账本原子性；必须按[数据库升级流程](11.数据库升级方法.md)先应用前向迁移，再更新API、Worker和前端。不要改写093/094或删除今日执行记录。若已应用旧095，先核对部署历史，不修改生产账本绕过校验和。默认每天07:00至09:00允许新领/恢复，已持有效租约者可跨窗口完成准备及研究，另受首次开始后7200秒总期限和模型超时约束；详见[新需求与边界](34.工作日每日AI投研流水线与旧简报停用方案.md)。

运行示例（API、Worker一致，修改后force-recreate）：每天07:00用`DAILY`/`07:00`；周一至周五08:00用`WEEKDAYS`/`08:00`。不需要NAS cron；已有当天流水线保留原计划时间及批次，修改配置不会消除当日模型槽。全天候调度跨午夜时，准备阶段以`MISSED/SourcePreparationCrossedDay`终止；重启只观察旧任务，有效租约不打断，过期未登记模型的任务归档MISSED，已登记模型的任务归档UNCERTAIN，不使用旧批次调用新日模型。

关闭`DAILY_RESEARCH_CATCH_UP`后，没有既有任务的重启才直接等待下次计划；已有任务仍每60秒观察、按冻结窗口归档，但不重新领取。此边界修复不修改095或生产迁移账本，默认仍为每天07:00。

每日服务初始化、领取前状态读取/领取遇到瞬时数据库连接、超时、重启或锁冲突时，日志`daily_research_database_retry phase=initialize|preclaim ... retry_seconds=60`表示正在保留原计划等待重连；轮询归档使用`daily_research_observation_failed`。重连跨过计划时间不改变原启动策略，超过原启动窗口不补跑。此规则不允许重试模型调用或模型后的报告保存，也不接管CLAIMED批次；权限/认证/语法等错误仍须修复配置或程序。

2026-10-31最终可靠性修订在尚未上线的095增加`start_window_ends_at`与`runtime_deadline_at`两个NOT NULL字段。旧流水线的窗口/运行期限不随env缩短或延长；页面执行详情可核对冻结值。三个前置阶段过期后统一归档MISSED，有效租约及独立正式模型槽不会误归档。CLAIMED公共采集批次被强杀后不自动接管，页面明确等待原任务，可能错过当天；不应通过手动改状态或删除记录补跑。若NAS已经应用过旧095，先核实迁移历史，不修改生产账本跳过校验和。

首次更新这些开关的代码需要新镜像。在使用现有 NAS 构建部署脚本的环境中，在项目根目录执行：

```bash
bash build_docker_wealthsail.sh
```

新镜像已经构建后，仅变更 env 可执行 `bash build_docker_wealthsail.sh --deploy-only` 重建运行服务；
只做 `docker restart` 不会重新读取 env。若采用本手册第 3 节的两文件 Compose，则使用对应的构建和
`dc up -d --force-recreate api worker`；已有外网接入 overlay 的环境继续使用原脚本，避免丢失入口配置。
本次开关无需 SQL；若同时升级尚未执行的数据库迁移，仍按第 8 节先迁移再部署。

本地测试验证开关与任务入口的行为；是否已在 NAS 生效需实际部署后核对 API/Worker 的这四项配置与
Worker 日志。本文提供配置步骤，不表示已经替当前 NAS 部署或关闭任务。完整需求和设计边界见

## 8. 备份与后续更新

先为独立库创建逻辑备份。例如 PG 容器本地 socket 允许 `admin` 连接时：

```bash
mkdir -p backups
chmod 700 backups
umask 077
docker exec postgres pg_dump -U admin -Fc wealthsail > "backups/wealthsail-$(date +%Y%m%d-%H%M%S).dump"
```

若你的本地认证要求密码，使用受限 `.pgpass`/NAS 密钥管理配置，不把密码写进备份脚本命令行。检查命令退出码和文件大小，定期恢复到隔离库验证。备份还应覆盖四份生成配置、头像卷及 `codex_auth` 卷；它们包含身份/加密密钥、可刷新的登录凭证或用户文件。认证卷备份/恢复时先停止 Runner，使用加密且限制访问的备份；详见 [Codex 指南](./32.Codex统一模型与NAS认证操作指南.md)。不要依赖直接复制运行中的 PG 数据目录。

`build_docker_wealthsail.sh` **不会自动执行数据库迁移**。重新编译只是将 `migrations/` 和 `scripts/` 放入镜像；默认部署和 `--deploy-only` 都只启动运行服务。因此，包含新 SQL 的更新必须先显式迁移，再部署新版本。

既有数据库使用 `scripts/migrate.py` 增量迁移。不要重复执行首装入口 `scripts/initialize_postgres.py`；它还会配置集群角色及运行账号口令。不要重新生成 env、执行首次数据清理，也不要用 API/Worker 的受限数据库账号执行 DDL。

以下步骤在 **NAS 项目根目录的交互式 Bash 终端**运行，先完成上面的备份。正在使用 `build_docker_wealthsail.sh` 的部署，设置 `NAS_TOOLS` 为该脚本所用 `nas-compose` 的实际所在目录（只替换路径，不填密码）：

```bash
export NAS_TOOLS='/你的NAS工具目录'
ws() { sudo "$NAS_TOOLS/nas-compose" ws "$@"; }
bash build_docker_wealthsail.sh --build-only
```

`ws` 保留现有 Cloudflare、网络和存储 overlay；不要改成缺少 overlay 的普通 `docker compose up`。若原来只使用本手册第 3 节的两文件部署，则把本节后续的 `ws` 换为 `dc`，构建使用 `dc build api frontend`，最后启动使用 `dc up -d --force-recreate codex-runner api worker frontend`。

构建成功后，选择没有运行中任务的维护窗口，停止 Worker 和 API，避免旧进程在迁移期间读写。此时 Web 暂时不可用；不停止或重建已有 PostgreSQL：

```bash
ws stop worker api
```

定义一次临时迁移命令。它只从既有 API 配置取数据库地址和 SSL 参数，改用 `POSTGRES_ADMIN_USER` 指定的管理员身份，并在终端隐藏提示输入数据库管理员密码。密码不会出现在命令行、Shell 历史或新配置文件中：

```bash
MIGRATION_COMMAND=$(cat <<'PY'
import getpass
import os
import runpy
import sys
from urllib.parse import quote, urlsplit, urlunsplit

target = urlsplit(os.environ["DATABASE_URL"])
admin_user = os.environ.get("POSTGRES_ADMIN_USER", "admin")
admin_password = getpass.getpass("PostgreSQL admin password: ")
authority = target.netloc.rsplit("@", 1)[-1]
admin_authority = (
    quote(admin_user, safe="") + ":" + quote(admin_password, safe="")
    + "@" + authority
)
os.environ["MIGRATION_DATABASE_URL"] = urlunsplit(
    target._replace(netloc=admin_authority)
)
sys.argv = [
    "scripts/migrate.py", "--environment", "production",
    "--confirm-target", "postgres:5432/wealthsail", *sys.argv[1:],
]
runpy.run_path("scripts/migrate.py", run_name="__main__")
PY
)
```

`--confirm-target` 必须与实际数据库的 `host[:port]/database` 完全一致；如首装用了其他主机、端口或库名，在上面显式修改确认目标。不要自动跳过目标校验。接下来先预览待执行迁移：

```bash
ws run --rm --no-deps --entrypoint python db-init -c "$MIGRATION_COMMAND" --dry-run
```

这里借用 `db-init` 服务的数据库网络和交互终端，但通过 `--entrypoint python` **替换首装入口**，实际只运行 `scripts/migrate.py`，不初始化数据库或轮换运行账号口令。新版本显示 `PLAN`，已应用且 checksum 相符的版本显示 `SKIP`。`--dry-run` 会连接数据库、获取迁移锁并检查/确保迁移账本，不是离线 SQL 预览。

确认预览成功且目标、待执行版本正确后，执行增量迁移（再次隐藏输入管理员密码）：

```bash
ws run --rm --no-deps --entrypoint python db-init -c "$MIGRATION_COMMAND"
```

必须看到新增版本的 `APPLIED` 和末尾 `READBACK OK`，才能继续部署。例如 AI 用量功能首次升级需要应用 `091_ai_usage.sql`；已经应用的版本只会 `SKIP`。如遇 `checksum drift` 或权限/readback 错误，保持 API/Worker 停止，先核对源码与数据库迁移历史；不要删除账本、跳版本或直接用 `--reconcile-drift` 绕过报错。

```bash
bash build_docker_wealthsail.sh --deploy-only
unset MIGRATION_COMMAND
```

按脚本末尾输出确认服务状态、前端配置和 Codex 登录，再验收 Web 登录、AI 用量及 Worker 日志。上述是操作步骤，不能替代在实际 NAS 上执行后的结果验证。
