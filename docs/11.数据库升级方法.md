更新代码重启服务之前，需要手动执行数据库迁移。

因为这次不仅修改了 Python 代码，还修复了数据库层的企业微信绑定规则。systemctl restart 只会加载新代码，不会自动执行 SQL migration。
020_channel_binding_uniqueness_hardening.sql 做了三件事：
同一租户、用户、渠道最多只能有一个 ACTIVE binding，避免换绑后新旧企微账号同时收到报告。
清理历史上的重复 ACTIVE binding。
修复跨用户绑定冲突：同一个企微身份已属于其他用户时明确拒绝，防止错误消费新用户的绑定码。

---
这里的 “migration readback” 不是另一条独立命令。`scripts/migrate.py` 正式执行完 migration 后，会自动执行数据库权限和结构回读检查。

下面按你服务器目录 `/opt/wealthsail` 和 systemd 服务给出完整命令。

## 二、准备迁移管理员数据库连接

不要使用普通的 `wealthsail_api_login` 或 `wealthsail_worker_login`，它们通常没有执行 DDL、创建函数和索引的权限。

应使用：

- Supabase 的 `postgres`/数据库 owner 连接；
- 或单独的 migration 管理员连接；
- 推荐直连端口 5432，不要使用 transaction pooler 6543。

为避免数据库密码进入 shell history，执行：

```bash
read -rsp "请输入 MIGRATION_DATABASE_URL: " MIGRATION_DATABASE_URL
echo
export MIGRATION_DATABASE_URL
```

输入完整 DSN，例如：

```text
postgresql://postgres:经过URL编码的密码@数据库地址:5432/postgres?sslmode=require
```

注意：密码如果包含 `@`、`#`、`:`、`/`、`?` 等字符，必须进行 URL 编码。

## 三、安全显示迁移目标

下面命令只打印数据库地址和库名，不会打印用户名、密码或查询参数：

```bash
MIGRATION_TARGET="$(
  .venv/bin/python -c \
  'import os; from scripts.migrate import safe_target_name; print(safe_target_name(os.environ["MIGRATION_DATABASE_URL"]))'
)"

printf '准备迁移数据库：%s\n' "$MIGRATION_TARGET"
```

输出类似：

```text
准备迁移数据库：db.example.com:5432/postgres
```

请认真确认这确实是生产数据库。

如果这里显示成测试库、开发库或错误服务器，不要继续执行。

## 四、先执行 dry-run

```bash
.venv/bin/python scripts/migrate.py \
  --environment production \
  --confirm-target "$MIGRATION_TARGET" \
  --dry-run
```

正常情况下，已经执行的 migration 会显示：

```text
SKIP 001_initial_schemas.sql (already applied)
...
SKIP 019_multi_user_report_delivery.sql (already applied)
```

待执行的 020 应显示：

```text
PLAN 020_channel_binding_uniqueness_hardening.sql sha256=...
```

如果出现下面这些错误，不要继续正式迁移：

```text
duplicate migration version
checksum drift
target confirmation mismatch
MIGRATION_DATABASE_URL is required
```

特别是如果看到：

```text
checksum drift at migration 017
```

说明服务器数据库 migration ledger 或服务器代码不是预期状态，需要先检查，不能强行修改 ledger。

## 五、正式执行 migration 020

确认 dry-run 只计划执行 020 后，执行：

```bash
.venv/bin/python scripts/migrate.py \
  --environment production \
  --confirm-target "$MIGRATION_TARGET"
```

预期关键输出：

```text
SKIP 001_initial_schemas.sql (already applied)
...
SKIP 019_multi_user_report_delivery.sql (already applied)
APPLIED 020_channel_binding_uniqueness_hardening.sql
READBACK OK: roles, browser grants and demo-user guard
```

其中：

```text
APPLIED 020_channel_binding_uniqueness_hardening.sql
```

表示 020 已成功提交。

下面这一行：

```text
READBACK OK: roles, browser grants and demo-user guard
```

就是我之前说的 migration readback。它由迁移程序自动执行，不需要再运行另一个 Python 命令。

readback 会检查：

- `wealthsail_api`、`wealthsail_worker` 角色是否存在；
- Worker 是否为 `NOINHERIT BYPASSRLS`；
- Worker 是否能降权到 `wealthsail_api`；
- 浏览器 `authenticated` 角色是否仍有危险的系统事实写权限；
- 生产数据库是否误装了可登录演示用户；
- Worker 是否有写市场快照和行情观测的权限；
- API 是否有投影重建所需权限；
- 开发 seed 是否误入生产 migration ledger。

## 六、手工确认 migration 020 已记录

如果服务器安装了 `psql`，执行：

```bash
psql "$MIGRATION_DATABASE_URL" \
  -X \
  -v ON_ERROR_STOP=1 \
  -c "
SELECT version, filename, applied_at
FROM public.wealthsail_schema_migrations
WHERE version = 20;
"
```

预期返回一行：

```text
20 | 020_channel_binding_uniqueness_hardening.sql | ...
```

确认唯一索引已经创建：

```bash
psql "$MIGRATION_DATABASE_URL" \
  -X \
  -v ON_ERROR_STOP=1 \
  -c "
SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'identity'
  AND indexname = 'uq_channel_bindings_active_user_channel';
"
```

确认不存在重复 ACTIVE binding：

```bash
psql "$MIGRATION_DATABASE_URL" \
  -X \
  -v ON_ERROR_STOP=1 \
  -c "
SELECT tenant_id, user_id, channel_type, COUNT(*) AS active_count
FROM identity.channel_bindings
WHERE status = 'ACTIVE'
GROUP BY tenant_id, user_id, channel_type
HAVING COUNT(*) > 1;
"
```

正常结果应为：

```text
(0 rows)
```

确认绑定函数已经收紧权限：

```bash
psql "$MIGRATION_DATABASE_URL" \
  -X \
  -v ON_ERROR_STOP=1 \
  -c "
SELECT
    p.oid::regprocedure AS function_name,
    p.prosecdef AS security_definer,
    p.proconfig AS fixed_configuration,
    p.proacl AS execute_acl
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'identity'
  AND p.proname = 'consume_binding_challenge';
"
```

预期应看到：

- `security_definer = t`
- `fixed_configuration` 包含固定 `search_path`
- `execute_acl` 包含 `wealthsail_api=X/...`
- 不应存在 PUBLIC EXECUTE

## 七、清除管理员 DSN

完成后立即清理 shell 环境中的管理员连接：

```bash
unset MIGRATION_DATABASE_URL
unset MIGRATION_TARGET
```

确认已经清除：

```bash
test -z "${MIGRATION_DATABASE_URL:-}" \
  && echo "OK: migration credential cleared" \
  || echo "WARNING: credential still exists"
```

## 八、重启服务

先确认服务器实际存在的 WealthSail 服务：

```bash
systemctl list-unit-files --type=service \
  | grep -E '^wealthsail'
```

你目前使用的是 `wealthsail.service`，执行：

```bash
sudo systemctl restart wealthsail
```

如果还有独立 Worker，例如 `wealthsail-worker.service`，再执行：

```bash
sudo systemctl restart wealthsail-worker
```

检查状态：

```bash
sudo systemctl status wealthsail --no-pager -l
```

如果有 Worker：

```bash
sudo systemctl status wealthsail-worker --no-pager -l
```

## 最简可复制版本

确认已准备好管理员 DSN后，可以按下面这一组执行：

```bash
cd /opt/wealthsail

git pull origin master
git rev-parse --short HEAD

read -rsp "请输入 MIGRATION_DATABASE_URL: " MIGRATION_DATABASE_URL
echo
export MIGRATION_DATABASE_URL

MIGRATION_TARGET="$(
  .venv/bin/python -c \
  'import os; from scripts.migrate import safe_target_name; print(safe_target_name(os.environ["MIGRATION_DATABASE_URL"]))'
)"

printf '迁移目标：%s\n' "$MIGRATION_TARGET"

.venv/bin/python scripts/migrate.py \
  --environment production \
  --confirm-target "$MIGRATION_TARGET" \
  --dry-run

.venv/bin/python scripts/migrate.py \
  --environment production \
  --confirm-target "$MIGRATION_TARGET"

unset MIGRATION_DATABASE_URL
unset MIGRATION_TARGET

sudo systemctl restart wealthsail
sudo systemctl status wealthsail --no-pager -l

sudo journalctl -u wealthsail \
  --since "5 minutes ago" \
  --no-pager \
  -o cat

curl -fsS http://127.0.0.1:8000/healthz
echo
```

正式执行前，dry-run 的关键判断是：旧版本全部 `SKIP`，并且只出现一个 `PLAN 020_channel_binding_uniqueness_hardening.sql`。
