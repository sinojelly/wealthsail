## 1. 先理解 WealthSail 的发布单元

WealthSail 不是一个“重启一次就全部更新”的单进程应用。它至少包含下列独立发布单元：

| 发布单元 | 代码/配置来源 | 运行产物 | 更新后通常要做什么 |
|---|---|---|---|
| Web 前端 | `frontend/src/`、`frontend/package.json`、`frontend/nginx.conf` | `frontend/dist/` 或 `wealthsail-frontend` 镜像 | 重新安装锁定依赖、执行 `pnpm build`，再让静态服务器切换到新产物 |
| API | `backend/`、`requirements.txt` | Python 虚拟环境进程或 `wealthsail-backend` 镜像 | 安装依赖、完成必要迁移后重启 API |
| Background Worker | `backend/worker.py` 及其调用模块 | 独立 Worker 进程，或与 API 共用后端镜像 | 在 API 健康后重启 Worker，检查任务、Outbox 和报告调度 |
| PostgreSQL Schema | `migrations/*.sql`、`scripts/migrate.py` | Supabase/PostgreSQL 中的表、函数、RLS、授权和 migration ledger | 使用迁移管理员连接执行 forward-only migration 和自动 readback |
| 反向代理 | `frontend/nginx.conf` 或宿主机 `/etc/nginx/` 配置 | Nginx 进程配置 | 先 `nginx -t`，仅配置变化时 reload；静态文件变化本身不要求 reload |
| Runtime Monitor | `deployment/systemd/wealthsail-monitor.*` | systemd oneshot/timer | 脚本或环境改变后 reload systemd、重启 timer，并执行一次手工检查 |

必须记住以下边界：

- `sudo systemctl restart wealthsail` 只会重启 API，不会构建或发布 React 前端；
- `sudo systemctl restart wealthsail-worker` 只会重启 Worker，不会执行数据库迁移；
- `sudo systemctl reload nginx` 只会重新加载 Nginx 配置，不会生成 `frontend/dist`；
- `docker compose restart` 只会重启现有容器，不会重新构建镜像；
- `pnpm build` 只生成 `frontend/dist`。如果 Nginx 的 `root` 指向别处，还必须同步或原子切换静态目录；
- 浏览器运行时只连接同源 `/api`，前端进程不得获取数据库 DSN、JWT Secret 或 Worker Secret。

## 2. 部署模式选择

| 模式 | 前端 | API / Worker | 适用场景 | 当前建议 |
|---|---|---|---|---|
| A. 全栈 Docker Compose | Nginx 前端容器 | API、Worker 容器 | 新生产环境、NAS、Linux VPS、希望环境一致 | **正式架构首选** |
| B. Linux 宿主机原生部署 | 宿主机 Nginx 托管 `dist` | systemd 管理 API、Worker | 当前已有 VPS、排障简单、用户规模较小 | **当前服务器可继续使用** |
| C. 独立静态站点/CDN + 后端服务 | 对象存储、CDN 或独立 Nginx | Compose、systemd 或托管容器 | 需要独立扩缩容和全球静态分发 | 后续目标，需完成同源和缓存设计 |
| D. Windows 本地开发 | Vite 开发服务器 | 本地 Uvicorn，可连接受控 Supabase | 开发、调试、TDD | 仅开发，不作为生产部署 |
| E. 前端容器 + 宿主机后端混合模式 | 当前前端容器 | systemd API、Worker | 历史环境过渡 | **默认不支持，不推荐直接使用** |

模式 E 默认不兼容的原因是 [`frontend/nginx.conf`](../frontend/nginx.conf) 把 `/api/` 代理到
Compose 网络中的 `api:8000`。单独启动前端容器时，容器内没有名为 `api` 的服务发现目标。
如果确需混合部署，必须显式提供容器到宿主机 API 的受控网络地址、重写 upstream、限制 API
监听边界并重新完成安全测试，不能把 API `8000` 端口直接暴露到公网来规避问题。

## 3. 所有模式共用的发布原则

### 3.1 发布前检查

在服务器仓库执行：

```bash
cd /opt/wealthsail

git status --short --branch
git fetch origin
git log --oneline HEAD..origin/master
git pull --ff-only origin master
git rev-parse --short HEAD
```

要求：

- 服务器工作区没有来源不明的修改；
- 只进行 fast-forward，不在生产服务器现场制造 merge commit；
- 记录部署 commit、操作者、开始时间和目标环境；
- 先查看提交范围，判断是前端、API、Worker、Migration 还是代理配置变化；
- 发现 migration 时，先创建可恢复数据库快照，再启动应用更新。

### 3.2 推荐发布顺序

一次同时包含数据库与全栈代码的发布，推荐顺序为：

1. 确认 CI、单元测试和全栈冒烟已经通过；
2. 创建数据库备份或 Supabase 可恢复快照；
3. 拉取代码，构建新前端/后端镜像或安装新依赖，但暂不切换服务；
4. 使用迁移管理员 DSN 执行 migration dry-run；
5. 正式执行 migration，确认自动 readback 成功；
6. 更新并验证 API；
7. 更新并验证 Worker；
8. 发布前端静态产物；
9. 执行公网、登录、只读查询及本次变更对应的业务冒烟；
10. 保存脱敏日志和版本证据，清除 shell 中临时 migration 变量。

只修改前端时，不需要重启 API/Worker，也不需要执行数据库迁移。只修改后端实现且没有 migration
时，不需要重建前端。任何“为了保险把所有东西都重启一遍”的操作都会扩大故障面，不应作为标准
发布流程。

### 3.3 变更范围与动作矩阵

| 变更内容 | 构建前端 | 更新 API | 更新 Worker | 执行 Migration | reload Nginx |
|---|---:|---:|---:|---:|---:|
| 仅 `frontend/src/` 或前端依赖 | 是 | 否 | 否 | 否 | 仅 Nginx 配置同时变化时 |
| 仅 API 路由/领域服务 | 否 | 是 | 视 Worker 是否引用同模块 | 否 | 否 |
| 仅 Worker/调度/Provider | 否 | 否 | 是 | 否 | 否 |
| `requirements.txt` | 否 | 是 | 是 | 否 | 否 |
| 新增 `migrations/*.sql` | 视提交而定 | 通常是 | 通常是 | **是** | 否 |
| `frontend/nginx.conf` 或宿主机站点配置 | 通常是 | 否 | 否 | 否 | **是** |
| `deployment/systemd/*` | 否 | 视单元而定 | 视单元而定 | 否 | 否；需要 `systemctl daemon-reload` |

## 4. 模式 A：全栈 Docker Compose

### 4.1 架构和入口

根目录 [`docker-compose.yml`](../docker-compose.yml) 定义基础编排；NAS + Cloudflare 部署必须叠加 NAS 和外网 overlay，完整命令见 [外网部署步骤](../external-access/DEPLOYMENT.md)。以下基础 Compose 示例适用于已有 TLS 代理的部署，不能省掉你当前使用的 overlay。

- `frontend`：多阶段构建 React，运行层使用 Nginx，宿主机仅绑定 `127.0.0.1:8080`；
- `api`：只在 Compose 私网暴露 `8000`；
- `worker`：不开放端口，等待 API 健康后启动；
- `codex-runner`：独立内部模型服务，供 API/Worker 调用，不发布 8090，不持有数据库或 Web 会话密钥；
- `codex-auth`：一次性设备登录工具，与 Runner 共享独立 `codex_auth` 认证卷，不需要常驻启动；
- 外部 TLS 代理：把公网 HTTPS 请求转发到 `127.0.0.1:8080`；
- API 与 Worker 分别加载 `deployment/env/api.env`、`deployment/env/worker.env`，不得复用权限。
- Runner 单独加载 `deployment/env/codex.env`；全部模型请求统一使用 Codex，不再配置 `MODEL_API_KEY`。认证、旧配置升级和首次启动见 [Codex 指南](./32.Codex统一模型与NAS认证操作指南.md)。

部署前先检查配置插值，但不要把带密钥的完整输出保存到日志或工单：

```bash
cd /opt/wealthsail
docker compose config --quiet
```

### 4.2 只更新前端

```bash
cd /opt/wealthsail
git pull --ff-only origin master

docker compose build --pull frontend
docker compose up -d --no-deps frontend

docker compose ps frontend
curl -fsSI http://127.0.0.1:8080/
```

`docker compose restart frontend` 不会使用新源码重新构建镜像，因此不能代替 `build + up`。

### 4.3 只更新 API/Worker，且没有 Migration

API、Worker 与 Codex Runner 共用 `wealthsail-backend` 镜像。更新共享模块、Codex 或 Python 依赖时，构建镜像后重新创建相关容器：

```bash
cd /opt/wealthsail
git pull --ff-only origin master

docker compose build --pull api
docker compose up -d --no-deps --force-recreate codex-runner
docker compose up -d --no-deps --force-recreate api

# API 健康后再更新 Worker。
docker compose exec -T api \
  python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=3)"

docker compose up -d --no-deps --force-recreate worker
docker compose ps codex-runner api worker
docker compose logs --since=10m api worker
```

即使只修改 Worker，重新构建的也是共用后端镜像，但可以只重建 `worker` 容器。必须确认改动没有
被 API 导入，否则只更新 Worker 会造成同一 commit 在两个进程中版本不一致。

### 4.4 含 Migration 的全栈更新

先构建包含最新 migration runner 的后端镜像，再使用只在当前 shell 中存在的管理员 DSN 运行
一次性迁移容器。不要把 DSN 写进 Compose 文件或命令参数值：

```bash
cd /opt/wealthsail
docker compose build --pull api

read -rsp "请输入 MIGRATION_DATABASE_URL: " MIGRATION_DATABASE_URL
echo
export MIGRATION_DATABASE_URL

docker compose run --rm --no-deps \
  -e MIGRATION_DATABASE_URL \
  api python scripts/migrate.py \
  --environment production \
  --confirm-target db.example:5432/postgres \
  --dry-run

docker compose run --rm --no-deps \
  -e MIGRATION_DATABASE_URL \
  api python scripts/migrate.py \
  --environment production \
  --confirm-target db.example:5432/postgres

unset MIGRATION_DATABASE_URL
```

把 `db.example:5432/postgres` 替换为 runner 安全打印的准确目标。readback 是正式迁移命令的一部分，
不是再执行一条名为 readback 的命令。成功后按 API → Worker → frontend 顺序切换容器。

### 4.5 Compose 验证

```bash
docker compose ps
docker compose logs --since=10m api worker frontend

curl -fsSI http://127.0.0.1:8080/
docker compose exec -T api \
  python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=3)"
```

不要为了从宿主机直接访问健康端点而临时暴露 API `8000` 端口；宿主机验证容器 API 应使用上面的
容器内检查，公网业务检查则继续经过前端 Nginx 和受控 TLS 边缘。

## 5. 模式 B：Linux 宿主机 Nginx + systemd

这是当前 VPS 常见方式：代码位于 `/opt/wealthsail`，API 和 Worker 由 systemd 管理，宿主机
Nginx 直接托管静态前端并代理 `/api`。

### 5.1 首先确认真实运行配置

不同服务器的 unit 和 Nginx 静态目录可能不同，发布前必须读实际配置，不能只凭服务名猜测：

```bash
sudo systemctl cat wealthsail
sudo systemctl cat wealthsail-worker
sudo systemctl cat wealthsail-monitor.timer 2>/dev/null || true

sudo nginx -T 2>/dev/null \
  | grep -nE 'server_name|root[[:space:]]+|location|try_files|expires|proxy_pass'
```

不要把 `systemctl show ... Environment`、完整 env 文件或未脱敏的 `nginx -T` 输出复制到公开日志。

无论 Web Root 在哪里，生产站点都必须满足下面三条静态资源契约；仓库提供了可复制核对的
[`deployment/nginx/wealthsail-static-locations.conf.example`](../deployment/nginx/wealthsail-static-locations.conf.example)：

- `index.html` 每次使用前重新验证，不能设为长期缓存；
- `/assets/` 下的内容哈希文件可以长期缓存，但缺失时必须直接返回 `404`；
- 只有页面路由才能 fallback 到 `index.html`，`.js`/`.css` 请求不得 fallback 成 HTML。

如果控制台出现 `Expected a JavaScript module but the server responded with text/html`，说明第三条已经被
违反。这不是 API、Worker 或数据库故障，重启它们不会修复问题。

### 5.2 更新前端：Nginx 直接读取 `frontend/dist`

如果站点配置为：

```nginx
root /opt/wealthsail/frontend/dist;
```

执行：

```bash
cd /opt/wealthsail
git pull --ff-only origin master
cd frontend

node --version
corepack enable
corepack prepare pnpm@11.23.0 --activate
pnpm install --frozen-lockfile
pnpm build

test -s dist/index.html \
  && echo "OK: frontend build succeeded" \
  || { echo "ERROR: frontend build failed"; exit 1; }

sudo nginx -t
curl -fsSI -H 'Host: wealthsail.example.com' http://127.0.0.1/dashboard
```

这种配置下，构建完成即发布静态文件。静态文件内容变化不需要重启 `wealthsail`、Worker 或
Nginx。但 Vite 会在构建前清空 `dist`，已经打开的旧页面可能仍请求上一版懒加载分包，所以直接
原地构建只适合本地、停机维护窗口或低并发临时部署。面向持续在线用户时，应改用下一节的独立
Web Root 发布方式，先补齐新资源、保留旧哈希资源，再原子替换 `index.html`。

### 5.3 更新前端：Nginx 读取独立 Web Root

如果 Nginx 使用专用目录，例如：

```nginx
root /var/www/wealthsail;
```

先完成上一节的 `pnpm install` 与 `pnpm build`，再按“资源先行、HTML 最后”的顺序发布：

```bash
cd /opt/wealthsail/frontend

test -s dist/index.html \
  || { echo "ERROR: dist/index.html missing"; exit 1; }

# 路径必须先通过 nginx -T 核对为 WealthSail 专用 Web Root。
sudo install -d -m 0755 /var/www/wealthsail/assets

# 1. 先追加新哈希资源；不要 --delete，仍打开的旧页面还可能请求旧分包。
sudo rsync -a \
  /opt/wealthsail/frontend/dist/assets/ \
  /var/www/wealthsail/assets/

# 2. 同步 assets/index.html 之外的根级静态文件（如将来新增 favicon）。
sudo rsync -a \
  --exclude='assets/' --exclude='index.html' \
  /opt/wealthsail/frontend/dist/ \
  /var/www/wealthsail/

# 3. 最后在同一文件系统内原子替换 HTML 发布指针。
sudo install -m 0644 \
  /opt/wealthsail/frontend/dist/index.html \
  /var/www/wealthsail/index.html.next
sudo mv -f \
  /var/www/wealthsail/index.html.next \
  /var/www/wealthsail/index.html

sudo nginx -t
```

静态发布不要使用 `rsync --delete`：它会立即清理旧哈希资源，使发布前已打开的页面在后续点击
懒加载路由时失败。旧资源可以按容量和访问窗口制定独立的保留策略，例如至少保留 30 天并仅由
受审计的清理任务删除；不要把清理混入发布事务。仅替换静态文件且 Nginx 配置未变时不要求 reload；
配置发生变化时才执行 `sudo nginx -t && sudo systemctl reload nginx`。

### 5.4 更新 API/Worker，且没有 Migration

```bash
cd /opt/wealthsail
git pull --ff-only origin master

.venv/bin/python -m pip install -r requirements.txt

sudo systemctl restart wealthsail
sudo systemctl status wealthsail --no-pager -l
curl -fsS http://127.0.0.1:8000/healthz

sudo systemctl restart wealthsail-worker
sudo systemctl status wealthsail-worker --no-pager -l

sudo journalctl -u wealthsail \
  --since "10 minutes ago" --no-pager -o cat
sudo journalctl -u wealthsail-worker \
  --since "10 minutes ago" --no-pager -o cat
```

API 必须先恢复健康，再启动依赖新数据库/新代码契约的 Worker。不要同时重启后立即只看
`systemctl` 的退出码；还要检查健康端点和近期日志。

### 5.5 含 Migration 的更新

按照 [《数据库升级方法》](./11.数据库升级方法.md)创建备份并使用 migration 管理员 DSN：

```bash
cd /opt/wealthsail

read -rsp "请输入 MIGRATION_DATABASE_URL: " MIGRATION_DATABASE_URL
echo
export MIGRATION_DATABASE_URL

.venv/bin/python scripts/migrate.py \
  --environment production \
  --confirm-target db.example:5432/postgres \
  --dry-run

.venv/bin/python scripts/migrate.py \
  --environment production \
  --confirm-target db.example:5432/postgres

unset MIGRATION_DATABASE_URL
```

确认自动 readback 成功后，再执行 5.4 的 API → Worker 更新；若同一提交还改了前端，再执行 5.2
或 5.3。迁移已经提交但应用启动失败时，不能删除 migration ledger 或反向删除金融约束，应部署
兼容新 schema 的前一版本或新增 forward-fix。

### 5.6 systemd 单元变化

当 unit 文件、启动命令或 timer 变化时：

```bash
sudo systemctl daemon-reload
sudo systemctl restart wealthsail
sudo systemctl restart wealthsail-worker

sudo systemctl restart wealthsail-monitor.timer 2>/dev/null || true
sudo systemctl list-timers wealthsail-monitor.timer --no-pager 2>/dev/null || true
```

当前仓库完整版本化了 runtime monitor unit；API/Worker unit 的真实内容仍需以服务器
`systemctl cat` 为准。后续应把经过脱敏和环境解耦的 API/Worker unit 也纳入基础设施版本管理，
避免服务器之间漂移。

## 6. 模式 C：独立静态站点/CDN + 后端服务

这种模式把 `frontend/dist` 发布到独立 Nginx、对象存储或 CDN，后端继续采用 Compose、systemd
或托管容器。适合静态资源访问量明显增加以后使用，但认证边界比同机部署更复杂。

### 6.1 推荐的同源形态

推荐让用户始终访问同一个 HTTPS Origin：

```text
https://wealthsail.example.com/       -> 静态站点/CDN
https://wealthsail.example.com/api/   -> API 反向代理
https://wealthsail.example.com/static/avatars/... -> API 受控能力 URL
```

这样前端仍可使用默认 `VITE_API_BASE_URL=/api`，HttpOnly Refresh Cookie、CSP、CSRF/Origin 验证和
企业微信回调边界也更清晰。

如果前端和 API 使用不同 Origin，必须重新设计并验证：

- CORS 精确 allowlist，不能使用 `*` 搭配凭据；
- Refresh Cookie 的 `Secure`、`SameSite`、Domain 和 Path；
- CSP `connect-src`；
- CSRF/Origin 校验；
- 头像和 SSE 跨域；
- 前端构建时的 `VITE_API_BASE_URL`。

这些工作完成前，不应只把 `dist` 上传到另一个域名就宣称部署完成。

### 6.2 前端更新

```bash
cd /opt/wealthsail/frontend
corepack prepare pnpm@11.23.0 --activate
pnpm install --frozen-lockfile
pnpm build
test -s dist/index.html
```

随后使用目标平台的原子发布能力上传 `dist/`。缓存策略应为：

- `index.html`：使用 `Cache-Control: no-cache`，确保刷新时重新验证并引用新哈希；
- `assets/*-[hash].js/css`：可使用长期 immutable 缓存；
- 发布顺序要保证新 `index.html` 出现时，它引用的哈希资源已经可用；
- 至少在兼容窗口内保留上一版哈希资源，不能在切换 HTML 时同步删除；
- `/assets/` 不存在的文件必须返回 `404`，不能返回 SPA 的 `index.html`；
- 回滚时切换完整 release，不单独覆盖某个 JS/CSS 文件。

### 6.3 后端更新

后端仍按其实际运行模式选择本文第 4 或第 5 章。静态站点独立后，并不改变 migration、API →
Worker 启动顺序、数据库权限或运行监控要求。

## 8. CI/全栈冒烟与正式发布的关系

CI 是部署门禁，不是部署模式。当前流程会执行前端 lint/test/build、后端测试、配置契约和受保护的
全栈冒烟。它能拦截基本破坏，但不能替代：

- 生产数据库备份和 migration readback；
- 目标服务器 systemd/Nginx/Compose 配置检查；
- 企业微信、SMTP、Provider 和公网 TLS 的真实环境验证；
- 发布后的浏览器登录、读取、导入预览和本次变更专项冒烟。

生产环境禁止为了让冒烟通过而扩大数据库权限或开放 Worker/API 端口。

## 9. 发布后验证

### 9.1 前端静态版本验证

宿主机 Nginx 模式可执行：

```bash
HTML="$(curl -fsS -H 'Host: wealthsail.example.com' http://127.0.0.1/dashboard)"

printf '%s' "$HTML" \
  | grep -oE '/assets/[^" ]+\.(js|css)' \
  | sort -u

# HTML 必须要求重新验证。
curl -fsSI -H 'Host: wealthsail.example.com' \
  http://127.0.0.1/index.html \
  | grep -iE '^(HTTP/|Content-Type:|Cache-Control:)'

# 随机缺失的 JS 必须是 404，且绝不能返回 text/html。
curl -sSI -H 'Host: wealthsail.example.com' \
  http://127.0.0.1/assets/does-not-exist.js \
  | grep -iE '^(HTTP/|Content-Type:)'
```

确认 HTML 返回的是当前构建的新哈希资源，`Cache-Control` 含 `no-cache`，不存在的 JS 返回
`404`。浏览器按 `Ctrl+F5` 只能用于排除本地缓存，不应作为服务端发布是否成功的唯一证据。

### 9.2 API/Worker 验证

至少检查：

- API `/healthz` 返回成功；
- 登录、refresh、`/api/v1/auth/me` 的鉴权生命周期正常；
- Worker 启动后没有权限、schema、Provider 或 Outbox 连续错误；
- 迁移后的 API/Worker 使用各自最小权限 DSN；
- 当前提交涉及的业务路径有专项冒烟，例如导入预览、确认、行情读取或企微回调；
- `journalctl`/Compose 日志不输出 Secret、Authorization、Cookie 或完整数据库 DSN。

### 9.3 Nginx/边缘验证

- SPA 深链接（例如 `/dashboard`、`/onboarding`）能回退到 `index.html`；
- `/api/` 正确代理且不暴露 API 端口；
- SSE 路径禁用缓冲并保留有界超时；
- 静态哈希资源使用 immutable 缓存，`index.html` 不被长期缓存；
- 外层 TLS 代理覆盖客户端伪造的转发头，HSTS 只在 HTTPS 域名验证完成后启用。

## 10. 回滚和失败处理

### 10.1 前端回滚

前端是不可变静态产物，推荐保留按 commit 命名的 release 目录或镜像 tag，回滚时切换完整 release。
不要把旧 `index.html` 与新哈希资源混合，也不要只回退一两个 JS 文件。

### 10.2 API/Worker 回滚

- Compose 使用经过验证的 commit/release 镜像 tag，不依赖重新构建一个含义变化的 `latest`；
- systemd 部署应从已验证 release 目录切换，而不是在脏工作区运行 `git reset --hard`；
- API 与 Worker 共享领域模型时必须回到相互兼容的版本；
- 回滚后再次检查健康端点、任务恢复和 Outbox。

### 10.3 数据库不能按文件反向回滚

Migration 是 forward-only。已经提交并登记 checksum 后：

- 不删除 migration ledger；
- 不改写已经执行过的 SQL；
- 不物理删除账本事实或不可变触发器；
- 发现问题时新增编号 migration 做 forward-fix；
- 应用回滚只能回到仍兼容当前 schema 的版本。

## 11. 当前 VPS 的推荐日常命令

如果当前服务器确认是“`/opt/wealthsail` + systemd API/Worker + 宿主机 Nginx”，一次纯前端更新可
按下面执行：

```bash
cd /opt/wealthsail
git status --short --branch
git pull --ff-only origin master
git rev-parse --short HEAD

cd frontend
corepack prepare pnpm@11.23.0 --activate
pnpm install --frozen-lockfile
pnpm build
test -s dist/index.html

sudo nginx -t
curl -fsSI -H 'Host: wealthsail.example.com' http://127.0.0.1/dashboard
```

然后依据 `sudo nginx -T` 查到的真实 `root` 判断是否还要同步到 `/var/www/...`。不要重启
`wealthsail` 或 Worker 来“刷新前端”。

一次后端更新则按下面执行；如果包含 migration，必须在重启之前插入第 5.5 节的迁移步骤：

```bash
cd /opt/wealthsail
git pull --ff-only origin master
.venv/bin/python -m pip install -r requirements.txt

sudo systemctl restart wealthsail
curl -fsS http://127.0.0.1:8000/healthz

sudo systemctl restart wealthsail-worker
sudo systemctl status wealthsail-worker --no-pager -l
```

## 12. 常见误区速查

| 现象 | 常见错误操作 | 正确判断 |
|---|---|---|
| 前端仍是旧界面 | 只重启 API/Worker | 重新构建并发布 `dist` 或重建前端镜像 |
| 已执行 `pnpm build` 仍未更新 | 未核对 Nginx `root` | 检查 `nginx -T`，确认是否需要同步到独立 Web Root |
| Compose 更新后仍是旧代码 | 只执行 `docker compose restart` | `docker compose build` 后 `up -d` 重建容器 |
| 后端报缺表/缺列/RLS 错误 | 先重启应用，未迁移 | 停止发布，按当前数据库升级文档执行 migration/readback |
| 静态页面刷新 404 | Nginx 没有 SPA fallback | `location /` 使用 `try_files $uri $uri/ /index.html` |
| 退出或切换页面后白屏，JS 响应为 `text/html` | 旧页面请求已删除分包，且静态资源误走 SPA fallback | `/assets/` 缺失直接 404，HTML 设 `no-cache`；资源先行、HTML 最后并保留旧哈希 |
| 浏览器强刷后偶发资源 404 | 非原子发布或错误缓存 `index.html` | 先上传哈希资源，再切换 `index.html`；保留兼容窗口内的旧哈希资源 |
| 前端容器访问不到 API | 单独运行当前 Compose 前端 | 当前 upstream 是 `api:8000`，必须使用同一 Compose 网络或重新设计 upstream |
| 本地 `pnpm dev` 能运行就直接上线 | 把 Vite dev 当生产服务 | 生产必须 `pnpm build` 并由 Nginx/CDN 托管 |
