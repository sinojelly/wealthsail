对于构建一个具备高容错、状态记忆和复杂推理链路的投研中台，裸写大模型 API 确实容易陷入**状态丢失**和**死循环耗尽 Token** 的陷阱。引入合适的框架是明智的，但需要根据后端语言和应用场景进行精准选型。

针对您提到的几个技术栈方向，以下是详细的分析与选型建议：

### 一、 Agent 框架：解决推理断点与 Token 治理

构建多步推理和“人机协同（Human-in-the-loop）”机制，确实需要一个强状态管理的框架，这与构建类似 Hermes Agent 或 OpenClaw 等复杂智能体工具链的底层逻辑是一致的：

* **LangGraph (Python)**：**强烈推荐用于后端逻辑层**。
* **断点续传 (Checkpointer)**：原生支持基于 SQLite/PostgreSQL 的状态持久化。执行到一半可以暂停（如等待用户确认交易指令），下次直接从断点恢复图节点。
* **防死循环 (Recursion Limit)**：可以严格设置图流转的最大步数（`recursion_limit`），一旦超出强制中断，防止 Agent 陷入无意义的循环调用消耗 Token。


* **为何不用裸手撕**：手写 Session 管理和消息修剪（Message Pruning）在前期看似简单，但面对多 Agent 交互（如多空辩论）时，上下文视窗的裁剪逻辑会极其复杂。

### 二、 Vercel AI SDK 与 Mastra：前端与全栈选项

如果您打算使用 React 体系来构建前端 UI，这两个工具的定位各有侧重：

* **Vercel AI SDK**：**极度推荐用于前端展示层**。
* 它专注于解决“UI 渲染与流式响应”的鸿沟。特别是它的 `useChat` 和 `AI/RSC (React Server Components)`，能极其丝滑地将后端 Python Agent 吐出的结构化数据渲染为可交互的 React 组件（如股票卡片、图表）。


* **Mastra**：这是一个较新的基于 TypeScript 的强主见 Agent 框架。
* **适用场景**：如果您希望彻底抛弃 Python，用全栈 TypeScript (Node.js) 写完包含数据抓取、RAG 和路由的完整逻辑，Mastra 提供了很好的工作流封装。
* **潜在冲突**：金融量化生态（如 AkShare、Backtrader、Qlib）几乎全在 Python 侧。强行用 Mastra/TS 做后端，会导致频繁的跨语言 RPC 调用，得不偿失。



### 三、 Harness (评测框架)：MVP 阶段的非必要组件

在 AI 领域，Harness 通常指代**大模型评估与基准测试框架**（如 `lm-evaluation-harness`）。

* **MVP 阶段**：**不需要**。系统早期主要依赖人工复盘和业务层的向量记忆来修正认知，并不需要对底层模型进行微调（SFT）或规模化的打分评估。
* **后期演进**：当您的系统沉淀了上万条交易复盘数据，准备微调一个专属的“金融交易模型”时，才需要引入 Harness 框架来验证微调后模型的逻辑胜率。

### 四、 综合技术选型建议

为了兼顾量化生态与现代 Web UI，最优的整合方案是：

1. **AI 逻辑与回测后端**：**Python + LangGraph + FastAPI**。负责执行策略、连接工具、管理断点状态并控制 Token 流转。
2. **前端交互与渲染**：**React (或 Next.js) + Vercel AI SDK**。负责流式接收后端的推演过程，渲染交互卡片。
3. **底层数据抓取**：利用 **Go** 的高并发优势写独立服务，将行情数据写入 Supabase 供 Python 端提取。

您目前是希望将主要精力放在 Python 端的 LangGraph 工作流编排上，还是更倾向于先打通 Vercel AI SDK 在前端渲染结构化卡片的链路？
