## 1. 测试目标

MVP 验收不是证明“AI 会说漂亮的话”，而是证明：

1. 三类资产的账务、时点和数据状态正确；
2. 2–3 用户在 Web、数据库、缓存、搜索、消息和日志中隔离；
3. 盘前、盘中、14:30、盘后四时段能在失败和重试下形成闭环；
4. 企业微信身份、发送、交互、去重和撤销安全；
5. 模型只使用当前 tenant 的证据，能引用、弃权并抵抗 Prompt 注入；
6. 崩溃、重复、乱序、Provider 故障不会导致错账、错发或伪实时结论。

## 2. 状态与证据

### 2.1 状态

| 状态 | 含义 |
|---|---|
| NOT_RUN | 尚未执行，默认状态 |
| RUNNING | 正在受控环境执行 |
| PASS（通过） | 当前证据满足期望 |
| FAIL | 实际与期望不符 |
| BLOCKED | 外部依赖/环境阻断，需 owner 和解除条件 |
| WAIVED | 风险已接受，需批准人、原因和到期日；P0 不允许长期豁免 |

### 2.2 每次 Run 必填

```text
run_id, git_commit, environment, started_at, finished_at,
database_migration, fixture_version, provider_contract_version,
model/provider/prompt/skill_version, command, result_summary,
logs/traces/report_url, operator, known_exclusions
```

## 3. 测试层次

| 层次 | 目标 | 网络策略 |
|---|---|---|
| 纯单元/Property | 金融不变量、状态机、风险和格式 | 禁止网络，固定时钟 |
| Schema/Contract | API、事件、Provider、模型 JSON、WeCom | 固定 fixture；实时契约单独执行 |
| 数据质量 | 单位、时点、新鲜度、冲突、修订、交易日历 | Golden dataset + 跨源 fixture |
| PostgreSQL 集成 | 事务、约束、RLS、并发、migration | 真 PostgreSQL 临时库 |
| 故障注入 | kill/restart、重复/乱序、部分失败 | 受控进程/容器 |
| Agent 离线评估 | 工具、引用、弃权、注入、成本 | 固定模型或录制响应 + Golden set |
| WeCom 契约 | 绑定、路由、分片、回执、去重 | 测试账号/官方 sandbox 或适配器 fixture |
| E2E | 用户旅程和关键异常 | 稳定测试 tenant/数据 |
| NFR/灾备 | p95/p99、队列、成本、RPO/RTO | 明确负载与恢复演练 |

## 12. 发布门禁

发布 L1 必须：

- 所有 L0/L1 Must 的正常和异常/安全用例有证据；
- P0/P1 无未解释 FAIL/BLOCKED；
- 金融不变量、跨租户、密钥、绑定、幂等、故障恢复全部通过；
- 四时段在 3 tenant 中 E2E 通过；
- 数据缺失/冲突不会伪造实时结论；
- flake 率在约定阈值内；任何 WAIVED 有 owner、批准、原因和到期日；
- 测试证据可由同 commit、migration 和 fixture 复现。

测试总通过率不是唯一门禁；低风险非关键用例的受控豁免不能掩盖 P0 风险。
